# Download queue and workers

Migrated out of the root CLAUDE.md so this only loads when touching the download pipeline.

- **Chapter identity and sync**: `Chapter.Number` is stored as REAL — EF Core SQLite can't `ORDER BY` it directly, so any "next N chapters" ordering happens in memory (`Chapter.NextWanted`); identity is `(Number, Language)` with Volume as wildcard. `ChapterSyncService.MergeDuplicates` heals dupes on every refresh. **Two languages of one chapter are two rows that both want a file**, and the default chapter format carries no `{Chapter Language}` — so `FileNameBuilder` appends ` [es]` to anything that is not `en` when the format has no language token of its own. Only the non-default language is suffixed, deliberately: every file on disk today is English, so a second language adds names instead of renaming the library. The cost is that a Spanish-only series has `[es]` on every file. `RefreshMonitoredSeriesJob` compares against highest chapter number, never count — sources carry specials MangaBaka doesn't count, so count comparisons falsely read "ahead" or "behind".
- **A mapping's `LanguageFilter` is a comma-separated list** (`en,es`), read through `SourceLanguages.Parse`; null still means English, **not** every language — an untouched mapping has to keep listing exactly what it listed before, or every existing series grows a chapter row per translation on the next sync. Only sources declaring `SourceCapabilities.SupportsLanguageFilter` honour it (MangaDex, MangaFire). Adding a language multiplies that mapping's chapter rows, its wanted/missing counts and its downloads, which is why the picker says so.
- **`Chapter.Wanted` is user intent and has exactly three writers**: `ChapterSyncService` stamps it once at discovery (`Chapter.WantedUnder`), the user flips it (`ChapterController.SetWanted`/`SetWantedBulk`), and `MergeDuplicates` ORs it. **Nothing in the download pipeline may write it.** `SmartDownloadJob` used to rewrite every flag in a series on each top-up so only its window stayed set, and `SeriesController.SetMonitorMode` rewrote all of them on a mode change — so a user's own ticks never survived, and every count surface reported the machine's window instead of the series (a held-back series read "10 / 10", not "10 / 207"). Smart's window is now just `Chapter.NextWanted`, evaluated per tick and discarded; re-running is safe because `EnqueueChapterAsync` already drops an already-queued chapter. `SetMonitorMode` governs chapters released *later* and nothing else.
- **A deleted-on-purpose file is `Chapter.FileRemovedAt`, never `Wanted = false`.** A removed chapter (`FileRemovedAt` set, no file) still counts toward the total (`Wanted || ChapterFileId != null || FileRemovedAt != null`) and its reads still count, but it is not missing, so `Chapter.IsMissing` (every download selector, `NextWanted`, Smart, "Download N wanted", torrent span states) passes over it. Setting `Wanted` instead would shrink the series total and break the three-writers rule above. `MakiDbContext.StampFileAndCompletion` clears the stamp whenever a file is linked, so no linking path has to; an `ExecuteUpdate` that links files bypasses it and must clear it itself. The frontend reads `removedChapterCount` through `obtainedCount` (`lib/chapterCounts.ts`) wherever `chapterFileCount` meant "chapters the user has had". **Every on-purpose delete goes through `ChapterFileDeletion`** ("Delete file" = `POST chapter/deletefiles`, the Files tab, automatic cleanup): it stamps every chapter on the file, not just the named ones, since a volume file backs several. "Remove chapters" (`DELETE chapter`) is the other path and still deletes rows outright, for a wrong source match. Health deletion deliberately does not stamp: a broken file should be fetched again. **`ChapterFileDeletion.ClaimedAsync` is the only "is this file still somebody's" check**: it compares absolute paths across every root folder with query filters off, because nested roots name one file by two relative paths and a root the caller can't see still holds it. A per-root relative-path comparison (what all three paths used to do) misses both.
- **`Series.MonitorNewItems` is the only series-level monitoring flag** (no series-level `Monitored` — removed, it was write-once-at-Add and drifted; `SeriesDto.Monitored` is derived). The series still *monitors*; individual chapters are *wanted*, and keeping the two words apart is what stops them reading as one setting.
- **`RefreshMonitoredSeriesJob` skips the enqueue for Smart series explicitly.** New chapters there are wanted like anyone else's (so they count toward the total) and Smart decides *when* they're queued. That gate used to be implicit — `MonitoredUnder` returned false for Smart, so new chapters landed unmonitored and the predicate never matched — which also meant "Search missing" silently did nothing on a Smart series. `Chapter.WantedUnder` now returns a real answer for Smart, honouring `monitoring.unmonitorspecials` directly since Smart can't be combined with MainOnly.
- **Read file cleanup is opt-in twice over** (`ReadFileCleanupService`, `ReadFileCleanupJob` every six hours). `cleanup.readfiles.enabled` is off unless an admin sets it, and `Series.ReadFileCleanup` (Default/On/Off) lets one series opt in without it or out of it. A chapter is due `cleanup.readfiles.days` after the **last** reader finished it (the later of `ChapterProgress.CompletedAt` and `UpdatedAt`, so a chapter re-read to the end counts as recent while the first-completion stamp stays put; `UpdatedAt` only counts when the row sits at its last page, so merely opening a finished chapter or an OPDS prefetch does not move it), and only once **every** user with progress in that series has; users with none hold nothing back. A volume file goes only when every chapter on it is due, and `cleanup.readfiles.keeplast` (on unless set) holds back each reader's most recent finish. `ScheduleAsync` is also what the chapter list calls for its "File removed in N days" hint, so the hint and the job cannot disagree; it reads progress with query filters off. Deletion goes through `ChapterFileDeletion`, under the series lock, and skips a series with any in-flight download.
- **Smart's window starts after the furthest reader, and a never-read series gets one batch on its own** (`SmartDownloadJob.SeriesNeedingTopUpAsync`/`Ahead`). With no `ReadingState` a series is due only while nothing wanted is on disk, so an add downloads its first batch and then waits for reading; with one, it is due once downloaded, unread chapters past the furthest `MaxChapter` number `smartdownload.chaptersleft` or fewer, zero included. Batches skip chapters at or below that mark, so a series read to 40 on a tracker does not download 1-10. It used to need both a reading state and a downloaded chapter, which meant a Smart series added and left alone downloaded nothing. "Download next N" on the series page still starts at the lowest missing chapter: that one is the user asking.
- **A series added without an explicit mode takes `monitoring.defaultmode`** (`MonitorDefaults.ForNewSeriesAsync`: All unset, MainOnly or Smart; None is refused because it would contradict a monitoring switch that is on). The add form omits the mode when monitoring is on, library import and an approval without a mode use it too; import lists keep their own per-tracker choice. All still narrows to MainOnly under `monitoring.unmonitorspecials`.
- **`monitoring.unmonitorspecials` applies at discovery, never retroactively.** It picks a new series' *mode* in `SeriesCreationService.DefaultedMonitorMode` (All → MainOnly) and stamps each newly listed special on a Smart series. Nothing re-reads it when deciding what to download: `Wanted` is the single eligibility rule, which is why `SmartDownloadJob` no longer filters specials itself. `All` deliberately ignores it — the mode downgrade already covers new series, so honouring it twice would skip specials on a series set to All by hand.
- **The chapter-total denominator is `Wanted || ChapterFileId != null`**, shared by `SeriesController.ChapterTalliesAsync` (list and detail) and mirrored once on the frontend in `seriesProgressVisual`. The `|| hasFile` term is what makes a fully downloaded series read 39/39 rather than 40/39. It used to be spelled out in four places that were free to drift. `SeriesDto.WantedChapterCount` is that count; `LibraryCompositionTotalsDto.ChapterCount` is *every* chapter — they shared the name `ChapterCount` and did not mean the same thing.
- **Scrobbling runs two passes**: `KavitaPassAsync` (writes `ScrobbleSyncState`) and `NativePassAsync` (series the reader tracks that Kavita never reported, resolves remote ids off `Series` cross-id columns, no title search, writes a **separate** `SeriesScrobbleState` table). Don't merge the two tables — different key spaces, shared with `ScrobbleMapping`/`ScrobbleUnmatched`.
- **Two acquisition protocols share one `DownloadQueue`** (`AcquisitionProtocol` per item): scraper downloads via `DownloadWorkerHostedService`; torrent releases via Prowlarr → qBittorrent → `CompletedDownloadJob`. Startup worker-recovery only resets scraper items.
- **`ReleaseNameParser` runs its patterns twice and strips only extensions it recognises.** The tag strip has to happen first, or `(2024)` and `(f)` read as numbers; but it used to take a marker that lived only inside a bracket with it, so `My Series (v01).cbz` was dropped as unrecognized. The whole name is therefore retried when the stripped one parses to nothing — as a fallback, never first, because `(v2)` marks a second scan of a chapter file and a name that already parses must not pick up a volume from one. `GetFileNameWithoutExtension` is likewise gone: it read the `.1` of `My Series vol.1` as an extension, so only the extensions in `ArchiveExtensions` are stripped now. The markers break on `_` as well as on a word boundary (`Narutaru_vol.03`), which `` could not do since `_` is a word character.
- **A series with one chapter and one file links them whatever the file is called** (`CbzLinkService.LinkLoneFileAsync`). A one-shot or single-volume work usually has no number in its name — `Look Back.cbz` matches no pattern and nothing else would ever place it. Only a file whose name parses to *nothing* qualifies: a name carrying a number disagrees with the chapter rather than saying nothing about it, and a series whose chapter list is still syncing would otherwise adopt the wrong file.
- **A volume file can be recognised and still end up unlinked, and that is a different failure from unrecognised.** `LinkChapters`' volume branch matches on `Chapter.Volume`, which is NULL for any series whose source publishes no volume assignments, and `NULL >= 1` is false — so an identically named `v01` links for a series with volume data and not for one without. `SeriesController` reports the two states apart (`SeriesFileDto.Status`: `unlinked` vs `unrecognized`), and the Files tab draws them differently; keep that split, because from outside both look like "Maki didn't pick this up".
- **A volume compilation's own file name is where its chapters' volume comes from when nothing else has one** (`CbzLinkService.AdoptParsedVolume`). `ReleaseNameParser` reads the `v11` out of `Series v11 (2019) (Digital) (lfp).cbz`, and every chapter the file links takes it — by range, by the chapter markers in its page names, or by the fill pass. Without that the value existed only in the parsed name and died with the rename, leaving `{Chapter Volume}` blank for exactly the files it was meant for and `CoversWholeVolumes` unable to call the result `Vol.11`. A chapter that already has a volume keeps it (a provider's assignment outranks a scene release's), and a `v01-02` compilation assigns none at all, since it says nothing about which of its volumes any one chapter belongs to.
- **Not every release is a CBZ, and both import paths convert rather than refuse** (`Maki.Core/Import`: `ComicSourceScanner` finds them, `ComicSourceConverter` builds them). A `.zip` is the same container a `.cbz` is, so it is placed as it is and can still be hardlinked; `.cbr`/`.rar`/`.7z`/`.tar` are read with SharpCompress and written back into a zip. **The container is decided by the leading bytes (`ArchiveSignature.Sniff`), never by the extension**: scene releases ship 7z and RAR data under `.cbz` (the `.simulated` library's `By Spring - Volume 1.cbz` is one), and by extension such a file opened as an empty zip and was dropped from the plan, or would have been hardlinked into the library as a CBZ nothing can read. Only a real zip is placed as it is; everything else is repacked into a new file beside the seeding copy.; a folder of loose page images becomes one CBZ per folder; and an archive holding only archives (a `.cbr` of per-chapter `.rar`s) yields one comic per inner entry. A mislabelled `.cbz` already sitting in the series folder (library import, rescan) would be rebuilt onto its own name, so `ComicSourceConverter` first renames the original to the extension its bytes call for (`.cb7`/`.cbr`/`.cbt`) and builds the CBZ under the old name. Skipping it because the name was taken is how a 7z ended up linked and unreadable. **Page names are carried over exactly, never renumbered** — a compilation's chapter markers live in them and `VolumeChapterScanner` is the only thing that can link it. Scanning never extracts: it lists entry names, so a plan can be shown and a whole root folder can be scanned cheaply. A **solid** archive takes the forward-only `ExtractAllEntries` reader instead of picking entries out by hand, which on a solid RAR is quadratic at best. **Nothing is ever deleted**: a torrent keeps seeding and an import folder is the user's own copy, so the original stays and the built CBZ lands beside it.
- **A PDF is placed as it is and read in place, never converted to a CBZ.** `ComicSourceKind.Pdf` is `IsReadyToPlace` alongside `Cbz`/`Zip`, so `ComicSourceConverter.Materialize` hardlinks or copies it under its own `.pdf` name rather than repacking it, `ComicSourceScanner.PdfName` keeps the extension where `CbzName` would swap it. Page count comes from `Maki.Core.Reading.PdfReader.PageCount`, a 0 (unreadable/encrypted) is treated exactly like an archive that yields no images and silently dropped. A folder holding a `.pdf` is that comic's, the same rule that already applies to an archive, the loose-image scan skips it rather than reading it as a stray-page set. Naming a **rename** of an existing PDF (`SeriesRenameService`) must keep the `.pdf` extension: `FileNameBuilder.BuildChapterFileName`/`NamingService.BuildChapterFileNameAsync` take an optional extension override for exactly this, since the format builders otherwise always append `NamingDefaults.ChapterExtension` (`.cbz`). A file Maki downloads itself is always `.cbz`, only a placed, pre-existing PDF keeps its own extension.
- **A finished torrent that would displace library files is parked, never imported.** `CompletedDownloadJob` asks `TorrentImportService.PlanAsync` first; when the download's files cover chapters that already have one, the item goes to `QueueStatus.AwaitingImport` and the job must not advance it again (the explicit `item.Status != AwaitingImport` gate in the poll loop). The user settles it from the activity list via `POST queue/{id}/import`: `Replace` imports everything and moves what it superseded to the trash, `SkipExisting` imports only files bringing a chapter nothing backs (and passes `replaceExisting: false` so `CbzLinkService` cannot move a chapter off its current file), `Reject` cancels the item and touches nothing. Both the job and the endpoint go through `TorrentImportService` so the unattended path and the reviewed path can't grow two sets of rules about deleting a user's library.
- **Superseded means "lost every chapter to this import", computed before and after linking.** `TrashSupersededAsync` diffs the chapter→file map, so a file that was already spare (an adopted archive nothing matched) is never touched, and a file keeping even one chapter stays. Superseded files are never deleted: each is renamed into `.maki-trash/<SeriesId>/<FileId>-<name>` (a rename, so a hardlinked file keeps seeding), gets an `UpgradeHistory` row sharing one `GroupId` per import with the old path and chapters in `DetailJson`, and its `ChapterFile` row is removed; `UpgradeRevertService.RevertGroupAsync` undoes the whole import. The history row and the row removal are saved before the move and undone when the move fails, so the trash never holds a file without a row; a superseded file already missing from disk gets no history row at all, or the whole group would read `trashGone`. `DetailJson.TakenChapters` records every chapter the import took and its previous file, so a revert hands a chapter back to a file the import did not supersede and unlinks only chapters that had none. That is why `UpgradeHistory` has no FK to `ChapterFiles`. It is the only code path that trashes a library file the user didn't name, hence `LibraryPaths.Resolve` rather than `Path.Combine` and the per-file failure handling. The housekeeping purge and the `upgrade-trash` health row count these files like any other trash.
- **A torrent upgrade the volume search auto-grabbed (`TorrentUpgradeInfo` on `UpgradeInfoJson`, `Kind = "torrent"`, `ProposalId` null) imports on its own even though it displaces files**, because displacing them is why it was grabbed. A proposal the user grabbed does not: it parks like any conflicting torrent, with `SkipFileNames` filled so the review opens with the suggested skips ticked. Before an unattended import `CompletedDownloadJob` runs `CheckVolumeGuardAsync`, which measures every non-skipped file, volume or chapter, that takes chapters off a file in `ReplacedFileIds`; one that cannot be measured or has fewer pages than the single-chapter files it replaces parks the item (`error.upgrades.volumeGuard`, outcome `parked`) instead of replacing. Only such an item passes `ReplacedFileIds` to `CbzLinkService` as the displaceable set, and with a set present nothing outside it loses a chapter (a protected or already good single-chapter file inside the volume keeps its chapter); that set is also the one way a volume may take chapters off an older volume file. An upgrade item with an empty `ReplacedFileIds` is treated as a plain torrent and parks on conflict (`TorrentImportService.DecideUnattendedAsync` decides for the job). `UpgradeInfo.Parse` would happily read a torrent row's JSON as an empty scraper row, so anything reading `UpgradeInfoJson` asks `TorrentUpgradeInfo.Parse` first.
- **A volume with chapter markers in its page names never takes a chapter off another file by provider range alone.** The range still links chapters nothing backs; taking one off a single file needs the markers to name it. Without that, a partial `v01` (pages for 1-3) claimed chapters 1-6 and a Replace import superseded the files for 4-6. The same limit is in `CbzLinkService.LinkChapters`, `TorrentImportService.ChaptersCoveredBy` (the preview) and `FileRelinkPlanner.Rank`; keep all three in step. A volume with no markers still takes by range, since that is the only evidence it has.
- **A hardlinked torrent import may never be rewritten.** `download.usehardlinks` (default on) imports completed torrents with `FileLinker.Place`: hardlink first, copy when the filesystem refuses (different volume, no hardlink support). The library name and the still-seeding torrent then share one set of bytes, so `CompletedDownloadJob` passes `updateComicInfo: false` for anything it did not copy byte-for-byte, `library.writecomicinfo` included. The rewrite would not corrupt the torrent — `ComicInfoUpdater` builds a new archive and `File.Move`s it over the name, leaving the seeded inode alone — it would just quietly replace the shared file with the second full copy the hardlink existed to avoid. Renames (`SeriesRenameService`) and deletes are safe either way: they touch the directory entry, not the data.
- **A claimable queue item may legitimately have no `SourceMapping`.** A failed resolve leaves the row Failed with `SourceMappingId` still null and `RequeueEligibleFailuresAsync` flips it back to Queued; the FK is also `SetNull`, so deleting a mapping nulls live rows. Such an item belongs to no tracker, so no cooldown applies — `ClaimNextAsync` must treat null `SourceName` as claimable and let `ChapterDownloadProcessor` re-resolve. Feeding it to the cooldown dictionary threw out of the worker loop and silently killed every worker.
- **Chapter-list listings are cached per series, not per chapter (`SourceChapterListCache`).** Resolution is per chapter but `ISource.ListChaptersAsync` is per series, so a bulk enqueue used to fire one full catalog listing per queued chapter, all in parallel, all behind that source's shared rate limiter (`QueueLimit = int.MaxValue`) — they aged out against the HttpClient timeout instead of returning, the whole batch failed, and `RetryFailedDownloadsJob` re-queued it five minutes later to do it again. Single-flighted, successes only, 5-minute TTL. A failure is replayed (same exception, so a `RateLimitException` still parks the item; a timeout arrives as `TimeoutException` wrapping the original, so a waiter whose own token is live is not told it was cancelled) only to callers that were already queued behind it, for 20 s; a caller arriving afterwards fetches again. The gate itself is `SingleFlightGate`, shared with `SourceExternalIdCache`. `ChapterSyncService` still lists **uncached** (a refresh must see the site as it is now) but calls `Store` with the result — otherwise a monitored refresh's own enqueues resolve against a listing older than the chapter it just discovered and report it "not listed".
- **Detached resolves are gated (`MaxConcurrentResolves`) and deadlined (`ResolveDeadline`).** Every enqueue starts one; a bulk enqueue starts hundreds at once. The gate is taken *after* registering in `_resolving` so a row waiting its turn still reads as owned and the sweep doesn't start a second one. The deadline exists because a resolve that never returns leaves the row Resolving with a live owner, which is exactly the state `SweepOrphanedAsync` reads as "still working" and skips forever.
- **A worker holding one item forever is indistinguishable from a dead queue** — the row keeps an in-flight status *and* a registered owner, so the orphan sweep cannot rescue it, and two such items stop a default-sized pool dispatching at all (everything else reads "Queued" with nothing wrong). `download.itemtimeoutminutes` (default 120, 0 = off, re-read every cooldown poll and applied per item as it starts) is the only thing that ends it; on expiry the worker fails the item so the normal retry backoff owns what happens next.
- **`ClaimNextAsync` excludes cooling-down sources in SQL, not in memory.** Every worker runs it on every wake, five seconds apart, forever; materializing the queue and filtering client-side turned a single-row pick into a repeated full scan that contended with the pipeline's own status writes under SQLite's writer lock.
- **Nothing in the download worker may throw out of its loop.** `Task.WhenAll` can't surface a faulted worker while `PeriodicWakeAsync` is still running, and that never ends — a dead worker used to produce no log line and no shutdown, just a queue that stopped dispatching. `SuperviseAsync` restarts each loop, and the `ClaimNextAsync` call sits inside a try rather than in the `while` condition.
- **Download concurrency is live, so all `MaxConcurrentChapters` worker loops always exist.** The ones at or above the configured count park on a delay and must not touch the channel: a channel write is only a wake-up, and a parked worker that read one would swallow it, leaving real work waiting for the next cooldown poll.
- **Ownership of an in-flight row is tracked in memory, not by a timestamp** (`_inFlight`/`_resolving`, registered inside `ClaimNextAsync`/`ResolveAndActivateAsync` so there's no gap after the status flip). `SweepOrphanedAsync` (run by `RetryFailedDownloadsJob`, ahead of the `download.retry.enabled` gate — an unowned row is breakage, not policy) re-queues in-flight statuses nobody owns. A time-based heuristic would instead kill genuinely slow downloads. Workers must `ReleaseClaim` in a `finally`.
- **`DownloadQueueItem.PreferredMappingId` is a hard pin, not a preference.** It comes from "Find better copy", where the user looked at that source's scan and picked it. Every resolve of a pinned row passes `onlyPreferred: true` to `ChapterSourceResolver.ResolveAsync`, and the processor's 404 fallback fails the row (`error.download.pickedSourceUnavailable`) instead of moving to the next source. Falling back would hand the user a file from a source they didn't choose. Re-pinning a live row is a conditional `ExecuteUpdate` (a worker may have claimed it since the read), and the resolve re-reads the pin under a write transaction before saving, so a pick landing mid-resolve is not lost.
- **`ChapterDownloadProcessor`'s 404 fallback must carry its tried-mapping set across the recursion.** Excluding only the mapping in use made two mappings that both 404 ping-pong A → B → A forever, holding a worker and settling nothing.
- **Repeated source-side failures fail over like a 404 does, on every third one** (`SourceFailover`). `sourceRejected`, `sourceError` and `network` count; challenge, rate limit, disk and page errors stay on their source, and a pinned (`PreferredMappingId`), health-repair or upgrade row never leaves it. There is no per-mapping counter: it is `RetryCount % 3 == 0`, so the automatic retry cap still bounds how often an item can hop (with the default cap of 5 the second source gets two tries). Moving goes through `FailOverAsync`, shared with the 404 path.
- **Bulk retry and remove of Failed rows share `DownloadQueueService.FailedWhere`** (failure key and/or source, where source is the name the queue lists: a mapping's, `torrent`, or `?`). `RetryFailedAsync` is `RequeueEligibleFailuresAsync` with the attempt cap and backoff off, like the single `Retry`, and still leaves torrents, health repairs and `PermanentErrorKeys` alone. `remove-failed` only deletes rows still Failed when the delete runs.
- **`DownloadQueueItem.Origin` is what makes "automatic downloads only" expressible.** Every enqueue path funnels through `DownloadQueueService.EnqueueChapterAsync` and is indistinguishable afterwards, so the trigger is recorded on the row (and survives a restart). Only `SmartDownload`/`MonitorRefresh`/`RequestApproval` raise inbox rows; `Manual` stays silent because the user watched themselves click it. Pre-migration rows read as `Unknown`, which never notifies. There is no `Retry` origin — a retry reuses the original row and keeps its origin. `RequestApproval` carries the **requester's** `QueuedByUserId`, not the approving admin's.
- **Bulk downloads coalesce through `DownloadBatchNotifier`, not the inbox.** Inbox rows are raised from the same open/summarize points, so a 200-chapter add produces 2 rows rather than 200. `Batch.Origin` is fixed when the batch opens; items of a different origin joining it inherit that.

- **A download failure is a key plus a detail, never the bare `error.download.unexpected`.** `DownloadFailureReason.Classify` maps the exception (401/403, other HTTP status, a site's own error body as `SourceErrorException`, network/SSL/timeout, disk, a chapter no source lists) to a key, and `SetError(key, detail: ...)` puts what the site or exception said in `ErrorMessage`, which the client shows after the keyed reason. Keys still take no placeholders (the batch summary has one reason per series), which is why the detail rides beside the key rather than inside it. A key the client's `ERROR_LABELS` lacks renders as nothing, so a new server key needs its client twin in the same change.
- **`QueueItemDto`'s `Release` / `One-shot` / `Vol.{v} Ch.{n}` labels belong on the client.** They are pure formatting of structured data the client already has, and `Vol.`/`Ch.` need per-language abbreviations. `Status` already sends the enum name and is fine as it is.
- **Library import never waits on a source site.** The request does metadata, rename, cover, building CBZs and `CbzLinkService.RegisterFilesAsync` (rows, no links, no ComicInfo), then sets `SourceMatchPending` + `Series.PendingImportLink` in the same series-locked section and queues the match in the background lane. `SourceMatchWorkerHostedService` matches two series at a time, then its single-reader link stage re-runs `LinkFilesAsync` over the registered rows, rewriting ComicInfo only when the marker says `LinkAndComicInfo`. Not `RescanSeriesAsync`: it lacks the lone-file rule and rewrites nothing for rows it already knows. The link stage clears the marker under the lock it links in, keeps it when the root is unreachable, and clears it on any other failure. A reimport into a series that already has chapters still links synchronously in the request.
- **Library import runs `MaxConcurrentImports` (8) folders at once, each in its own DI scope** (`LibraryImportController.ImportInOwnScopeAsync`). A fresh scope starts anonymous, unfiltered and in the default language, so the request's `CurrentUserContext`, `DataScope` and locale are copied in; skip that and the import sees series in root folders the caller was never granted. Nothing in the fan-out may touch the request's own `DbContext`, which is why the notification locale is read before it. Two guards stand in for what serial order used to give for free: `LibraryImportService.ImportLanes` puts items naming the same series or the same folder in one lane that runs in request order (`MangaBakaId` has no unique index, so two parallel imports of one series would both add it), and `SeriesLocks.FolderNamesAsync` (process-wide) is held from the folder-name snapshot through the row insert or `Directory.Move`, in `SeriesCreationService.AddAsync` as well, so two folders standardizing to one name cannot both be told it is free. Lock order is provider id, then series, then folder names. The scan fans out the same way (`ScanConcurrency`), keeping candidates in folder order.
- **A series can have files in more than one root-level folder.** The keep-new-standard folder naming mode imports a folder by leaving the files where they are and pointing `Series.FolderName` at the standard folder future downloads go to, so `FolderName` alone does not say where a series' files are. `SeriesFolders.ForAsync` does: `FolderName` plus the top folder of every `ChapterFile.RelativePath`, minus folders another series owns. Rescan, the Files tab, delete and move go through it; `CbzLinkService.LinkFilesAsync` prefixes paths with the folder it was handed, never `FolderName`. Rows stored under the wrong folder before that fix are repointed once at startup by `ImportPathRepairService`. The import scan counts a folder as claimed once any series has a file in it.
- **`ChapterFiles` has no unique index on `(SeriesId, RelativePath)`, so `CbzLinkService.LinkFilesAsync` is the guard.** It looks each incoming path up by `LibraryPaths.ComparisonKey` (case- and separator-insensitive) and reuses the row it finds; a torrent import re-run for files already in the folder (a poll cut off before the queue row was saved, a parked item settled after the job had placed its files) used to insert a second row per file, which listed it twice on the Files tab and hid it from anything keyed by first match. `ChapterFileDuplicateRepairService` folds the pairs that exist once, marker-gated at startup: lowest id survives, chapters are re-pointed, `ReaderArchiveCache` forgets the removed ids.
- **One active queue row per chapter is enforced by the database, not by the enqueue check.** `DownloadQueueItem.ActiveChapterId` is a computed column (`ChapterId` unless `Status` is Completed/Failed/Cancelled, else NULL) with a unique index, so every settle nulls it and every re-activation sets it without any code path having to remember. `EnqueueChapterAsync` still checks first, but a lost race surfaces as a unique violation that it turns into the normal "already queued" answer; `RequeueEligibleFailuresAsync` and `QueueController.Retry` skip or 409 a chapter that is active again. Migration `DownloadQueueActiveChapter` cancels pre-existing duplicates (oldest survives) before building the index.
- **`RateLimited` rows survive a restart parked.** `ClaimNextAsync` only takes rows whose `NextAttempt` is null or past, and startup recovery leaves `RateLimited` rows alone while reseeding the in-memory `_cooldowns` from their `NextAttempt`. Flipping them to `Queued` at boot used to hammer a source right after a 429.
- **A label the parser can't number becomes a one-shot, and giving those one-shots their label as a title is what made them distinct.** WeebCentral labels chapters "<word> <number>" with the word picked per series ("Episode 12", "Plot 49", "Mischief 225"), so `WeebCentralSource.ParseLabel` falls back to the trailing number; before that, each listed with a null Number and (at first) a null Title, so `ChapterIdentity` folded a whole series into one row. Titling them split that into one wanted one-shot per episode, and every refresh queued the whole series. `ChapterSyncService.PromotableOneShot` numbers such a row in place once its label parses (matched on `Title == NumberRaw`), so it keeps its file instead of a second numbered row being created and downloaded. That titling is now central: `ChapterIdentity.Labelled` gives any chapter with neither number nor title its `NumberRaw` as title, applied in `SourceChapterList.Normalize` and again in `ChapterSyncService`, so a source only has to fill `NumberRaw`.
- **An empty listing never replaces a mapping that has links.** `ChapterSyncService` treats it as a failed sync (`LastError` set, links kept, nothing stored in `SourceChapterListCache`), because a challenge page or a changed layout parses to nothing. JSON sources also throw when the container they read is missing, and only return `[]` when it is present but empty.
- **`RefreshMonitoredSeriesJob` holds back a burst instead of queueing it** (`monitoring.bulkholdthreshold`, default 5, 0 = off, edited in the Downloads settings panel). More new wanted chapters than that in one refresh of a non-Smart series is almost always a source renumbering or backfilling its list, and queueing it downloads the whole series. The chapters stay wanted and the notification/inbox row says they were held (`*.chapters.held.*`), so "Download N wanted" on the series page picks them up. Smart series skip the check: they drip-feed anyway.
- **`SeriesLocks` is a non-reentrant per-series async lock; rescan, import linking, download placement, torrent import, rename, move, series/file/chapter delete all hold it.** Never take it inside a path that is already under it. Series and chapter delete also refuse while `SeriesLocks.InFlight` sees a worker on that series: scraper items in the active statuses, rows in `Importing`, plus the ids in `TorrentImportService.AutomaticImportIds()`. The unattended torrent path never persists `Importing` (the poll would reset it), so `CompletedDownloadJob` registers the id in that static set around its import, and `TorrentImportService.ImportAsync` re-reads the series' existence, `FolderName` and `RootFolderId` after taking the lock and returns `error.torrentImport.seriesChanged` rather than recreating a deleted folder.
- **A `RateLimited` row whose `ErrorKey` is `error.download.rootFolderUnavailable` is parked, not throttled.** Startup recovery must not feed its `NextAttempt` into `RestoreCooldown`, or a share outage puts the whole source into cooldown.
