# Download queue and workers

Migrated out of the root CLAUDE.md so this only loads when touching the download pipeline.

- **Chapter identity and sync**: `Chapter.Number` is stored as REAL — EF Core SQLite can't `ORDER BY` it directly, so any "next N chapters" ordering happens in memory (`Chapter.NextWanted`); identity is `(Number, Language)` with Volume as wildcard. `ChapterSyncService.MergeDuplicates` heals dupes on every refresh. `RefreshMonitoredSeriesJob` compares against highest chapter number, never count — sources carry specials MangaBaka doesn't count, so count comparisons falsely read "ahead" or "behind".
- **`Chapter.Wanted` is user intent and has exactly three writers**: `ChapterSyncService` stamps it once at discovery (`Chapter.WantedUnder`), the user flips it (`ChapterController.SetWanted`/`SetWantedBulk`), and `MergeDuplicates` ORs it. **Nothing in the download pipeline may write it.** `SmartDownloadJob` used to rewrite every flag in a series on each top-up so only its window stayed set, and `SeriesController.SetMonitorMode` rewrote all of them on a mode change — so a user's own ticks never survived, and every count surface reported the machine's window instead of the series (a held-back series read "10 / 10", not "10 / 207"). Smart's window is now just `Chapter.NextWanted`, evaluated per tick and discarded; re-running is safe because `EnqueueChapterAsync` already drops an already-queued chapter. `SetMonitorMode` governs chapters released *later* and nothing else.
- **`Series.MonitorNewItems` is the only series-level monitoring flag** (no series-level `Monitored` — removed, it was write-once-at-Add and drifted; `SeriesDto.Monitored` is derived). The series still *monitors*; individual chapters are *wanted*, and keeping the two words apart is what stops them reading as one setting.
- **`RefreshMonitoredSeriesJob` skips the enqueue for Smart series explicitly.** New chapters there are wanted like anyone else's (so they count toward the total) and Smart decides *when* they're queued. That gate used to be implicit — `MonitoredUnder` returned false for Smart, so new chapters landed unmonitored and the predicate never matched — which also meant "Search missing" silently did nothing on a Smart series. `Chapter.WantedUnder` now returns a real answer for Smart, honouring `monitoring.unmonitorspecials` directly since Smart can't be combined with MainOnly.
- **`monitoring.unmonitorspecials` applies at discovery, never retroactively.** It picks a new series' *mode* in `SeriesCreationService.DefaultedMonitorMode` (All → MainOnly) and stamps each newly listed special on a Smart series. Nothing re-reads it when deciding what to download: `Wanted` is the single eligibility rule, which is why `SmartDownloadJob` no longer filters specials itself. `All` deliberately ignores it — the mode downgrade already covers new series, so honouring it twice would skip specials on a series set to All by hand.
- **The chapter-total denominator is `Wanted || ChapterFileId != null`**, shared by `SeriesController.ChapterTalliesAsync` (list and detail) and mirrored once on the frontend in `seriesProgressVisual`. The `|| hasFile` term is what makes a fully downloaded series read 39/39 rather than 40/39. It used to be spelled out in four places that were free to drift. `SeriesDto.WantedChapterCount` is that count; `LibraryCompositionTotalsDto.ChapterCount` is *every* chapter — they shared the name `ChapterCount` and did not mean the same thing.
- **Scrobbling runs two passes**: `KavitaPassAsync` (writes `ScrobbleSyncState`) and `NativePassAsync` (series the reader tracks that Kavita never reported, resolves remote ids off `Series` cross-id columns, no title search, writes a **separate** `SeriesScrobbleState` table). Don't merge the two tables — different key spaces, shared with `ScrobbleMapping`/`ScrobbleUnmatched`.
- **Two acquisition protocols share one `DownloadQueue`** (`AcquisitionProtocol` per item): scraper downloads via `DownloadWorkerHostedService`; torrent releases via Prowlarr → qBittorrent → `CompletedDownloadJob`. Startup worker-recovery only resets scraper items.
- **A claimable queue item may legitimately have no `SourceMapping`.** A failed resolve leaves the row Failed with `SourceMappingId` still null and `RequeueEligibleFailuresAsync` flips it back to Queued; the FK is also `SetNull`, so deleting a mapping nulls live rows. Such an item belongs to no tracker, so no cooldown applies — `ClaimNextAsync` must treat null `SourceName` as claimable and let `ChapterDownloadProcessor` re-resolve. Feeding it to the cooldown dictionary threw out of the worker loop and silently killed every worker.
- **Chapter-list listings are cached per series, not per chapter (`SourceChapterListCache`).** Resolution is per chapter but `ISource.ListChaptersAsync` is per series, so a bulk enqueue used to fire one full catalog listing per queued chapter, all in parallel, all behind that source's shared rate limiter (`QueueLimit = int.MaxValue`) — they aged out against the HttpClient timeout instead of returning, the whole batch failed, and `RetryFailedDownloadsJob` re-queued it five minutes later to do it again. Single-flighted, successes only, 5-minute TTL. `ChapterSyncService` still lists **uncached** (a refresh must see the site as it is now) but calls `Store` with the result — otherwise a monitored refresh's own enqueues resolve against a listing older than the chapter it just discovered and report it "not listed".
- **Detached resolves are gated (`MaxConcurrentResolves`) and deadlined (`ResolveDeadline`).** Every enqueue starts one; a bulk enqueue starts hundreds at once. The gate is taken *after* registering in `_resolving` so a row waiting its turn still reads as owned and the sweep doesn't start a second one. The deadline exists because a resolve that never returns leaves the row Resolving with a live owner, which is exactly the state `SweepOrphanedAsync` reads as "still working" and skips forever.
- **A worker holding one item forever is indistinguishable from a dead queue** — the row keeps an in-flight status *and* a registered owner, so the orphan sweep cannot rescue it, and two such items stop a default-sized pool dispatching at all (everything else reads "Queued" with nothing wrong). `download.itemtimeoutminutes` (default 120, 0 = off, read once at startup) is the only thing that ends it; on expiry the worker fails the item so the normal retry backoff owns what happens next.
- **`ClaimNextAsync` excludes cooling-down sources in SQL, not in memory.** Every worker runs it on every wake, five seconds apart, forever; materializing the queue and filtering client-side turned a single-row pick into a repeated full scan that contended with the pipeline's own status writes under SQLite's writer lock.
- **Nothing in the download worker may throw out of its loop.** `Task.WhenAll` can't surface a faulted worker while `PeriodicWakeAsync` is still running, and that never ends — a dead worker used to produce no log line and no shutdown, just a queue that stopped dispatching. `SuperviseAsync` restarts each loop, and the `ClaimNextAsync` call sits inside a try rather than in the `while` condition.
- **Ownership of an in-flight row is tracked in memory, not by a timestamp** (`_inFlight`/`_resolving`, registered inside `ClaimNextAsync`/`ResolveAndActivateAsync` so there's no gap after the status flip). `SweepOrphanedAsync` (run by `RetryFailedDownloadsJob`, ahead of the `download.retry.enabled` gate — an unowned row is breakage, not policy) re-queues in-flight statuses nobody owns. A time-based heuristic would instead kill genuinely slow downloads. Workers must `ReleaseClaim` in a `finally`.
- **`ChapterDownloadProcessor`'s 404 fallback must carry its tried-mapping set across the recursion.** Excluding only the mapping in use made two mappings that both 404 ping-pong A → B → A forever, holding a worker and settling nothing.
- **`DownloadQueueItem.Origin` is what makes "automatic downloads only" expressible.** Every enqueue path funnels through `DownloadQueueService.EnqueueChapterAsync` and is indistinguishable afterwards, so the trigger is recorded on the row (and survives a restart). Only `SmartDownload`/`MonitorRefresh`/`RequestApproval` raise inbox rows; `Manual` stays silent because the user watched themselves click it. Pre-migration rows read as `Unknown`, which never notifies. There is no `Retry` origin — a retry reuses the original row and keeps its origin. `RequestApproval` carries the **requester's** `QueuedByUserId`, not the approving admin's.
- **Bulk downloads coalesce through `DownloadBatchNotifier`, not the inbox.** Inbox rows are raised from the same open/summarize points, so a 200-chapter add produces 2 rows rather than 200. `Batch.Origin` is fixed when the batch opens; items of a different origin joining it inherit that.
