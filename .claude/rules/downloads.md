# Download queue and workers

- **Chapter identity and sync**: `Chapter.Number` is stored as REAL, which EF Core SQLite can't `ORDER BY`, so any "next N chapters" ordering happens in memory (`Chapter.NextWanted`); identity is `(Number, Language)` with Volume as wildcard. `ChapterSyncService.MergeDuplicatesAsync` heals dupes on every refresh. **Two languages of one chapter are two rows that both want a file**, and the default chapter format has no `{Chapter Language}`, so `FileNameBuilder` appends ` [xx]` to any non-`en` chapter when the format has no language token. `RefreshMonitoredSeriesJob` compares against the highest chapter number, never the count: sources carry specials MangaBaka doesn't count.
- **A mapping's `LanguageFilter` is a comma-separated list** (`en,es`, `SourceLanguages.Parse`); null still means English, **not** every language, so an untouched mapping keeps listing what it did. Only sources declaring `SourceCapabilities.SupportsLanguageFilter` honour it (MangaDex, MangaFire). Each added language multiplies that mapping's chapter rows, counts and downloads.
- **`Chapter.Wanted` is user intent and has exactly three writers**: `ChapterSyncService` stamps it once at discovery (`Chapter.WantedUnder`), the user flips it (`ChapterController.SetWanted`/`SetWantedBulk`), and `MergeDuplicatesAsync` ORs it. **Nothing in the download pipeline may write it**, or count surfaces report the machine's window instead of the series. Smart's window is just `Chapter.NextWanted`, evaluated per tick and discarded; re-running is safe because `EnqueueChapterAsync` drops an already-queued chapter. `SeriesController.SetMonitorMode` governs chapters released *later* and nothing else.
- **A deleted-on-purpose file is `Chapter.FileRemovedAt`, never `Wanted = false`.** A removed chapter still counts toward the total and its reads still count, but `Chapter.IsMissing` (every download selector, `NextWanted`, Smart, "Download N wanted", torrent span states) passes over it. `MakiDbContext.StampFileAndCompletion` clears the stamp whenever a file is linked; an `ExecuteUpdate` that links files bypasses it and must clear it itself. The frontend reads `removedChapterCount` through `obtainedCount` (`lib/chapterCounts.ts`) wherever `chapterFileCount` meant "chapters the user has had". **Every on-purpose delete goes through `ChapterFileDeletion`** ("Delete file" = `POST chapter/deletefiles`, the Files tab, automatic cleanup), which stamps every chapter on the file, since a volume file backs several. "Remove chapters" (`DELETE chapter`) still deletes rows outright, for a wrong source match. Health deletion deliberately does not stamp: a broken file should be fetched again. **`ChapterFileDeletion.ClaimedAsync` is the only "is this file still somebody's" check**: it compares absolute paths across every root folder with query filters off, because nested roots name one file by two relative paths and a root the caller can't see still holds it.
- **User deletes go to the recycle bin, automatic ones do not.** "Delete file" (`ChapterFileDeletion.DeleteAsync` with a `RecycleReason`), "Remove chapters" and series delete with files rename each file into `<root>/.maki-trash/bin/<SeriesId>/<tag>-<name>` and record a `RecycleBinEntry` (original path, series, chapters and the whole `ChapterFile` as JSON; no FKs, since all may be gone at restore). Read file cleanup deletes for good and upgrades keep the upgrade trash.
  - Series delete bins every regular file in a folder the series owns whatever its extension (plus tracked files elsewhere), skips files `ClaimedAsync` gives to another series, then prunes bottom-up: empty folders and a `cover.jpg` Maki wrote (`CoverService.IsMakiLibraryCover`) go, anything else keeps the folder. Never a recursive delete.
  - **Record, save, move, settle**: the entry is saved before its file moves and removed only after the file has left the bin, so the bin never holds an unrecorded file; a failed move leaves the file and its rows in place.
  - The move is `SameVolumeMove` (native rename without copy), never `File.Move`, which silently copies across volumes and breaks hardlinks. `RecycleBinService.Refusal` probes every folder first and refuses the whole delete with `error.recycleBin.crossVolume` (or `unavailable`); the refusal carries `permanentDeleteAvailable` and the dialogs offer `permanent=true` under the same permission.
  - Restore never overwrites (`targetExists`), goes into the series' current `FolderName` when the stored folder is no longer the series' (`RestorePathsAsync`), relinks only chapters of a series still in the same root that have no file now, and otherwise leaves the file unlinked and queues a root health scan.
  - `library.recyclebindays` (default 14) is purged by `UpgradeTrashService.PurgeAsync` with the upgrade trash; its orphan sweep re-asks the database before deleting an unreferenced bin file, because a binned file keeps its old write time. Endpoints need `DeleteSeries`; entries are scoped by root folder.
- **`Series.MonitorNewItems` is the only series-level monitoring flag** (`SeriesDto.Monitored` is derived from it). The series *monitors*; individual chapters are *wanted*. Keep the two words apart.
- **`RefreshMonitoredSeriesJob` skips the enqueue for Smart series explicitly.** New chapters there are still wanted (they count toward the total) and Smart decides *when* they're queued. `Chapter.WantedUnder` honours `monitoring.unmonitorspecials` directly for Smart, since Smart can't be combined with MainOnly.
- **Read file cleanup is opt-in twice over** (`ReadFileCleanupService`, `ReadFileCleanupJob` every six hours). `cleanup.readfiles.enabled` is off unless an admin sets it, and `Series.ReadFileCleanup` (Default/On/Off) lets one series opt in or out. A chapter is due `cleanup.readfiles.days` after the **last** reader finished it (a re-read to the end counts; opening a finished chapter or an OPDS prefetch does not), and only once **every** user with progress in that series has; users with none hold nothing back. A volume file goes only when every chapter on it is due, and `cleanup.readfiles.keeplast` (on unless set) holds back each reader's most recent finish. The chapter list's "File removed in N days" hint calls the same `ScheduleAsync`, which reads progress with query filters off. Deletion goes through `ChapterFileDeletion`, under the series lock, and skips a series with any in-flight download.
- **Smart's window starts after the furthest reader, and a never-read series gets one batch on its own** (`SmartDownloadJob.SeriesNeedingTopUpAsync`/`Ahead`). With no `ReadingState` a series is due only while nothing wanted is on disk; with one, it is due once downloaded, unread chapters past the furthest `MaxChapter` number `smartdownload.chaptersleft` or fewer, zero included. Batches skip chapters at or below that mark, so a series read to 40 on a tracker does not download 1-10. A series also waits while any of Smart's own rows is queued, in flight or failed inside its backoff (`PreviousBatchPendingAsync`), or the window slides a batch per tick through a series whose downloads all fail; a chapter out of attempts stops holding it. "Download next N" on the series page still starts at the lowest missing chapter.
- **A series added without an explicit mode takes `monitoring.defaultmode`** (`MonitorDefaults.ForNewSeriesAsync`: All unset, MainOnly or Smart; None is refused because it would contradict a monitoring switch that is on). The add form omits the mode when monitoring is on, library import and an approval without a mode use it too; import lists keep their own per-tracker choice. All still narrows to MainOnly under `monitoring.unmonitorspecials`.
- **`monitoring.unmonitorspecials` applies at discovery, never retroactively.** It picks a new series' mode in `SeriesCreationService.DefaultedMonitorMode` (All → MainOnly) and stamps each newly listed special on a Smart series. `Wanted` is the single download eligibility rule; nothing re-reads the setting. `All` deliberately ignores it, so a series set to All by hand keeps its specials.
- **The chapter-total denominator is `Wanted || ChapterFileId != null || FileRemovedAt != null`**, computed only in `SeriesController.ChapterTalliesAsync` (list and detail) and sent as `SeriesDto.WantedChapterCount`, which `seriesProgressVisual` reads rather than recomputing. The file terms make a fully downloaded series read 39/39, not 40/39. `LibraryCompositionTotalsDto.ChapterCount` is *every* chapter, a different number.
- **Scrobbling runs two passes**: `KavitaPassAsync` (writes `ScrobbleSyncState`) and `NativePassAsync` (series the reader tracks that Kavita never reported, resolves remote ids off `Series` cross-id columns, no title search, writes a **separate** `SeriesScrobbleState` table). Don't merge the two tables — different key spaces, shared with `ScrobbleMapping`/`ScrobbleUnmatched`.
- **Two acquisition protocols share one `DownloadQueue`** (`AcquisitionProtocol` per item): scraper downloads via `DownloadWorkerHostedService`; torrent releases via the active indexer (`IReleaseIndexer`, Prowlarr or Jackett, chosen by `indexer.backend`) → the configured torrent client (`ITorrentClient`, resolved by `TorrentClientRegistry` from `downloadclient.kind`) → `CompletedDownloadJob`. Startup worker-recovery only resets scraper items.
- **One indexer backend is active at a time, and each keeps its own keys** (`prowlarr.*`, `jackett.*`), because their indexer ids differ (Prowlarr ints, Jackett slugs like `nyaasi`) and switching back should find the old selection intact. Release guids differ between backends too, so switching makes old Dismissed `TorrentProposal` rows stop blocking anything. Jackett is driven only through API-key routes (native JSON search, the torznab `all` endpoint for `t=indexers` and `t=caps`); its `/api/v2.0/indexers` and `server/config` JSON routes want the admin cookie. Jackett's key travels in the query string, so its URLs must not reach the logs.
- **`ReleaseNameParser` runs its patterns twice and strips only extensions it recognises.** Tags are stripped first, or `(2024)` and `(f)` read as numbers; when the stripped name parses to nothing the whole name is retried (`My Series (v01).cbz`), as a fallback only, because `(v2)` marks a second scan and a name that already parses must not pick up a volume from it. Only `ArchiveExtensions` are stripped (`GetFileNameWithoutExtension` reads the `.1` of `vol.1` as an extension). Markers break on `_` as well as a word boundary (`Narutaru_vol.03`).
- **Non-English volume and chapter words are opt-in per language** (`parsing.languages`, `ReleaseMarkers` table, `NameParsingProfile.Current`). English is always read and unchanged, and the `.simulated` library parses identically with every language on. The profile is process-wide, set at startup and by `PUT settings/nameparsing`; tests pass one to `ParseFileName(name, profile)` or sit in the `NameParsingProfile` collection, which runs alone. A word belongs to every language that uses it (`T` is French and Polish). Single letters (`T`, `т`) only count when no full volume word is in the name (`Terminator T2 v05` is volume 5). CJK markers follow the number (`第12巻`, `3권`) with no letter test in front; `全12巻` is volumes 1 to 12. With German on, `Brass Band 2` reads as volume 2: an accepted trade-off, since no pattern separates it from a real `Band 2`. `ChapterNumberParser` (source labels) deliberately takes none of this, because a label that parses differently changes chapter identity on the next sync.
- **Always on, whatever the languages:** NFKC folding at the entry of both parsers (fullwidth digits and brackets in CJK names; done once on the way in, never on a copy, because `ReleaseTitleParser` cuts by match index and NFKC changes length), `【】` as tag brackets, language names, uppercase codes and container formats as noise rather than a group (`[CBZ]` used to be the group of every scene release), and a marker in any language as "not a group". Scene names (`ReleaseNameParser.IsSceneStyle`: no spaces, words joined by `.`/`_`) get their `-GROUP` suffix appended to the tags, which is what gives them a group and a Scanlator tier, and `ReleaseTitleParser` adds the text before the first span token as a title candidate, because the author and language after the volume drag the full candidate below the match threshold.
- **The release search says when a switched-off language would have read a release** (`SpanVerdictReasons.MarkersOff`, parsed again with `NameParsingProfile.AllLanguages` only when the span came out empty). A digital release with no span reads as a whole-series pack, so the reason can sit on a stored proposal. **A parked import refuses a plan reviewed under other parsing settings**: the plan carries `parsingFingerprint` and `POST queue/{id}/import` answers `error.queue.planStale` when it no longer matches, so Replace never supersedes a different set than the review showed.
- **A torrent title has to name the series at least as well as it names any related work** (`ReleaseTitleMatcher.Match`, rivals from `TorrentUpgradeService.RivalTitlesAsync`). The extension rule that lets `Hajime no Ippo: Fighting Spirit!` match `Hajime no Ippo` also let `My Dress-Up Darling XOXO!` match `My Dress-Up Darling`, and text alone cannot tell a subtitle from a spin-off. Rivals are every title of the works one MangaBaka relation away, of any type (`MangaBakaLocalStore.GetRelatedTitlesAsync` over `FranchiseGraph.RelatedTargets`, deliberately wider than the same-work set, merged rows followed on both ends), plus every other library series, kept only when shaped like a whole-word extension of one of the series' titles (`ReleaseTitleMatcher.Rivals`); anything else is already stopped by the coverage and shape gates, and scoring every library title against every release would cost seconds per manual search. The rival's score is the same gated `ScrobbleMatching.MatchScore`, compared per title candidate (a dual-title release is decided by the half that named us), strictly greater, ties keep ours. No margin: a long title with a one-word suffix beats its parent by only 0.03 to 0.06. The library titles are read once per service instance, which is one read per volume search run. A beaten release reads `title_related_series` instead of `title_uncertain` and carries `RivalTitle` to the results tooltip. Without the dump only library rivals apply. The XOXO release's parsed candidate is `My Dress-Up Darling XOXO! 001-013 as`: an unmarked range in front of `as v01` stays in the title.
- **A series with one chapter and one file links them whatever the file is called** (`CbzLinkService.LinkLoneFileAsync`), so `Look Back.cbz` gets placed. Only a file whose name parses to nothing qualifies (`ReleaseNameParser` `IsRecognized` false): a name carrying a number disagrees with the chapter, and a series still syncing its list would adopt the wrong file.
- **A volume file can be recognised and still end up unlinked, and that is a different failure from unrecognised.** `LinkChapters`' volume branch matches on `Chapter.Volume`, which is NULL for any series whose source publishes no volume assignments, and `NULL >= 1` is false — so an identically named `v01` links for a series with volume data and not for one without. `SeriesController` reports the two states apart (`SeriesFileDto.Status`: `unlinked` vs `unrecognized`), and the Files tab draws them differently; keep that split, because from outside both look like "Maki didn't pick this up".
- **A volume compilation's file name supplies its chapters' volume when nothing else has one** (`CbzLinkService.AdoptParsedVolume`): every chapter `Series v11 (2019) (Digital) (lfp).cbz` links takes `11`, so `{Chapter Volume}` and `CoversWholeVolumes` still work after the rename. A chapter that already has a volume keeps it (a provider's assignment outranks a scene release's), and a `v01-02` compilation assigns none.
- **Not every release is a CBZ; both import paths convert rather than refuse** (`Maki.Core/Import`: `ComicSourceScanner` finds them, `ComicSourceConverter` builds them).
  - **The container is decided by the leading bytes (`ArchiveSignature.Sniff`), never the extension**: scene releases ship 7z and RAR data under `.cbz` (`.simulated`'s `By Spring - Volume 1.cbz`). Only a real zip is placed as it is and can be hardlinked; `.cbr`/`.rar`/`.7z`/`.tar` are read with SharpCompress and repacked into a new CBZ beside the seeding copy.
  - A folder of loose page images becomes one CBZ per folder; an archive holding only archives (a `.cbr` of per-chapter `.rar`s) yields one comic per inner entry.
  - A mislabelled `.cbz` already in the series folder (library import, rescan) is first renamed to the extension its bytes call for (`.cb7`/`.cbr`/`.cbt`), then the CBZ is built under the old name.
  - **Page names are carried over exactly, never renumbered**: a compilation's chapter markers live in them and `VolumeChapterScanner` links by them.
  - Scanning lists entry names and never extracts. A **solid** archive takes the forward-only `ExtractAllEntries` reader; picking entries out by hand is quadratic on a solid RAR.
  - **Nothing is ever deleted**: a torrent keeps seeding and an import folder is the user's own copy, so the original stays and the built CBZ lands beside it.
- **A PDF is placed as it is and read in place, never converted.** `ComicSourceKind.Pdf` is `IsReadyToPlace` like `Cbz`/`Zip` and keeps its own `.pdf` name (`ComicSourceScanner.PdfName`). A `PdfReader.PageCount` of 0 (unreadable/encrypted) drops it like an archive with no images. A folder holding a `.pdf` belongs to that comic, so the loose-image scan skips it. Renaming an existing PDF (`SeriesRenameService`) must pass the extension override to `FileNameBuilder.BuildChapterFileName`/`NamingService.BuildChapterFileNameAsync`, which otherwise append `.cbz`. Files Maki downloads are always `.cbz`.
- **A grab resolves the infohash before the row exists** (`ReleaseService.AddToClientAsync`), or `CompletedDownloadJob.ClaimTorrent` cannot match it and the item fails as `torrentMissing` after two hours. A `.torrent` link is fetched through the active indexer's proxy URL, hashed (`TorrentInfoHash`) and uploaded with `AddFileAsync`; a redirect to a magnet is added as that magnet. Prowlarr replaces every magnet with its own proxy link, API key in the query, so `ProwlarrClient` keeps `MagnetUrl` only when it starts with `magnet:` and otherwise uses it as the download URL (or drops it when there is one); a release's magnet never goes to the browser either. Both magnet branches fall back to the indexer's `InfoHash` when the magnet has no `btih`. A driver that returns the hash from its add call (Transmission, Deluge) wins over the computed one. A hashless URL add is only the fallback when no hash can be had (the fetch failed, or the link served neither). Such a row first claims a torrent named exactly like its release (`CompletedDownloadJob.ComparableName`), whenever it was added and even when Completed/Failed/Cancelled rows of the same series hold its hash, because the add-time window misses a torrent the client already had and a retried row is older than its window. When a live row or another series holds that torrent nothing is guessed from the window, and the row fails as `error.download.torrentHeldElsewhere` naming the holder's series; only with no same-named torrent at all does the window apply. Base32 magnet hashes are converted to lowercase hex, which is what every driver lists and what `ClaimTorrent` compares.
- **The client is a driver behind `ITorrentClient`, and the callers only know the record.** `ClientTorrent` carries `Hash`, `Name`, `Progress`, `IsComplete`, `ContentPath`, `AddedAt`, `IsErrored`; nothing outside a driver may read a client's own state strings. `IsComplete` is the driver's verdict (qBittorrent: progress 1 and not `error`/`missingFiles`/`checking*`; Transmission: `isFinished` or `percentDone` 1 unless `error` is 3, a local error; tracker errors 1 and 2 do not block it; Deluge: `is_finished` or progress 100 outside Checking/Error/Allocating/Moving), so a torrent that reports 100 % while broken is not imported. `ListAsync` means Maki's torrents: filtered by category or label where the client can (qBittorrent category, Deluge Label plugin, Transmission and others client-side on `labels`), every torrent where it cannot; hashed rows still match and the hashless `ClaimTorrent` has its own guards. Drivers hold their own session state (cookies, CSRF ids) and take `TorrentClientSettings` on every call, so a settings change needs no restart. `PUT settings/downloadclient` refuses a kind or label change (409 `error.settings.downloadClientTorrentsInFlight`) while any torrent row the poll still covers (anything but Completed, Failed or Cancelled, so a parked AwaitingImport row counts) exists: the next poll would list through the new driver or label, fail those rows as `torrentRemoved`/`torrentMissing`, and `BlamesRelease` would decline every release. Transmission 4.1 renamed its RPC fields to snake_case, but answers a request without a JSON-RPC 2.0 envelope in the old names, so the driver speaks the legacy names on every version and reads `rpc-version` only to decide whether labels go on `torrent-add` (17 and up) or through `torrent-set`.
- **An errored torrent holds its row, never fails it.** `CompletedDownloadJob` sets `error.download.torrentClientError` with the client's message on a row whose torrent reports `IsErrored` and clears it when the error goes; the status is left alone. The usual cause is a disk the client lost for a while, and a Failed row is never polled again, so failing it would strand a torrent that later finishes. **A label filter makes an unlabelled torrent invisible**, so once labels work a driver must not let a grab end with the torrent unlabelled: Deluge fails the grab (grabbing again finds it present and labels it), tolerates losing the race to create the label, and a Deluge label must pass `DelugeClient.IsValidLabel` to be saved. qBittorrent refuses a duplicate upload; when the torrent it already has sits in another category the grab fails as `TorrentClientFailure.HeldOutsideLabel` instead of recategorising it, because a category change moves the files under automatic torrent management. The volume search treats that failure as the user's client setup: it neither declines the release nor takes the one-day `RetryAfterFailure`, so the series waits out the normal interval instead of re-uploading the same torrent daily. Transmission below rpc 16 has no labels at all and lists unfiltered.
- **A finished torrent that would displace library files is parked, never imported.** `CompletedDownloadJob` asks `TorrentImportService.PlanAsync` first; when the download's files cover chapters that already have one, the item goes to `QueueStatus.AwaitingImport` and the job must not advance it again (the explicit `item.Status != AwaitingImport` gate in the poll loop). The user settles it from the activity list via `POST queue/{id}/import`: `Replace` imports everything and moves what it superseded to the trash, `SkipExisting` imports only files bringing a chapter nothing backs (and passes `replaceExisting: false` so `CbzLinkService` cannot move a chapter off its current file), `Reject` cancels the item and touches nothing. Both the job and the endpoint go through `TorrentImportService` so the unattended path and the reviewed path can't grow two sets of rules about deleting a user's library.
- **Superseded means "lost every chapter to this import", computed before and after linking** (`TrashSupersededAsync` diffs the chapter→file map), so an already-spare file is never touched and a file keeping one chapter stays. Superseded files are never deleted: each is renamed into `.maki-trash/<SeriesId>/<FileId>-<name>`, gets an `UpgradeHistory` row (one `GroupId` per import; `UpgradeRevertService.RevertGroupAsync` undoes the group) and loses its `ChapterFile` row. Row changes are saved before the move and undone if it fails, so the trash never holds a file without a row; a superseded file already missing from disk gets no history row, or the group reads `trashGone`. `DetailJson.TakenChapters` records each taken chapter's previous file so a revert can hand it back, which is why `UpgradeHistory` has no FK to `ChapterFiles`. This is the only path that trashes a file the user didn't name: use `LibraryPaths.Resolve`, not `Path.Combine`, and handle failures per file.
- **A torrent upgrade the volume search auto-grabbed (`TorrentUpgradeInfo` on `UpgradeInfoJson`, `Kind = "torrent"`, `ProposalId` null) imports unattended even though it displaces files**, but only past the volume guard: `TorrentImportService.DecideUnattendedAsync` (which decides for the job) runs `CheckVolumeGuardAsync`, and any non-skipped file taking chapters off a `ReplacedFileIds` file that cannot be measured or has fewer pages than the single-chapter files it replaces parks the item (`error.upgrades.volumeGuard`). A proposal the user grabbed parks like any conflicting torrent, with `SkipFileNames` pre-ticked; so does an upgrade with empty `ReplacedFileIds`. A Replace import of an upgrade passes `ReplacedFileIds` to `CbzLinkService` as the displaceable set: nothing outside it loses a chapter, and it is the one way a volume may take chapters off an older volume file. `UpgradeInfo.Parse` happily reads a torrent row's JSON as an empty scraper row, so read `UpgradeInfoJson` with `TorrentUpgradeInfo.Parse` first.
- **A volume with chapter markers in its page names never takes a chapter off another file by provider range alone.** The range still links chapters nothing backs; taking one off a file needs the markers to name it. A volume with no markers still takes by range. Keep `CbzLinkService.LinkChapters`, `TorrentImportService.ChaptersCoveredBy` (the preview) and `FileRelinkPlanner.Rank` in step.
- **A hardlinked torrent import is never rewritten.** `download.usehardlinks` (default on) places completed torrents with `FileLinker.Place` (hardlink, copy when the filesystem refuses). `TorrentImportService` writes ComicInfo only when every file was a fresh copy, whatever `library.writecomicinfo` says, because `ComicInfoUpdater` `File.Move`s a new archive over the name and so replaces the shared file with the second full copy the hardlink avoided. Renames and deletes are safe.
- **A claimable queue item may legitimately have no `SourceMapping`.** A failed resolve leaves the row Failed with `SourceMappingId` still null and `RequeueEligibleFailuresAsync` flips it back to Queued; the FK is also `SetNull`, so deleting a mapping nulls live rows. Such an item has no cooldown: `ClaimNextAsync` must treat null `SourceName` as claimable and let `ChapterDownloadProcessor` re-resolve. Feeding it to the cooldown dictionary throws out of the worker loop and kills every worker.
- **Chapter listings are cached per series, not per chapter (`SourceChapterListCache`)**: resolution is per chapter but `ListChaptersAsync` is per series, and a bulk enqueue would otherwise fire one listing per chapter behind the source's rate limiter. Single-flighted through `SingleFlightGate` (shared with `SourceExternalIdCache`), successes only, 5-minute TTL. A failure is replayed for 20 s only to callers already waiting (same exception, so a `RateLimitException` still parks; a timeout arrives as `TimeoutException` wrapping the original). `ChapterSyncService` lists uncached but must `Store` the result, or its own enqueues resolve against a listing older than the chapter it just found.
- **Detached resolves are gated (`MaxConcurrentResolves`) and deadlined (`ResolveDeadline`, 15 min).** The gate is taken after registering in `_resolving`, so a waiting row still reads as owned; the deadline stops a hung resolve reading as "still working" to `SweepOrphanedAsync` forever.
- **A worker holding one item forever looks like a dead queue**: the row keeps an in-flight status and an owner, so the orphan sweep cannot rescue it, and two such items stall a default-sized pool. `download.itemtimeoutminutes` (default 120, 0 = off, read per item as it starts) fails the item so retry backoff takes over; `DownloadQueueService.CancelWork` (user cancel, mapping removal) also ends it.
- **`ClaimNextAsync` excludes cooling-down sources in SQL, never by materializing and filtering in memory**: every worker runs it every five seconds, and a full scan contends with status writes under SQLite's writer lock.
- **A pause only stops `ClaimNextAsync` handing out new scraper items; it never changes a row.** `DownloadPauseService` (singleton, `download.pause` JSON via the settings cache) holds an optional global pause and paused source names, each with an optional resume time. A global pause returns null before any query; paused sources join the cooling-down list. Queued rows stay `Queued` and the client derives Paused from `isHeldByPause`, so resume restores nothing. Torrents are unaffected. Resume times are checked at read time (`WithoutLapsed`); the `PeriodicWakeAsync` tick calls `ExpireAsync`, which clears the stored copy, broadcasts `queuePauseChanged` (to every active `ManageDownloadQueue` holder) and wakes workers. `GET/PUT/DELETE queue/pause` canonicalise source names through `SourceRegistry.Find`. Call `WakeWorkersAsync` on every lift; nothing else signals the channel. An unresolved row is still claimable while sources are paused, so the resolve leaves paused and cooling-down sources out (`DownloadQueueService.HeldSourcesAsync`), `FailOverAsync` puts them last, and a chapter only such a source lists is parked on it (`HoldAsync`: Queued for a pause, RateLimited until the cooldown).
- **Nothing in the download worker may throw out of its loop**: a faulted worker dies silently. `SuperviseAsync` restarts each loop, and the `ClaimNextAsync` call sits inside a try rather than in the `while` condition.
- **Download concurrency is live, so all `MaxConcurrentChapters` worker loops always exist.** The ones at or above the configured count park on a delay and must not touch the channel: a channel write is only a wake-up, and a parked worker that read one would swallow it, leaving real work waiting for the next cooldown poll.
- **Ownership of an in-flight row is tracked in memory, not by a timestamp** (`_inFlight`/`_resolving`, registered inside `ClaimNextAsync`/`ResolveAndActivateAsync` so there's no gap after the status flip). `SweepOrphanedAsync` (run by `RetryFailedDownloadsJob`, ahead of the `download.retry.enabled` gate — an unowned row is breakage, not policy) re-queues in-flight statuses nobody owns. A time-based heuristic would instead kill genuinely slow downloads. Workers must `ReleaseClaim` in a `finally`.
- **`DownloadQueueItem.PreferredMappingId` is a hard pin, not a preference.** It comes from "Find better copy", where the user looked at that source's scan and picked it. Every resolve of a pinned row passes `onlyPreferred: true` to `ChapterSourceResolver.ResolveAsync`, and the processor's 404 fallback fails the row (`error.download.pickedSourceUnavailable`) instead of moving to the next source. Falling back would hand the user a file from a source they didn't choose. Re-pinning a live row is a conditional `ExecuteUpdate` (a worker may have claimed it since the read), and the resolve re-reads the pin under a write transaction before saving, so a pick landing mid-resolve is not lost.
- **`ChapterDownloadProcessor`'s 404 fallback must carry its tried-mapping set across the recursion.** Excluding only the mapping in use made two mappings that both 404 ping-pong A → B → A forever, holding a worker and settling nothing.
- **Repeated source-side failures fail over like a 404 does, on every third one** (`SourceFailover`). `sourceRejected`, `sourceError` and `network` count; challenge, rate limit, disk and page errors stay on their source, and a pinned (`PreferredMappingId`), health-repair or upgrade row never leaves it. There is no per-mapping counter: it is `RetryCount % 3 == 0`, so the automatic retry cap still bounds how often an item can hop (with the default cap of 5 the second source gets two tries). Moving goes through `FailOverAsync`, shared with the 404 path.
- **Bulk retry and remove of Failed rows share `DownloadQueueService.FailedWhere`** (failure key and/or source, where source is the name the queue lists: a mapping's, `torrent`, or `?`). `RetryFailedAsync` is `RequeueEligibleFailuresAsync` with the attempt cap and backoff off, like the single `Retry`, and still leaves torrents, health repairs and `PermanentErrorKeys` alone. `remove-failed` only deletes rows still Failed when the delete runs.
- **A torrent release is blocked for the volume search by recording it as a Dismissed proposal** (`TorrentUpgradeService.DeclineAsync`), since a removed torrent row is hard-deleted and a Failed row is not in `BlockedGuidsAsync`. That happens when the user removes or cancels a torrent row (`blockRelease`, default on, also on `remove-failed`) and when `CompletedDownloadJob` fails one for a reason in the `BlamesRelease` allow-list (the release's own fault). The scraper counterpart is `UpgradeReasons.RepeatedFailure`: after `UpgradeCandidateRules.FailedAttemptLimit` Failed upgrade rows for one candidate, the daily scan stops reopening it; a manual scan or profile edit tries it again.
- **`DownloadQueueItem.Origin` records what triggered a download** (and survives a restart), which is what makes "automatic downloads only" expressible; every enqueue path, including the bulk `AddRange` in `EnqueueChaptersAsync`, must set it. `IsAutomatic` (`SmartDownload`/`MonitorRefresh`/`RequestApproval`/`Upgrade`) raises inbox rows; `Manual` stays silent. Pre-migration rows are `Unknown` and never notify. There is no `Retry` origin: a retry reuses the row. `RequestApproval` carries the **requester's** `QueuedByUserId`, not the approver's.
- **Bulk downloads coalesce through `DownloadBatchNotifier`, not the inbox.** Inbox rows are raised from the same open/summarize points, so a 200-chapter add produces 2 rows rather than 200. `Batch.Origin` is fixed when the batch opens; items of a different origin joining it inherit that.
- **A download failure is a key plus a detail, never the bare `error.download.unexpected`.** `DownloadFailureReason.Classify` maps the exception (401/403, other HTTP status, a site's own error body as `SourceErrorException`, network/SSL/timeout, disk, a chapter no source lists) to a key, and `SetError(key, detail: ...)` puts what the site or exception said in `ErrorMessage`, shown after the keyed reason. Keys take no placeholders (the batch summary has one reason per series), hence the separate detail. A key the client's `ERROR_LABELS` lacks falls back to the bare detail, or nothing without one, so add the client twin in the same change.
- **`QueueItemDto`'s `Release` / `One-shot` / `Vol.{v} Ch.{n}` labels belong on the client.** They are pure formatting of structured data the client already has, and `Vol.`/`Ch.` need per-language abbreviations. `Status` already sends the enum name and is fine as it is.
- **Library import never waits on a source site.** The request does metadata, rename, cover, CBZ builds and `CbzLinkService.RegisterFilesAsync` (rows only: no links, no ComicInfo), then sets `SourceMatchPending` + `Series.PendingImportLink` under the series lock and queues a background match. `SourceMatchWorkerHostedService` matches two series at a time; its single-reader link stage re-runs `LinkFilesAsync` over the registered rows (not `RescanSeriesAsync`, which lacks the lone-file rule), rewriting ComicInfo only for `LinkAndComicInfo`. It clears the marker under the lock it links in, keeps it when the root is unreachable (retrying after 30 s, doubling to 30 min), and clears it on any other failure. A reimport into a series that already has chapters links synchronously.
- **Library import runs `MaxConcurrentImports` (8) folders at once, each in its own DI scope** (`LibraryImportController.ImportInOwnScopeAsync`). Copy the request's `CurrentUserContext`, `DataScope` and locale into each scope, or the import sees root folders the caller was never granted, and never touch the request's own `DbContext` in the fan-out. `LibraryImportService.ImportLanes` serialises items naming the same series or folder (`MangaBakaId` has no unique index), and `SeriesLocks.FolderNamesAsync` (process-wide) is held from the folder-name snapshot through the insert or `Directory.Move`, in `SeriesCreationService.CreateAsync` too, so two folders standardizing to one name cannot both get it. Lock order: provider id, series, folder names. The scan fans out the same way (`ScanConcurrency`), keeping folder order.
- **The import scan skips ignored and empty folders before any metadata search.** `ImportIgnoredFolder` is per root folder ("Ignore this folder" in the review, un-ignored from the same page) and compared with `LibraryPaths.FolderComparer`; a folder with no comic in it is dropped whether or not a series owns it. Both checks sit before `provider.SearchAsync`, which is the expensive part of a scan.
- **The import preview runs the import's own rules, read instead of carried out.** `LibraryImportService.PlanAsync` (`POST libraryimport/plan`) calls the same `DecideFolder` (keep, rename, merge, or the refusal) and `PlanComics` (register, build, rebuild in place, use existing, unreadable, duplicate) that `ImportAsync` and `MaterializeComics` run, so a new rule goes into those two methods and the preview follows. It writes nothing and takes no locks. While the series has no chapters the expected links are read off the file names (`LinkDeferred`); `LibraryImportPlanTests` imports the fixture it planned and checks the two agree, through the link stage.
- **An import can be undone for 30 days, and undo reverses only what the import recorded** (`ImportBatchFolder.OperationsJson` holds `ImportOperations`, grouped by the client's `operationId`; `LibraryImportUndoService`). It removes a series only when the import created it and nothing was downloaded or read since, recording what `SeriesController.Delete` records (`SeriesRemovalRecord`). It cancels the deferred stages first: clears `SourceMatchPending` (created series only) and `PendingImportLink` with `ExecuteUpdate`, waits on `SourceMatchQueue.MatchInProgress`, then takes the series lock; a match still running after `MatchWait` gets its flags back and a successor match, never a link. **A built CBZ is deleted only when its original, re-read, still holds every page the build read** (`ImportBuiltFile.Pages`, `OriginalIntact`), because loose pages have the folder itself as source. Undo refuses when the original folder name belongs to another series, the registered rows were renamed since (`RegisteredPaths`), or the caller may not delete the series (`DeleteSeries`, unless they ran the import). `UndoneAt` is re-read under the lock; a failed disk half leaves `DiskPending` so undoing again retries only that. `HousekeepingJob` prunes after `RetentionDays`.
- **A series can have files in more than one root-level folder.** The keep-new-standard folder naming mode imports a folder by leaving the files where they are and pointing `Series.FolderName` at the standard folder future downloads go to. `SeriesFolders.ForAsync` gives the real set: `FolderName` plus the top folder of every `ChapterFile.RelativePath`, minus folders another series owns. Rescan, the Files tab, delete and move go through it; `CbzLinkService.LinkFilesAsync` prefixes paths with the folder it was handed, never `FolderName`. The import scan counts a folder as claimed once any series has a file in it.
- **`ChapterFiles` has no unique index on `(SeriesId, RelativePath)`, so `CbzLinkService.LinkFilesAsync` is the guard**: it looks each incoming path up by `LibraryPaths.ComparisonKey` (case- and separator-insensitive) and reuses the row it finds, since a torrent import can re-run for files already placed.
- **One active queue row per chapter is enforced by the database, not by the enqueue check.** `DownloadQueueItem.ActiveChapterId` is a computed column (`ChapterId` unless `Status` is Completed/Failed/Cancelled, else NULL) with a unique index, so no code path has to remember it. `EnqueueChapterAsync` still checks first and turns a lost race's unique violation into the normal "already queued" answer; `RequeueEligibleFailuresAsync` and `QueueController.Retry` skip or 409 a chapter that is active again.
- **`RateLimited` rows survive a restart parked.** `ClaimNextAsync` only takes rows whose `NextAttempt` is null or past, and startup recovery leaves `RateLimited` rows alone while reseeding the in-memory `_cooldowns` from their `NextAttempt`.
- **A label the parser can't number becomes a one-shot titled with its label** (`ChapterIdentity.Labelled`, applied in `SourceChapterList.Normalize` and again in `ChapterSyncService`), so unnumbered chapters stay distinct and a source only has to fill `NumberRaw`. `WeebCentralSource.ParseLabel` falls back to the trailing number of its per-series "<word> <number>" labels ("Episode 12", "Plot 49"). `ChapterSyncService.PromotableOneShot` numbers such a row in place once its label parses (matched on `Title == NumberRaw`), so it keeps its file instead of a second numbered row being downloaded.
- **An empty listing never replaces a mapping that has links.** `ChapterSyncService` treats it as a failed sync (`LastError` set, links kept, nothing stored in `SourceChapterListCache`), because a challenge page or a changed layout parses to nothing. JSON sources also throw when the container they read is missing, and only return `[]` when it is present but empty.
- **The monitored refresh syncs only series that are due** (`Series.NextCheckAt`, `RefreshMonitoredSeriesJob.DueSeriesIdsAsync`, 15-minute tick, half a tick of slack, most overdue first). Every full `ChapterSyncService.SyncSeriesAsync` (job, manual refresh, add, re-match, health recovery) writes `LastCheckAt`/`NextCheckAt` from `RefreshSchedule.Plan`; a partial `SyncMappingsAsync` never does. The tier comes from the newest chapter (`ReleaseHistory.LastNewChapter`: Maki's own `ChapterSourceLink.FirstSeenAt` or a date from a source whose `ISource.ReleaseDatesAreReliable` holds, falling back to re-stamped dates only when nothing else exists), so a failing source does not pull a series onto the fast tier, and a series that speeds up waits at most one tier interval. An `INextReleaseSource` (MANGA Plus) stores its announced time on `SourceMapping.AnnouncedNextReleaseAt` and pulls the check to just after it. `monitoring.adaptiverefresh` = "false" plans every series at 30 minutes; flipping it clears every `NextCheckAt` so nothing waits out a plan made under the other mode. **`FirstSeenAt` is written once and only for an arrival**: never on a mapping's first snapshot, never for a chapter numbered at or below what that mapping already listed unless it is new to the series, and not at all when one listing brings more than `ChapterSyncService.MaxArrivalsPerSync` (20), because each of those is a catalogue appearing, not a release. Merging duplicate chapters must carry it to the replacement link. The Upcoming tab and the series page's "Next chapter" read the same history through `ReleaseOutlookService`; `ReleaseCadence` draws a window only when the series' own past windows were hit often enough (smoothed hit rate of at least 0.55 over at least three tested releases, with fewer reading as Unknown rather than Irregular, and a window no wider than two thirds of the cycle, except the one-day floor on daily series), and the only date it ever shows is a source's announcement. Numbers behind every threshold are in `docs/design-release-aware-polling.md`.
- **`RefreshMonitoredSeriesJob` holds back a burst instead of queueing it** (`monitoring.bulkholdthreshold`, default 5, 0 = off, edited in the Downloads settings panel). More new wanted chapters than that in one refresh of a non-Smart series is almost always a source renumbering or backfilling its list, and queueing it downloads the whole series. The chapters stay wanted and the notification/inbox row says they were held (`*.chapters.held.*`), so "Download N wanted" on the series page picks them up. Smart series skip the check: they drip-feed anyway.
- **`SeriesLocks` is a non-reentrant per-series async lock** (holders listed on the class); never take it inside a path already under it. Series and chapter delete also refuse while `SeriesLocks.InFlight` sees a worker on the series, including the ids in `TorrentImportService.AutomaticImportIds()`: the unattended torrent path never persists `Importing` (the poll would reset it), so `CompletedDownloadJob` registers the id there around its import. `TorrentImportService.ImportAsync` re-reads the series' existence, `FolderName` and `RootFolderId` after taking the lock and returns `error.torrentImport.seriesChanged` rather than recreating a deleted folder.
- **A `RateLimited` row whose `ErrorKey` is `error.download.rootFolderUnavailable` is parked, not throttled.** Startup recovery must not feed its `NextAttempt` into `RestoreCooldown`, or a share outage puts the whole source into cooldown.
- **`IPageClientSource` swaps only the page client and the address check.** A source whose pages live at an admin-configured origin (Suwayomi on the LAN) cannot pass `PublicAddressGuard`, so `PageDownloader.DownloadAsync` takes it as an optional `pageClient` and uses its named client and `IsPageUrlAllowed`; cooldown, 429/503 mapping, 404 failover, the stall timeout and XOR are unchanged. `IsPageUrlAllowed` replaces the SSRF guard, so it must refuse everything outside the one configured origin, and the interface must never go on a source whose page URLs come from the site. Every `DownloadAsync` caller passes `source as IPageClientSource`; one that forgets gets the plain guard and fails loudly on LAN pages.
- **`SourceRegistry` is a snapshot, not a fixed list**: registered sources plus whatever each `ISourceProvider` supplies, swapped whole by `ReloadAsync`, which whatever writes provider state calls after saving. A registered source keeps its name against a provider. Read `All`/`Find` at call time and never cache the result. A mapping whose source is gone is skipped by sync and resolution, not failed, so re-exposing a provider source restores its mappings.
- **A converted file is scored as the copy it was acquired as.** Page conversion (`library.pageconversion.*`, `ArchivePageConverter`) shrinks `ChapterFile.Size` and changes `ImageFormat`, and `MeasuredQuality` would read that as a worse release and queue an upgrade that gets converted again, forever. So `ConversionSavedBytes` and `OriginalImageFormat` record what conversion did, and everything that judges quality reads `QualitySize`/`QualityImageFormat` instead: `UpgradeEvaluator.Candidate` and `Snapshot` (which also carries `StoredImageFormat`/`ConversionSavedBytes` so `RestoreFormatOnto` can put a revert back exactly), `SourceQualitySamples` from downloads and the measure backfill, `SourceQualitySeeder`, and the two `new ChapterFile { ... }` projections in `ChapterController` and `UpgradeEvaluationService`, which must copy both columns. `Size` stays the bytes on disk because the reader cache, page ETags and disk totals key on it. **Anything that puts new bytes under an existing row calls `ResetConversion()`** (re-download, upgrade, `CbzLinkService` size change and repack); a new row starts clean.
- **Conversion order in the download processor is measure, convert, place.** An upgrade is measured and judged on the archive as downloaded (`tmpCbz`), converted beside it (`.converted`) before the series lock, and the converted copy is what moves into place; the normal path measures the pages as downloaded for `OriginalImageFormat` and swaps the converted archive over `tmpCbz`. Health repairs are never converted: `RequiresReset` compares page bytes. Imports and torrents are only converted by the library pass, which skips hardlinked files (`HardLinks.IsShared`: rewriting one would store a second copy next to the seeding one) and series with a download in flight.
- **The library pass puts originals in the upgrade trash with no history row** (`.maki-trash/<SeriesId>/conv-<FileId>-<name>`), so `UpgradeTrashService.PurgeAsync`'s orphan sweep deletes them after `upgrades.trashRetentionDays`. The swap hardlinks the original into the trash (copies it where there are no hardlinks), then renames the converted copy over it, so the library path always holds a whole archive; never move the original out first, which leaves the path empty when the move back fails too. A rename that reports a failure but landed (`SameVolumeMove.Landed`) counts as done. On Windows the converter reads a copy in `.maki/tmp` (`conv-<FileId>.source.cbz`), because a file held open for the minutes an AVIF volume takes blocks a rename of it and of its series folder. The worker counts a file that throws as failed and moves on, or the pass would restart on it every minute. Pages load with `FailOn.Error`: libvips otherwise greys out a truncated JPEG and conversion would bake the damage into a page that looks whole. The input is untrusted (imports, torrents), so the health scan's limits hold before anything is allocated or decoded: an entry over `ArchiveHealthAnalyzer.MaxEntryBytes`, or a running total over `MaxExpandedBytes`, makes the file `Unreadable`, and a page over `MaxPixels` is kept as `TooLarge`. Changing the format clears `ConversionCheckedAtUtc` only on files left as they were; a converted page is never converted again.
