# Download queue and workers

Migrated out of the root CLAUDE.md so this only loads when touching the download pipeline.

- **Chapter identity and sync**: `Chapter.Number` is stored as REAL — EF Core SQLite can't `ORDER BY` it directly, so any "next N chapters" ordering happens in memory (`Chapter.NextWanted`); identity is `(Number, Language)` with Volume as wildcard. `ChapterSyncService.MergeDuplicates` heals dupes on every refresh. **Two languages of one chapter are two rows that both want a file**, and the default chapter format carries no `{Chapter Language}` — so `FileNameBuilder` appends ` [es]` to anything that is not `en` when the format has no language token of its own. Only the non-default language is suffixed, deliberately: every file on disk today is English, so a second language adds names instead of renaming the library. The cost is that a Spanish-only series has `[es]` on every file. `RefreshMonitoredSeriesJob` compares against highest chapter number, never count — sources carry specials MangaBaka doesn't count, so count comparisons falsely read "ahead" or "behind".
- **A mapping's `LanguageFilter` is a comma-separated list** (`en,es`), read through `SourceLanguages.Parse`; null still means English, **not** every language — an untouched mapping has to keep listing exactly what it listed before, or every existing series grows a chapter row per translation on the next sync. Only sources declaring `SourceCapabilities.SupportsLanguageFilter` honour it (MangaDex, MangaFire). Adding a language multiplies that mapping's chapter rows, its wanted/missing counts and its downloads, which is why the picker says so.
- **`Chapter.Wanted` is user intent and has exactly three writers**: `ChapterSyncService` stamps it once at discovery (`Chapter.WantedUnder`), the user flips it (`ChapterController.SetWanted`/`SetWantedBulk`), and `MergeDuplicates` ORs it. **Nothing in the download pipeline may write it.** `SmartDownloadJob` used to rewrite every flag in a series on each top-up so only its window stayed set, and `SeriesController.SetMonitorMode` rewrote all of them on a mode change — so a user's own ticks never survived, and every count surface reported the machine's window instead of the series (a held-back series read "10 / 10", not "10 / 207"). Smart's window is now just `Chapter.NextWanted`, evaluated per tick and discarded; re-running is safe because `EnqueueChapterAsync` already drops an already-queued chapter. `SetMonitorMode` governs chapters released *later* and nothing else.
- **`Series.MonitorNewItems` is the only series-level monitoring flag** (no series-level `Monitored` — removed, it was write-once-at-Add and drifted; `SeriesDto.Monitored` is derived). The series still *monitors*; individual chapters are *wanted*, and keeping the two words apart is what stops them reading as one setting.
- **`RefreshMonitoredSeriesJob` skips the enqueue for Smart series explicitly.** New chapters there are wanted like anyone else's (so they count toward the total) and Smart decides *when* they're queued. That gate used to be implicit — `MonitoredUnder` returned false for Smart, so new chapters landed unmonitored and the predicate never matched — which also meant "Search missing" silently did nothing on a Smart series. `Chapter.WantedUnder` now returns a real answer for Smart, honouring `monitoring.unmonitorspecials` directly since Smart can't be combined with MainOnly.
- **`monitoring.unmonitorspecials` applies at discovery, never retroactively.** It picks a new series' *mode* in `SeriesCreationService.DefaultedMonitorMode` (All → MainOnly) and stamps each newly listed special on a Smart series. Nothing re-reads it when deciding what to download: `Wanted` is the single eligibility rule, which is why `SmartDownloadJob` no longer filters specials itself. `All` deliberately ignores it — the mode downgrade already covers new series, so honouring it twice would skip specials on a series set to All by hand.
- **The chapter-total denominator is `Wanted || ChapterFileId != null`**, shared by `SeriesController.ChapterTalliesAsync` (list and detail) and mirrored once on the frontend in `seriesProgressVisual`. The `|| hasFile` term is what makes a fully downloaded series read 39/39 rather than 40/39. It used to be spelled out in four places that were free to drift. `SeriesDto.WantedChapterCount` is that count; `LibraryCompositionTotalsDto.ChapterCount` is *every* chapter — they shared the name `ChapterCount` and did not mean the same thing.
- **Scrobbling runs two passes**: `KavitaPassAsync` (writes `ScrobbleSyncState`) and `NativePassAsync` (series the reader tracks that Kavita never reported, resolves remote ids off `Series` cross-id columns, no title search, writes a **separate** `SeriesScrobbleState` table). Don't merge the two tables — different key spaces, shared with `ScrobbleMapping`/`ScrobbleUnmatched`.
- **Two acquisition protocols share one `DownloadQueue`** (`AcquisitionProtocol` per item): scraper downloads via `DownloadWorkerHostedService`; torrent releases via Prowlarr → qBittorrent → `CompletedDownloadJob`. Startup worker-recovery only resets scraper items.
- **`ReleaseNameParser` runs its patterns twice and strips only extensions it recognises.** The tag strip has to happen first, or `(2024)` and `(f)` read as numbers; but it used to take a marker that lived only inside a bracket with it, so `My Series (v01).cbz` was dropped as unrecognized. The whole name is therefore retried when the stripped one parses to nothing — as a fallback, never first, because `(v2)` marks a second scan of a chapter file and a name that already parses must not pick up a volume from one. `GetFileNameWithoutExtension` is likewise gone: it read the `.1` of `My Series vol.1` as an extension, so only the extensions in `ArchiveExtensions` are stripped now. The markers break on `_` as well as on a word boundary (`Narutaru_vol.03`), which `` could not do since `_` is a word character.
- **A series with one chapter and one file links them whatever the file is called** (`CbzLinkService.LinkLoneFileAsync`). A one-shot or single-volume work usually has no number in its name — `Look Back.cbz` matches no pattern and nothing else would ever place it. Only a file whose name parses to *nothing* qualifies: a name carrying a number disagrees with the chapter rather than saying nothing about it, and a series whose chapter list is still syncing would otherwise adopt the wrong file.
- **A volume file can be recognised and still end up unlinked, and that is a different failure from unrecognised.** `LinkChapters`' volume branch matches on `Chapter.Volume`, which is NULL for any series whose source publishes no volume assignments, and `NULL >= 1` is false — so an identically named `v01` links for a series with volume data and not for one without. `SeriesController` reports the two states apart (`SeriesFileDto.Status`: `unlinked` vs `unrecognized`), and the Files tab draws them differently; keep that split, because from outside both look like "Maki didn't pick this up".
- **A volume compilation's own file name is where its chapters' volume comes from when nothing else has one** (`CbzLinkService.AdoptParsedVolume`). `ReleaseNameParser` reads the `v11` out of `Series v11 (2019) (Digital) (lfp).cbz`, and every chapter the file links takes it — by range, by the chapter markers in its page names, or by the fill pass. Without that the value existed only in the parsed name and died with the rename, leaving `{Chapter Volume}` blank for exactly the files it was meant for and `CoversWholeVolumes` unable to call the result `Vol.11`. A chapter that already has a volume keeps it (a provider's assignment outranks a scene release's), and a `v01-02` compilation assigns none at all, since it says nothing about which of its volumes any one chapter belongs to.
- **Not every release is a CBZ, and both import paths convert rather than refuse** (`Maki.Core/Import`: `ComicSourceScanner` finds them, `ComicSourceConverter` builds them). A `.zip` is the same container a `.cbz` is, so it is placed as it is and can still be hardlinked; `.cbr`/`.rar`/`.7z`/`.tar` are read with SharpCompress and written back into a zip; a folder of loose page images becomes one CBZ per folder; and an archive holding only archives (a `.cbr` of per-chapter `.rar`s) yields one comic per inner entry. **Page names are carried over exactly, never renumbered** — a compilation's chapter markers live in them and `VolumeChapterScanner` is the only thing that can link it. Scanning never extracts: it lists entry names, so a plan can be shown and a whole root folder can be scanned cheaply. A **solid** archive takes the forward-only `ExtractAllEntries` reader instead of picking entries out by hand, which on a solid RAR is quadratic at best. **Nothing is ever deleted**: a torrent keeps seeding and an import folder is the user's own copy, so the original stays and the built CBZ lands beside it.
- **A PDF is placed as it is and read in place, never converted to a CBZ.** `ComicSourceKind.Pdf` is `IsReadyToPlace` alongside `Cbz`/`Zip`, so `ComicSourceConverter.Materialize` hardlinks or copies it under its own `.pdf` name rather than repacking it, `ComicSourceScanner.PdfName` keeps the extension where `CbzName` would swap it. Page count comes from `Maki.Core.Reading.PdfReader.PageCount`, a 0 (unreadable/encrypted) is treated exactly like an archive that yields no images and silently dropped. A folder holding a `.pdf` is that comic's, the same rule that already applies to an archive, the loose-image scan skips it rather than reading it as a stray-page set. Naming a **rename** of an existing PDF (`SeriesRenameService`) must keep the `.pdf` extension: `FileNameBuilder.BuildChapterFileName`/`NamingService.BuildChapterFileNameAsync` take an optional extension override for exactly this, since the format builders otherwise always append `NamingDefaults.ChapterExtension` (`.cbz`). A file Maki downloads itself is always `.cbz`, only a placed, pre-existing PDF keeps its own extension.
- **A finished torrent that would displace library files is parked, never imported.** `CompletedDownloadJob` asks `TorrentImportService.PlanAsync` first; when the download's files cover chapters that already have one, the item goes to `QueueStatus.AwaitingImport` and the job must not advance it again (the explicit `item.Status != AwaitingImport` gate in the poll loop). The user settles it from the activity list via `POST queue/{id}/import`: `Replace` imports everything and deletes what it superseded, `SkipExisting` imports only files bringing a chapter nothing backs (and passes `replaceExisting: false` so `CbzLinkService` cannot move a chapter off its current file), `Reject` cancels the item and touches nothing. Both the job and the endpoint go through `TorrentImportService` so the unattended path and the reviewed path can't grow two sets of rules about deleting a user's library.
- **Superseded means "lost every chapter to this import", computed before and after linking.** `DeleteSupersededAsync` diffs the chapter→file map, so a file that was already spare (an adopted archive nothing matched) is never deleted, and a file keeping even one chapter stays. It is the only code path that deletes a library file the user didn't name, hence `LibraryPaths.Resolve` rather than `Path.Combine` and the per-file try/catch.
- **A hardlinked torrent import may never be rewritten.** `download.usehardlinks` (default on) imports completed torrents with `FileLinker.Place`: hardlink first, copy when the filesystem refuses (different volume, no hardlink support). The library name and the still-seeding torrent then share one set of bytes, so `CompletedDownloadJob` passes `updateComicInfo: false` for anything it did not copy byte-for-byte, `library.writecomicinfo` included. The rewrite would not corrupt the torrent — `ComicInfoUpdater` builds a new archive and `File.Move`s it over the name, leaving the seeded inode alone — it would just quietly replace the shared file with the second full copy the hardlink existed to avoid. Renames (`SeriesRenameService`) and deletes are safe either way: they touch the directory entry, not the data.
- **A claimable queue item may legitimately have no `SourceMapping`.** A failed resolve leaves the row Failed with `SourceMappingId` still null and `RequeueEligibleFailuresAsync` flips it back to Queued; the FK is also `SetNull`, so deleting a mapping nulls live rows. Such an item belongs to no tracker, so no cooldown applies — `ClaimNextAsync` must treat null `SourceName` as claimable and let `ChapterDownloadProcessor` re-resolve. Feeding it to the cooldown dictionary threw out of the worker loop and silently killed every worker.
- **Chapter-list listings are cached per series, not per chapter (`SourceChapterListCache`).** Resolution is per chapter but `ISource.ListChaptersAsync` is per series, so a bulk enqueue used to fire one full catalog listing per queued chapter, all in parallel, all behind that source's shared rate limiter (`QueueLimit = int.MaxValue`) — they aged out against the HttpClient timeout instead of returning, the whole batch failed, and `RetryFailedDownloadsJob` re-queued it five minutes later to do it again. Single-flighted, successes only, 5-minute TTL. `ChapterSyncService` still lists **uncached** (a refresh must see the site as it is now) but calls `Store` with the result — otherwise a monitored refresh's own enqueues resolve against a listing older than the chapter it just discovered and report it "not listed".
- **Detached resolves are gated (`MaxConcurrentResolves`) and deadlined (`ResolveDeadline`).** Every enqueue starts one; a bulk enqueue starts hundreds at once. The gate is taken *after* registering in `_resolving` so a row waiting its turn still reads as owned and the sweep doesn't start a second one. The deadline exists because a resolve that never returns leaves the row Resolving with a live owner, which is exactly the state `SweepOrphanedAsync` reads as "still working" and skips forever.
- **A worker holding one item forever is indistinguishable from a dead queue** — the row keeps an in-flight status *and* a registered owner, so the orphan sweep cannot rescue it, and two such items stop a default-sized pool dispatching at all (everything else reads "Queued" with nothing wrong). `download.itemtimeoutminutes` (default 120, 0 = off, read once at startup) is the only thing that ends it; on expiry the worker fails the item so the normal retry backoff owns what happens next.
- **`ClaimNextAsync` excludes cooling-down sources in SQL, not in memory.** Every worker runs it on every wake, five seconds apart, forever; materializing the queue and filtering client-side turned a single-row pick into a repeated full scan that contended with the pipeline's own status writes under SQLite's writer lock.
- **Nothing in the download worker may throw out of its loop.** `Task.WhenAll` can't surface a faulted worker while `PeriodicWakeAsync` is still running, and that never ends — a dead worker used to produce no log line and no shutdown, just a queue that stopped dispatching. `SuperviseAsync` restarts each loop, and the `ClaimNextAsync` call sits inside a try rather than in the `while` condition.
- **Ownership of an in-flight row is tracked in memory, not by a timestamp** (`_inFlight`/`_resolving`, registered inside `ClaimNextAsync`/`ResolveAndActivateAsync` so there's no gap after the status flip). `SweepOrphanedAsync` (run by `RetryFailedDownloadsJob`, ahead of the `download.retry.enabled` gate — an unowned row is breakage, not policy) re-queues in-flight statuses nobody owns. A time-based heuristic would instead kill genuinely slow downloads. Workers must `ReleaseClaim` in a `finally`.
- **`ChapterDownloadProcessor`'s 404 fallback must carry its tried-mapping set across the recursion.** Excluding only the mapping in use made two mappings that both 404 ping-pong A → B → A forever, holding a worker and settling nothing.
- **`DownloadQueueItem.Origin` is what makes "automatic downloads only" expressible.** Every enqueue path funnels through `DownloadQueueService.EnqueueChapterAsync` and is indistinguishable afterwards, so the trigger is recorded on the row (and survives a restart). Only `SmartDownload`/`MonitorRefresh`/`RequestApproval` raise inbox rows; `Manual` stays silent because the user watched themselves click it. Pre-migration rows read as `Unknown`, which never notifies. There is no `Retry` origin — a retry reuses the original row and keeps its origin. `RequestApproval` carries the **requester's** `QueuedByUserId`, not the approving admin's.
- **Bulk downloads coalesce through `DownloadBatchNotifier`, not the inbox.** Inbox rows are raised from the same open/summarize points, so a 200-chapter add produces 2 rows rather than 200. `Batch.Origin` is fixed when the batch opens; items of a different origin joining it inherit that.

- **`DownloadQueueItem.ErrorMessage` is still English prose** and is the next stored-prose column due for conversion to a key plus params, following the `UserNotification` pattern. Six write sites.
- **`QueueItemDto`'s `Release` / `One-shot` / `Vol.{v} Ch.{n}` labels belong on the client.** They are pure formatting of structured data the client already has, and `Vol.`/`Ch.` need per-language abbreviations. `Status` already sends the enum name and is fine as it is.
