# Enhance: browser shaders and server upscaling

User-facing summary in `docs/features.md`. Two tiers share one reader setting: `a4k-*` methods run Anime4K in WebGL2 in the browser, `server:*` methods go through the ONNX queue and show `enhanceFallback` (an `a4k-*` preset, default `a4k-m`, or `off` for the plain page) until the server page is ready. With `off` the engine never loads and `PageEnhance` carries a null `preset` and `engine`.

## Server output

- WebP cannot exceed 16383 px per side, and tall 2x webtoon slices do. `ImageCodec.EncodeUpscaled` switches to JPEG q90 past that. Below it: WebP q85, effort 4 for colour and 2 for grey, sharp YUV off (it doubled colour encode time and native peak for no smaller file). WebP also has no greyscale mode: a grey page is encoded from one band but decodes as three equal bands. JPEG writes a true one-band file.
- The server tier takes sources up to `ImageCodec.MaxUpscalePixels` (16 MP), checked in `DecodeForUpscale` from the header. Bigger pages are `Skipped`/`tooLarge` and the browser fallback covers them. Peak memory scales with source pixels, so this, not `ArchiveHealthAnalyzer.MaxPixels` (40 MP), bounds the worker and `POST upscaling/benchmark` alike.
- The output is untagged sRGB, so `DecodeForUpscale` converts an embedded profile to sRGB first (`Raster.ToSrgb`). Without it an Adobe RGB colour page comes back washed out next to the colour-managed original. A one-band page keeps one band after a grey profile's transform, or it loses the luma path.
- The cache root `cache/upscale/` is separate from `cache/reader/`. `HousekeepingJob.PruneReaderCacheDir` deletes names it does not recognise, so never put upscale files in the reader cache and never change that method.
- `GET .../page/{n}/enhanced` calls `PageCache.DropAfterScan` on the served file in `Response.OnCompleted`: the browser keeps it as immutable, so its pages would only sit in the container's page cache. Never drop on write, the warm fetch comes seconds later.
- `UpscaleCache` keeps its own access-time index. Filesystem atime is useless (NTFS, `relatime`). A delete can fail on Windows while a file streams; the entry is kept and retried on the next write.

## Models and tiling

- Maki 2x is the default: `ReaderPrefsSpec.EnhanceMethodDefault` and `DEFAULT_ENHANCE_METHOD` are `server:maki-2x`, the fallback default stays `a4k-m` (`EnhanceFallbackDefault`), and `UpscaleOptions` reads an unset `library.upscaling.models` as `maki-2x` (a saved empty string stays empty). Because of that, `UpscalingController.Save` starts downloads for every ticked model on the first save, not only for newly ticked ones. The reader's picker shows the default as its fallback where the server does not offer it (`shownEnhanceMethod`); a server method picked by hand still shows as chosen. Catalogue order puts Maki 2x first. The settings page's speed and quality markers and the Recommended pill come from `SERVER_ENHANCE_METHODS` (`speed`, `quality`, `recommended`), on a five-step scale set by hand: speed from measured per-tile times (Maki 2x 20.6 ms, SPAN-S 43.5, Real-ESRGAN 62.4 on one thread; NAS 1.5 s against 4.2 s a page), quality from the owner's eye, where Real-ESRGAN stays a step above Maki 2x (owner, 2026-11-06).
- waifu2x swin_unet art was dropped before release: 19 MB and about 4x slower than SPAN-S (25 s a page on a 9950X3D, minutes on a NAS).
- SPAN-S takes and returns float16. The engine reads tensor types from the model file, not the catalogue.
- Real-ESRGAN is a 4x model. Each tile's 4x output is Lanczos-halved to 2x before the context crop and stitch (`Plain4xThenHalve`), so a full 4x page never sits in memory. Per-tile halving differs from whole-page halving by at most a few levels near tile edges.
- Greyscale detection (`UpscalePixels.IsGreyscale`) is a fraction test, not a mean: a page is colour when more than 1 in 2000 sampled pixels has a channel spread over 16, or the mean spread passes 6. A red title on a grey page must stay red.
- Run it on the decoded source, never on the model output. Real-ESRGAN tints flat screentone purple (SPAN-S barely), and a tinted output fails the test. Before encoding, `UpscalePixels.TakeColourFrom` keeps the model's luma and takes colour from the Lanczos-resized source, so grey areas stay grey on colour pages too. An exact-grey source (`UpscalePixels.IsExactGrey`, R = G = B everywhere, as every one-band JPEG or PNG decodes) skips the resize and the colour pass: the tiles are stitched as `Luma` into one band, which is bit-identical to colour pass plus `ToSingleBand`. Near-grey RGB scans keep the full path.
- `UpscaleCache.Generation` (`g3`) is part of every cached name. Raise it, with the regex and `ENHANCE_GENERATION` in `frontend/src/api/reader.ts`, whenever the pipeline's output changes: old names are then never served and housekeeping prunes them. Without it, tinted pages made by an older build keep being served. The enhanced URL carries it as `g=` and the ETag ends with it: the browser keeps the page as immutable by URL, so a server-side bump alone never replaces a page a browser already has (owner report, 2026-11-08). A URL without the current `g` is answered `no-cache`.
- The browser's final resample takes luma from the shader chain and chroma from the source tile. Restore CNN tints screentone the same way; a grey page must come out grey.
- `manifesturl` has no API. In dev it is a row in the `AppConfig` table of the config dir's SQLite database (key `library.upscaling.manifesturl`).
- Server tiling takes `ceil(n / 96)` tiles per axis, split into equal spans, with a 12 px context pad (within 2 levels of 16 px on SPAN-S, raw output within 4 levels of the old 384/16 tiling); every tile of a page shares one context shape (rounded to the model multiple), so ORT plans one memory pattern and IoBinding binds one shape. Small tiles let several run at once in the memory one 384 px tile took and turn margins and bubble interiors into whole flat tiles. Browser tiling is `min(MAX_TEXTURE_SIZE, 4096)/2` with a 16 px overlap.
- The browser hook sizing stays at 2x (`OUTPUT` is 2w x 2h) and `//!WHEN` is not parsed. The reader's Auto gate (display at 1.2x source, or a soft page) replaces it.
- A context tile that is one grey value throughout (pad included) skips inference and is filled with that value: any value for SPAN-S and Maki 2x, only 0 and 255 for Real-ESRGAN, which drifts a few levels on mid-grey flats. SPAN-S and Real-ESRGAN were checked bit-identical on colour manhwa pages; a new model needs the same check before it joins `KeepsFlat`. Maki 2x is the exception: its reach (19 px) is past the 12 px pad, so a flat tile comes back as a ramp up to 6 levels off near the tile edge (within a level deep inside), a faint grid on flat light-grey panels, and filling is closer to what the model means than running it.
- A page's tiles go to `min(UpscaleOptions.Threads, MaxWorkers)` workers on dedicated threads, each running one tile on one thread and taking the next from a shared counter; the session itself has one intra-op thread. ORT's intra-op threading splits every layer into equal chunks and waits for the slowest thread, which on a P/E-core CPU (the owner's NAS is an i5-14500 on 10 threads) is an E-core at every layer. `MaxWorkers` keeps the workers' activations under `WorkerBudgetBytes` (240 MB, about 22 MB a SPAN-S worker at 96 px), so threads past 10 add nothing. Each worker has its own `OnnxPageUpscaler.TileBuffers`: pinned arrays sized to the context tile, one `OrtValue` pair, bound with `OrtIoBinding` so ORT writes results in place. They are per run, never per session, because `POST upscaling/benchmark` can run beside the worker on the same session. The test hooks `TileCompleted`/`TileSkipped` fire from worker threads under a lock, in no fixed order. When the worker's queue drains after a burst it runs one aggressive compacting gen2 collect and `NativeHeap.Trim()`.
- `UpscaleModelStore.DeleteAsync` throws if the ORT session still holds the file. Call `OnnxPageUpscaler.ReleaseModel` first.
- `UpscaleOptions.Threads` is read per run and only sets the worker count; changing it never rebuilds the session.
- `ImageWorkGate` is not reentrant. Wrap the decode and encode leaf calls only, never the whole run. Inference runs outside it.
- Measured 2026-11-05 on SPAN-S: inference is about 95% of a page and ORT's convs run near the CPU's fp32 peak (one Zen 5 core about 70%), so a single tile has little left. CPU arena (5%, costs the memory work), spinning, `ORT_ENABLE_EXTENDED`/`BASIC` (slower, they drop the NCHWc layout), an fp32 copy and splitting the final Concat into four 1x1 convs (exact, 60 MB less, 5% faster, needs a new model file) were within noise or small. A third of kernel time at 16 threads, a fifth at 4, is NCHWc `ReorderInput`/`ReorderOutput` around the scalar `Sub` in each block, which ORT cannot keep blocked. int8 QDQ was 2.2x faster with VNNI but off by 70 to 100 levels on single pixels (PSNR 33 to 38 dB), also with conv-only and percentile calibration: not usable. Workers on 96 px tiles against one 384 px tile on the same threads: equal on 4 uniform cores with 110 MB less, 1.53x on 10 unpinned Zen 5 threads, 1.44x (SPAN-S) and 1.41x (Real-ESRGAN) on 10 threads of mixed speed.

## Queue and endpoints

- `ReaderController` is a primary-constructor class built by hand in several tests. New services go in through `[FromServices]` on the action, not the constructor.
- Lanes, waiters and abandonment are keyed by `UpscaleReader` (user id plus the tab's `session`, one `randomUUID()` per tab in `api/reader.ts`, sent with the POST and the DELETE), so two tabs or devices on one account never drop or cancel each other's pages. A request without a session (an older cached client) gets one shared lane per user, as before. Round robin is over users, never tabs, so several tabs never take more than one user's share. On a user's turn, their tabs that POSTed while visible in the last `UpscaleQueue.ActiveWindow` (2 minutes) take turns in a fixed rotation, every active tab's window before any active tab's whole-chapter rest (the POST's `window` says how many leading pages are the window); tabs not active lately run only once every active lane is empty, most recent first. So a phone tab left open with a whole chapter queued (its DELETE never goes out on screen lock) never slows the tabs being read, and two people on one account both see their own pages. The POST carries `visible` (`document.visibilityState`, absent counts as visible): a hidden tab's reconnect or back-forward re-POST never makes it active, and a new hidden tab starts inactive. A user keeps at most `MaxSessionsPerUser` (4) tabs with lanes of their own; a further tab, while those still have work, is folded into the shared lane instead of cancelling anyone, and a DELETE from the session that last filled the shared lane clears it. Pushes still go to the user, once per page.
- The reader POST replaces the tab's pending window. Failed and skipped outcomes are remembered for 10 minutes so a bad page is not re-queued forever.
- `UpscaleQueue.Replace` drops the reader's older pending pages behind the lowest page the request asks for in that chapter: they paged past them before they were done, and the one worker would otherwise start one and make the next new page wait a whole page (15 s for a tall webtoon slice on a 9950X3D). A running page whose last reader paged past it (behind that same lowest page) or moved to another chapter or model is abandoned through `UpscaleJob.Abandoned`; the worker completes it with `UpscaleReasons.Abandoned`, which is never remembered, and a page asked for again gets a fresh job. One that finished inference before the cancel is still cached.
- Near a chapter's end the reader POST also carries `nextChapterId`/`nextPages`: the window's overflow past the last page (paged: missing preload spreads; strip: `beyond` from `enhanceRange`). They fill the room left under the cap with the next chapter as their target, so that chapter's own first POST finds them still pending (same-chapter keys are kept) or ready. They are not in the response.
- On Auto those next-chapter pages, and the whole chapter's rest, are guesses: nothing measured them. The reader POST therefore carries `notWanted`, the pages the chapter's `EnhanceScope` measured as plain, and `Replace` drops them like pages behind (pending ones leave the lane, a running one is abandoned). `useServerEnhance` sends the first request of every chapter even when it asks for nothing, which ends the previous chapter's leftovers, and leaves plain pages out of `states`: a guessed page that came back `ready` but shows plain otherwise held the phase on `loading` forever (owner report, 2026-11-06).
- Whole chapter (`enhanceWholeChapter`): the POST sends `wholeChapter: true` with the window first, then the rest of the chapter (ahead, then behind, `chapterRest` in `useServerEnhance`), and the cap becomes `UpscaleQueue.MaxChapterPages` (1000, `MAX_CHAPTER_PAGES` client side). Leaving cancels through `DELETE reader/enhance` (`UpscaleQueue.Cancel`: drops the lane, abandons a running page nobody else waits on), sent with `keepalive` when the setting turns off, the reader unmounts or on `pagehide`; a back-forward-cache restore asks again. `ReaderPage` passes `whole` as undefined while the manifest loads, so a chapter turn never cancels the next chapter's queued pages. Only the window is polled while the hub is down. Every page turn re-POSTs the unsettled rest, which reorders the lane from the new position.
- `pageEnhanced` is pushed twice per page: `working` when the worker starts it, then the outcome. The push often beats the POST's own `queued` answer, so `useServerEnhance` never walks `working` back to `queued`. `useEnhancePhase` (in `ServerEnhanceStatus.tsx`) reads those states plus `shown` (the upscale is decoded and drawn) once in `ReaderPage`; the edge line or pill (`enhanceProgress`), the toolbar's compare button and the screen-reader status all take that one phase, so they never disagree.
- `HostStartupTests` fails on any WRN/ERR at boot. The store and the cache must start silently with no models and no cache folder.

## Reader

- Crop and split keep measuring the original `<img>` (`pageShape.ts` caches by `currentSrc`). Regions are fractions and apply unchanged to the enhanced canvas.
- `pageUrl()` must not change shape. Offline saving, `useWarmChapter` and the service worker regexes depend on it. The enhanced URL (`.../page/{n}/enhanced`) is deliberately outside every service-worker list, so offline it gets the synthetic 503 and the reader shows Balanced.
- A page whose server state is `ready` never runs the browser fallback: `EnhancedPage` only draws an engine cache hit while the server image loads, and the paged preload skips it. The fallback starts if that image fails, and the canvas is emptied once the server image shows. `failed`, `skipped` and pages the server has not answered still get the fallback.
- A paged turn mounts the incoming page in `STANDBY` (`position: fixed; inset: 0`), so its region box fills the viewport. `EnhancedPage` takes `standby` and never measures there: that box made every page count as stretched on Auto, queued it and the pages ahead with the server, then dropped the upscale 300 ms after the swap and left the phase on `loading`. It measures in the layout effect the moment standby ends, before the swap paints. `EnhancedPage.stories.tsx` covers it; a ReaderPage story cannot, the mock SVGs leave standby before the first ResizeObserver callback.
- `EnhancedPage` reports `onShowing` from a layout effect. The canvas hides in the same commit that holding H starts, so a passive effect paints one frame with neither the canvas nor the host's image.
- The strip's enhance range (`enhanceRange` in `ContinuousView`) is sized in displayed device pixels against `enhanceBudget()` (three quarters ahead, the rest behind, 32 pages at most), never a page count: webtoon chapters run from a handful of 15000 px slices to 100 short ones. The same range, minus the pages behind that are off screen (`server` from `enhanceRange`), is the server's window in vertical mode, so `MAX_PAGES` in `useServerEnhance` and `UpscaleQueue.MaxPendingPerUser` move together.
- Auto also takes pages that measure soft (`lib/enhance/softness.ts`, Crété-Roffet blur on up to 24 160 px tiles, `SOFT_BLUR` 0.28). The threshold was calibrated on about 100 `.simulated` pages at their own pixels: screentone and clean line art 0.08 to 0.2, sub-800 px scans and soft colour webtoons 0.25 to 0.45, volumes up to 0.3. Tiles are sampled at the shown scale (`shownScale` from the target, capped at 1, in twentieths), and scores are cached per URL and scale. At their own pixels a 2822 x 4000 Panther Scans release scored 0.30 to 0.49 and every page went to the server at 11 MP (owner report, 2026-11-08); at 1300 to 2400 px tall it scores 0.13 to 0.25. Chrome's canvas downscale stays soft on heavy upscales (a 3x upscale at a third still scores about 0.29), as the displayed `<img>` does. Softness waits for the first measured target, so `known` is undefined until then. A measurement costs 10 to 35 ms, so `EnhancedPage` uses `knownSoft` during render and measures after paint; the paged preload measures pages ahead so a turn finds the answer cached. "Stretched" in `EnhanceScope` and `onStretched` now means "wanted by Auto", stretched or soft.
- `enhanceSkipTiers` (default `['volume']`, filled by `ReaderPrefsSpec.Sanitized` when unset) turns enhance off for a chapter whose file tier is listed. The manifest's `tier` drives it through `enhanceFor()` in `ReaderPage`; pass that result, never `prefs.enhance`, to the views and `serverModelFor`, or the server queue still fills for a skipped chapter.
- The engine's `enhance()` closes the source bitmap. A result produced with a `key` belongs to the engine's LRU: draw it with `drawImage`, never close or transfer it.

## Model delivery

- Maki 2x is bundled: `src/Maki.Api/UpscaleModels/maki-2x.onnx` is copied to the build and publish output, and `Program.cs` hands `UpscaleModelStore` that folder (`BundledFolder` under `AppContext.BaseDirectory`). A bundled model is `Ready` from startup, `DownloadAsync` returns at once, `DeleteAsync` throws, `UpscalingController.Delete` answers `error.upscaling.modelBundled`, the catalogue DTO carries `bundled` and the settings page shows "Included" with no Delete button. A copy an older version downloaded into `{ConfigDir}/models/upscale` is deleted at startup. Bundling never turns the tier on: `library.upscaling.enabled` stays off until an admin flips it (owner, 2026-11-09: weak hardware must not upscale without the admin choosing it). Tests build the store without a bundle folder, although the file sits in the test output too. New weights mean replacing that file and raising `UpscaleCache.Generation`: cache names key on the model id, not the file, so pages from the old weights would keep being served. The `upscale-models-v1` release keeps its maki-2x entry for older versions.
- Release assets come from `distribution/upscale-models/prepare.py` and are uploaded by the owner with `distribution/publish-upscale-models.ps1`.
- In dev, point `library.upscaling.manifesturl` at a local `manifest.json` (a plain path or `file://`).
- Licences live in the root `THIRD_PARTY_NOTICES.md` and `distribution/upscale-models/licenses/`. SPAN-S is CC BY-NC 4.0, so it is non-commercial even though Maki's code is GPL-3.0.
