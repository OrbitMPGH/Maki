# Internationalization

Migrated out of the root CLAUDE.md so this only loads when touching localization.

English is the source and the default. Thirteen more languages ship: `sv de fr es pt-BR it nl pl ru
tr ja zh-Hans ko`, listed once in `SupportedLanguages.All` and once in `frontend/src/i18n.ts`.

## Never set ambient culture. This is the one that corrupts data.

**Never call `UseRequestLocalization`. Never assign `CurrentCulture` or `CurrentUICulture`.** They are
process- and thread-wide, and they change what `decimal.Parse` and `ToString("0.###")` mean.

About thirty sites in this codebase pass `CultureInfo.InvariantCulture` **on purpose**, parsing
chapter numbers, file sizes and dates (`Maki.Core/Parsing/ChapterNumberParser.cs`,
`Maki.Api/Dtos/QueueItemDto.cs`, others). Under an ambient German or Turkish culture, `"12.5"` silently
becomes `125`. Nothing fails, nothing logs, and a wrong chapter number reaches the filesystem and the
library. That is why localization here runs through an explicit locale everywhere:
`IRequestLocale.Locale` is read as a value, and `MessageFormat` takes a `CultureInfo` per call.

`RequestLocaleMiddleware` runs **before** `CurrentUserMiddleware`, so the 401 that middleware answers
with is localized too. It reads only the request. The stored preference that needs a user resolves
lazily on first read, by which point `CurrentUserMiddleware` has run for anything that gets further.

Locale resolution order, in `RequestLocaleContext.Resolve`: `?lang=`, then `X-Maki-Language`, then the
user's `ui.language`, then `Accept-Language`, then `ui.defaultlanguage`, then English. **The stored
setting sits above `Accept-Language`, not below.** Browsers attach that header to every request, so
ranking it higher means a Swede whose browser is in English never sees the language they picked.
`RequestLocaleTests` pins the order; it was a real bug before those tests existed.

## Two catalogues, keyed differently

`locales/{locale}/client.po` is the frontend. Its **msgid is the English source text**, because
`lingui extract` generates it by walking the source. **Never hand-edit `locales/en/client.po`.** Run
`npx lingui extract --clean` from `frontend/` and commit what it produces; that diff is also the
review artifact for a page conversion, far easier to check than a 2,000-line `.tsx` diff.

`locales/{locale}/server.po` is the API. Its **msgid is a dotted key** (`error.series.notFound`),
because C# has to name it, and the English lives in the msgstr. **`locales/en/server.po` is
hand-authored**, guarded by `LocalizationCatalogTests`, and propagated to the other thirteen with
`node scripts/i18n/sync-server-keys.mjs`.

PO entries are separated by blank lines and the sync script parses by block. **A missing blank line
merges two entries**, and the second key then vanishes from every language with no error. It has
happened once.

`ui.language` (a closed 14-entry list, validated) and `ui.titlelanguage` (any provider language code,
normalized but not validated) are different settings and are orthogonal. A Swede reading
Japanese-titled manga is the normal case.

## Adding user-facing text

Frontend: `t`/`<Trans>`/`plural` from the Lingui macros. Never a raw English literal.

A **module-scope table cannot hold rendered strings.** The module evaluates once, so whatever
language was active then is frozen for the session. Hold `MessageDescriptor`s from the `msg` macro
and render at the call site. Two shapes, both already in the tree:

- read one key at a time: `Record<K, MessageDescriptor>` plus `useLabel()` from `i18n-context`
- feeds a Mantine `data` prop: export a hook next to the table (`useIncognitoOptions`)

Any `useMemo` that renders labels **must list `i18n.locale` in its dependencies.** Without it the memo
holds the previous language, and because nothing throws, it reads as a caching bug.

`useLabel()` takes `string | MessageDescriptor` on purpose. A descriptor is this app's own copy; a
plain string is data (a series title, a wire value the client has no case for) and must pass through
untranslated. Keep fallbacks like `LABELS[x] ?? x` returning the raw `x`.

A `MessageDescriptor` is an object, so **never use one as a React key** or in a string comparison.
They all stringify to `[object Object]`.

Backend: `this.Fail(localizer, "error.area.thing")` and friends in `ApiResults.cs`, which answer
`{ code, error }`. `error` keeps the name and meaning it always had, so the client's single error path
needs no change; `code` is additive and nothing consumes it yet.

Do not convert a message that embeds a raw `ex.Message`. Getting the exception out of the response is
its own change, and half-converting it just hides the exception behind a key.

## The gates, and why they are not optional

`LocalizationCatalogTests` scans **every string literal in a catalogue namespace** across `src/**/*.cs`,
with comments stripped, and asserts the catalogue and the code agree both ways. It matches literals
rather than call shapes because keys are routinely hoisted to a `const`, handed to a local helper or
picked by a ternary; matching only `Fail(...)` once reported seven live keys as orphans.

The namespace list is `error`, `inbox`, `achievement` and nothing else. `queue.`, `health.`,
`scrobble.` and `opds.` are **also `SettingKeys` prefixes** (`scrobble.intervalminutes`), so scanning
those would read settings as catalogue keys. Errors in those areas key under `error.` anyway.

Two key families are named indirectly and the test expands them: an `InboxMessage.Key` names
`{key}.title` and `{key}.body`, and every achievement's name, description and tier is built from
`AchievementCatalog`. Whether an `inbox.` key is a pair or a single entry is decided by asking the
English catalogue, not by guessing from the name.

`InboxRendererTests` actually renders every notification. The catalogue test proves keys exist and
placeholder sets match; it cannot prove the ICU parses. A broken `=0 {}` or `select` surfaces weeks
later as a literal `{count}` in somebody's bell.

`node scripts/i18n/validate.mjs` is the acceptance gate for translations and runs in CI. Its plural
check is the one that earns its keep: a model handed an English `one`/`other` pair returns the same
two forms for Polish, which needs `one`/`few`/`many`/`other`. The result is wrong for most numbers and
completely invisible to anyone who does not read Polish.

## Translating

**One write rule, and it is the whole protocol:**

> Only ever write an entry whose translation is empty, or which is flagged `#, fuzzy`.
> Never touch a translated entry with no fuzzy flag.

A non-fuzzy translation is one a human reviewed or Weblate pushed. `#, fuzzy` means "needs review",
which is exactly what a machine translation is, so anything automated **keeps the flag on what it
writes**. Because that is read off the file itself rather than a state file beside it, pulling
somebody else's commits cannot put the two out of step.

`scripts/i18n/TRANSLATING-AGENT.md` is the self-contained brief; `glossary.md` is the do-not-translate
list and the tone. Point a translating agent at those rather than re-explaining.

Translate once, at the end, not per stage. Otherwise the English keeps moving and every fuzzy
re-fuzzies on the next extract, churning thirteen locale files for nothing. **Pull Weblate's commits
before starting a run.**

## Stored prose

Notifications store a **key and parameters**, never a rendered sentence, and render at read time in
the reader's language. One event goes to several people who may not share a language.

`UserNotification.MessageKey` is **not** `InboxEventType` and does not inherit its append-only rule
(see `stats-notifications.md`). It is presentation and can be renamed with its catalogue.

**Never put a series title in params.** It freezes the title, and this app resolves display titles per
user. Pass `SeriesId` and let the render fill `{series}`.

`Title`/`Body` on the row are English, written at raise time, and exist for rows created before this
change and for `InboxMessage.Unkeyed`. Health notifications still use `Unkeyed`; converting them is
outstanding. Once `HousekeepingJob` retention has aged the pre-migration rows out, both columns can go.

Discord and webhook recipients are chat channels, not users, so they render in `ui.defaultlanguage`.

`AuthEvent` is the model shape for structured records: an enum plus fields plus free-text `Detail`,
rendered by the frontend. It needs no change and never did.

Still English, each its own change: `DownloadQueueItem.ErrorMessage`, the Health message columns, the
Maki-authored half of `ScrobbleLogEntry` (the rest is the tracker's own response text and is not ours
to translate), and OPDS feed titles.

## Two things to know before they bite

`@mantine/dates` is **not** a dependency and nothing here uses a date picker. Adding it drags in dayjs,
whose locales are a second lazy-loading problem. Mantine's own built-in English is all prop-overridable
and invisible in a visual pass: `Pagination` aria labels, `Modal` `closeButtonProps['aria-label']`,
`Spoiler` `showLabel`/`hideLabel`, `FileInput` placeholder, `Select`/`MultiSelect`
`nothingFoundMessage`.

None of the fourteen languages is RTL. `document.documentElement.dir` is set anyway, so adding Arabic
later is a data change rather than a code change. Prefer logical CSS properties (`marginInlineStart`,
`paddingInline`) in new code; do not go back and convert `theme.css`.
