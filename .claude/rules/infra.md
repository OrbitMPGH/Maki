# Infra: logging, backup, scoping, settings, migration

- **Multi-user migration inserts a placeholder admin at `Id = 1`; that id is part of the schema.** Migrations can't compute a password hash (PBKDF2 needs `UserManager`), so it inserts `PasswordHash = null, PendingSetup = 1`. Only `POST auth/setup` may claim it, only while the flag is set; `auth/login` refuses such a row. This is how an existing single-user install upgrades losslessly (its library is already user 1). `MultiUserMigrationTests` runs real `Migrate()` over a populated pre-upgrade DB — `TestDb` (`EnsureCreated()`) can't cover this.
- **Reading/preferences/trackers are per-user; the library is not.** `StatsEvent.UserId` is nullable on purpose: null = library event (visible to everyone), non-null = someone's reading (visible only to them).
- **Scoping is structural**: `DataScope` + EF global query filters on every user-owned table (`UserId == scope.UserId` unless `Unrestricted`), plus a root-folder EXISTS filter on `Series` and matching filters on `Chapter`/`ChapterFile`/`SourceMapping`/`DownloadQueueItem` (skipping these leaves the child table readable by id regardless of series visibility). `DataScope` defaults to **unrestricted**, not deny-all; don't flip it (see the class doc). Background jobs filter by user explicitly instead. `OpdsAccessService` is the one place that must bypass the filter (`IgnoreQueryFilters()` + explicit `UserId ==`) since an OPDS request starts with scope narrowed to nobody.
- **Kavita is bound to exactly one Maki user** (`kavita.userid`, `KavitaUserResolver`, defaults to lowest-numbered enabled admin). All Kavita sync paths act as that user only; `reader.pushtokavita` pushes only for them.
- **Per-user vs instance settings** (`UserSettingKeys`): instance = deployment/shared app registration; user = personal preference. Two scrobble keys stay instance-wide despite describing per-user data because they describe the *job* (`scrobble.lastsyncat`, `scrobble.libraryids`) and Kavita is single-user anyway. A spec with nothing set **deletes the row** rather than storing `{}` — "no default" and "default that constrains nothing" are the same state. Read per-user keys through `IUserSettings` (or `IUserSettingsStore` for background paths) — never `SettingsService`, which opens a fresh DbContext per key.
- **Logging is configured in one place (`Maki.Api/Logging/`), and the interesting half is what it *drops*.** Everything logs through `ILogger<T>`; `MakiLogging` owns levels, sinks, the category floors (`System.Net.Http.HttpClient` at Warning, `Microsoft.EntityFrameworkCore`, `Quartz`) and `IsKnownBenign`. Don't remove the floors: `OutboundHttpLoggingHandler` (registered via `ConfigureAll<HttpClientFactoryOptions>`, last so it sits innermost and sees each retry) replaces the framework's per-call lines. `HostStartupTests` boots an empty config dir and fails on any ERR or WRN line. Inbound, `HttpRequestLogPolicy` tiers by what a request *did*: exceptions and 5xx at Error, other 4xx (not 401/403/404/499) and anything over `SlowRequestMs` at Warning, writes at Information, successful reads at Debug, and images/assets/hub traffic below that. The read/write split is deliberately not a list of polling endpoints, which would rot. The `config.json` logging keys are read once at startup because the sinks are built before the host exists.
- **The access log (`AccessLog` in config.json, off by default) is a separate Serilog logger, not a category of the main one** (`MakiLogging.BuildAccessLog`, `AccessLogMiddleware`). It writes every request in the combined log format to `logs/access-*.log` so CrowdSec and fail2ban parse it unchanged, ignoring `HttpRequestLogging`. Keep the line shape exactly combined (`AccessLogLineTests` pins it with the grok CrowdSec's nginx parser uses), keep the middleware after `UseForwardedHeaders`, and keep `AccessLogLine` redacting the OPDS path token and the sensitive query values: the redaction there is the only thing standing between those and the file. The shipped CrowdSec parser, whitelist and brute-force scenarios are in `distribution/crowdsec` and key off the sign-in paths and their failure codes (401 for login and 2fa, 400 for the password confirmations, 429 from `LoginRateLimit`); changing either side means changing the other, and `docs/crowdsec.md` lists both.
- **The logger is up before `config.json` is read** (`MakiLogging.Bootstrap`, so `RestoreBootstrap` and the pre-migration backup are logged). `MakiLogging.Configure` disposes *the bootstrap logger specifically*, never `Log.CloseAndFlush()`, because `WebApplicationFactory` boots the host more than once per process. `ConfigFileProvider` rewrites config.json whenever a release adds a key the file predates, since these settings have no UI.
- **Settings secrets are stored in plaintext** in `AppConfig` (deliberate, same as Sonarr/Radarr/Prowlarr — an encryption key would just live beside the DB anyway). Treat `{ConfigDir}`, backups, and any copy of `maki.db` as credential material.
- **Rate limits are shared state.** Any 429/503 becomes `RateLimitException`, feeding one `DownloadQueueService` cooldown. Exception: `challenge-fetcher` only converts 429 — Cloudflare serves its challenge as 503, which `ChallengeAwareFetcher` needs intact to hand off to FlareSolverr. Retries skip 429/503 and only cover GET/HEAD (so a qBittorrent add is never replayed). Outbound budgets come from `RateLimitingHandler.TokenBucket`, a `LazyTokenBucket` that works out the next permit from the clock: never build a `TokenBucketRateLimiter` with `AutoReplenishment` here, because each one keeps a timer firing every period for the life of the process, and about 25 of them were most of an idle instance's wakeups.
- **Backup/restore**: backup = consistent `maki.db` snapshot (SQLite online-backup API, never `File.Copy` a live WAL db) + `config.json` + `manifest.json`; exclusions are listed on `BackupService`. `Program.cs` auto-backs-up **before** `Database.Migrate()` (migrations are forward-only), except on a fresh database with no applied migrations, where `BackupService` would query tables that do not exist yet. Restore is staged into `{ConfigDir}/restore-pending`, applied at next startup, then the app self-exits for a supervisor to restart it. A downgrade guard rejects a backup from a newer schema. **EF Core holds a row in `__EFMigrationsLock` for the length of `Migrate()`** and a process killed inside it leaves the row, after which every start waits in `AcquireDatabaseLock` forever. `SqliteStartup.Prepare` records whether any other process had `maki.db` open (`SqliteFiles.IsUnattached`: no `-shm`, or nothing holds the attach lock, asked once per process before anything opens the database), and `Program.cs` deletes the row (`MigrationLock.ClearAbandoned`) before `Migrate()` only then, and only when its timestamp is older than this process, so two processes starting together cannot clear each other's live lock.
- **Docker Desktop's virtiofs bind mounts kill SQLite with SIGBUS whenever a `-shm` is truncated or created again under a mapping** (exit 135, no log line). The guards: `SqliteStartup.Prepare` deletes every `-shm` in the config and cache dirs that no process holds SQLite's attach lock on, before anything opens a database (a crash, a kill or any `docker stop` leaves one); it creates `maki.db` empty itself (`SqliteFiles.CreateIfMissing`), because a file created inside the container reports a provisional inode number until its size is set and SQLite treats connections from either side of the switch as two databases; and `SqliteKeeper` holds one idle connection to each WAL database (`maki.db`, `embeddings.db`) while Maki runs, so the `-shm` is created once per run and is not deleted, recreated, or left behind by a read-only connection closing last. Keepers close at `ApplicationStopped` after `ClearAllPools`, so a clean stop checkpoints and leaves no sidecars; `For()` hands out a keeper that opens only for a path `SqliteStartup.Prepare` passed to `Allow` and not yet released, so a late opener at shutdown cannot recreate the `-shm`, and tools and tests that use `EmbeddingStore` directly keep SQLite's checkpoint-on-last-close (a test that reads a store's file bytes depends on it). A new vector database is copied into the live `embeddings.db` with the backup API (`VectorIndexCache.SwapDatabaseAsync`), never moved over it: a move needs `Suspend()`, which closes the keeper and recreates the `-shm`, and is only the fallback for a page size the live file cannot take or a corrupt live file; when a writer holds the database the swap aborts and the installer retries on its next run. Code that opens `embeddings.db` calls `SqliteKeeper.For(path).Attach()` first (rule repeated in `recommendations.md`), a new SQLite file created in place goes through `CreateIfMissing` (one moved into place is fine, the rename settles it), and since the keeper keeps the `-wal` from ever being deleted, writable embeddings connections set `journal_size_limit` and `Compact` ends with `wal_checkpoint(TRUNCATE)`.

- **Read `GET api/v1/system/memory` (admin, `MemoryDiagnostics`), never a single RSS figure.** It separates managed heap from native (ONNX weights, SQLite and Playwright never appear in `GC.GetTotalMemory`), live from collectable (`?collect=true` forces a compacting collection, stalling requests, hence opt-in), and anonymous memory from page cache. **What Unraid and most dashboards show is the cgroup's `memory.current`, which counts page cache**; without a container memory limit the kernel never asks for those pages back.

- **Only one heavy artifact build runs at a time** (`ArtifactBuildGate`, taken by `MangaBakaDumpRefreshJob`, `MangaBakaTableBackfillJob` (once, 10 s after startup, so an upgraded install gets the dump's browse and franchise tables without waiting for the refresh's first run at +2 minutes), `PrebuiltIndexJob`, `RecoGraphJob`, `CoReadJob`, `TasteVectorJob`, `ReaderCohortJob` and `DiscoverCacheWarmJob`), so startup peak memory is the largest build rather than the sum. **Not a Quartz `MaxConcurrency` setting**, which would throttle the download workers and the completed-download poll too; the pool is raised to 20 instead. Lease disposal and the compacting collect on the last release are documented on the gate. **Page conversion and health verifies wait for the gate to go idle** (`WaitUntilIdleAsync`) before each file or verify scan, so an encoder or a full read never stacks on a dump install; they never take the gate themselves, since a conversion pass holding it would stall every build behind it. The server upscaler does not wait: a reader is looking at that page. `DiscoverCacheWarmJob` builds the vector and catalogue indexes on a non-scheduled trigger (a dump install) **only when something read that index within `RecentUse` (6 h, `IdleStamp.UsedWithin`)**, so the nightly install no longer pushes an idle instance into the used state; keep the window shorter than the gap between dump installs, because the warm's own build counts as a read. On its first scheduled fire after startup it builds **only when the dump, vector database or taste file changed since the last warm** (`discover.warmedstamp`, saved after every successful run), so the first search after a plain restart builds them itself (~9 s). Later scheduled fires only refresh an index that is loaded but stale (`IsCurrent`).

- **A scan that reads a file end to end drops it from the page cache afterwards** (`PageCache.DropAfterScan`, `posix_fadvise(POSIX_FADV_DONTNEED)`, Linux only, `MAKI_DROP_SCAN_CACHE=0` disables). Callers: a health **verify** (not a plain analysis), the catalogue index build, the vector index build, the franchise scan (`VectorIndexCache.LoadFranchises`), a dump install or browse-index backfill (`MangaBakaDumpRefreshJob`, and during the install itself as it writes and indexes the staged file, see `series-matching.md`), the Node driver and headless shell files once the last browser exits (`SharedPlaywright.ReleaseAsync`), the text embedder's model files once its ONNX session holds the weights (`TextEmbedder`, 105 MB), page conversion (`PageConversionService`: the original in the trash after a swap, and on a library pass the source of a file left as it was and the converted copy, which `ArchivePageConverter` flushes before the rename so its pages are clean; the download queue keeps both, since a fresh download is likely read next), and `DiscoverService` after a batch of rails, which is safe only because the rails cache for twelve hours. That drop is **deferred** (`ScheduleScanCacheDrop`, two-minute quiet period, re-armed by each batch) so genre rails built in the same page view don't hit a cold file. Not a leak fix: the pages are clean, but dashboards count them and they evict other containers' cache. Do **not** extend it to point queries: their pages are worth keeping.

- **The Docker image sets `DOTNET_EnableWriteXorExecute=0`** to drop the JIT's double mapping (both views count toward RSS); the trade-off is in the Dockerfile comment and `-e DOTNET_EnableWriteXorExecute=1` takes the hardening back. The real saving is about 29 MB of working set, because the code pages move from `RssShmem` to `RssAnon`: quote the working-set difference, never the shmem column on its own.

- **The image caps glibc to two malloc arenas (`MALLOC_ARENA_MAX=2`) and fixes both malloc thresholds at 128 KB (`MALLOC_MMAP_THRESHOLD_`, `MALLOC_TRIM_THRESHOLD_`)**, or native heap grows with the host's core count and freed ONNX and libvips buffers stay in the arenas (reasons and measurements in the Dockerfile).
- **Every unload calls `NativeHeap.Trim()` (`malloc_trim(0)`, Linux only)**: the artifact idle unload and build gate after their compacting collect, the embedder, upscaler and browser idle jobs when something went, and `ImageWorkGate` two minutes after it goes empty. `GET system/memory` reports glibc's own numbers under `nativeHeap` (`mallinfo2`; `freeBytes` is what a trim can return), and `?collect=true` trims after collecting. libvips runs two threads per pipeline (`NetVips.Concurrency = ImageCodec.EncoderThreads`, set once in its static constructor; it is a process global, so never change it per call); the gate provides the parallelism. Two because libaom spreads an AVIF encode across them for about one thread's memory, so the gate runs half as many AVIF pages instead.
- **The first monitored-series sync starts at +20 minutes, not +5**: it launches a headless browser (MangaFire), and startup job timings are a memory budget. Keep the browser-launching sync out of the artifact build window.
