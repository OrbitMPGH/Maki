# Infra: logging, backup, scoping, settings, migration

Migrated out of the root CLAUDE.md so this only loads when touching startup/logging/backup/settings/scoping code.

- **Multi-user migration inserts a placeholder admin at `Id = 1`; that id is part of the schema.** Migrations can't compute a password hash (PBKDF2 needs `UserManager`), so it inserts `PasswordHash = null, PendingSetup = 1`. Only `POST auth/setup` may claim it, only while the flag is set; `auth/login` refuses such a row. This is how an existing single-user install upgrades losslessly (its library is already user 1). `MultiUserMigrationTests` runs real `Migrate()` over a populated pre-upgrade DB — `TestDb` (`EnsureCreated()`) can't cover this.
- **Reading/preferences/trackers are per-user; the library is not.** `StatsEvent.UserId` is nullable on purpose: null = library event (visible to everyone), non-null = someone's reading (visible only to them).
- **Scoping is structural**: `DataScope` + EF global query filters on every user-owned table (`UserId == scope.UserId` unless `Unrestricted`), plus a root-folder EXISTS filter on `Series` and matching filters on `Chapter`/`ChapterFile`/`SourceMapping`/`DownloadQueueItem` (skipping these leaves the child table readable by id regardless of series visibility). `DataScope` defaults to **unrestricted**, not deny-all — several singletons open a child scope mid-request and a deny-all default would intermittently show them an empty library. Background jobs filter by user explicitly instead. `OpdsAccessService` is the one place that must bypass the filter (`IgnoreQueryFilters()` + explicit `UserId ==`) since an OPDS request starts with scope narrowed to nobody.
- **Kavita is bound to exactly one Maki user** (`kavita.userid`, `KavitaUserResolver`, defaults to lowest-numbered enabled admin). All Kavita sync paths act as that user only; `reader.pushtokavita` pushes only for them.
- **Per-user vs instance settings** (`UserSettingKeys`): instance = deployment/shared app registration; user = personal preference. Two scrobble keys stay instance-wide despite describing per-user data because they describe the *job* (`scrobble.lastsyncat`, `scrobble.libraryids`) and Kavita is single-user anyway. A spec with nothing set **deletes the row** rather than storing `{}` — "no default" and "default that constrains nothing" are the same state. Read per-user keys through `IUserSettings` (or `IUserSettingsStore` for background paths) — never `SettingsService`, which opens a fresh DbContext per key.
- **Logging is configured in one place (`Maki.Api/Logging/`), and the interesting half is what it *drops*.** Everything logs through `ILogger<T>`; `MakiLogging` owns levels, sinks and the category floors. Three of those floors are load-bearing: `System.Net.Http.HttpClient` at Warning (the framework writes four Information lines per outbound call and a full stack trace at *Information* when one fails — `OutboundHttpLoggingHandler` replaces all of it with one line, registered via `ConfigureAll<HttpClientFactoryOptions>` so it lands on every named client, last so it sits innermost and sees each retry attempt), `Microsoft.EntityFrameworkCore`, and `Quartz` (scheduler boilerplate at every boot; the jobs log under `Maki.Api.Jobs.*` and are unaffected). Inbound, `HttpRequestLogPolicy` tiers by what a request *did*: writes at Information, failures and anything over `SlowRequestMs` at Warning, successful reads at Debug, and images/assets/hub traffic below that. The read/write split is deliberately not a list of polling endpoints — those change with the frontend, and any list would rot. Config lives in `config.json` (`LogLevel`, `HttpRequestLogging`, `SlowRequestMs`, `LogFileSizeMb`, `RetainedLogFiles`), read once at startup because the sinks are built before the host exists.
- **The logger is up before `config.json` is read.** `MakiLogging.Bootstrap` runs on defaults so `RestoreBootstrap` (which may replace config.json itself) and the pre-migration backup land in the log file; `MakiLogging.Configure` then rebuilds the pipeline and disposes *the bootstrap logger specifically*, not whatever `Log.Logger` holds — `WebApplicationFactory` boots the host more than once per process, and a blanket `Log.CloseAndFlush()` would close another boot's logger and take its file handle with it. `ConfigFileProvider` rewrites config.json whenever a release adds a key the file predates, since these settings have no UI and an operator can't set a key they've never seen.
- **Settings secrets are stored in plaintext** in `AppConfig` (deliberate, same as Sonarr/Radarr/Prowlarr — an encryption key would just live beside the DB anyway). Treat `{ConfigDir}`, backups, and any copy of `maki.db` as credential material.
- **Rate limits are shared state.** Any 429/503 becomes `RateLimitException`, feeding one `DownloadQueueService` cooldown. Exception: `challenge-fetcher` only converts 429 — Cloudflare serves its challenge as 503, which `ChallengeAwareFetcher` needs intact to hand off to FlareSolverr. Retries skip 429/503 and only cover GET/HEAD (so a qBittorrent add is never replayed).
- **Backup/restore**: backup = consistent `maki.db` snapshot (SQLite online-backup API, never `File.Copy` a live WAL db) + `config.json` + `manifest.json`. Excludes big/regenerable state. `Program.cs` auto-backs-up **before** `Database.Migrate()` (migrations are forward-only, no down path). Restore is staged into `{ConfigDir}/restore-pending`, applied at next startup, then the app self-exits for a supervisor to restart it. Downgrade guard rejects restoring a backup from a newer schema.

- **A single "Maki is using 900 MB" figure answers nothing; `GET api/v1/system/memory` (admin, `MemoryDiagnostics`) is what to read instead.** Three distinctions decide what, if anything, to do. Managed heap against native: the discovery artifacts are on the heap and shrinkable in code, while the ONNX weights, SQLite and the Playwright processes are not and never appear in `GC.GetTotalMemory`. Live against collectable: workstation GC on an idle process sits on a lot of uncollected heap, so `?collect=true` reports the managed total from both sides of a forced compacting collection (it stalls every request for the length of one, hence opt-in). And anonymous memory against page cache, which is the one that misleads most often - **what Unraid and most dashboards show for a container is the cgroup's `memory.current`, and that counts every file page the kernel cached on the app's behalf.** A health verify scan reads thousands of archives and a catalogue index build scans a multi-GB dump, so on a real NAS 628 MB of a 1153 MB container total was reclaimable page cache while the process itself held 330 MB anonymous. Set a container memory limit if the number needs to mean something: unlimited means nothing ever asks the kernel to give those pages back, so it never does.

- **Only one heavy artifact build runs at a time** (`ArtifactBuildGate`, taken by `MangaBakaDumpRefreshJob`, `PrebuiltIndexJob`, `RecoGraphJob`, `CoReadJob`, `TasteVectorJob`, `ReaderCohortJob` and `DiscoverCacheWarmJob`). The startup schedule fires all seven inside the first seven minutes and Quartz runs jobs concurrently, so peak memory used to be the sum of every build's churn rather than the largest one's - and that peak lands three minutes after a user starts the container, which on a NAS is the worst possible moment. Serialising costs wall-clock on a cold start and nothing else; none of these is on a request path and every cache they fill builds lazily if a request beats them to it. **Not a Quartz `MaxConcurrency` setting**, which would throttle the download workers and the fifteen-second completed-download poll alongside the builds; the pool is instead raised to 20 so a queue of gated jobs waiting their turn cannot starve everything else. The lease is idempotent on dispose, since a job that disposes it and then unwinds through a catch would otherwise release twice and widen the gate permanently. **Releasing the last lease in the queue forces a compacting collect**: a build churns through far more heap than it keeps, mostly large arrays, and the large object heap is not compacted by default - six minutes into a start on a NAS, 84 MB of a 245 MB managed heap was fragmentation. Nothing else would have compacted it until the next idle unload an hour later. Skipped when another build is waiting, since it would only have to be redone.

- **A scan that reads a file end to end drops it from the page cache afterwards** (`PageCache.DropAfterScan`, `posix_fadvise(POSIX_FADV_DONTNEED)`, Linux only, `MAKI_DROP_SCAN_CACHE=0` disables). Four callers: a health **verify** (not a plain analysis - that reads the central directory and nothing else), the catalogue index build, the vector index build, and `DiscoverService` after a batch of rails. That last one is the largest: every rail is a scan of the multi-gigabyte dump and there are six plus one per genre, and opening Discover on a NAS took the container's page cache from 183 MB to 626 MB **while the process itself did not grow at all** - which is how a page that adds nothing to the heap reads as half a gigabyte on a dashboard. It is only safe there because the rails cache for twelve hours, so the scans that filled the cache are not about to repeat. **Deferred, not immediate** (`ScheduleScanCacheDrop`, two-minute quiet period, re-armed by each batch): the first version dropped the cache as soon as the main rails were built and the genre rails then rebuilt against a cold file **in the same page view**, which a user reported as Discover getting slower. `DiscoverCacheWarmJob` also moved from 24 hours to 12 to match the rail cache, since at 24 one of every two expiries landed on whoever opened Discover next. Each is a single linear pass over something large that nothing reads again until the next rebuild, and on a NAS six minutes into a start the container held 744 MB of page cache against 405 MB of anonymous memory for the process. Those pages are clean and the kernel would drop them under pressure, so this is not a leak fix - it matters because **every container dashboard counts them**, so an operator cannot tell it apart from a process genuinely using a gigabyte, and because cache this container will never read again evicts cache other containers would have. Do **not** extend it to point queries: their pages are worth keeping, and dropping the whole file after one sends the next query back to the disk.

- **The Docker image sets `DOTNET_EnableWriteXorExecute=0`.** The runtime maps JIT code twice - an executable view and a separate writable one the JIT writes through - so no page is ever both writable and executable. **Both views count toward RSS**, and it measured as 77 MB inside the container on a NAS (`RssShmem` 77 MB with it on, zero with it off; it is the shmem half of the double mapping, which is why no amount of managed-heap work ever touched it). It is a real mitigation being given up, not free: defence in depth against an attacker who already has an arbitrary write in the process and wants to turn that into running code. Judged the wrong trade for hardware where 8 GB is common; `-e DOTNET_EnableWriteXorExecute=1` takes it back. **The saving is about 29 MB, not 77**: comparing two like-for-like readings, `RssShmem` went 77 MB to zero but `RssAnon` rose 53 MB, because with the double mapping gone the code pages are simply counted once, as anonymous memory. Working set went 476 MB to 447 MB. Quote the working-set difference, never the shmem column on its own.

- **The image caps glibc to two malloc arenas (`MALLOC_ARENA_MAX=2`).** glibc gives each thread that mallocs its own arena, up to eight per core, each growing to 64 MB and trimmed only from its own top, so a container on a many-core NAS accumulates native heap in proportion to the **host's core count** rather than to anything the app does. This app has native allocators that run on the thread pool (the image decoders during a health scan, SQLite on every query), so it is exposed to exactly that. The cost is contention when many threads allocate natively at once.
- **The first monitored-series sync starts at +20 minutes, not +5.** It is the one startup job that launches a headless browser (MangaFire), so at +5 it added ~120 MB of native memory at the same minute the index builds were at their peak. It repeats every half hour regardless, so nothing needs the first one sooner. Startup job timings are a memory budget as much as a schedule: whatever else moves in there, keep the browser-launching sync out of the build window.
