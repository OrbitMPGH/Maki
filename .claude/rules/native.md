# Native builds: Windows tray app, Linux tarballs

- **Maki.Desktop only supervises; Maki.Api is the same program on every OS.** The tray starts `server\Maki.Api.exe` as a child with `MAKI_RUNTIME=desktop`, `MAKI_DESKTOP_PARENT=1` and `MAKI_CONFIG_DIR=%LOCALAPPDATA%\Maki`. Anything a user sets or reads belongs in the web UI, never in the tray, or the desktop and Docker builds drift. The tray's menu text lives under `desktop.*` in `locales/*/server.po` (scanned by `LocalizationCatalogTests`) and is read by `Strings`, not hard-coded.
- **The two processes talk through exit codes, standard input and one file.** Exit 10 (`HostRuntime.RestartExitCode`) means start again, 11 means apply the downloaded update, anything else non-zero is a crash and is retried three times in ten minutes. Closing the child's standard input is the shutdown request (`DesktopParentWatcher`), which also stops Maki when the tray is killed. The tray writes `{ConfigDir}/update-ready` with the downloaded version; `HostRestarter.ReadyUpdateVersion` ignores it unless it is newer than the running build. Keep the constants in `ServerProcess` and `DesktopPaths` in step with `HostRuntime`.
- **Restarts used to exit 0.** `HostRestarter` now exits 10 for a restore too, which Docker's restart policy and systemd `Restart=on-failure` both treat as a reason to restart. A bare `dotnet run` just stops, and the restore message says so (`error.system.restoreStagedManualStart`) by checking `HostRuntime.IsSupervised`, which reads systemd's `INVOCATION_ID`.
- **Shutdown can take 30 seconds** while the MangaBaka dump job winds down, so the tray waits 30 s before killing the child and the uninstall hook waits 20 s.
- **Velopack deletes its install folder on uninstall**, which is why the data lives in `%LOCALAPPDATA%\Maki`, apart from it. The wizard installs to `%LOCALAPPDATA%\Programs\Maki` by default; Velopack's own Setup.exe defaults to `%LOCALAPPDATA%\{packId}`, which is why the pack id is `Maki.Desktop` and not `Maki`, and it stays that way because it also keys the Apps entry existing installs update through. Never move the config dir under the install root. The tray and the server are published into separate folders (`app\` and `app\server\`) because each carries its own self-contained runtime and a shared folder would let one project's copy of an assembly overwrite the other's.
- **A vpk 1.2.161 MSI deletes Maki's data folder on uninstall.** Its `RustCleanup` action runs `remove_dir_all(%LOCALAPPDATA%\{RustAppId})`, and that template sets `RustAppId` to the pack title, `Maki`, which is exactly `DesktopPaths.ConfigDir`. Seen happen on 2026-10-26 (a real `%LOCALAPPDATA%\Maki` gone, not in the Recycle Bin). Velopack's unreleased template keys it on the pack id instead (`Maki.Desktop`, the updater's own fallback folder). Setup.exe's uninstall does not do this. Never ship an MSI from 1.2.161 unless `RustAppId` is changed in the built MSI or the vpk version has the fix.
- **The download is an Inno Setup wizard (`distribution/native/windows-setup.iss`) wrapping Velopack's Setup.exe**, because Velopack's Setup.exe has no UI and its MSI's folder dialog is never opened. The wizard only picks a folder and runs `Setup.exe --installto <dir>` from `PrepareToInstall` (`--silent` too under `/SILENT`, which also means Maki is not started). Velopack still owns the install, the Apps entry, shortcuts, hooks and updates; the wizard is `Uninstallable=no` and leaves nothing behind. Facts from the 1.2.161 source that shape it: **uninstall deletes the whole install root** and an install over a non-empty folder **renames it away and deletes it on success**, so the folder page refuses any non-empty folder that is not already a Maki install, a drive root, and anything that is or contains `%LOCALAPPDATA%\Maki`. Velopack writes the Apps entry to HKCU only (`Uninstall\Maki.Desktop`, whose `InstallLocation` the wizard reads to find an existing copy and refuses a second one elsewhere), so an "all users" mode would not be real and there is none: `PrivilegesRequired=lowest`, and a folder the user cannot write is refused up front. The default is `{userpf}\Maki` (`%LOCALAPPDATA%\Programs\Maki`), never `{localappdata}\Maki`, which is the data folder. Inno appends the default's last part to a folder picked with Browse, so a browsed folder gets `\Maki` too and the data-folder check still guards it. Velopack's own Setup.exe is not uploaded. CI uses the Inno Setup preinstalled on `windows-latest`; `build-windows.ps1` finds ISCC on PATH or in the usual folders.
- **Testing from Claude's desktop app: its shell is MSIX-packaged, so HKCU reads and writes from anything started there go through the package's private overlay.** A Run value written or deleted by a process launched from that shell is invisible to the real hive and the other way round, which made a working install hook look broken. Read the real registry from a process started outside the package (`Invoke-CimMethod Win32_Process -MethodName Create` with `reg query`), and launch an installer through `explorer.exe` to get a real double-click.
- **Velopack applies a downloaded update by itself at the next start** (`VelopackApp` auto-apply, on by default). "Restart to update" is not the only way an update lands: a sign-in after a download applies it too.
- **Velopack hooks:** start with Windows is set in `OnAfterInstallFastCallback`, not on first run, because a silent install never launches the app. The Run key points at the root stub (`<install root>\Maki.exe`), which survives updates; `current\Maki.exe` does not. `OnBeforeUninstallFastCallback` stops running copies first, or the uninstall leaves `current\` behind with files in use (seen in testing).
- **`BindAddress` in config.json defaults to `localhost` on the desktop build and `*` elsewhere.** It is applied at startup only (`ConfigFileProvider.ListenUrl`); `UpdateOnDisk` writes the next value without touching `Config`, so `GET system/host` can show both. Docker refuses the setting, because localhost inside a container is unreachable.
- **The content root is the executable's folder when a `wwwroot` sits there**, otherwise the current directory. Without that, an installed build started from anywhere but its own folder served `/initialize.json` and 404'd the SPA. A development checkout keeps the old behaviour because `bin\` has no `wwwroot`.
- **The browser for MangaFire and TopManhua installs on first use** (`BrowserInstaller`, via `SharedPlaywright.AcquireAsync`), into Playwright's default folder so a dev checkout and an installed build share one copy. It is detected by the `INSTALLATION_COMPLETE` marker for the revision in `.playwright/package/browsers.json`. One install runs on its own token for every waiter, is cancelled only by shutdown, checks for 600 MB free first, and backs off 15 minutes after a failure. `SourceCapabilities.NeedsBrowser` drives the Health row. Both sources also need FlareSolverr, so most native users never trigger it.
- **`Maki.Api --selftest` is what the smoke tests trust, not `/initialize.json`.** pdfium and libvips load lazily, so a package missing them starts and serves pages. The self-test opens SQLite, renders a generated one-page PDF through pdfium and decodes it through libvips, loads ONNX Runtime, runs the bundled Node and checks `wwwroot`. It runs before any config or logging, so it needs no config dir.
- **The Linux tarball is built on its own architecture**, so the self-test means something and the executable bits survive (a tar made on Windows loses them). The bundled `node` is made world-executable because the service user is often not the one who unpacked it. The Docnet `runtimes/linux` layout that the Dockerfile has to keep by hand comes out right in a RID publish; the self-test is what proves it.
- **`native.yml` runs only on a `v*` tag push, like `docker.yml`, plus `workflow_dispatch` for an existing tag** (offered once the file is on `main`). The builds start before the release exists, because `release.ps1` pushes the tag several confirmations before `gh release create`, so a separate `publish` job waits up to 90 minutes for the release and then attaches every platform's files in one go; if the release never appears, the files stay on the run as artifacts and a manual run with upload on attaches them. Building on the tag push is also what makes the delta work: `vpk download github` fetches the latest release, which is still the previous one. Velopack refuses versions below 0.0.1, which is why the local scripts default to `0.0.1-local`. Everything is packed, release candidates included: an RC's feed files are ignored because the tray reads releases through `GithubSource` with prereleases off. The feed files keep Velopack's own names; only the Inno installer and the portable zip are renamed.
- **The Windows build ships unsigned.** SignPath Foundation needs evidence of adoption Maki cannot show yet, and Azure Artifact Signing is US and Canada only for individuals. When a certificate exists, signing goes into `vpk pack` (`--signParams` or `--signTemplate`), because Velopack signs the app binaries and its own Setup.exe while packing.
- **Testing an update without publishing:** pack two versions into one folder with `vpk pack -o`, install the first, and start the tray with `MAKI_DESKTOP_UPDATE_FEED` pointing at that folder. The first check runs two minutes after start. `MAKI_DESKTOP_SERVER` points the tray at a dev build of Maki.Api (a `.dll` runs through `dotnet`).
