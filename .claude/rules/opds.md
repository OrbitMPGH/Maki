# OPDS

Token scope, the 404-never-401 rule and the `OpdsAccessService.EvictUser` cache rule are in `auth.md`, which loads for the same files.

- **The OPDS token lives in the path.** `ApiKeyAuthenticationHandler` returns `NoResult` when there is no `X-Api-Key` header, so OPDS requests fall through and `OpdsController` resolves the path token itself on every action through `OpdsAccessService` (SHA-256 digest lookup on `UserApiKeys`, no stored secret, so no fixed-time compare). Serves OPDS 1.2 (Atom) + PSE for page streaming, not 2.0. `pse:count` must be the chapter's **slice** length, not the archive's.
- **Path-borne tokens land in request logs.** `HttpRequestLogPolicy` drops `/api/v1/opds` below every configured level, ahead of the 5xx tier and regardless of `HttpRequestLogging` mode; `OpdsController` logs its own redacted line (rejections only). Don't "restore" normal logging there.
- **Chapter identity is `(Number, Language)`** but `ChapterLabel` never renders the language, so `OpdsCatalogService.AmbiguousWithoutLanguage` appends `[en]`/`[es]` when a feed page would show duplicates.
- **An OPDS page fetch *is* the progress signal** (`opds.trackprogress`, default on). `OpdsProgressWriter` writes it off the response path through the native reader's `ReaderService.SaveProgressAsync`, folding concurrent fetches for the same user and chapter. Readers prefetch the last page to size their page bar, so `OpdsProgressPolicy` makes a last-page fetch with no prior progress row write nothing; a one-page chapter instead stores `Completed = false` so its next fetch can finish it.
- **Kavita push-back** (`reader.pushtokavita`, default off) is gated on `KavitaSeriesId != null`: pushing an un-adopted native row's echo would land in a different row and double-count into Rewind.
- **Feed text goes through the scoped `ILocalizer`.** Locale order: `?lang=`, then `X-Maki-Language`, then the token user's `ui.language`, then `Accept-Language`. The user's own `ui.language` deliberately outranks `Accept-Language` (whoever pasted the URL into Panels or Chunky owns the preference); `?lang=` pins a reader app that sends no `Accept-Language`. English in a feed means an untranslated `msgstr`, not a missing key.
- **Some OPDS clients cache feeds**, so a language change will not retro-fix a navigation feed already fetched. Not worth solving.

- **KOReader progress sync (`/api/v1/kosync`, `KoreaderSyncController`) signs in with the OPDS token as the *username*.** KOReader sends the username raw in `x-auth-user` but only an MD5 of the password in `x-auth-key`, and only a SHA-256 of each token is stored, so the password can never be checked and is ignored. It resolves through `OpdsAccessService`, so the catalogue switch, `UseOpds` and the eviction rules all apply. Unlike the feed it answers **401** (KOReader's client only accepts 200/401 there) and the token is a header, so it stays in normal request logging.
- **Status codes are KOReader's, not REST's.** Every authorized push answers **200** at once, an unknown document included, never 202 or 404: `KOSyncClient` counts only 200 as success, everything but 401 is queued for retry, and `KOSyncQueue`'s drain stops at the first failure, so one non-Maki book would block every later push. A pull with nothing to report is `200 {}`.
- **Pushes are written by `KoreaderPushWriter`, never on the request.** A push at the end of a volume completes every earlier chapter, which can outlast KOReader's 2 s/5 s timeouts, and a client abort mid-loop would leave the volume half written, so the writer runs it with `CancellationToken.None`. Pushes fold per user and document. One that resolves to no file waits (500 per user at most, a week at most) and is retried by `KoreaderDocumentIndexJob` after a pass that added ids, so a file copied to the device before the index reached it keeps its progress; `OpdsAccessService.ForUserAsync` re-checks the owner before any write. A write that throws is tried once more, then waits the same way, since KOReader already had its 200; its document usually resolves already, so no pass adds ids for it, and it is retried on a timer instead (`RetryFailedAfter` times the failed rounds, up to `FailedRounds`) and after every index pass (`RetryWaiting(failedOnly: true)` when the pass added nothing). The waiting set is in memory only, so a restart drops it (persisting it needs a table).
- **A document id resolves through `KoreaderDocument` rows, never by hashing on demand.** Binary ids are KOReader's `util.partialMD5` (`KoreaderDigest.PartialMd5`, first offset 0 because LuaJIT's `lshift(1024, -2)` is 0). Rows are added, never rewritten: the device keeps the digest of the bytes it was served, so a ComicInfo rewrite adds a row and the old one keeps resolving. The one update is `FileVersion`: a new length or write time that hashes to a digest the file already has (a copy to a new disk, a touched mtime) restamps that row, or every pass would hash the file again. Ids cascade with their `ChapterFile` row, so a flow that swaps rows must carry them: a volume upgrade keeps the superseded files' ids in `VolumeReplacementDetail.KoreaderDocuments` and its revert puts them on the restored rows (`KoreaderDocumentIndexer.CarryAsync`/`RestoreAsync`), and a health repair that keeps every page in place moves them to the replacement (`MoveAsync`). A replacement with different pages lets them go. Recorded on OPDS download and by `KoreaderDocumentIndexJob` (6 h, skipped while nobody has OPDS on). A miss fires it early only when `KoreaderDocumentIndexer.AnyUnindexedAsync` finds a file past the last complete pass with no ids: most misses are books from elsewhere, KOReader pulls on every book open, and a pass stats every file in the library. A digest naming more than one visible file resolves to nothing; filename ids collide across series ("Ch. 12.cbz").
- **A push writes through `ReaderService.SaveProgressAsync` per chapter slice of the file** (`KoreaderSyncService.WriteFor`): chapters behind the page complete, the one it falls in gets the position, a chapter sharing the archive with no range of its own completes only on the last page. The last push is echoed back on a pull (memory cache keyed by user and file) while the latest `ChapterProgress` row is unchanged, so a device sees its own position under its own device id instead of a rounded copy under Maki's.
