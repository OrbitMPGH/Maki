# Reader and reading progress

Migrated out of the root CLAUDE.md so this only loads when touching reader/progress code.

- **`ReadingState` is one row per series, shared by Kavita scan and the built-in reader**, `ReadingProgressService` is its only writer — this is what makes double-counting impossible (delta vs stored mark = 0 on re-report). Duplicate rows per `SeriesId` are legal (two Kavita series can map to one local series) — never add a plain unique index on it; every index is prefixed `UserId`. Always pick via `ReadingProgressService.PickAsync`, ordered by `MaxChapter` not `UpdatedAt` (Kavita restamps `UpdatedAt` on every touch, so it flips between calls).
- **Reader settings resolve in four layers** via `ReadingProfileService.ResolveAsync` only: series override → pinned profile → profile claiming `Series.Type` → user's `reader.prefs`. A `Series.Type` is claimed by at most one profile per user (409 on conflict). `Series.Type` isn't backfilled on upgrade — lands null, filled by metadata refresh.
- **Reader page order is `CbzReader.PageNames`** (extension filter, minus macOS `__MACOSX`/dot-file stubs, ordered by `NaturalFileNameComparer`); `VolumeChapterScanner.ScanCbzBoundaries` maps chapter markers onto that same list; drift between them opens chapters at the wrong page. When markers don't name a chapter, or name it more than once, the reader serves the **whole archive** rather than guess a range. `ReaderArchiveCache` is a bounded LRU singleton; its `Invalidate` must be called on delete (SQLite reuses rowids) or a later adopt inherits a stale page list. Page bytes go through `ReaderArchiveCache.OpenPageAsync` (via `ReaderService.OpenPageAsync`), which reuses a parsed `ZipArchive` per recently read file (`ReaderArchiveHandles`, 8 entries, 2 min idle) but **closes the file handle after every request** and re-validates length + write time on the next open. Do not "optimise" that into a held-open `FileStream`: on Windows an open handle, even with `FileShare.Delete`, makes `File.Move(..., overwrite: true)` over the archive (re-download, ComicInfo rewrite) and `Directory.Move` of its series folder fail.
- **A PDF backing a chapter is read in place, never converted.** `CbzReader.PageNames`/`OpenPage` handle a `.pdf` path transparently: pages are synthetic names (`0001.jpg`..`NNNN.jpg`, one per PDF page) rendered on demand via `PdfReader`, so the reader and OPDS page endpoints need no branch on file type. There are no embedded chapter markers to scan, so a PDF never splits into more than the one chapter its `ChapterFile` already names.
- **`ChapterProgress` is ground truth for read state; `MaxChapter` is not.** Read counts = completed `ChapterProgress` rows for downloaded chapters, or chapters whose file was removed on purpose (`Chapter.FileRemovedAt`), so clearing read files never un-reads them (list and detail endpoints must use the identical condition). `ChapterProgress.CompletedAt` (first false-to-true flip) is stamped and cleared in `MakiDbContext` on save, not by the writers. `MaxChapter` survives only as an internal aggregate for Rewind deltas / forward-only tracker pushes. Marking unread leaves an `UnreadAt` tombstone rather than deleting the row (a delete gets recreated by the next Kavita tick).
- **`ChapterProgress.Watched` is "ticked off, not read"** ("I've seen the anime"). Always carried alongside `Completed`, so the UI stops calling those chapters unread, but it emits **no `StatsEvent`** — this is the same trade the Kavita read import makes, for the same reason (dating a whole back catalogue to one day wrecks Rewind). `ReadCounts.Read` counts it and `ReadCounts.ReadFor` does **not**: the first is the UI count, the second feeds progression (`UserMetricsService.FullyReadAsync`) and must not hand out "fully read" for a season nobody read. Anything new counting reads has to pick a side deliberately. `MarkWatchedAsync` still raises `MaxChapter`, silently, via `ImportSilentAsync` — skip that and the first genuine read after a watched season emits a delta of the whole season — which does mean the scrobbler pushes that progress to AniList/MAL, again exactly as a Kavita import does. The ticked state survives merely opening the chapter: `useReaderProgress` remembers the page the chapter opened at and sends nothing while the page still equals it with no completion, so a sub-second visit writes nothing; the first page turn, a heartbeat or unmount flush with banked time, or a completion makes the first write. A save that does not complete the chapter leaves `Completed` and `Watched` as they are (the position and any reading time are still stored). `Watched` clears only on a completing save (last page or an explicit `completed`), and that is the genuine read, which is why `SaveProgressCoreAsync`'s transition gate is `row is { Completed: true, Watched: false }` and not `row.Completed` — the sticky flag is already set, so keying off it alone would swallow the read as a re-read. `OpdsProgressWriter` passes `existing is { Watched: false }` as "has a progress row", so a lone last-page prefetch of a watched chapter does not complete it. `AnimeResumeService.ApplyAsync` is the bulk caller of `MarkWatchedAsync` (ticks 1..N from the reader's finished anime seasons) and calls `ImportSilentAsync` itself even when `markWatched` is false, because its chapters are usually not downloaded yet and the baseline must still land at N before the reader opens N+1; `AnimeResumeServiceTests.Apply_raises_the_mark_so_the_next_real_read_counts_one_chapter` pins the delta at 1.
- **Reading days exclude bulk-marked rows.** `ChapterProgress.BulkMarked` is set by `ReaderService.MarkReadAsync` and by new rows from the Kavita read sync, and cleared on mark-unread or a genuine completion in the reader. `ReadingBehaviourService` days and `ActivityStatsService` series-started skip those rows and date the rest by `CompletedAt`; they do not require `ReadSeconds > 0`, because OPDS reads carry no time but are real. Pages-read still requires `ReadSeconds > 0`, so an OPDS-only reader has days and starts but no pages.
- **`ChapterProgress.CountedAt` is the never-cleared token that a one-shot's `ChaptersRead` event was emitted.** `Completed` clears on mark-unread, and a one-shot has no `MaxChapter` to absorb a second completion, so `OnChapterCompletedAsync` gates `RecordUnnumberedReadAsync` on it. Do not key that off `UnreadAt`, `Watched` or `BulkMarked`: each is cleared or set by paths that are not reads.
- **Three progress fields, don't conflate**: `PageIndex` (resume position, may move backward), `Completed` (sticky, idempotency token), `ReadingState.MaxChapter` (forward-only high-water mark). Marking unread clears the first two, never lowers the third. One-shots (`Number == null`) must not touch `MaxChapter` — no number to raise it to.
- **`ChapterProgress.ReadSeconds` accumulates across re-reads on purpose**, so `ReadingTimeEstimateService`'s per-chapter median runs high for a series the user has fully re-read. Accepted: the median blunts partial re-reads and a per-reading split would need a new column.
- **Reading time is measured client-side and reported as deltas** (`useReadingClock`, tab visible+focused+not idle). `flushProgress` always sets `Final` on hide/unmount/chapter-change to flush banked time regardless of threshold. `ReaderService` clamps a single report to 15 min. Native reader only — OPDS page fetches and `MarkRead` pass `TimeReport.None` (a page request isn't proof anyone looked at it).
- **`ReadingSession` rows are stitched server-side by gap** (`ReadingSessionService.Stitch`, shared with the backfill so the rule lives once): a report whose start lands within 10 minutes of the user's latest sitting extends it, otherwise a new row starts. The client resets its clock per chapter and sends no session id, so there is nothing better to key on; a two-tab overlap can drop a few seconds or split a sitting, accepted. Only native-reader time counts (`SaveProgressCoreAsync` records when the clamped report is > 0 or the chapter just completed; a zero-second completion only credits an already open sitting, so OPDS/`MarkRead` never create one). Recording runs after the completion events and a failure only logs, since a session never gates progress, and `IncognitoMode.Full` series are skipped. `RecordAsync` takes an explicit `userId` and ignores query filters. `ReadingSessionBackfillService` seeds history once from `ReadingTime` events (marker `stats.sessionsBackfillDone`, skips users that already have rows; backfilled sittings have `ChaptersCompleted = 0`, and include time on series later set to Full incognito, since sessions carry no series and it cannot be filtered afterwards). Never purged.
- **Kavita read-status import is invisible to Rewind on purpose** (`KavitaReadImportService` → `ReadingProgressService.ImportSilentAsync`) — Kavita doesn't say *when* chapters were read, so dating them today would dump the whole back catalogue onto one day. Imported rows carry `PageCount = 0`; `Completed AND PageCount = 0` is how later code identifies an import.
- **`KavitaProgress.Compute` is the one reading of Kavita's volumes payload**, for both the tracker push (`MaxChapter`/`MaxVolume`) and the per-chapter read marks (`Chapters` ranges, `Volumes`, via `ExternalReadSyncService.MarkAsync`). Keep it that way: they used to be separate, the marks only matched numbered chapters, and a library of volume archives scrobbled to MAL while nothing was marked read (discussion #109). Kavita reports a Maki "Vol. 01" archive as a volume holding one loose-leaf chapter numbered `-100000`, so a fully read volume marks every chapter whose file parses as that volume (`ReleaseNameParser.IsVolume`), and a half-read one counts chapters through the archive's scanned page boundaries (`VolumeBoundaryService`, shared and cached). Pass the boundaries everywhere `Compute` runs, or the import's silent baseline and the tick's mark disagree and the difference lands in Rewind.
- **Kavita live read sync (`KavitaLiveReadSync`, opt-in `reader.pullfromkavita`) only writes `ChapterProgress`**, via `KavitaReadImportService.MarkSeriesAsync`, so its rows look exactly like imported ones. It must **not** raise `MaxChapter` (no `ImportSilentAsync`, no `TrackKavitaAsync`): the scrobble tick still reads the same series and its mark delta is what feeds Rewind and the trackers; raising the mark early turns that delta into zero. It listens on Kavita's `/hubs/messages` for `UserProgressUpdate`, which Kavita sends **only to online admins and for every user**, so a non-admin API key gets nothing (status `NotAdmin`) and every event is filtered to the key's own Kavita user id (`nameid` in the JWT). Events fire per page turn, hence the per-series quiet/max-wait coalescing.
- **`ContinueReadingService.NextForAsync` is the only "what's next" resolver** — reads `ChapterProgress` only, never `ReadingState` (would double-count/multiply on duplicate rows).
