# Reader and reading progress

- **`ReadingState` is one row per series, shared by Kavita scan and the built-in reader**; `ReadingProgressService` is its only progress writer (`SeriesIdentityService.AdoptOrphansAsync` only merges and removes rows), which is what makes double-counting impossible (delta vs stored mark = 0 on re-report). Duplicate rows per `SeriesId` are legal (two Kavita series can map to one local series), so never add a plain unique index on it. Pick a row by `MaxChapter` descending then `Id`, never `UpdatedAt` (Kavita restamps it on every touch); `ReadingProgressService.PickAsync` and `KavitaReadImportService.AdoptedSeriesIdAsync` both do.
- **Reader settings resolve in four layers** via `ReadingProfileService.ResolveAsync` only: series override → pinned profile → profile claiming `Series.Type` → user's `reader.prefs`. A `Series.Type` is claimed by at most one profile per user (409 on conflict). `Series.Type` isn't backfilled on upgrade — lands null, filled by metadata refresh.
- **Page shaping is display only.** Split halves (`splitWide`), rotation and border crop (`pageShape.ts`, measured client-side on a downscaled canvas, cached by URL) never change the page index: a split page is one page for progress, `half` lives beside `page` in `ReaderPage`, except that the first half of a wide last page records the page before it (`recordedTo`), so the chapter completes only once its second half is up. A one-page chapter has no page before it, so its first half sends an explicit `completed: false` (`holdCompletion`) and the hook passes `false` through, where `undefined` still lets the server derive completion. The offline queue keeps that `false` as a `held` row and replays it, and derives completion from the position only for a write that sent none. The crop never changes the image URL, so offline-saved chapters keep working, and it is paged-only: cropping each strip slice on its own scaled neighbours differently under fit-width. `autoWebtoon` is a nullable `ReaderPrefsSpec` field that each layer fills when unset (`WithAutoWebtoon`): on for the global defaults, off for a profile or series override, since choosing a layout there is the explicit choice detection must not override. Detection probes a few page headers before the reader renders. A layout or fit picked by hand over a detected Continuous is saved as the series' own override with `autoWebtoon: false` (`keepForSeries`), since written to a profile or the global defaults it would be undone by the next visit's detection.
- **Reader page order is `CbzReader.PageNames`** (extension filter, minus macOS `__MACOSX`/dot-file stubs, ordered by `NaturalFileNameComparer`); `VolumeChapterScanner.ScanCbzBoundaries` maps chapter markers onto that same list; drift between them opens chapters at the wrong page. When markers don't name a chapter, or name it more than once, the reader serves the **whole archive** rather than guess a range. `ReaderArchiveCache` is a bounded LRU singleton; its `Invalidate` must be called on delete (SQLite reuses rowids) or a later adopt inherits a stale page list. Page bytes go through `ReaderArchiveCache.OpenPageAsync` (via `ReaderService.OpenPageAsync`), which reuses a parsed `ZipArchive` per recently read file (`ReaderArchiveHandles`, 8 entries, 2 min idle) but **closes the file handle after every request** and re-validates length + write time on the next open. Do not "optimise" that into a held-open `FileStream` (Windows breaks `File.Move`/`Directory.Move`; see `ReaderArchiveHandles`).
- **A PDF backing a chapter is read in place, never converted.** `CbzReader.PageNames`/`OpenPage` handle a `.pdf` path transparently: pages are synthetic names (`0001.jpg`..`NNNN.jpg`, one per PDF page) rendered on demand via `PdfReader`, so the reader and OPDS page endpoints need no branch on file type. There are no embedded chapter markers to scan, so a PDF never splits into more than the one chapter its `ChapterFile` already names.
- **`ChapterProgress` is ground truth for read state; `MaxChapter` is not.** Read counts = completed `ChapterProgress` rows for downloaded chapters, or chapters whose file was removed on purpose (`Chapter.FileRemovedAt`), so clearing read files never un-reads them (list and detail endpoints must use the identical condition). `ChapterProgress.CompletedAt` (first false-to-true flip) is stamped and cleared in `MakiDbContext` on save; the one writer that sets it directly is `SaveProgressCoreAsync`, on every completion it makes, because a replayed offline write dates it by `ClientTime` and a watched row's `Completed` never went false for the context to notice. `MaxChapter` survives only as an internal aggregate for Rewind deltas / forward-only tracker pushes. Marking unread leaves an `UnreadAt` tombstone rather than deleting the row (a delete gets recreated by the next Kavita tick).
- **`ChapterProgress.Watched` is "ticked off, not read"** ("I've seen the anime"). It is carried alongside `Completed` but emits **no `StatsEvent`**, like the Kavita read import. `ReadCounts.Read` counts it and `ReadCounts.ReadFor` does **not** (see `ReadCounts`); anything new counting reads has to pick a side deliberately. `MarkWatchedAsync` raises `MaxChapter` silently via `ImportSilentAsync` (so the scrobbler pushes it, as a Kavita import does); skip that and the first genuine read after a watched season emits the whole season. `useReaderProgress` sends nothing while the page still equals the one the chapter opened at with no completion, so merely opening a ticked chapter writes nothing. A non-completing save leaves `Completed` and `Watched` alone; a completing save clears `Watched` and is the genuine read, which is why `SaveProgressCoreAsync`'s transition gate is `row is { Completed: true, Watched: false }`, not `row.Completed`. Mark-unread clears it too. `OpdsProgressWriter` passes `existing is { Watched: false }` as "has a progress row", so a lone last-page prefetch does not complete a watched chapter. `AnimeResumeService.ApplyAsync` calls `ImportSilentAsync` itself even when `markWatched` is false, because its chapters are usually not downloaded; `AnimeResumeServiceTests.Apply_raises_the_mark_so_the_next_real_read_counts_one_chapter` pins the delta at 1.
- **Reading days exclude bulk-marked rows.** `ChapterProgress.BulkMarked` is set by `ReaderService.MarkReadAsync` and by new rows from the Kavita read sync, and cleared on mark-unread or a genuine completion in the reader. `ReadingBehaviourService` days (dated by `CompletedAt`) and `ActivityStatsService` series-started (dated by the earliest `StartedAt`) skip those rows; they do not require `ReadSeconds > 0`, because OPDS reads carry no time but are real. Pages-read still requires `ReadSeconds > 0`, so an OPDS-only reader has days and starts but no pages.
- **`ChapterProgress.CountedAt` is the never-cleared token that a one-shot's `ChaptersRead` event was emitted.** `Completed` clears on mark-unread, and a one-shot has no `MaxChapter` to absorb a second completion, so `OnChapterCompletedAsync` gates `RecordUnnumberedReadAsync` on it. Do not key that off `UnreadAt`, `Watched` or `BulkMarked`: each is cleared or set by paths that are not reads.
- **Three progress fields, don't conflate**: `PageIndex` (resume position, may move backward), `Completed` (sticky, idempotency token), `ReadingState.MaxChapter` (forward-only high-water mark). Marking unread clears the first two, never lowers the third. One-shots (`Number == null`) must not touch `MaxChapter` — no number to raise it to.
- **`ChapterProgress.ReadSeconds` accumulates across re-reads on purpose**, so `ReadingTimeEstimateService`'s per-chapter median runs high for a series the user has fully re-read. Accepted: the median blunts partial re-reads and a per-reading split would need a new column.
- **Reading time is measured client-side and reported as deltas** (`useReadingClock`, tab visible+focused+not idle). `flushProgress` always sets `Final` on hide/unmount/chapter-change to flush banked time regardless of threshold. `ReaderService` clamps a single report to 15 min. Native reader only — OPDS page fetches and `MarkRead` pass `TimeReport.None` (a page request isn't proof anyone looked at it).
- **`ReadingSession` rows are stitched server-side by gap** (`ReadingSessionService.Stitch`, shared with the backfill): a report starting within 10 minutes of the user's latest sitting extends it, otherwise a new row starts (the client sends no session id). Only native-reader time counts: `SaveProgressCoreAsync` records when the clamped report is > 0 or the chapter just completed, and a zero-second completion only credits an already open sitting, so OPDS/`MarkRead` never create one. The session is staged and saved with the progress, before the completion events; a failure only logs, and `IncognitoMode.Full` series are skipped. `RecordAsync` takes an explicit `userId` and ignores query filters. `ReadingSessionBackfillService` seeds history once from `ReadingTime` events (marker `stats.sessionsBackfillDone`; backfilled sittings have `ChaptersCompleted = 0` and may include later-incognito series, since sessions carry no series). Never purged.
- **Kavita read-status import is invisible to Rewind on purpose** (`KavitaReadImportService` → `ReadingProgressService.ImportSilentAsync`) — Kavita doesn't say *when* chapters were read, so dating them today would dump the whole back catalogue onto one day. Imported rows carry `PageCount = 0`; `Completed AND PageCount = 0` is how later code identifies an import.
- **A Mihon import's read chapters wait in `PendingReadImport` until the series has chapters** (`PendingReadImportService`, one row per series and reader, a second import merges its numbers). The import stores the row, then applies it at once only if chapters already exist; otherwise `ChapterSyncService.SyncSeriesAsync` applies it after a sync that wrote new chapters (same hook and gate as `AnimeResumePendingService`), so auto match, manual link, refresh and rescan all land it. The row keeps the numbers that matched no chapter yet and is deleted only once none are left (both guarded on `NumbersJson` being unchanged since read). Rows take the Kavita import's shape (`Completed`, `BulkMarked`, `External`, `PageCount` 0), skip rows already completed or carrying `UnreadAt`, raise no StatsEvent, XP or inbox row, and are written with `IgnoreQueryFilters` and an explicit `UserId` because the sync runs unrestricted. Matching is by exact `Chapter.Number`; one-shots are never marked and never raise `MaxChapter`, and a series whose chapters are all unnumbered gets no silent mark at import either. The silent mark is raised at import by `ImportSilentAsync` from the highest read number, or from the tracker's `lastChapterRead` only when the backup had no chapter rows for that manga (that number may follow the tracker's numbering). Mihon does record read dates; they are ignored on purpose, for the Rewind reason above.
- **`KavitaProgress.Compute` is the one reading of Kavita's volumes payload**, for both the tracker push (`MaxChapter`/`MaxVolume`) and the per-chapter read marks (`Chapters` ranges, `Volumes`, via `ExternalReadSyncService.MarkAsync`). Keep it that way. Kavita reports a Maki "Vol. 01" archive as a volume holding one loose-leaf chapter numbered `-100000`, so a fully read volume marks every chapter whose file parses as that volume (`ReleaseNameParser.IsVolume`), and a half-read one counts chapters through the archive's scanned page boundaries (`VolumeBoundaryService`, shared and cached). Pass the boundaries everywhere `Compute` runs, or the import's silent baseline and the tick's mark disagree and the difference lands in Rewind.
- **Kavita live read sync (`KavitaLiveReadSync`, opt-in `reader.pullfromkavita`) only writes `ChapterProgress`**, via `KavitaReadImportService.MarkSeriesAsync`, so its rows look exactly like imported ones. It must **not** raise `MaxChapter` (no `ImportSilentAsync`, no `TrackKavitaAsync`): the scrobble tick still reads the same series and its mark delta is what feeds Rewind and the trackers; raising the mark early turns that delta into zero. Kavita sends `UserProgressUpdate` on `/hubs/messages` only to online admins, for every user, so a non-admin API key gets nothing (status `NotAdmin`) and every event is filtered to the key's own Kavita user id. Events fire per page turn, hence the per-series coalescing.
- **"How is it so far?" prompts are armed by a genuine completion, never by state** (`RatingCheckpointService.ArmAsync`, called from `ReaderService.SaveProgressAsync` after `OnChapterCompletedAsync`, so native and OPDS reads both arm and bulk `MarkReadAsync` does not). Evaluating on a page load would arm every series at once after a Kavita or Mihon import or an anime watch mark. Each checkpoint is a condition re-checked on every completion, so the one-per-UTC-day cap (the max `UserSeriesState.LastRatingCheckpointAt` across the reader's rows) defers rather than drops. Hooked counts `ReadFor`; Caught up compares `ReadCounts.Read` (watched included, the end screen's number) against the wanted count, because it is about position. Volume end (opt-in, `ratings.prompts.volumes` = "on") needs the completed chapter, so `ArmAsync` takes it: a volume entry, or the highest-numbered chapter its volume has; it shares Caught up's 30-day gate per series and the staleness test. The arm call has its own try/catch: a prompt must never cost the progress write. The end screen fetches `GET series/{id}/rating-checkpoint` and asks again a few times (`useRatingCheckpoint`), because the debounced completing write may still be in flight when it opens.
- **`ContinueReadingService.NextForAsync` is the only "what's next" resolver** — reads `ChapterProgress` only, never `ReadingState` (would double-count/multiply on duplicate rows).
- **Progress writes may be replays from the PWA's offline queue** (`SaveProgressRequest.ClientTime`, `OpId`, both optional). `OpId` (1 to 64 chars, no spaces) is remembered in `ChapterProgress.RecentOpIds`, the last 32 per row space-separated; a known id answers success and changes nothing, which is how a queued copy of a write that did land is recognised even after later live writes. `ClientTime` is clamped to the last 30 days. Older than the row's `UpdatedAt` means stale: seconds are added, a completion is applied unless `UnreadAt` is later than `ClientTime` (a mark-unread made after the offline read wins), and `PageIndex` and `UpdatedAt` stay put. Otherwise `ClientTime` dates the write: `UpdatedAt`, `StartedAt` on a new row, `CompletedAt` (set explicitly, `MakiDbContext` only fills a null one), the `ReadingTime` event, the sitting, and the `ChaptersRead`/`VolumesRead`/`SeriesFinished` events through the `at` parameter of `TrackNativeAsync` and `RecordUnnumberedReadAsync`. `ReadingState.LastProgressAt` only moves forward. A write with `ClientTime` stages only its own seconds as the `ReadingTime` event at `ClientTime` (`StageReadingTime`'s `onlySeconds`); anything else banked was read live after it and flushes on the next live write, dated then. Absent fields behave exactly as before.
- **`ReadingSessionService.Stitch` is two-sided.** A report joins a sitting only when `[now - seconds, now]` overlaps it or comes within the gap on either side, and `StageAsync` picks the latest sitting that started no later than the report's end plus the gap. For a live report both reduce to the old rule; a replayed morning report becomes its own row (or joins the morning sitting) instead of merging into the afternoon.
