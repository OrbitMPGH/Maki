# Reader and reading progress

- **`ReadingState` is one row per series, shared by Kavita scan and the built-in reader**; `ReadingProgressService` is its only progress writer (`SeriesIdentityService.AdoptOrphansAsync` only merges and removes rows), which is what makes double-counting impossible (delta vs stored mark = 0 on re-report). Duplicate rows per `SeriesId` are legal (two Kavita series can map to one local series), so never add a plain unique index on it. Pick a row by `MaxChapter` descending then `Id`, never `UpdatedAt` (Kavita restamps it on every touch); `ReadingProgressService.PickAsync` and `KavitaReadImportService.AdoptedSeriesIdAsync` both do.
- **Reader settings resolve in four layers** via `ReadingProfileService.ResolveAsync` only: series override → pinned profile → profile claiming `Series.Type` → user's `reader.prefs`. A `Series.Type` is claimed by at most one profile per user (409 on conflict). `Series.Type` isn't backfilled on upgrade — lands null, filled by metadata refresh.
- **Page shaping is display only.** Split halves (`splitWide`), rotation and border crop (`pageShape.ts`, measured client-side on a downscaled canvas, cached by URL) never change the page index: a split page is one page for progress, `half` lives beside `page` in `ReaderPage`, except that the first half of a wide last page records the page before it (`recordedTo`), so the chapter completes only once its second half is up. A one-page chapter has no page before it, so its first half sends an explicit `completed: false` (`holdCompletion`) and the hook passes `false` through, where `undefined` still lets the server derive completion. The offline queue keeps that `false` as a `held` row and replays it, and derives completion from the position only for a write that sent none. The crop never changes the image URL, so offline-saved chapters keep working, and it is paged-only: cropping each strip slice on its own scaled neighbours differently under fit-width. `autoWebtoon` is a nullable `ReaderPrefsSpec` field that each layer fills when unset (`WithAutoWebtoon`): on for the global defaults, off for a profile or series override, since choosing a layout there is the explicit choice detection must not override. Detection probes a few page headers before the reader renders. A layout or fit picked by hand over a detected Continuous is saved as the series' own override with `autoWebtoon: false` (`keepForSeries`), since written to a profile or the global defaults it would be undone by the next visit's detection.
- **Hidden credit pages are a window, not a filtered list** (`creditWindow.ts`, `GET reader/chapter/{id}/credits`, `CreditDetector`). They are always a run at the start and one at the end, so `ReaderPage` keeps `[first, last]` over the real page indexes: `useSpreads`, `seekToPage` (which clamps every jump), the strip, scrubber, rail and page counter work inside it, while image URLs, progress, bookmarks, notes and server upscales keep the chapter's own index. Reaching the last page shown records the real last index (`recordedTo`), so it completes the chapter exactly as the real last page does; a resume inside a hidden run opens at the nearest page shown, and opening at the first page shown is still "opened at its start" for the recap and for "no write on open". A cold search decodes up to seven chapters' edges and loads the OCR models (loaded in parallel, `IPageTextReader.PrepareAsync`), so it is started ahead: the series page and Home's Continue lead call `POST reader/chapter/{id}/credits/warm` (`warmReaderCredits`; Next up and rail cards on hover or focus), which resolves the series' prefs server-side and runs `ReaderCreditsCache.Warm` only when they hide credits and the background scan is on, and the reader asks for the next chapter's answer as soon as its own is known. The first render waits up to 1.2 s for the result. A later one (the usual case on a cold server: seven chapters' edges decoded plus OCR) still trims the start while the reader is on the part it leaves out, and jumps to where an on-time answer would have opened, rebasing `useReaderProgress`'s opened position (`rebase`) so the jump is not a write; once the reader is past it the start stays. The end is trimmed unless the reader is past where it begins. **The end can also cut the last page shown** (`CreditPages.TailOffset`, the share of that page from its bottom, for an aggregator banner fused under the story art of a webtoon's last slice; `tailCut`/`clampToCut` in `creditWindow.ts`). Only Continuous does it: every strip page renders one `StripPage` with the same `.reader-strip-page` wrapper, `display: contents` (no box, the image stays a flex item of the strip) except on the last page with a cut, where `data-cut` makes it a positioned box with `overflow-y: clip` and a height of the image's measured height times `1 - cut`. So the strip, its end sentinel and the next-chapter meter end at the cut, while the `<img>` keeps its full size and URL and `PageOffset` stays a share of the real page. Because every page has the same element type and key, a page that becomes or stops being the last one (a late tail trim, Show) is never remounted; `ReaderPage.stories.tsx` `LateTailTrimKeepsTheImage` checks the node survives. `NotesMargin` adds a cut box's offset, and `EnhancedPage` places its overlay in the overlay's own `offsetParent` (the strip, or the cut box). The reading settings' "Show" row appears for a cut alone too ("End of the last page hidden in this chapter"; a cut is never counted as a page), and Show brings the cut back with the pages. A resume inside the cut opens at the cut, and a late answer leaves the page whole when the cut line is already on screen (`cutOnScreen`). Paged modes show the page whole, and split, rotation and border crop are paged-only, so they never meet the cut. Offline or on a failed search nothing is hidden. **Answers are found ahead of time and stored** (`ChapterCredits`, `CreditStore`, `CreditScanWorker`), so the reader usually never waits: the manifest carries `credits` when a current row exists and `ReaderPage` seeds `readerCreditsQuery` from it, and `GET credits` and the warm-up read the store before searching; every search, the reader's included, writes its answer through. A row belongs to the slice's `EdgeKey` (page count plus the zip directory's CRC and size of the first and last `CreditDetector.EdgePages` pages, `ReaderService.EdgeKeyOf`), not the archive version, because a ComicInfo rewrite copies every page and must not throw answers away; it also needs the current `CreditDetector.Version`, `CreditText.Version` and `PageTextReader.Version` (bump the one whose output changes), and an answer the colour rule gave alone stops counting once the OCR models load. The worker, and the warm-up with it, runs only while an admin has it on (Settings > Library > Credit pages, `PUT settings/creditscan`, key `SettingKeys.CreditScanEnabled`, unset is off; `CreditScanWorker.SetEnabled` applies a save at once); readers who hide credit pages still get them searched when a chapter opens. It goes series by series in reading order (series read in the last 14 days first, from the chapter after the last read, then new files, then the rest), waits on series with a download in flight, an import link pending or any file queued for conversion (a swap changes the pages) and while a conversion pass runs, runs one decode at a time, pauses while a reader was served a page in the last 10 s (`ReaderArchiveCache.SinceLastServed`, which work done ahead of a reader leaves alone through `OpenPageAsync(..., forReader: false)`: prepare-ahead's `ReaderPageCache` and the recap search) and searches a chapter again only when its file, a version or its neighbours' edge keys (`ReferencesKey`, through the same `ReaderService.NearbyOf` the reader's `NearbySlicesAsync` agrees with) changed. Volume files and chapters cut from one are stored `Skipped` unless a probe of some volume file's first and last two pages in the series reads as a scanlator's (`ReaderCreditsCache.ProbeAsync`, kept per row in `ProbeHit`), since published volumes carry none and a volume download is most of the work; a probe that could not read a page leaves the volumes as they are, and one made without the OCR models is stored as the colour rule's so it is probed again once they load. A failed search stays a failed row (retried after a day), never a "no credits" answer: the worker saves only when `ReaderCreditsCache.SearchAsync` says it did not fail. A series a pass cannot settle, or that throws, is kept out of the pick for an hour per language, so nothing spins. The warm-up runs one search at a time and drops the rest (hover warms a card per row). Credit searches read pages through `ReaderArchiveCache.OpenPageUnmarkedAsync`, never `OpenPageAsync`, or every file a search touches would hold its page conversion for `ReadingQuiet`. Edge strips are kept on disk too (`CreditStrips`, `cache/credits`, pruned by `HousekeepingJob`). **Credits nothing nearby repeats come from the bank** (`CreditBank`, `CreditBankEntry`): an edge with no repeated candidate is offered to the entries (`CreditDetector.SignatureOf`/`Alike` first, then `BankCandidates`), leaving out entries from the chapter and the neighbours it was compared with, and up to four proposals are judged in turn (most are margins the judge turns down). A bank candidate is hidden only when OCR read and accepted it; the colour rule never accepts one. A tail whose only repeated candidate is a partial at page 0 (`ReaderCreditsCache.OnlyPartial`) still asks the bank first, exactly as when tail partials did not exist, and an accepted bank answer (always whole pages at a tail) wins; otherwise the partial is judged. Two chapters of the 2026-11-14 scan would otherwise swap a hidden whole page for a cut. Tail partials come from repetition only, because the bank route was not measured for them: `BankCandidates` drops them, `LearnAsync` never seeds from a tail whose first candidate is partial, and the recheck below treats a tail holding only such a partial (and no whole page hidden) as open, which is what it was before. The in-memory result key carries the bank's newest entry id, or a run from before an entry arrived answers for it (and the recheck below would requeue that chapter forever). Entries are only learned from a region repetition found at the edge itself and OCR accepted (never from a bank match, never from the colour rule alone), one per distinct notice (one an entry already matches counts a `Hits`). A lone chapter (no usable neighbours) is still searched once the bank has entries. `ChapterCredits.BankSeen` is the newest entry a search compared against; `CreditScanWorker.RecheckBankAsync` runs when no series is due and compares rows below the newest from their stored strips against newer entries (any but the chapter's own) at the edges the bank would be asked about (nothing hidden and no repetition candidate in `CandidatesJson`, `JudgedCandidate.FromBank` false), sending a match back for a full search (`CreditStore.RequeueAsync`, `DetectorVersion` 0) and marking the rest seen. It leaves out rows below `CreditDetector.MinPages`: the pass settles those without a search, so they never get strips or a new `BankSeen`, and requeueing them spun the worker with nothing searched. Only entry signatures stay in memory; strips load from the database when a signature passes (`CreditBank.StripAsync`, last 256 kept). `research/credit-pages/2026-11-13-lone-credits/bankport` replays the app's matcher over the 4,942-chapter scan (126 matches, 33 of 34 cross-series and 40 of 40 same-series credits kept); rerun it after touching `Alike` or `BankCandidates`. **Each candidate's verdict goes through the notice store** (`CreditNoticeStore`, `CreditNotice`, `CreditNoticeRead`, `ChapterCreditNotice`), so a credit page is read once, not in every chapter that carries it and again in every predecessor a new chapter sends back (on the 4,981-chapter scan, git-ignored `research/credit-pages/2026-11-14-efficiency`: 64% fewer reads on a backfill, 93% fewer for a new chapter, no chapter hiding less). A notice is one distinct repeated region (credit page, banner, publisher card, title page) with one verdict. A candidate is a notice when its page has the same zip CRC, length, share and end as a page read before (`CreditNoticeRead`, `Bottom` set for a tail partial, read with `IPageTextReader.ReadBottomAsync`, so the top and bottom 0.3 of one page are two reads; its stored text is judged again with this candidate's colour flag and counts as no read), else when it is the same kind (whole with whole, partial with partial within 0.03 share), its 16 by 16 fingerprint is within 6 and `CreditNotices.SameRows` confirms, trying the 6 closest. `SameRows` is what keeps blank and near-blank pages from all falling into one notice: a region with fewer than 8 informative rows matches nothing and is always read. The rule: an accepted notice stays accepted; a rejected one is read again on its next member and trusted only after two reads (`TrustedRejection`), because one OCR read missing a keyword must not settle it; one accepting read accepts it for every member, and the chapters judged under it before (`ChapterCreditNotice` rows with the verdict false) are requeued (`CreditStore.RequeueAsync`, `CreditScanWorker.Signal`), with the store's `Generation` in the in-memory result key so the requeued search does not get the old run back. That requeue only reaches chapters whose links are saved, so a search running meanwhile would store the old verdict as current: `RunAsync` takes the `Generation` it started at and, after its save and links, calls `RequeueIfChangedAsync`, which sends the chapter back when a notice it judged changed after that (kept per notice in `_changed` with the chapter that changed it; a search that made the change itself, or started after it, does not come back, so nothing loops). An admin's override marks the change before reading the links, so either the override requeues the chapter or the chapter's check sees the mark. A read that returns null stores nothing and the caller falls back to the colour rule; without the OCR models the store is never asked. A store that throws (a busy database, anything but a cancellation) is logged and the candidate is judged on its own read, as before the store existed, so a store fault never fails the search or stores a failed row. The suggestion backfill on load is caught on its own, and `CreditGroupName` answers no suggestion when a pattern times out. Never create or accept a notice from a colour-only verdict: that is what keeps a bank proposal hidden only on read text. Notices from another `PageTextReader.Version` are cleared on load with every read and link (their chapters are searched again anyway), except a notice carrying a user's decision (an override, a Site mark, a confirmed group): it keeps its region, fingerprint and the user's fields, loses its OCR state (verdict, reads, text, suggestion) and is read again when a candidate matches it, an overridden one once and still answering its override (`RereadAsync`). A `CreditText.Version` change judges each notice again from its stored reads. Do not bump either without thinking about that, and do not bump `CreditDetector.Version` for anything that leaves candidates alone. `ChapterCreditNotice` is rewritten per search and indexed by notice, for listing the chapters that carry one; `HousekeepingJob` deletes notices no chapter links to after a day, never one carrying a user's decision. The store holds fingerprints in memory, loads a notice's rows only when its fingerprint passes, judges one candidate at a time behind a gate, and stops adding notices at 20,000. `CreditDetector.Close` rejects a row pair by two exact lower bounds (row sums, then eight block sums) before a `Vector<float>` sum; it gives the scalar loop's answer exactly because strip values are multiples of 1/16 below 256, which `CreditRowCompareTests` checks. Downloads and file links call `CreditScanWorker.Signal()`; anything else that adds files is picked up by its 30-minute fallback. The answer carries the manifest's `pageVersion` and the client caches it per version (`readerCreditsQuery`, `prefetchReaderCredits`), so a file replaced by an upgrade or a page conversion is searched again instead of losing real pages to the old answer. The detector compares head with head and tail with tail only, which is what keeps a recap from ever counting, and hides scanlator pages only. Aggregators paste the same notice a few pixels off per chapter, so each reference is matched at 20 sub-row and sub-column placements (`CreditDetector.Placements`, the chapter's own rows stay sharp; a blur on both sides was tried and matched story bubbles), and a region needs two references to start but runs on as far as any one repeats it. After touching matching, rerun `research/credit-pages/2026-11-13-shifted-banners/credits-ab` and look at the changed cuts. Its repeated pages are candidates (`CreditDetector.Candidates`), judged edge inward by the text OCR reads off them (`PageTextReader`, bundled PP-OCRv3 models in `src/Maki.Api/OcrModels`, then the keyword rule in `CreditText`), and the first one that is not a scanlator's ends the run, along with everything behind it (`CreditDetector.Settle`). Without the models the colour rule judges alone: a repeated page has to be in colour, and in a colour chapter not mostly white. `CreditText` weighs an official staff block (a line reading "STAFF", then "Original:" or "Adaptation:" labels, `StaffBlock`) as two publisher markers, since such blocks name a typesetter; added with `CreditText.Version` 3 and `CreditDetector.Version` 2 (tail partials), checked by the git-ignored `research/credit-pages/2026-11-14-efficiency/textcheck` (no verdict flips on the labelled set or the baseline scan, only the 15 staff blocks among the tail bottoms). `CreditText`'s lists and `PageTextReader`'s constants were tuned on hand-labelled pages in the git-ignored `research/credit-pages/2026-11-12-probe` (`OCR_SPEC.md`, `ocr_ref.py`, `ocr_rule.py`, `ocr-parity/`); change them only against that set. The endpoint tests run on a reader pointed at a missing folder, because noise pages carry no text and OCR would keep them all.
- **A credit notice is the release group's identity; the name read off its text is only a suggestion** (`CreditNotice.Kind`, `GroupName`, `GroupSource`, `SuggestedName`, `Invite`, `Override`; `CreditGroupsService`, `CreditGroupsController`, admin only like `PUT settings/creditscan`). On the 2026-11-14 scan (git-ignored `research/credit-pages/2026-11-14-efficiency`, "Release group from the credit") propagation was right 554 of 554 times but reached 103 of 826 ungrouped chapters, while the text named 729 and agreed with known groups only two times in three, so neither the suggestion nor a propagated group ever reaches a chapter by itself. `Kind` is Unknown, Group or Site (an aggregator's ad, "just previews", bato.to "do not repost": never names a chapter, never takes a group, and setting it clears the name). `GroupSource` Propagated comes from `CreditNoticeStore.PropagateAsync`, run after `SaveLinksAsync` writes a chapter's links: a hidden notice that is not Site and not Confirmed takes the group most of its chapters' files carry (`ChapterFile.Group`, compared case-insensitively), a tie or no grouped chapter changes nothing, and the update re-checks Site and Confirmed so a user's change made meanwhile wins. Confirmed is set only by the user and is never overwritten automatically. `SuggestedName` and `Invite` come from `CreditGroupName.Suggest` (pure, Maki.Core, ported from the research's `groups/groupname.py` and `evaluate.py`: every read of the notice votes, OCR variants within a small edit distance merge, and a name the user confirmed on any notice settles a close guess's spelling). The store fills them when a notice is created or read again, on load for notices below `CreditGroupName.Version`, and for every notice after a name is confirmed. The port differs from the prototype in two places on purpose: a line that is only "Scans"/"Scanlations"/"Translations" takes the name from the lines above (the prototype's branch never fired), and `blogspot` is a generic host. **`Override` outranks every read**: `JudgeAsync` answers Hide as accepted and Keep as rejected before anything else, without a read, through the same-bytes path too, with the notice's own text (`Verdict.ByUser`), so a Hide passes `ReaderCreditsCache`'s "a bank proposal needs read text" rule. That is not the colour verdict the rule keeps out. `SetOverrideAsync` requeues every chapter linked to the notice (`CreditStore.RequeueAsync`) and moves `Generation`, as accepting a notice does. Without the OCR models the store is not asked, so an override does nothing there. **Applying a group is an explicit admin action** (`POST creditgroups/apply`, `CreditGroupsService.ApplyAsync`): Group notices with a Confirmed or Propagated name give it to every linked chapter's file whose `Group` is empty, never replacing one, and a file two applicable notices name different groups for is skipped as a conflict, counted over every applicable notice linked to the file, not only the ones asked for. The list's `chaptersWithoutGroup` is exactly what apply would change for the bucket's notices, by the same rule (`Applicable`, `Conflicted`). Then, per series under `SeriesLocks.SeriesAsync` and in one transaction, the files whose name changes with the group (the format's name with the group against without it) go through `SeriesRenameService.RenameFilesAsync`, which leaves the folder alone, as after an import; `library.renameimportedfiles` off keeps files not `NamedByMaki` where they are. A refused rename (a download in flight, a name collision, no root folder: `Applied` false) rolls the series back so it keeps no group and returns the reason as a warning, and a file the rename skipped loses its group again, so a later apply does both. ComicInfo is not rewritten (a rewrite breaks a hardlink to a seeding copy, as with tags). A second run finds every file grouped and does nothing. The endpoints: `GET creditgroups` (buckets by name key, plus `site` and `unnamed`; only hidden, named or marked notices unless `?all=true`), `POST creditgroups/notices` with `{ noticeIds }` in the body (notices with series and chapters; a body because the Site and Unnamed buckets hold hundreds of ids), `GET creditgroups/notices/{id}/image` (the region cut from a linked chapter's page through `OpenPageUnmarkedAsync`, top share for a head, bottom for a tail partial, at most 640 px wide, skipped by `AntiforgeryTokenMiddleware.ShouldIssue` so its cache header survives), `PUT creditgroups/notices/{id}`, `PUT creditgroups/name` (one name for several notices) and `POST creditgroups/apply`.
- **Reader page order is `CbzReader.PageNames`** (extension filter, minus macOS `__MACOSX`/dot-file stubs, ordered by `NaturalFileNameComparer`); `VolumeChapterScanner.ScanCbzBoundaries` maps chapter markers onto that same list; drift between them opens chapters at the wrong page. When markers don't name a chapter, or name it more than once, the reader serves the **whole archive** rather than guess a range. `ReaderArchiveCache` is a bounded LRU singleton; its `Invalidate` must be called on delete (SQLite reuses rowids) or a later adopt inherits a stale page list. Page bytes go through `ReaderArchiveCache.OpenPageAsync` (via `ReaderService.OpenPageAsync`), which reuses a parsed `ZipArchive` per recently read file (`ReaderArchiveHandles`, 8 entries, 2 min idle) but **closes the file handle after every request** and re-validates length + write time on the next open. Do not "optimise" that into a held-open `FileStream` (Windows breaks `File.Move`/`Directory.Move`; see `ReaderArchiveHandles`). `OpenPageAsync` also records each path it serves for `ReaderArchiveCache.ReadWithin`, which page conversion's queue reads to hold a swap until the chapter has gone ten minutes without a page request; anything new that serves pages to a reader must go through it.
- **A PDF backing a chapter is read in place, never converted.** `CbzReader.PageNames`/`OpenPage` handle a `.pdf` path transparently: pages are synthetic names (`0001.jpg`..`NNNN.jpg`, one per PDF page) rendered on demand via `PdfReader`, so the reader and OPDS page endpoints need no branch on file type. There are no embedded chapter markers to scan, so a PDF never splits into more than the one chapter its `ChapterFile` already names.
- **`ChapterProgress` is ground truth for read state; `MaxChapter` is not.** The UI read count (`ReadCounts.Read`, and `SeenFor` for completion) is every completed `ChapterProgress` row, whatever the chapter's file state: requiring a file or a `FileRemovedAt` stamp dropped a read series to 0 once Wanted was flipped on and off, since that clears the stamp. A chapter the reader finished is therefore never "switched off" for the progress total (`LibraryListRows.ChapterTalliesAsync` takes the same read rows and moves those chapters to `Wanted`), and `SeriesProgressScope` clamps read to the total. `ReadFor` (achievements, taste, Hooked) and the reader end screen still count only chapters the user had a file for. List and detail endpoints must use the identical condition. `ChapterProgress.CompletedAt` (first false-to-true flip) is stamped and cleared in `MakiDbContext` on save; the one writer that sets it directly is `SaveProgressCoreAsync`, on every completion it makes, because a replayed offline write dates it by `ClientTime` and a watched row's `Completed` never went false for the context to notice. `MaxChapter` survives only as an internal aggregate for Rewind deltas / forward-only tracker pushes. Marking unread leaves an `UnreadAt` tombstone rather than deleting the row (a delete gets recreated by the next Kavita tick).
- **`ChapterProgress.Watched` is "ticked off, not read"** ("I've seen the anime"). It is carried alongside `Completed` but emits **no `StatsEvent`**, like the Kavita read import. `ReadCounts.Read` counts it and `ReadCounts.ReadFor` does **not** (see `ReadCounts`); anything new counting reads has to pick a side deliberately. `MarkWatchedAsync` raises `MaxChapter` silently via `ImportSilentAsync` (so the scrobbler pushes it, as a Kavita import does); skip that and the first genuine read after a watched season emits the whole season. `useReaderProgress` sends nothing while the page still equals the one the chapter opened at with no completion, so merely opening a ticked chapter writes nothing. A non-completing save leaves `Completed` and `Watched` alone; a completing save clears `Watched` and is the genuine read, which is why `SaveProgressCoreAsync`'s transition gate is `row is { Completed: true, Watched: false }`, not `row.Completed`. Mark-unread clears it too. `OpdsProgressWriter` passes `existing is { Watched: false }` as "has a progress row", so a lone last-page prefetch does not complete a watched chapter. `AnimeResumeService.ApplyAsync` calls `ImportSilentAsync` itself even when `markWatched` is false, because its chapters are usually not downloaded; `AnimeResumeServiceTests.Apply_raises_the_mark_so_the_next_real_read_counts_one_chapter` pins the delta at 1.
- **Reading days exclude bulk-marked rows.** `ChapterProgress.BulkMarked` is set by `ReaderService.MarkReadAsync` and by new rows from the Kavita read sync, and cleared on mark-unread or a genuine completion in the reader. `ReadingBehaviourService` days (dated by `CompletedAt`) and `ActivityStatsService` series-started (dated by the earliest `StartedAt`) skip those rows; they do not require `ReadSeconds > 0`, because OPDS reads carry no time but are real. Pages-read still requires `ReadSeconds > 0`, so an OPDS-only reader has days and starts but no pages.
- **`ChapterProgress.CountedAt` is the never-cleared token that a one-shot's `ChaptersRead` event was emitted.** `Completed` clears on mark-unread, and a one-shot has no `MaxChapter` to absorb a second completion, so `OnChapterCompletedAsync` gates `RecordUnnumberedReadAsync` on it. Do not key that off `UnreadAt`, `Watched` or `BulkMarked`: each is cleared or set by paths that are not reads.
- **`ReadingState.Finished` is sticky, but a reread finish still emits `SeriesFinished`** (`ReadingProgressService.IsNewPassAsync`, native path only). It counts when a native completion makes the *recomputed* mark (not the stored forward-only one) reach the end and every completed numbered chapter, downloaded or file-removed, grouped by number, has its latest `CompletedAt` after the series' latest `SeriesFinished` event. With no such event (finished silently by an import, a first sighting or incognito) every number needs a genuine completion instead. Re-marking only the last chapter, re-saving a completed one, and the Kavita path never count.
- **Three progress fields, don't conflate**: `PageIndex` (resume position, may move backward), `Completed` (sticky, idempotency token), `ReadingState.MaxChapter` (forward-only high-water mark). Marking unread clears the first two, never lowers the third. One-shots (`Number == null`) must not touch `MaxChapter` — no number to raise it to.
- **`ChapterProgress.PageOffset` is reader-internal**: how far down `PageIndex` the Continuous strip was, as a share of that page's height (0 to 1, never pixels, since slice height depends on screen width). Every non-stale write sets it, so OPDS, Komga, KOReader, mark read/unread and anything else that passes none resets it to 0, and nothing external reads it. A stale replay keeps the stored one with the stored page. `ResumeOffsetFor` returns 0 wherever `ResumePageFor` resets (completed chapter, page out of range), so a finished chapter always reopens at its start. The client records it only for a page taller than the screen after scrolling pauses, and `useReaderProgress`'s "no write on open" rule compares it too.
- **Page conversion's tall-strip split renumbers pages** (`PageSplitRemap`): it moves `PageIndex`/`PageOffset` (a share of a split page lands in the matching piece), the `PageCount` snapshot, bookmarks and page notes with `ExecuteUpdate`, so the save hook's Reading promotion and `UpdatedAt` stay untouched. KOReader devices, Kavita and offline replays still hold the old numbering for that file.
- **`ChapterProgress.ReadSeconds` accumulates across re-reads on purpose**, so `ReadingTimeEstimateService`'s per-chapter median runs high for a series the user has fully re-read. Accepted: the median blunts partial re-reads and a per-reading split would need a new column.
- **Reading time is measured client-side and reported as deltas** (`useReadingClock`, tab visible+focused+not idle). `flushProgress` always sets `Final` on hide/unmount/chapter-change to flush banked time regardless of threshold. `ReaderService` clamps a single report to 15 min. Native reader only — OPDS page fetches and `MarkRead` pass `TimeReport.None` (a page request isn't proof anyone looked at it).
- **`ReadingSession` rows are stitched server-side by gap** (`ReadingSessionService.Stitch`, shared with the backfill): a report starting within 10 minutes of the user's latest sitting extends it, otherwise a new row starts (the client sends no session id). Only native-reader time counts: `SaveProgressCoreAsync` records when the clamped report is > 0 or the chapter just completed, and a zero-second completion only credits an already open sitting, so OPDS/`MarkRead` never create one. The session is staged and saved with the progress, before the completion events; a failure only logs, and `IncognitoMode.Full` series are skipped. `RecordAsync` takes an explicit `userId` and ignores query filters. `ReadingSessionBackfillService` seeds history once from `ReadingTime` events (marker `stats.sessionsBackfillDone`; backfilled sittings have `ChaptersCompleted = 0` and may include later-incognito series, since sessions carry no series). Never purged.
- **Kavita read-status import is invisible to Rewind on purpose** (`KavitaReadImportService` → `ReadingProgressService.ImportSilentAsync`) — Kavita doesn't say *when* chapters were read, so dating them today would dump the whole back catalogue onto one day. Imported rows carry `PageCount = 0`; `Completed AND PageCount = 0` is how later code identifies an import.
- **A Mihon import's read chapters wait in `PendingReadImport` until the series has chapters** (`PendingReadImportService`, one row per series and reader, a second import merges its numbers). The import stores the row, then applies it at once only if chapters already exist; otherwise `ChapterSyncService.SyncSeriesAsync` applies it after a sync that wrote new chapters (same hook and gate as `AnimeResumePendingService`), so auto match, manual link, refresh and rescan all land it. The row keeps the numbers that matched no chapter yet and is deleted only once none are left (both guarded on `NumbersJson` being unchanged since read). Rows take the Kavita import's shape (`Completed`, `BulkMarked`, `External`, `PageCount` 0), skip rows already completed or carrying `UnreadAt`, raise no StatsEvent, XP or inbox row, and are written with `IgnoreQueryFilters` and an explicit `UserId` because the sync runs unrestricted. Matching is by exact `Chapter.Number`; one-shots are never marked and never raise `MaxChapter`, and a series whose chapters are all unnumbered gets no silent mark at import either. The silent mark is raised at import by `ImportSilentAsync` from the highest read number, or from the tracker's `lastChapterRead` only when the backup had no chapter rows for that manga (that number may follow the tracker's numbering). Mihon does record read dates; they are ignored on purpose, for the Rewind reason above.
- **`KavitaProgress.Compute` is the one reading of Kavita's volumes payload**, for both the tracker push (`MaxChapter`/`MaxVolume`) and the per-chapter read marks (`Chapters` ranges, `Volumes`, via `ExternalReadSyncService.MarkAsync`). Keep it that way. Kavita reports a Maki "Vol. 01" archive as a volume holding one loose-leaf chapter numbered `-100000`, so a fully read volume marks every chapter whose file parses as that volume (`ReleaseNameParser.IsVolume`), and a half-read one counts chapters through the archive's scanned page boundaries (`VolumeBoundaryService`, shared and cached). Pass the boundaries everywhere `Compute` runs, or the import's silent baseline and the tick's mark disagree and the difference lands in Rewind.
- **Kavita live read sync (`KavitaLiveReadSync`, opt-in `reader.pullfromkavita`) only writes `ChapterProgress`**, via `KavitaReadImportService.MarkSeriesAsync`, so its rows look exactly like imported ones. It must **not** raise `MaxChapter` (no `ImportSilentAsync`, no `TrackKavitaAsync`): the scrobble tick still reads the same series and its mark delta is what feeds Rewind and the trackers; raising the mark early turns that delta into zero. Kavita sends `UserProgressUpdate` on `/hubs/messages` only to online admins, for every user, so a non-admin API key gets nothing (status `NotAdmin`) and every event is filtered to the key's own Kavita user id. Events fire per page turn, hence the per-series coalescing.
- **While the live hub is connected, the scrobble tick's Kavita pass reuses the volumes it fetched last time** (`KavitaLiveCoverage`, a singleton the live sync and `ScrobbleService` share). A series is fetched again only when the hub reported it (`Saw` on every `UserProgressUpdate`), it was never fetched, its `all-v2` summary `Pages`/`PagesRead` moved, or its last fetch failed; a full sweep runs while the hub is down, on the first pass after each connect or reconnect, after a full sweep that did not finish, and every six hours; a partial pass that did not finish hands every series it took as dirty to the next pass. Everything after the fetch (`MarkAsync`, `TrackKavitaAsync`, the tracker pushes of Maki's own reading of a Kavita-adopted series) still runs for every series on the reused volumes, because the native pass skips those series. Kavita's bulk "mark as read" may not send the event; the summary check or the next full sweep picks it up. The cache is dropped on every disconnect.
- **"How is it so far?" prompts are armed by a genuine completion, never by state** (`RatingCheckpointService.ArmAsync`, called from `ReaderService.SaveProgressAsync` after `OnChapterCompletedAsync`, so native and OPDS reads both arm and bulk `MarkReadAsync` does not). Evaluating on a page load would arm every series at once after a Kavita or Mihon import or an anime watch mark. Each checkpoint is a condition re-checked on every completion, so the one-per-UTC-day cap (the max `UserSeriesState.LastRatingCheckpointAt` across the reader's rows) defers rather than drops. Hooked counts `ReadFor`; Caught up compares `ReadCounts.Read` (watched included, the end screen's number) against the wanted count, because it is about position. Volume end (opt-in, `ratings.prompts.volumes` = "on") needs the completed chapter, so `ArmAsync` takes it: a volume entry, or the highest-numbered chapter its volume has; it shares Caught up's 30-day gate per series and the staleness test. The arm call has its own try/catch: a prompt must never cost the progress write. The end screen fetches `GET series/{id}/rating-checkpoint` and asks again a few times (`useRatingCheckpoint`), because the debounced completing write may still be in flight when it opens.
- **Completed is set by reaching the end, never by the Wanted switch alone** (`SeriesCompletion`). `ReadingProgressService` moves a series to `ReadingStatus.Completed` (raw upsert after the save, `MakiDbContext.PromoteToCompletedAsync`, so it lands after the save hook's Reading promotion; only from Plan to read or Reading, since watched ticks, anime ticks and the volume hand-over reach it without a read and must not undo On hold or Dropped) when the series is `Finished` and `ReadThroughAsync` holds: publication Completed and `ReadCounts.SeenFor` reaching how long the series is (`SeriesProgressScope.Compute` through `LibraryListRows.SeriesLength`: the locked or MangaBaka total, raised to the listing, specials MangaBaka counts taken out). That is not what the series page shows: On disk counts the chapters wanted and Read counts the downloaded ones, as the reader toolbar and end screen do (`SeriesProgressScope.Wanted`, `LibraryListRows.ProgressTotals`). MangaBaka's number must never pad those (the owner reverted an attempt, and one counting Read against the wanted total, which made Smart mode's "8 of 10" in the reader turn into "8 of 200" on the series page), while completion has to know a source is missing chapters the reader would want. Both are needed: `Finished` alone completes a series whose source lacks the final chapters (the MangaBaka floor keeps the total above the mark), and the total alone completes a 3-of-100 try-out when there is no MangaBaka total (switched-off chapters leave it). Neither the automatic step nor the ask happens while `ReleaseOutlookService.ExpectsMore` (announced date, or cadence Expected or Late): a series can be Completed on MangaBaka while its translation is still releasing. A finished, read-through series held back that way stays Reading and `AskAsync` offers it later with nothing left out; so does one MangaBaka marked Completed only after the last read, since `Finished` is only computed on a progress write (`ReadingProgressService` and `SeriesController.Get`/`ReaderController.Ending` take the outlook service as an optional parameter, so hand-built instances skip the gate). Native completions always check, one-off imports (`ImportSilentAsync`) always check, and the Kavita tick checks only when its mark moves, or a reader who set a finished series back to Reading would be overruled every 30 minutes. Switched-off chapters standing between the reader and the end are a question, not an answer: `AskAsync` asks when every kept chapter is read and what the series-length total still counts as unread is no more than the switched-off chapters (zero for a None series, whose switches mean nothing), which is what keeps a source missing the final chapters from asking. It drives the series page hint and the end screen's ask (the chapter on screen counts as read, the completing write may still be in flight), and "not yet" stamps `UserSeriesState.CompleteHintDismissedAt`. The trackers get Completed through `held` (`ScrobbleService.HeldAs`), and the planner fills progress to the tracker's own total, since a tracker counting skipped specials would otherwise never complete. `SeriesCompletionBackfillService` (marker `reading.completedBackfillDone`) gave series finished before the status existed the same answer once and leaves On hold and Dropped alone.
- **`ContinueReadingService.NextForAsync` is the only "what's next" resolver** — reads `ChapterProgress` only, never `ReadingState` (would double-count/multiply on duplicate rows).
- **Progress writes may be replays from the PWA's offline queue** (`SaveProgressRequest.ClientTime`, `OpId`, both optional). `OpId` (1 to 64 chars, no spaces) is remembered in `ChapterProgress.RecentOpIds`, the last 32 per row space-separated; a known id answers success and changes nothing, which is how a queued copy of a write that did land is recognised even after later live writes. `ClientTime` is clamped to the last 30 days. Older than the row's `UpdatedAt` means stale: seconds are added, a completion is applied unless `UnreadAt` is later than `ClientTime` (a mark-unread made after the offline read wins), and `PageIndex` and `UpdatedAt` stay put. Otherwise `ClientTime` dates the write: `UpdatedAt`, `StartedAt` on a new row, `CompletedAt` (set explicitly, `MakiDbContext` only fills a null one), the `ReadingTime` event, the sitting, and the `ChaptersRead`/`VolumesRead`/`SeriesFinished` events through the `at` parameter of `TrackNativeAsync` and `RecordUnnumberedReadAsync`. `ReadingState.LastProgressAt` only moves forward. A write with `ClientTime` stages only its own seconds as the `ReadingTime` event at `ClientTime` (`StageReadingTime`'s `onlySeconds`); anything else banked was read live after it and flushes on the next live write, dated then. Absent fields behave exactly as before.
- **`ReadingSessionService.Stitch` is two-sided.** A report joins a sitting only when `[now - seconds, now]` overlaps it or comes within the gap on either side, and `StageAsync` picks the latest sitting that started no later than the report's end plus the gap. For a live report both reduce to the old rule; a replayed morning report becomes its own row (or joins the morning sitting) instead of merging into the afternoon.
- **A read moves the series to `ReadingStatus.Reading`, and only `MakiDbContext`'s save hook does it** (`ReadsToPromote`, then a raw upsert after the save, so a race on a missing `UserSeriesState` row can never fail the progress write). A read is a new row completed or past page 0, a false-to-true completion, a watched row completing, or a page move; watched ticks and mark-unread are not. `ExecuteUpdate` on `ChapterProgress` bypasses it. Because a first read now creates the state row, code that inserts a `UserSeriesState` after progress was saved must look the row up first (test helpers included). On hold and Dropped keep a series off Home's Continue reading and the OPDS and Komga on-deck shelves; the auto rules (`ReadingStatusAutoService`, per-user `reading.autohold.days`/`reading.autodrop.days`) only count idle days while a downloaded chapter is waiting, and a rule's own change never restarts the clock (`StatusAuto`).
