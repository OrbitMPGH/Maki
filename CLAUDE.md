## Directory ownership

- `Maki.Core` — domain, no infra deps. Entities, `ISource`/`IMetadataProvider`, parsing, CBZ pipeline. Also `Security/` — the `MakiPermission` flags enum and `ICurrentUser`, so domain code can ask about permissions without an ASP.NET Identity reference.
- `Maki.Data` — EF Core + SQLite, migrations. **Exception to "entities live in Core":** `Identity/` holds `MakiUser`, `UserApiKey`, `UserRootFolder`, `AuthEvent`. `MakiUser : IdentityUser<int>` would drag `Microsoft.Extensions.Identity.Stores` into Core, and Core is deliberately infrastructure-free.
- `Maki.Sources` — one `ISource` impl per site.
- `Maki.Metadata` — MangaBaka provider + local dump + embeddings.
- `Maki.Api` — host, controllers, Quartz jobs, DI wiring, download workers.
- `frontend` — Vite/React/Mantine SPA.

## Build/run gotchas

- API: `:8990`. Frontend dev server: `:5173`, proxies `/api` + `/signalr` to `:8990`.
- EF migrations auto-apply on startup — no manual step. To add one: `dotnet ef migrations add <Name> --project src/Maki.Data --startup-project src/Maki.Api`.
- State (SQLite, logs, covers, page cache, `config.json`, data-protection keys) resolves via `MAKI_CONFIG_DIR` → `/config` (Docker) → `%APPDATA%\Maki` (Windows). In dev, set `MAKI_CONFIG_DIR=$PWD/.devconfig` so you don't touch the real library/DB. `.claude/launch.json`'s `backend` preset uses the **real** APPDATA config — use `backend-dev` instead for anything destructive.
- `src/Maki.Api/wwwroot/` must exist or startup throws `DirectoryNotFoundException` from the static-web-assets loader, before any of Maki's own code runs. It's produced by the frontend build, so a fresh clone that has only ever run the backend needs it created by hand.
- Frontend type-checking is `npx tsc -b`, **not** `npx tsc --noEmit`: the root `tsconfig.json` is `"files": []` plus project references, so the `--noEmit` form checks nothing at all and exits 0 on a broken tree.

## Non-obvious domain facts

- **There is no instance API key any more.** Auth is ASP.NET Core Identity: an HttpOnly session cookie for the SPA (`Maki.Session`), and per-user `UserApiKey` rows for everything else. `config.json` no longer holds a credential — `ConfigFileProvider` actively rewrites the file to drop a leftover `apiKey` on first start after upgrade, so nobody concludes the dead secret still works. **`?apikey=` is accepted nowhere**: `ApiKeyAuthenticationHandler` reads the `X-Api-Key` header only, because a query string lands in browser history, `Referer`, and every reverse-proxy access log. The three places that needed a credential in a URL — reader page images, reader thumbnails, the SignalR handshake — are same-origin and ride on the cookie instead; `/api/v1/mediacover` lost its anonymous carve-out for the same reason. `/initialize.json` is still anonymous but now returns only `{apiRoot, version, setupNeeded}`. Only **`UserApiKey.KeyHash`** (SHA-256 hex) is stored, never the key: a plain fast hash is correct there because the input is 256 bits of `RandomNumberGenerator` output, so there is no guessable password to slow an attacker against, and lookup becomes an indexed digest match with no timing side channel — which is what retired the fixed-time compare `OpdsAccess.Allows` used to need. The consequence users notice: a key (including the OPDS feed URL) is displayed **exactly once**, on the response that mints it.
- **`{ConfigDir}/dataprotection-keys` is load-bearing and is credential material.** It signs session cookies and antiforgery tokens. Unconfigured, ASP.NET puts the key ring under the user profile — in Docker a path that does not survive recreating the container — and every restart then silently invalidates every session, logging everyone out with nothing in any log to explain it. Whoever holds these keys can mint a session cookie for any user, so it sits behind the same filesystem-permission boundary as `maki.db`, and **`BackupService` must never include it**: a leaked backup would otherwise be a permanent authentication bypass. The cost is that restoring onto a different machine signs everyone out once, which is the right trade. (On Windows the keys are written unencrypted and Serilog says so at startup; DPAPI protection would tie the config dir to one machine, which breaks the portability the whole `MAKI_CONFIG_DIR` design depends on.)
- **The multi-user migration inserts a placeholder admin at `Id = 1`, and that id is part of the schema.** A migration cannot compute a password hash (PBKDF2 lives in `UserManager`, which does not exist that early in startup), so `MultiUserIdentity` inserts an unclaimed row — `PasswordHash` null, `PendingSetup = 1` — and every per-user column a later migration adds will default to 1. `AspNetUsers` is created empty a few statements earlier, so the first insert is deterministically 1. `PendingSetup` is an explicit flag rather than inferred from a null `PasswordHash` because an OIDC-only user legitimately has no password. `POST auth/setup` is the only thing that may claim it and only while the flag is set; `auth/login` refuses such a row outright. This is what makes the upgrade lossless for an existing single-user install: their whole library and history is already attached to user 1, and setup only bolts a login onto it. `MultiUserMigrationTests` is the guard — it runs the real `Migrate()` over a *populated* pre-upgrade database, which `TestDb` (`EnsureCreated()`, no migrations) structurally cannot.
- **Authorization fails closed via `AuthorizationOptions.FallbackPolicy`**, so a controller added without an `[Authorize]` attribute requires a signed-in user rather than being wide open. Two consequences: `MapFallbackToFile("index.html")` **must** carry `.AllowAnonymous()` or the SPA shell 401s and the login page can never load, and `OpdsController` needs a class-level `[AllowAnonymous]` because it authenticates its own path token. Permissions are checked against `ICurrentUser` — one database read per request, cached in `HttpContext.Items` by `CurrentUserMiddleware` — **not** against claims baked into the cookie, so revoking a permission takes effect on the very next request with no security-stamp staleness to reason about. Always test permissions with `MakiPermissions.Grants`, never a bare `HasFlag`: `Admin` implies every other permission and holds only its own bit, so a direct flag test refuses the one account that certainly may act. `MakiPermission` values are persisted in `AspNetUsers.Permissions` — append members, never renumber or reuse a retired bit.
- **An antiforgery token is bound to the identity it was issued to**, so the token a visitor holds while anonymous stops validating the moment they sign in. `AntiforgeryTokenMiddleware` therefore reissues on **every** GET, not only when the cookie is missing — an "only if absent" check keeps serving the dead anonymous token and every mutation after login fails with "invalid or missing antiforgery token". `AuthController.CompleteSignInAsync` also reissues directly, after setting `HttpContext.User` to the new principal (`SignInAsync` does not update it within the same request), which closes the window where a mutation issued before any GET would fail once. `AntiforgeryCookieFilter` validates **only** cookie-authenticated mutations: a header credential is never sent ambiently by a browser, so API-key and anonymous requests have nothing to forge and demanding a token there would break every script and third-party client for no gain.
- **`SettingsController` is admin per *action*, not per class**, and the five exceptions are deliberate: `GET ui`, `metadata`, `setup`, `reader` and `library` are things the app needs before it knows whether the user is an admin (which page `/` resolves to, whether Discover has its local database, the reader's display defaults). Everything else there — and every write without exception — is admin-only, because the reads return the Prowlarr and Kavita API keys, the qBittorrent password and the tracker client secrets in plaintext. `reader`/`ui`/`discover` are per-user preferences wearing instance-wide clothing: they live in the shared `AppConfig` table, so admin-only *writes* is the honest guard until the per-user data split moves them.
- **The last-admin rule (`AdminGuard`) prevents a state unrecoverable through the UI.** With zero usable admins nobody can ever reach settings, root folders or user management again, and the only fix is editing `maki.db` by hand. So: an admin cannot drop their own `Admin` flag, cannot disable or delete themselves, and the flag cannot be removed from the last account that has it. "Usable" excludes `Disabled` and `PendingSetup` accounts on purpose — a second admin row that cannot sign in is not a way back in, and counting it would let the real admin lock everyone out.
- **The OPDS token is a `UserApiKey` with `Scope = Opds`, resolving to a user**, replacing the single instance-wide `opds.token` setting (the key is gone from `SettingKeys`). The scope split is the point: the feed URL is pasted into third-party reading apps, and a full-scope credential there would hand them the whole management API — so an `Opds` key is rejected on `/api/v1/*` and a `Full` key is rejected as a feed token. `OpdsAccessService.ResolveAsync` returns null (→ **404, never 401**) when the catalogue is disabled, the token is unknown or revoked, its owner is disabled, or its owner lacks `UseOpds`. It is two queries, not one — the catalogue switches are in `AppConfig` and the credential is in `UserApiKeys`, and it still avoids `IAppSettings`, which opens a fresh scope and DbContext per key. Covers moved from `/api/v1/mediacover` to `/api/v1/opds/{token}/cover/{id}`: mediacover requires a session now, and a reading app holds exactly one credential.
- **The cover proxy is an SSRF primitive, gated by `CoverHostPolicy` + `ISource.CoverHosts`.** `GET search/cover` fetches a caller-supplied URL server-side (several image CDNs hotlink-block every Referer but the site's own), so the target host must belong to the named source: its own domain including subdomains, or one of the extra CDN domains that source declares. `CoverHosts` is a default interface member returning `[]`, so adding a source stays "one impl plus one registration" — only Webtoons (`pstatic.net`), MangaPlus (`tokyo-cdn.com`) and Asura (`asuracomic.net`) serve images off their own domain. The match requires a dot boundary, or `evil-mangadex.org` would satisfy a suffix test for `mangadex.org`. A blocked host is logged **with its name**, so a missing entry shows up as a warning line naming exactly what to add rather than as a silent hole.
- **`auth.*` settings are read once at startup into `AuthRuntimeOptions`, so they need a restart** — they configure things the host builds exactly once (the cookie's `Secure` policy, HSTS, the trusted-proxy list, the lockout thresholds), and the Security settings card says so. Two defaults are deliberate and shouldn't be "improved": `auth.requirehttps` is **off**, because the common deployment is plain HTTP on a LAN where a `Secure` cookie is set and then never sent back — a login that fails with nothing in any log; and `auth.trustedproxies` is **empty**, meaning forwarded headers are ignored entirely, because honouring `X-Forwarded-For` from anyone lets a client claim any address and thereby forge the audit log and dodge per-IP rate limiting and lockout. `auth.lockoutmaxattempts` of `0` means "no lockout" and must survive as 0 rather than falling back to the default, which Identity would read as "lock on the first failure".
- **Login answers one generic 401 for every failure** — unknown user, wrong password, disabled account, lockout — because distinguishing them turns the form into an account enumerator. `AuthController` also verifies against a **dummy hash** when the username does not exist, using the *injected* hasher so it carries the configured 210,000 iterations: without that, "unknown user" returns in microseconds while a wrong password takes the full PBKDF2 cost, a difference measurable over the network.
- **`EventsHub` requires authentication and addresses groups, not `Clients.All`.** Each connection joins `user-{id}`, and admins additionally join `admins`; instance events (queue, imports, update availability) go to `admins` only. Group membership is read from the database at connect time rather than from a claim, so it is correct as of the connection — but fixed for its life, which is fine because nothing here is an authorization decision about data, only about who hears a progress ping.
- **MangaBaka has no MangaDex IDs** — cross-refs cover MAL/AniList/MangaUpdates/Kitsu only. `SourceMatchService` matches by normalized-title search per source, not shared UUID.
- **Local MangaBaka DB** (`{ConfigDir}/mangabaka.db`, ~3 GB, `MangaBakaLocalStore`, API fallback via `mangabaka.uselocaldb`). One flat `series` table (~130 cols, ~45% `state='merged'`); `total_chapters`/`final_volume`/`merged_with` are TEXT and may be fractional; genres/tags/authors/alt-titles are JSON text; `tags_v2` is richer — per-tag categorical weight (`core`/`defining`/`recurrent`/`incidental`/`unweighted`), `is_spoiler`, `series_count` (IDF), 96% coverage vs 50% for plain `tags` (and `genres_v2` is empty — use `genres`); cross-refs are flat `source_*_id` columns; FTS5 index `maki_search` built at install time.
- **User tags are not `Series.Tags`.** That list is metadata the provider owns — `SeriesMetadataRefreshService` replaces it wholesale on every refresh, so anything a user typed there would vanish on the next daily job. User tags are the `Tag` entity + `SeriesTags` join (skip nav `Series.UserTags`), so they survive refreshes and can be renamed/deleted library-wide. Query the join through **`db.SeriesTags`**, never `db.Series.SelectMany(s => s.UserTags)` — a skip-navigation `SelectMany` compiles to SQL APPLY, which SQLite doesn't support (500s at runtime, not build time). Saved Library filters (`SavedFilter`) store the filter spec as opaque JSON; the grid already holds every series client-side, so filtering stays in the browser and the server never interprets the spec. Serialize/deserialize it only through `LibraryFiltersController.SpecJson` (camelCase, case-**insensitive** read): a name mismatch doesn't throw, it yields an all-defaults spec, so a preset silently degrades to "no filter" instead of erroring. Adding a spec field is safe — missing JSON properties fall back to the record's parameter defaults — but never rename or reorder one.
- **Spoiler tags are stripped per series at ingest**, not at display. MangaBaka's flat `tags` column carries no spoiler flag; only `tags_v2` does, and the flag is genuinely **per series, not per tag name** — in a 4k-series sample 252 names appear both ways ("Love Triangle": spoiler for 140, ordinary for 225), so any global spoiler word list is wrong in both directions. `MangaBakaLocalStore.WithoutSpoilerTags` subtracts that series' spoiler names from its plain tag list, which keeps them out of `Series.Tags` and therefore out of the Library tag filter *and* the ComicInfo written into every CBZ. Two gaps by construction: the **API fallback path never sees `tags_v2`**, and series whose `tags_v2` is empty (~4% of the dump) keep everything — there's nothing to filter on. Existing rows heal on the next metadata refresh (daily job, or the Library's bulk "Metadata" action), not on upgrade.
- **`ReadingState` is one row per series shared by both progress sources** — the Kavita scan and the built-in reader — and `ReadingProgressService` is its only writer. That merge is what makes double-counting impossible: deltas are computed against the stored mark, so a chapter read in Maki and re-reported by Kavita next tick yields a delta of **0**. `KavitaSeriesId` is nullable; a row with it null is *native* (reader-owned), and the Kavita pass **adopts** such a row on first sighting — sets the id, takes `Math.Max` of both marks, emits **no** `StatsEvent` (that history predates Maki). The native path has no baseline at all: a first read emits immediately. `TrackKavitaAsync` **returns the merged marks and `KavitaPassAsync` must scrobble those, not Kavita's raw numbers** — otherwise reading on in Maki past what Kavita knows never reaches a tracker (`ScrobblePlanner` is forward-only, so nothing would push). Two Kavita series can resolve to one local series, so **duplicate rows per `SeriesId` are legal**: never add a plain unique index on it (`Migrate()` would throw at startup on real DBs — `IX_ReadingStates_NativeSeries` is filtered to native rows for exactly this reason), and always order when picking one — by `MaxChapter`, not `UpdatedAt`, and go through **`ReadingProgressService.PickAsync`** so every caller agrees. `UpdatedAt` is actively wrong: the Kavita pass restamps it on every row it touches each tick, so the pick flips between calls and the next native delta is measured against a lagging row — the same chapters counted into Rewind twice (regression test: `NativeReadPicksTheFurthestRowWhenASeriesHasSeveral`). `SmartDownloadJob` and `KavitaProgressPusher` order the same way. Writers hold the singleton `ReadingProgressGate`; the unique indexes are the backstop, not the mechanism — and the retry that swallows a lost race matches the **extended** SQLite codes (2067/1555), never the primary 19, which also covers FK/NOT NULL failures no retry can fix.
- **Reader page order is `CbzReader.PageNames`** — image-extension filter + `OrderBy(FullName, OrdinalIgnoreCase)` — and `VolumeChapterScanner.ScanCbzBoundaries` maps chapter markers onto that **same** list. If they ever drift, chapters open at the wrong page. Adopted/imported CBZs are never renamed internally, so page names are arbitrary scanlation strings; nothing may assume Maki's own `001.jpg`. A volume CBZ backs several chapters, so a chapter is a *slice* — and when the embedded markers don't name it, **or name it more than once** (pages in two runs, which sorted scanlation names do produce), the reader serves the **whole archive** rather than a guessed range (showing extra pages is recoverable, silently skipping them is not). `ReaderService.SliceAsync` is one query on purpose — chapter, file, series, root folder and the shares-an-archive test in a single projection — because every page *and* thumbnail request resolves a slice, so any extra round-trip multiplies by the page count. `ReaderArchiveCache` is a bounded LRU (`Capacity`), not a plain dictionary: it is a singleton holding hundreds of page-name strings per archive. Its `Invalidate` is load-bearing, not decorative — SQLite reuses rowids after a delete, so `CbzLinkService` must drop a `ChapterFile`'s entry when it removes the record or a later adopt inherits the stale page list at the same id. Page images are authenticated with `?apikey=` (an `<img>` can't send a header), deliberately **not** a middleware carve-out like cover art: covers are thumbnails, whole pages are the content.
- **`ChapterProgress` is the ground truth for read state; `MaxChapter` is not.** Every read count the UI shows (`SeriesDto.ReadChapterCount` → hero bar, library rings, chapter table) is a count of completed `ChapterProgress` rows for downloaded chapters — and the list and detail endpoints in `SeriesController` must apply the **identical** condition (completed *and* downloaded, null when zero), or the same series reads "0 read" on its own page while the grid hides the bar. It used to be "downloaded chapters numbered at or below `MaxChapter`", which over-reported permanently: the mark is forward-only, so one stale or mis-attributed Kavita read left a series reporting chapters read that had never been opened, with nothing able to clear it. `MaxChapter` survives as an internal aggregate only — Rewind deltas and forward-only tracker pushes. Both Kavita paths therefore write per-chapter rows through **`ExternalReadSyncService`** (`External = true`): the one-off import for the back catalogue, and `KavitaPassAsync` on every tick off the volumes payload it already fetches. Marking a chapter unread leaves an **`UnreadAt` tombstone** rather than deleting the row — a deleted one would be recreated within the hour by the next Kavita tick, since Kavita goes on reporting the chapter read. Tombstones read as plain unread (not "in progress") and are skipped by `Continue`, or unreading a chapter would hijack "Continue reading".
- **Three progress semantics that must not be conflated**: `ChapterProgress.PageIndex` is a resume position and may move backwards; `ChapterProgress.Completed` is sticky and is the idempotency token for read events; `ReadingState.MaxChapter` is a forward-only high-water mark. Marking a chapter unread clears the first two and **never** lowers the third. Marks are **recomputed** from `ChapterProgress` on each completion, never incremented — self-healing and immune to a series' duplicate rows across languages. A volume only counts once *every* downloaded chapter in it is complete (a naive `max()` reports volume 4 read one chapter in). **One-shots (`Number == null`) must not touch `MaxChapter`** — there is no number to raise it to, and inventing one mis-counts `SmartDownloadJob`'s unread and the library ring; they emit a standalone `ChaptersRead` event instead.
- **Importing read status from Kavita is deliberately invisible to Rewind** (`KavitaReadImportService`, Settings → Reader). Kavita doesn't say *when* those chapters were read, so dating them today would dump a whole back catalogue onto one day of the year in review. The import writes `ChapterProgress` rows and calls `ReadingProgressService.ImportSilentAsync`, which advances the high-water mark **emitting no `StatsEvent` and without touching `LastProgressAt`** (that field drives Rewind's dropped-series staleness). Advancing the mark is still mandatory: it's the baseline the next genuine read is measured against, so skipping it would make the first post-import chapter emit a delta of hundreds. Rewind counts only reading Maki observed — scrobble-job deltas and the built-in reader. Imported rows carry `PageCount = 0` (filling it would mean opening every archive in the library); the reader writes the real count on first open, and nothing reads it for an already-complete chapter. That zero is also how the `ExternalChapterReadState` migration back-filled `External` on rows written before the flag existed — the reader always stores a real slice length on the write that completes a chapter, so `Completed AND PageCount = 0` identifies an import.
- **`ContinueReadingService` is the only "what do I read next" resolver** — both `GET reader/series/{id}/continue` and Home's two rails go through its `NextForAsync(seriesIds)`, which answers a whole *set* of series in two queries. The per-series endpoint used to materialize every chapter row of the series to order in memory; that ordering has to stay in memory (`Chapter.Number` is a decimal stored as REAL, and one-shots sort last on a null — neither is expressible in SQLite's `ORDER BY`), so the fix was to bound the input, not to push it into SQL. It reads `ChapterProgress` **only**: joining `ReadingState` would both report chapters read that were never opened and multiply rows, since duplicates per `SeriesId` are legal there.
- **`/` is a redirect, not a page.** `StartPageRedirect` (App.tsx) resolves it to the `ui.startpage` setting's target with `<Navigate replace>`, so Home and Library each own a real path (`/home`, `/library`) and nav highlighting needs no special case. Both the Discover and Home options **must** fall back: `AppShellRoutes` bounces `/discover` → `/` without the local MangaBaka DB and `/home` → `/` when Home is disabled, so an unconditional `/` → either is an infinite bounce. Same reason it renders a loader while the setting is in flight rather than defaulting to Home and swapping.
- **Home's sections are user-ordered and individually switchable** (`ui.homesections`, a `HomeLayoutSpec` blob; same never-rename-a-property discipline as `ReaderPrefsSpec`). `HomeLayoutSpec.Merge` runs on every read *and* write and is what makes the setting survive a release that changes the section list: unknown keys are dropped, and keys the stored layout has never seen are **appended enabled** rather than slotted into their canonical position — the user's own ordering is the thing worth preserving. Adding a section = one key in `HomeSections.All` plus a node in `HomePage`'s `sections` record; existing users get it at the bottom, on. Each of `HomePage`'s queries is gated on whether its section is enabled, so a section switched off costs no request. `Enabled = false` turns Home off entirely for people who don't read in Maki (nav drops the tab, `/home` redirects to the library) — and `PUT settings/ui` demotes a `startpage` of "home" to "library" in that case, so the stored setting can't disagree with what the client will actually do.
- **Home's "recently added" rail reads `ChapterFile.DateAdded`, not `StatsEvents`** — the stats log is aggregated to one row per series per UTC day, so it can't name the newest chapter, and its `SeriesId` is set null on delete so deleted series would surface. It scans a fixed `RecentFileScan` newest files off `IX_ChapterFiles_DateAdded` and groups in memory; a `GROUP BY` over the table wouldn't use the index, and a *time window* would leave a dormant library with an empty rail. **Both reading rails use the same shape** — one bounded `RecentProgressScan` walk of `IX_ChapterProgress_UpdatedAt`, grouped in memory — for exactly that reason: an unbounded `GROUP BY SeriesId` over `ChapterProgress` aggregates every read chapter in the library on every landing-page load, which after a Kavita read-status import is the whole back catalogue. Known cosmetic gap: a first-time adopt/import stamps `DateAdded = now` on every file it discovers, so the rail is noisy right after one (rescans don't restamp).
- **OPDS is authenticated by a token in the path, and `ApiKeyMiddleware` carves `/api/v1/opds` out entirely** — reading apps take one feed URL and cannot be told to send a header, so `OpdsController` re-checks the token itself on **every** action (fixed-time compare); the carve-out is a handover, not a hole. The token is `opds.token`, deliberately **not** the instance API key: the URL is pasted into third-party apps, and the API key would hand them the whole management API. Disabled or wrong token answers **404, never 401** — a disabled catalogue shouldn't confirm it exists. Disabling keeps the token (so off/on doesn't break configured readers); `POST settings/opds/token` is the revoke. It serves **OPDS 1.2 (Atom)**, not 2.0: 2.0 is JSON and barely supported, and page streaming only exists as the 1.2-era **OPDS-PSE** extension. Hrefs are **root-relative** on purpose — building absolute ones from `Request.Scheme`/`Host` hands out `http://` links through any TLS-terminating proxy that doesn't rewrite them. `pse:count` must be the chapter's **slice** length, not the archive's, or a reader pages past the end of a volume-backed chapter; that's why `ReaderService.SlicesAsync` exists (one query for a whole feed page, same `SliceBounds` as the reader — never re-derive slicing next to it). Covers reuse `/api/v1/mediacover`, already open for `<img>`. `chapter/{id}/file` serves the **whole** archive for a volume-backed chapter, matching `SliceBounds`' "extra pages are recoverable, missing ones aren't".
- **A path-borne token is a token that lands in request logs**, so `Program.cs` drops `/api/v1/opds` below the minimum level in `UseSerilogRequestLogging` and `OpdsController` logs its own redacted line instead (rejections only — a success line per page image would be noise anyway). Every *other* Maki secret travels as a header or a query parameter, and Serilog's `RequestPath` excludes the query string, so this prefix is the only way one could reach `{ConfigDir}/logs`. Don't "restore" normal request logging for it. `SettingKeys.Opds*` are read through `OpdsAccessService` in **one** query rather than `SettingsService`, which opens a fresh scope and DbContext per key — three round-trips on every page a streaming reader fetches.
- **Chapter identity is `(Number, Language)`, and `ChapterLabel` renders only the number**, so a multi-language series would list two indistinguishable "Ch.1" entries. `OpdsCatalogService.AmbiguousWithoutLanguage` appends `[en]`/`[es]` to exactly the entries that collide *within the feed page being rendered* — per page, not per series, so it needs no extra query and a single-language library never sees a tag.
- **An OPDS page fetch *is* the progress signal** (`opds.trackprogress`, default on) — PSE has no write-back call, so streaming a page writes through the same `ReaderService.SaveProgressAsync` as the built-in reader, which is what makes an OPDS read reach the library, Rewind and the trackers. One deviation: a request for the **last** page of a chapter with **no progress row yet** is stored explicitly `Completed = false`. Several readers fetch the final page up front to size their page bar, and the reader's own "at the last page means finished" rule would mark the chapter read before a word of it was — a sticky flag that also fires a tracker event. Once any earlier page has been seen the normal rule applies. Prefetching readers still inflate the resume position slightly; that's what the setting turns off.
- **Kavita push-back (`reader.pushtokavita`, default off) is gated on `KavitaSeriesId != null`.** The echo — push to Kavita, read it back next tick — is harmless *only* because it lands in the same forward-only row and yields a zero delta. Pushing for an un-adopted native row would land the echo in a **different** row and double-count every chapter into Rewind.
- **Chapter.Number is stored as REAL** — EF Core SQLite can't `ORDER BY` decimal. Identity is `(Number, Language)` with Volume as wildcard; `ChapterSyncService.MergeDuplicates` heals dupes on every refresh (sources disagree on volume info).
- **Monitoring is only `Series.MonitorNewItems`** — there is no series-level `Monitored` flag (dropped in `RemoveSeriesMonitoredFlag`). It was write-once at Add and nothing ever updated it, so "Monitor: none" left every library card still showing the eye. `SeriesDto.Monitored` is now derived (`MonitorNewItems != None`) and can't drift. An unmonitored *add* is just mode `None`.
- **`RefreshMonitoredSeriesJob` skips only Completed series that already hold every chapter MangaBaka lists** — compared against the **highest chapter number**, never the count: sources carry specials/one-shots MangaBaka doesn't count, so a count reads "ahead" (244 vs 240) on a series that's exactly in step. Don't gate refresh on "behind MangaBaka's total" alone — its total lags the sources on active titles (real data: 195 chapters held against a reported 187), so that would stall the ongoing series until MangaBaka caught up.
- **MangaDex delists English chapters of licensed titles** (`isUnavailable: true`). For E2E tests use unlicensed titles (e.g. Hajime no Ippo) — licensed ones (Frieren) have 0 downloadable EN chapters.
- **MangaFire requires FlareSolverr.** `ChallengeAwareFetcher` caches solved cookies per host. Talks to the site's JSON API; FlareSolverr-fetched JSON comes back `<pre>`-wrapped (unwrapped in `MangaFireSource`).
- **MangaPlus (official Shueisha) needs a residential IP** — its JSON API (`jumpg-webapi.tokyo-cdn.com/api`, `?format=json`, no protobuf) bans datacenter IPs with an "Account Banned" error, so it won't work from most cloud hosts. Requests need a random per-process `Session-Token` header. Only the first-few and latest-few chapters per title are free (older ones error at the viewer endpoint). Page images are **XOR-encrypted** with a per-page hex key returned beside each page — carried on `PageRequest.XorKeyHex` and decrypted in `PageDownloader` (the second image-decode mode after MangaFire's `ScrambleOffset`).
- **TCB Scans / MangaPlus / Flame Comics have no search endpoint** — all three match against a cached full catalog (TCB's `/projects`, MangaPlus's `title_list/allV2`, Flame's `/browse`) filtered by normalized title. That TTL cache *and* the three-tier title ranking live in **`SourceCatalog`**; they were copied verbatim into each source before, which is the shape `SourceChapterList` already records the cost of. The cache deliberately treats an **empty** catalog as stale, so a failed fetch doesn't pin "no results" for the whole TTL. TCB's domain rotates on DMCA (`tcbonepiecechapters.com` at time of writing).
- **Flame Comics is read through its Next.js `__NEXT_DATA__` blob**, not its markup — it's a Pages Router app, so `/browse`, `/series/{id}` and `/series/{id}/{token}` each ship the exact server props the page renders from. The `/_next/data/{buildId}/…` JSON endpoints would be tidier but `buildId` changes every deploy and would need discovering first. Consequences: a missing `#__NEXT_DATA__` **throws** rather than returning empty (a Cloudflare interstitial would otherwise read as "this series has no chapters" and silently stall a monitored series), and `/browse` also lists the site's **prose novels**, which key on `novel_id` instead of `series_id` and have no page images — requiring `series_id` is what filters them, and "Omniscient Reader's Viewpoint" is listed both ways, so dropping that check yields a linkable twin that can never download. A chapter's `images` is an **object keyed by page index as a string**, so it must be ordered numerically: sorted as text, page 10 lands between 1 and 2. Series ids are numeric, chapter ids are the chapter's opaque `token`, and the whole chapter list (300+) arrives unpaginated in one request. Page/cover images are on `cdn.flamecomics.xyz` and need no Referer.
- **Webtoons chapter numbers are `episode_no`, not the "Ep. N" in the title.** Those restart every season ("[Season 1] Ep. 1" and "[Season 3] Ep. 1"), which collides on the `(Number, Language)` identity, and CANVAS titles print no episode number at all; `episode_no` is unique, ascending and permanent, and its gaps (pulled episodes) are cosmetic. Series id is `{genre}/{slug}/{titleNo}` and chapter id `{episodeNo}|{episodeSlug}` — only the numeric ids select anything (a wrong genre/slug 301s to the canonical URL) but carrying the path avoids a redirect hop per fetch, **and CANVAS 404s outside the literal `canvas` segment**, so never rebuild the path from a placeholder. Episode lists page **10 at a time with no bulk endpoint** (653-episode Tower of God = 73 requests, ~70 s), and an out-of-range page **clamps to the last one while still rendering the "next" arrow** — so `ListChaptersAsync` stops on the first page that adds no new episode, never on `pg_next` being absent. Two things the site simply won't serve anonymously on web: some Originals cut the public list to ~9 episodes ("Read more episodes on the app!" — Lore Olympus lists 9 of 200+), and mature titles need the consent/age cookies the client sets. Image URLs carry a `?type=q90` transform that costs ~⅔ of the file size; it's stripped for pages *and* covers. `webtoon-phinf.pstatic.net` hotlink-blocks every Referer but webtoons.com's own, so source covers only render through `SearchController`'s `/search/cover` proxy — never hand a raw pstatic URL to an `<img>`.
- **Asura is manhwa/manhua, not manga** — JSON API (`api.asurascans.com`), no descrambling in our impl (the site's tile-scramble isn't applied to the API's `page.url`). Chapter id packs `{slug}|{number}`; premium chapters with 0 pages are skipped.
- **ImageSharp pinned to 3.1.12** (Split License) — 4.x needs a paid build-time license key. Don't upgrade it.
- **Page fetching contract:** `GetPagesAsync` returns `PageRequest`s carrying their own `Headers` end-to-end to the downloader — never fetch without them, and resolve pages at **download** time not enqueue time (MangaDex at-home URLs are short-lived).
- **Scrobbling runs two passes** (`SyncInnerAsync` orchestrates). `KavitaPassAsync` is unchanged in behaviour and writes `ScrobbleSyncState`; `NativePassAsync` covers series the reader tracks that Kavita never reported, resolving remote ids **straight off the `Series` cross-id columns** (the `PushRatingAsync` switch) with no title search and no unmatched-review queue, and writing a **separate** `SeriesScrobbleState` table. Don't merge that into `ScrobbleSyncState`: its key space is shared with `ScrobbleMapping`/`ScrobbleUnmatched`, reverse-derived by title in `SeriesController`, and taken in `ScrobbleController` request bodies. Don't rewrite the push loop to iterate `ReadingStates` either — it carries no `LibraryId` (kills the library filter), `Pages`, `ReadPages` (kills the plan-to-read fallback), `LocalizedName`, or `volumesRaw` (kills boundary refinement), and the push path has **zero test coverage**.
- **Two acquisition protocols** share one `DownloadQueue` (`AcquisitionProtocol` on each item): scraper downloads run through `DownloadWorkerHostedService` (worker count from `download.concurrentchapters`, default 2, read once at startup); torrent releases go through Prowlarr search (`ReleaseService`) → qBittorrent grab → `CompletedDownloadJob` (polls, imports finished downloads). Startup worker-recovery only resets scraper items — torrent items are tracked externally.
- **Settings secrets are stored in plaintext** in the `AppConfig` table — qBittorrent password, Kavita/Prowlarr API keys, MAL client secret, tracker OAuth tokens. This is deliberate (same as Sonarr/Radarr/Prowlarr): an encryption key would have to live beside the DB in the config dir, so it would stop shoulder-surfing but not anyone with file access. The real boundary is filesystem permissions on `{ConfigDir}` — treat the config dir, backups, and any copy of `maki.db` as credential material.
- **Rate limits are shared state.** A 429/503 from any source becomes a `RateLimitException` (`RateLimitDetectingHandler` on the source clients; `RateLimitDetector` recognises it anywhere in an exception chain), and both the downloader (`ChapterDownloadProcessor`) and chapter sync (`ChapterSyncService`) feed it into the one `DownloadQueueService` cooldown. Exception: the `challenge-fetcher` client only converts 429 — **Cloudflare serves its challenge as 503**, and `ChallengeAwareFetcher` must see that status to hand off to FlareSolverr. Retries (`TransientRetryHandler`) deliberately skip 429/503 for the same reason, and only cover GET/HEAD so a qBittorrent add or Kavita scan is never replayed.
- **Backup/restore** (`BackupService`, `RestoreBootstrap`). A backup is a zip of a *consistent* `maki.db` snapshot (SQLite online-backup API — never `File.Copy` the live WAL db) + `config.json` + `manifest.json`, under `{ConfigDir}/backups`. Excludes the big/regenerable state (mangabaka.db, embeddings.db, cache, logs, models, MediaCover). The backup zip holds plaintext secrets — **it is credential material**, same boundary as the DB. The real safety net: migrations are forward-only with no down path, so `Program.cs` takes an `auto` backup **before** `db.Database.Migrate()` whenever there are pending migrations (by the time a bad upgrade shows, the migration already ran). Restore is **staged** into `{ConfigDir}/restore-pending`, not live-swapped; `RestoreBootstrap.ApplyPendingRestore` runs at startup *before* `ConfigFileProvider`/DbContext and swaps the files in, then the app self-exits so a supervisor (Docker `restart:`/systemd) restarts into it — a bare process just stops and the user restarts. Downgrade guard: restoring a backup whose `lastMigration` isn't in this binary's `db.Database.GetMigrations()` is rejected (can't un-apply a newer schema).
- **A globally disabled source never writes to `SourceMapping.Enabled`.** `sources.disabled` (CSV, read only through **`SourceAvailability`**) is a second, independent switch: the whole point is that flipping it back on restores the per-series layout the user had, so nothing may "helpfully" flip the mappings off and back. Every place that asks "is this mapping live?" must therefore test `m.Enabled && !disabled.Contains(m.SourceName)`, and there are **eight** of them — `ChapterSyncService` (loop *and* the `allFetched` count that clears a numbering clash), `ChapterDownloadProcessor` (the 404 fallback *and* `ResolveAcrossMappingsAsync`), `DownloadQueueService.EnqueueChapterAsync`, `CbzLinkService`, `RefreshMonitoredSeriesJob.RefreshableSeriesIdsAsync`, and both `HealthCheckService` checks. Miss one and a switched-off source still downloads, or a series it can no longer serve reports itself healthy. `AutoMatchAsync` skips disabled sources but still numbers `Priority` off the **full** ordered list, so toggling one doesn't renumber the mappings around it and the number stays in step with `SourceMappingController.PriorityForAsync`. The UI greys the per-series switch rather than clearing it; `POST sourcemapping` rejects a disabled source outright rather than storing an inert mapping.
- **Adding a source** = one `ISource` impl in `Maki.Sources` + one `AddSingleton<ISource, ...>()` in `Program.cs`. Return chapters via `SourceChapterList.Normalize` — it dedupes by `(Number, Volume, Language)` and orders ascending; pass a `preferred` picker if the source lists the same chapter twice (scanlation groups, official vs rip).
- **Discover search is dense + lexical + tags, fused by rank** (`SemanticSearcher`). The query is embedded with the bge **query instruction prefix** (passages are indexed bare — bge is asymmetric, dropping the prefix costs recall) and cosined against every vector; that ranking is fused with the FTS5 title index by reciprocal rank fusion, because dense-only search cannot find a title that is an ordinary word ("berserk" ranks Berserk #1 only via the lexical side). Two things measured *against intuition*, so don't "fix" them without re-running the numbers: (1) the embedded text leads with the **title** (`SeriesEmbeddingIndexer.BuildText`) and moving the description first is **worse** — MRR 0.393 → 0.298 on a 12k-series pool — because MangaBaka titles are largely descriptive; (2) the embedded text names only the top 10 non-spoiler core/defining tags, so a query naming a story arc the blurb doesn't state ("hero slowly loses his humanity") won't find it through the dense channel at any model size — that's what the **tag channel** is for: the query is matched against the ~2.5k embedded tag *names* (`tag_vectors`, written by the indexer) and every series is scored on its own packed tags. Two things it must not do, both measured: score at parity with the dense channel (worse than having no tag channel at all — 0.341 → 0.244 MRR), and use `TagMath.Score`, whose cosine divides by the candidate's own tag-vector norm and so buries the richly-tagged classics a search usually wants (Berserk carries 203 tags, Attack on Titan 191). `SemanticSearcher.ScoreAgainstQueryTags` normalizes by the query profile alone — "how much of what was asked for is present" — which took MRR 0.341 → 0.365 and first made Vagabond findable for "a wandering swordsman in feudal Japan".
- **The search vector index is RAM-resident and int8-quantized** (`VectorIndexCache` → `VectorIndex`), ~1 byte per dimension per series (~70 MB of vectors at 96k series × 768, plus the sidecar filter columns). Rebuilt lazily, warmed by `DiscoverCacheWarmJob`, dropped by `EmbeddingIndexJob` after a pass. Re-reading the BLOBs from SQLite per query — what `SemanticRecommender` does for its background job — takes seconds and is far too slow for a search box. Filters are applied **per row before top-K**, not to the result page, so a filtered query isn't truncated to nothing; that means `VectorIndex` duplicates `RecommendationFilters.BuildClause`'s semantics in C# (unknown year/chapter counts fall out of a bounded range, genres ANDed, types ORed) and the two must stay in step. Vector width comes from `EmbeddingOptions.Dimensions`, never from the first row read — during a model change the table holds both widths at once.
- **Rewind stats are an append-only event log** (`StatsEvents` + `ReadingStates`, aggregated by `RewindService`). Reads are Kavita high-water-mark **deltas** captured inside `ScrobbleService.SyncInnerAsync` (`TrackReadingAsync`) — the scrobble tick now runs whenever Kavita is configured, trackers optional; the first sighting of a series is a **silent baseline** (no event) and backwards movement is ignored, so never "fix" either into emitting. Don't derive reads from `ScrobbleSyncState` (per tracker service: double-counts with 2, records nothing with 0). Durable download history = `ChapterFile.DateAdded` (queue rows purge at 30 days); `StatsBackfillService` seeds from it once (`stats.backfillDone` marker). `SeriesRemoved` events carry a genres/tags JSON snapshot because series deletes are hard deletes with the event FK set null. Never purge `StatsEvents` in `HousekeepingJob`.
