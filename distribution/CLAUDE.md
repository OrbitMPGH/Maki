# CLAUDE.md — distribution

Search/recommendation tuning and crowd-graph fetch/publish facts. Migrated out of the root CLAUDE.md so they only load when working here (also relevant to `Maki.Metadata`'s embedding/recommendation code, which these tools tune).

- **Discover search is dense + lexical + tags, fused by reciprocal rank fusion** (`SemanticSearcher`). Query embeds with bge's query instruction prefix (asymmetric model, passages indexed bare). Embedded text leads with title, not description (moving description first measured *worse*, MRR 0.393→0.298). Tag channel matches query against ~2.5k embedded tag names, scored via `ScoreAgainstQueryTags` (normalized by query profile alone — `TagMath.Score`'s own-norm divide buries richly-tagged classics). Query-tag selection floor is relative to that query's own cosine distribution (`SelectQueryTags`), never an absolute number — absolute floors measured as literally never firing.
- **Popularity prior (`SearchTuning.PopularityWeight = 0.025`) is the single biggest lever on trope queries** — measured as an inverted-U optimum (premise MRR 0.373 at weight 0, 0.619 at 0.025, 0.308 at 0.30), not monotone, confirming it's tuned rather than just rewarding fame.
- **`distribution/eval-search.cs` is the tuning instrument** — `eval-embeddings.cs` scores the model in isolation and never runs the fusion (missed the tag channel contributing nothing for months). Weights live in `SearchTuning`, overridable via CLI. Gotcha: file-based app caches its build under `%TEMP%\dotnet\runfile` — delete when comparing `default` against an edited default.
- **Vector index is RAM-resident, int8-quantized** (`VectorIndexCache`, ~93MB for 95k×1024). Filters apply per-row **before** top-K, not to the result page (duplicates `RecommendationFilters.BuildClause` logic in C#, must stay in step). Tags are filtered in-index too, not post-rank (post-rank could only delete rows, never surface a tag-matching one the channels missed).
- **Query vector quantized once per search, not per row** (`EmbeddingMath.QuantizeQuery`) — avoids widening every row into a float scratch buffer.
- **Recommendation retrieval is multi-seed**: queries the centroid plus individual representative seeds (greedy farthest-point sampling), fused by RRF for *membership* only — final score keeps the best raw cosine across queries, not the RRF rank, since cosines here are already calibrated and comparable (unlike search's genuinely incomparable dense/lexical/tag channels).
- **Diversity dial defaults to 0** (`EmbeddingMath.SelectDiverse`, MMR) — plain relevance order by default so shipping the feature doesn't silently reorder existing recommendations.
- **The co-recommendation channel reads `reco-edges.db`, never `reco-graph.db`.** `distribution/fetch-reco-graph.cs` writes both: the second is its resumable working state (per-provider directed rows plus `fetch_state` bookkeeping), the first is the folded, VACUUMed, both-directions-indexed `pair` table that ships. `RecoGraphCache` loads it whole into a CSR adjacency (~3MB for the 113k-pair artifact) rather than `ATTACH`ing it, since the lookup is per-seed on the recommendation hot path. **An absent file is the normal state, not an error** - `GetAsync` returns null, the channel contributes nothing, and results are byte-identical to before the feature existed. Nothing publishes an artifact yet, so that is what every install currently does.
- **Two crowd channels, not one, and they must not be merged.** `RecoGraphCache`/`reco-edges.db` is what readers *said* (submitted "if you liked X, try Y" pairs, weight = vote count); `CoReadCache`/`coread-edges.db` is what they *did* (co-occurrence across finished AniList lists, weight = strength). They disagree on 73% of the pairs both cover, so agreement is real corroboration and `HybridScore` adds both terms rather than combining or maxing them. Separate kill-switches (`recommendations.cograph`, `recommendations.coread`), separate artifacts installed independently, both folded into the pool cache keys - one switch would make "turn off the noisy one" inexpressible.
- **`CoReadScorer` has no `log1p` and no degree penalty, and that is the point of it existing.** A co-read strength is already `cooccurrence / sqrt((users(a)+k)(users(b)+k))` - both endpoints' popularity divided out at build time. Applying the vote graph's degree penalty on top is the double normalization measured on that graph at `DegreePenalty = 0.5`, where the channel inverted into single-edge obscurities. `log1p` is there because votes span 1 to 6008; a strength is a bounded ratio and `log1p` of it is nearly itself. Reusing `RecoGraphScorer` here is the tempting mistake and there is a test pinning it (`DegreeDoesNotPenalize_BecauseTheStrengthAlreadyDividedByPopularity`).
- **`PairGraphIndex` is the shared CSR both graphs load into**, with a `float` weight because one stores votes and the other strengths; `PairGraphBuilder.Build` is the single copy of the fold. It was `RecoGraphIndex` and still cannot be called `RecoGraph` - a type cannot share its namespace's name.
- **`MangaBakaRecommendation.CoRead` now means the co-read graph; the vote graph's flag is `CoRecommended`.** The vote channel shipped holding the name `CoRead` before a real co-read graph existed. Both flags are the only "why" fields not derived from what a series says about itself, and which one vouched for a pick is a materially different explanation.
- **The two crowd channels' intensity dials are opposite ones, measured.** On the vote graph `MaxInjected` moves everything and `Weight` almost nothing; on the co-read graph `Weight` moves everything and `MaxInjected` is **inert** - 25, 50, 100, 200 and 400 all return a byte-identical pool, because fewer than 25 candidates ever clear `MinInjectedScore`. The reason is what each channel does: the vote graph earns its keep by *injecting* candidates retrieval never pooled, the co-read graph mostly *re-ranks* ones already in the pool (with injection fully off it still accounts for 31% of picks). Do not carry a tuning intuition from one to the other.
- **`eval-reco.cs spread` reported the co-read channel improving the pool while it was turning it into a popularity chart.** Distinct genres/tags rose and cohesion fell at every weight tested - a set of famous titles spans plenty of genres and tags. The `pop` column (median popularity rank of the picks) was added because of this and is the one that caught it: 9529 with no crowd channels, 8196 with the vote graph, 7135 at the shipping co-read weight, 5465 at 0.6, 3584 at 2.0. **Read `pop` together with the diversity columns, never the diversity columns alone.**
- **Per-edge normalization does not stop a collaborative channel skewing popular; summing over seeds does it.** Each co-read strength is already divided by both endpoints' popularity at build time, but a famous title is simply *reached from more seeds*: measured on a real library, candidates in the catalogue's top 200 came from 2.00 seeds on average against 1.02 for those past rank 20,000. A degree penalty does not fix it either (top-40 median popularity rank 117 to 173 at 0.25, 268 at 0.5, all still inside the top 0.2%) and would be a second normalization on an already-normalized weight. `CoReadTuning.Weight = 0.2` is the lever that works; 0.1 to 0.2 is a plateau at ~31% of picks, and 0.3 buys one more point of share for 667 ranks of skew.
- **`CoReadTuning.MinStrength` stays 0 and is confirmed inert-or-harmful.** The artifact is already filtered at build time (`minSupport` 3, `topPerItem` 60), so there is no noise floor left to cut: 0.005 is indistinguishable from 0, 0.02 cuts the channel's share of picks from 38% to 20%, and 0.15 makes the pool byte-identical to the channel being off. Kept as a sweepable knob only.
- **eval-reco variant prefixes: `graph` for `RecoGraphTuning`, `coread` for `CoReadTuning`.** Shorthands `nograph`, `nocoread` and `nocrowd` switch off one or both. The two key namespaces are disjoint today; a key that collided would need the prefix dispatch rewritten rather than extended. The `%TEMP%\dotnet\runfile` cache gotcha bites here in particular - editing a default in `src/` and re-running the harness scores the **previous** build, silently.
- **Both fetchers write to `.artifacts/`, not the config directory.** They are build products of distribution tools, git-ignored and hand-published, in the same place `build-embeddings.cs` and the `eval-*.cs` tools already put theirs. Only the *installed* `reco-edges.db` lives in `{ConfigDir}`, put there by `RecoGraphInstaller`. Both scripts fail fast when the default artifacts path is empty but a legacy file sits in the config directory, because silently starting a resumable multi-day fetch from zero is worse than an error; the check is skipped when `--work`/`--graph` was passed explicitly.
- **One packer and one publish script serve both graphs** (`distribution/graph-artifact.cs <reco|coread>`, `publish-graph.ps1 -Graph reco|coread|both`). Everything but the table-level validation is identical, and the half that would drift between two copies is the half deciding what is safe to publish. The packer's personal-data check runs **first**, before `quick_check` and before the shape check, and exits without writing anything: it is the last gate before those rows would leave the machine. Tags are hardcoded per graph and must match the `ReleaseTag` constants on `RecoGraphInstaller` and `CoReadInstaller`, which is what clients poll.
- **`CoReadInstaller` refuses any file carrying `user_entry`/`user_state`/`pending_user`, and that check is not about correctness.** `coread-graph.db` (the fetcher's working state, 6.1M per-user reading rows) and `coread-edges.db` (the aggregate that ships) differ by four characters and sit in the same folder, so publishing the wrong one is a privacy incident rather than a broken feature. The check runs **before** the `pair`-table shape check, because the likelier accident is a file that has both, and it is not skipped by `force` - "Download now" is not a way past it. Verified end to end: an archive with a valid manifest and matching SHA-256 was refused and the existing install left untouched.
- **`strength IS NULL OR NOT (strength > 0)`, never `strength <= 0`.** SQLite has no NaN - it stores one as NULL - so a strength that went wrong upstream arrives missing, and a three-valued comparison against NULL yields NULL, which a `CASE WHEN` falls through as false. The naive form passes exactly the rows it is meant to catch. (The `Microsoft.Data.Sqlite` driver refuses to bind NaN at all, which is how the first version of the test found this.)
- **The three artifact jobs are staggered 3/4/5 minutes after startup** (prebuilt index, reco graph, co-read graph) so a fresh install does not have them competing for bandwidth. Co-read goes last: at ~16 MB compressed it is the largest by an order of magnitude and the one recommendations least need.
- **`RecoGraphInstaller` is the only way an install gets the graph**, unlike `PrebuiltIndexInstaller` whose artifact is a shortcut around work the install could do itself. Building this one locally means days of paced requests with a tool that does not ship with the app, so a missing artifact logs at debug, never warning - it is the normal state of every install until something is published. `IsEnabledAsync` is tied to `recommendations.cograph`: no point downloading a file nothing may read.
- **`ValidateStaged` checks for a `pair` table by name**, because `reco-graph.db` and `reco-edges.db` are both SQLite files with near-identical names in one folder and installing the wrong one produces an empty graph rather than an error. It also rejects self-pairs (a seed scoring against itself) and negative votes (`log1p` of a negative is NaN, which propagates through every score it touches). `distribution/graph-artifact.cs` refuses the same things at publish time, plus a `meta` table whose `providers` disagrees with the votes actually present.
- **The artifact's `meta.providers` is derived from the edges, never hardcoded.** `RecoGraphCache` decides whether to rescale a provider's votes by whether that provider appears at all, so an AniList-only run claiming MAL data would leave a scale at zero and silently drop the term.
- **A hand-placed `reco-edges.db` carries no install marker and gets replaced by the first download.** `recommendations.cographgeneratedat` is the installer's own record, not read back out of the file, so "absent" means "nothing we installed" and the published artifact wins. Freshness is judged against that marker alone; `force` skips it but never the validation.
- **Votes are stored raw in the graph, not pre-compressed.** `RecoGraphTuning.MinVotes` is a floor the eval sweeps, and a floor cannot be applied to a number already through `log1p` at load time. The few hundred logarithms a request needs cost nothing next to baking tuning into the index.
- **MAL has no working API; `fetch-reco-graph.cs` scrapes its pages.** Jikan has answered 504 "failed to connect to MyAnimeList" for months, the same outage that already pushed `MalReviewClient` onto MAL's HTML. Recommendations come from `manga/{id}/_/userrecs` (the `_` is a placeholder for the title slug MAL's routing wants but never checks, exactly the trick `MalReviewClient` uses). Each recommendation carries a `/recommendations/manga/{a}-{b}` permalink holding both ids and one "Recommended by <user>" line per submitter, so the **vote count is a count of those lines** - there is no number on the page to read. No pagination. Send a browser User-Agent and accept gzip: pages are ~145KB (610KB for Berserk, and even a 404 is 40KB), so an ungzipped full pass moves ~10GB. 30 req/min default, because MAL publishes no limit and bans IPs, and there is no second route to this data.
- **AniList and MAL votes are different units and must never be added raw.** AniList is a net upvote score over a much larger population and reaches the thousands; MAL is a count of submitters and reaches the dozens. Berserk to Vinland Saga is **3200 on AniList, 29 on MAL**. Added raw, MAL is arithmetically invisible wherever AniList already has the pair (`log1p(3200)` vs `log1p(3243)` differ by 0.1%), which silently discards the entire point of the second provider. `RecoGraphCache.ReadPairs` divides each provider by **its own 90th percentile taken across the artifact** - a high percentile because the median is 1-2 votes on both and would calibrate on noise, a percentile rather than the max because the max is one outlier each. A single-provider artifact leaves the other scale at 0 and its term drops out, which is today's state.
- **`--top` is the honest way to run MAL.** Only 7,078 series carry a MAL id and no AniList one, so MAL is not mainly a coverage play - it is a second independent crowd voting on pairs the first already has. If the goal is reaching more titles, finishing the AniList run is far cheaper per title.
- **AniList's rate limit is per request, not per field, and the live ceiling is 30/min not the documented 90.** `X-RateLimit-Limit` reads 30; `Pacer.Observe` clamps to 0.8 of it and never revises up, so raising `--rpm` on an AniList fetcher is a no-op. Measured with a cleared window, a trivial one-field query got 429 after 20 requests while a 20-alias query ran 45 without one, so aliased batching is a free multiplier and is the only AniList lever there is. `fetch-coread-graph.cs` batches user lists this way (`--batch`, default 20, capped 25).
- **A batch containing one private AniList user 404s the whole request and nulls *every* alias.** Not just the offender: a user with 356 entries came back null purely for sharing a request with a private account. Believing those nulls files all twenty as "private", which `RecordUser` treats as settled and never retries, so the run silently keeps a fraction of what it fetched. `FetchUserLists` therefore never trusts a null above a batch of one. Recovery reads the offender's identity out of each error's `locations[].column`, matched against the alias columns recorded while the query was built - GraphQL requires the location, and AniList emits one `Private User` error per offending alias. Only `status: 404` errors are believed; anything else falls back to halving, because filing a transient fault as "private" dequeues somebody permanently. Halving alone was measured at twelve requests to resolve twenty users at a 3% private rate, barely better than not batching.
- **The co-read fetch is latency-bound, not budget-bound.** A 20-alias list query takes 5-13s, well over the pacer's 2.5s spacing, so a serial loop issues far fewer than the 24 req/min it is allowed. Batching alone moved measured throughput 24 to ~50 users/min; the remaining headroom is concurrent requests against the same shared `Pacer`, not a higher `--rpm`.
- **`fetch-coread-graph.cs build` accumulates co-occurrence in hash partitions, not one dictionary.** At 8,800 users the nested loop generates ~88M pair increments over ~39M distinct pairs, and 76% of those are seen exactly once and dropped by `minSupport` moments later. One dictionary holding all of them is several GB of random-access hash table that doubles and rehashes itself twenty-odd times on the way up; the measured symptom was a build that printed nothing for over half an hour. It now runs one pass per partition (`PairsPerPass = 12M`, count rounded to a power of two so the test is a mask), keeping only keys whose low bits match - the key is two dense indices, so its own low bits are already uniform and need no re-hash. **Memory is bounded by `PairsPerPass` however many users get fetched**; re-walking the cheap nested loop K times costs seconds. Two other fixes went with it: one `Dictionary<long, PairStat>` updated through `GetValueRefOrAddDefault` instead of two dictionaries and four lookups per pair, and each user's dense slots resolved once instead of twice per pair. 4m21s end to end, printing per pass.
- **A long silent loop in a distribution tool is itself the bug.** Nothing distinguished "thrashing" from "hung" from "nearly done" in that build, which is why it read as broken. Every phase that can run for minutes prints now, including the write.
- **Co-read coverage is what scale buys, measured.** At 108 users only 2 of a 14-series library had any co-read neighbour; at 8,828 users it is 12 of 14, over 31,570 series and 1.18M pairs (37 MB, far larger than the 3 MB recommendation graph, because `topPerItem` keeps up to 60 neighbours per series). The export ships `pair` and `meta` only - **`user_entry` is personal data and must never leave the working database**.
- **`RecoGraphScorer` normalizes by the maximum, never min-max.** A min-max would floor the weakest real candidate at 0, and 0 is exactly what `SemanticRecommender` reads as "no co-recommendation evidence" - which is what sets the `CoRead` flag and what the injection gate is a threshold on. The two states must stay distinguishable.
- **`MaxInjected`, not `Weight`, is the channel's intensity dial** - which is not what you would guess. Measured over `eval-reco.cs spread`'s 24 synthetic profiles, dropping `Weight` 0.60 to 0.10 moved the graph's share of picks only 82% to 70%; moving the injection cap moves it 0% (off) to 28% (50) to 37% (100) to 48% (200), before the corroboration gate below trims it further. A candidate that is in the pool at all is usually competitive on cosine anyway.
- **The graph channel does not collapse into a popularity chart, measured.** Every injection cap tested *improves* the over-fit metrics against baseline (more distinct genres and tags, lower mean pairwise cohesion). The cap ships at 100 for a different reason: at 300 barely a third of the pre-channel pool survives, and a feature on by default should refine an existing user's recommendations rather than replace them.
- **The corroboration gate costs measurable diversity and is kept anyway.** On the synthetic profiles, ungated injection scores strictly better on every over-fit metric (tags 689 against 620, cohesion 0.610 against 0.632). It is gated because `spread` measures how concentrated a pool is and cannot see a single under-evidenced title ranked first, which is the failure that actually reached a real user's recommendations. When the aggregate metric and reading the real output disagree here, the output wins - and no eval-level test would catch this regressing.
- **`DegreeSmoothing` exists because `degree^penalty` at degree 1 is exactly 1.0, i.e. no penalty.** Without it a series with a single edge outranked well-connected ones carrying an order of magnitude more votes. **Degree-1 nodes are 32% of the graph and stay 32% when the fetch completes** - measured across the partial and complete artifacts - so this is structural, not a sampling artifact of an unfinished fetch. Read the constant as a prior that a title has more neighbours than anyone bothered to record, which is permanently true: a pair count reflects how many people submitted a recommendation, not how related two series are.
- **Injection requires corroboration (`MinInjectedScore`), and that gate is load-bearing.** Pool entry is a bigger privilege than it looks: `FuseByRank` pools on cosine alone while `HybridScore` ranks on genre, tag, author and quality too, so an injected row can top the final ranking without ever being near the cosine top-200. On the real library an obscure one-shot with a single 26-vote edge to one seed came back at **rank 1**, having been absent from the entire 200-item pool with the channel off. Requiring 0.60 of the best candidate's normalized score stops it (it scored 0.55) and lifts pool overlap from 0.43 to 0.57. There was previously a separate lower cosine floor for graph-backed rows; it was **measured byte-identical at 0.15, 0.25 and 0.30** across both the synthetic profiles and the real library, so it never admitted anything and was removed rather than kept as a knob whose documented purpose the data contradicted.
- **Graph injection reuses `Scan`'s negative-infinity sentinel rather than re-testing filters.** `Scan` writes `float.NegativeInfinity` into every channel for a row that failed the filter plan, the exclusion set or the required tags, so `InjectGraphCandidates` testing channel 0 for it is the same predicate `FuseByRank` uses. Duplicating `RecommendationFilters` logic there would be a third copy to keep in step, and a way to smuggle rows past a filter.
- **`recommendations.cograph` is a kill-switch with an endpoint and deliberately no UI**, same as `recommendations.tasteweighting`: it switches a derivation off at deployment level rather than expressing a taste. It is read per request *and* folded into `RecommendationService`'s pool cache key and `SimilarSeriesService`'s entry key - both halves are needed, since a channel that changes results without changing the key sits invisible behind a 12-hour hit, and a key that moves without the read being wired is the trap `recommendations.prebuiltenabled` already fell into (written by `SettingsController`, read by nothing).
- **The channel reaches the series-page "More like this" rail too**, because `SimilarSeriesService` shares `SemanticRecommender.GetSimilarAsync`. That is wanted - a single seed's graph neighbours *are* "readers also liked" - but it means the rail's cache key had to gain the flag as well.
- **`RecoGraphIndex` is named that, not `RecoGraph`, because a type cannot share its namespace's name.** Anything inside `Maki.Metadata.*` resolves bare `RecoGraph` to the namespace, so the class compiled fine in `Maki.Metadata.Embedding` (which only names `RecoGraphCache`/`Scorer`/`Tuning`) and broke the moment a test referred to the type itself.
- **Seed weights are rating-first, behaviour-second** (`TasteWeights`/`TasteTuning` in `Maki.Core/Recommendations`, aggregated by `BehavioralTasteService`, killed by `recommendations.tasteweighting`). Ratings are sparse, so an unrated seed gets a weight derived from completed `ChapterProgress` + `ReadSeconds` + recency; `RatingBlendAlpha = 1` means a rated seed keeps `rating / 5.0` untouched. Three traps: **`Seconds == 0` means "unknown", not "no engagement"** — Kavita imports and OPDS never record time, so the engage channel is *dropped and renormalized* rather than scored zero, or an imported library sinks to `MinWeight` and the feature is worse than uniform; recency is computed against a **date**, not an instant, or the 12-hour pool cache dies on every chapter read (the cache key renders weights at one decimal, which is where that stability comes from); **`WeightQuantum` must stay well below that**, because `SemanticRecommender.PickRepresentativeSeeds` orders seeds by weight and breaks ties with `ThenBy(id)` — at 0.1 two series scoring 1.6533 and 1.7215 both became 1.7 and the more thoroughly read one lost the seed slot that starts the farthest-point walk to the lower catalogue id, which flipped 64% of the top 40 on a real 92-series library; and `RecencyFloor` sits *above* `NeutralSignal` on purpose, so an old favourite doesn't decay into "never opened". `IncognitoMode.Full` has to be excluded by hand here (its `ChapterProgress` rows exist, only the `StatsEvent`s are suppressed) — same gate as `UserMetricsService.FullyReadAsync`.
- **`RecommendationService` caches N pools, not one.** Behavioural weights make every user's cache key distinct, so the old single `_cacheKey`/`_cached` pair thrashed between users on a multi-user instance and recomputed a full index scan per request.
- **`distribution/eval-reco.cs` is the recommendation instrument, and its two modes claim different things.** `spread` builds synthetic narrow-and-deep profiles and reports pool concentration (distinct genres/authors/tags, mean pairwise cosine) against a `uniform` baseline — no labels, runs on any install, and it's what the over-fit risk is actually measured against. `loo` leave-one-outs the *installed* reading history: real behaviour, n = one library, a direction and a tripwire only — at the default `--limit` a 90-ish-series library returns all zeros, which the tool labels **NOT A RESULT** rather than letting a table of zeros read as a tie. Neither is `eval-search.cs`, which never touches seed weighting.
