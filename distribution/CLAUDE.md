# CLAUDE.md — distribution

Search/recommendation tuning and crowd-graph fetch/publish facts. Migrated out of the root CLAUDE.md so they only load when working here (also relevant to `Maki.Metadata`'s embedding/recommendation code, which these tools tune).

- **Discover search is dense + lexical + tags, fused by reciprocal rank fusion** (`SemanticSearcher`). Query embeds with bge's query instruction prefix (asymmetric model, passages indexed bare). Embedded text leads with title, not description (moving description first measured *worse*, MRR 0.393→0.298). Tag channel matches query against ~2.5k embedded tag names, scored via `ScoreAgainstQueryTags` (normalized by query profile alone — `TagMath.Score`'s own-norm divide buries richly-tagged classics). Query-tag selection floor is relative to that query's own cosine distribution (`SelectQueryTags`), never an absolute number — absolute floors measured as literally never firing.
- **Popularity prior (`SearchTuning.PopularityWeight = 0.025`) is the single biggest lever on trope queries** — measured as an inverted-U optimum (premise MRR 0.373 at weight 0, 0.619 at 0.025, 0.308 at 0.30), not monotone, confirming it's tuned rather than just rewarding fame.
- **`distribution/eval-search.cs` is the tuning instrument** — `eval-embeddings.cs` scores the model in isolation and never runs the fusion (missed the tag channel contributing nothing for months). Weights live in `SearchTuning`, overridable via CLI. Gotcha: file-based app caches its build under `%TEMP%\dotnet\runfile` — delete when comparing `default` against an edited default.
- **Vector index is RAM-resident, int8-quantized** (`VectorIndexCache`, ~93MB for 95k×1024). Filters apply per-row **before** top-K, not to the result page (duplicates `RecommendationFilters.BuildClause` logic in C#, must stay in step). Tags are filtered in-index too, not post-rank (post-rank could only delete rows, never surface a tag-matching one the channels missed).
- **Query vector quantized once per search, not per row** (`EmbeddingMath.QuantizeQuery`) — avoids widening every row into a float scratch buffer.
- **Recommendation retrieval is multi-seed**: queries the centroid plus individual representative seeds (greedy farthest-point sampling), fused by RRF for *membership* only — final score keeps the best raw cosine across queries, not the RRF rank, since cosines here are already calibrated and comparable (unlike search's genuinely incomparable dense/lexical/tag channels).
- **Diversity dial defaults to 0** (`EmbeddingMath.SelectDiverse`, MMR) — plain relevance order by default so shipping the feature doesn't silently reorder existing recommendations.
- **The co-recommendation channel reads `reco-edges.db`, never `reco-graph.db`.** `distribution/fetch-reco-graph.cs` writes both: the second is its resumable working state (per-provider directed rows plus `fetch_state` bookkeeping), the first is the folded, VACUUMed, both-directions-indexed `pair` table that ships. `RecoGraphCache` loads it whole into a CSR adjacency (~3MB for the 113k-pair artifact) rather than `ATTACH`ing it, since the lookup is per-seed on the recommendation hot path. **An absent file is the normal state, not an error** - `GetAsync` returns null, the channel contributes nothing, and results are byte-identical to before the feature existed. Nothing publishes an artifact yet, so that is what every install currently does.
- **Two crowd channels, not one, and they must not be merged.** `RecoGraphCache`/`reco-edges.db` is what readers *said* (submitted "if you liked X, try Y" pairs, weight = vote count); `CoReadCache`/`coread-edges.db` is what they *did* (co-occurrence across finished AniList lists, weight = strength). They disagree on 73% of the pairs both cover, so agreement is real corroboration and `HybridScore` adds both terms rather than combining or maxing them. Separate kill-switches (`recommendations.cograph`, `recommendations.coread`), separate artifacts installed independently, both folded into the pool cache keys - one switch would make "turn off the noisy one" inexpressible.
- **`CoReadScorer` has no `log1p` and no degree penalty, and that is the point of it existing.** A co-read strength is already `cooccurrence / sqrt((users(a)+k)(users(b)+k))` - both endpoints' popularity divided out at build time. Applying the vote graph's degree penalty on top is the double normalization measured on that graph at `DegreePenalty = 0.5`, where the channel inverted into single-edge obscurities. `log1p` is there because votes span 1 to 6008; a strength is a bounded ratio and `log1p` of it is nearly itself. Reusing `RecoGraphScorer` here is the tempting mistake and there is a test pinning it (`DegreeDoesNotPenalize_BecauseTheStrengthAlreadyDividedByPopularity`).
- **`PairGraphIndex` is the shared CSR both graphs load into**, with a `float` weight because one stores votes and the other strengths; `PairGraphBuilder.Build` is the single copy of the fold. It was `RecoGraphIndex` and still cannot be called `RecoGraph` - a type cannot share its namespace's name.
- **`MangaBakaRecommendation.CoRead` now means the co-read graph; the vote graph's flag is `CoRecommended`.** The vote channel shipped holding the name `CoRead` before a real co-read graph existed. Both flags are the only "why" fields not derived from what a series says about itself, and which one vouched for a pick is a materially different explanation.
- **Neither crowd channel is dialled by its injection cap; both turn on a threshold.** This was the reverse once, and the reversal is the point. The vote graph's dial was `MaxInjected` (0%/28%/37%/48% of picks at off/50/100/200) and the co-read graph's was `Weight`. On the denser artifacts (134,818 vote pairs, 1.58M co-read pairs) `MaxInjected` went **inert on both** - 50, 100, 150 and 200 return a byte-identical pool for the vote graph, and 25 through 400 always did for co-read - because fewer candidates clear `MinInjectedScore` than the cap would ever admit. The live dials are now `RecoGraphTuning.MinInjectedScore` (co-rec share 11% injection-off, 28% at 0.50, 23% at 0.60, 18% at 0.70, 15% at 0.80) and `CoReadTuning.Weight`. **A cap that is inert today was load-bearing on a smaller artifact and may be again** - re-sweep both after a fetch, never carry the intuition forward.
- **`eval-reco.cs spread` reported the co-read channel improving the pool while it was turning it into a popularity chart.** Distinct genres/tags rose and cohesion fell at every weight tested - a set of famous titles spans plenty of genres and tags. The `pop` column (median popularity rank of the picks) was added because of this and is the one that caught it: 9529 with no crowd channels, 8196 with the vote graph, 7135 at the shipping co-read weight, 5465 at 0.6, 3584 at 2.0. **Read `pop` together with the diversity columns, never the diversity columns alone.**
- **Per-edge normalization does not stop a collaborative channel skewing popular; summing over seeds does it.** Each co-read strength is already divided by both endpoints' popularity at build time, but a famous title is simply *reached from more seeds*: measured on a real library, candidates in the catalogue's top 200 came from 2.00 seeds on average against 1.02 for those past rank 20,000. A degree penalty does not fix it either (top-40 median popularity rank 117 to 173 at 0.25, 268 at 0.5, all still inside the top 0.2%) and would be a second normalization on an already-normalized weight. `CoReadTuning.Weight` is the lever that works. It shipped at 0.2 against 8,828 readers and is **0.15 against 19,667**: the coefficient did not stop being right, the extra coverage made it louder, and 0.15 on the bigger artifact reproduces what 0.2 did on the smaller one.
- **`CoReadTuning.MinStrength` stays 0 and is confirmed inert-or-harmful.** The artifact is already filtered at build time (`minSupport` 3, `topPerItem` 60), so there is no noise floor left to cut: 0.005 is indistinguishable from 0, 0.02 cuts the channel's share of picks from 38% to 20%, and 0.15 makes the pool byte-identical to the channel being off. Kept as a sweepable knob only.
- **eval-reco variant prefixes: `graph` for `RecoGraphTuning`, `coread` for `CoReadTuning`.** Shorthands `nograph`, `nocoread` and `nocrowd` switch off one or both. The two key namespaces are disjoint today; a key that collided would need the prefix dispatch rewritten rather than extended. The `%TEMP%\dotnet\runfile` cache gotcha bites here in particular - editing a default in `src/` and re-running the harness scores the **previous** build, silently.
- **Both fetchers write to `.artifacts/`, not the config directory.** They are build products of distribution tools, git-ignored and hand-published, in the same place `build-embeddings.cs` and the `eval-*.cs` tools already put theirs. Only the *installed* `reco-edges.db` lives in `{ConfigDir}`, put there by `RecoGraphInstaller`. Both scripts fail fast when the default artifacts path is empty but a legacy file sits in the config directory, because silently starting a resumable multi-day fetch from zero is worse than an error; the check is skipped when `--work`/`--graph` was passed explicitly.
- **One packer and one publish script serve both graphs** (`distribution/graph-artifact.cs <reco|coread>`, `publish-graph.ps1 -Graph reco|coread|both`). Everything but the table-level validation is identical, and the half that would drift between two copies is the half deciding what is safe to publish. The packer's personal-data check runs **first**, before `quick_check` and before the shape check, and exits without writing anything: it is the last gate before those rows would leave the machine. Tags are hardcoded per graph and must match the `ReleaseTag` constants on `RecoGraphInstaller` and `CoReadInstaller`, which is what clients poll.
- **`CoReadInstaller` refuses any file carrying `user_entry`/`user_state`/`pending_user`, and that check is not about correctness.** `coread-graph.db` (the fetcher's working state, 6.1M per-user reading rows) and `coread-edges.db` (the aggregate that ships) differ by four characters and sit in the same folder, so publishing the wrong one is a privacy incident rather than a broken feature. The check runs **before** the `pair`-table shape check, because the likelier accident is a file that has both, and it is not skipped by `force` - "Download now" is not a way past it. Verified end to end: an archive with a valid manifest and matching SHA-256 was refused and the existing install left untouched.
- **`strength IS NULL OR NOT (strength > 0)`, never `strength <= 0`.** SQLite has no NaN - it stores one as NULL - so a strength that went wrong upstream arrives missing, and a three-valued comparison against NULL yields NULL, which a `CASE WHEN` falls through as false. The naive form passes exactly the rows it is meant to catch. (The `Microsoft.Data.Sqlite` driver refuses to bind NaN at all, which is how the first version of the test found this.)
- **The three artifact jobs are staggered 3/4/5 minutes after startup** (prebuilt index, reco graph, co-read graph) so a fresh install does not have them competing for bandwidth. Co-read goes last: at ~16 MB compressed it is the largest by an order of magnitude and the one recommendations least need.
- **`RecoGraphInstaller` is the only way an install gets the graph**, unlike `PrebuiltIndexInstaller` whose artifact is a shortcut around work the install could do itself. Building this one locally means days of paced requests with a tool that does not ship with the app, so a missing artifact logs at debug, never warning - it is the normal state of every install until something is published. `IsEnabledAsync` is tied to `recommendations.cograph`: no point downloading a file nothing may read.
- **`ValidateStaged` checks for a `pair` table by name**, because `reco-graph.db` and `reco-edges.db` are both SQLite files with near-identical names in one folder and installing the wrong one produces an empty graph rather than an error. It also rejects self-pairs (a seed scoring against itself) and negative votes (`log1p` of a negative is NaN, which propagates through every score it touches). `distribution/graph-artifact.cs` refuses the same things at publish time, plus a `meta` table whose `providers` disagrees with the votes actually present.
- **The artifact's `meta.providers` is derived from the edges, never hardcoded.** `RecoGraphCache` decides whether to rescale a provider's votes by whether that provider appears at all, so an AniList-only run claiming MAL data would leave a scale at zero and silently drop the term.
- **A hand-placed `reco-edges.db` carries no install marker and gets replaced by the first download.** `recommendations.cographgeneratedat` is the installer's own record, not read back out of the file, so "absent" means "nothing we installed" and the published artifact wins. Freshness is judged against that marker alone; `force` skips it but never the validation.
- **Votes are stored raw in the graph, not pre-compressed.** `RecoGraphTuning.MinVotes` is a floor the eval sweeps, and a floor cannot be applied to a number already through `log1p` at load time. The few hundred logarithms a request needs cost nothing next to baking tuning into the index.
- **MAL has no working API; `fetch-reco-graph.cs` scrapes its pages.** Jikan has answered 504 "failed to connect to MyAnimeList" for months, the same outage that already pushed `MalReviewClient` onto MAL's HTML. Recommendations come from `manga/{id}/_/userrecs` (the `_` is a placeholder for the title slug MAL's routing wants but never checks, exactly the trick `MalReviewClient` uses). Each recommendation carries a `/recommendations/manga/{a}-{b}` permalink holding both ids and one "Recommended by <user>" line per submitter, so the **vote count is a count of those lines** - there is no number on the page to read. No pagination. Send a browser User-Agent and accept gzip: pages are ~145KB (610KB for Berserk, and even a 404 is 40KB), so an ungzipped full pass moves ~10GB. 30 req/min default, because MAL publishes no limit and bans IPs, and there is no second route to this data.
- **AniList and MAL votes are different units and must never be added raw.** AniList is a net upvote score over a much larger population and reaches the thousands; MAL is a count of submitters and reaches the dozens. Berserk to Vinland Saga is **3200 on AniList, 29 on MAL**. Added raw, MAL is arithmetically invisible wherever AniList already has the pair (`log1p(3200)` vs `log1p(3243)` differ by 0.1%), which silently discards the entire point of the second provider. `RecoGraphCache.ReadPairs` divides each provider by **its own 90th percentile taken across the artifact** - a high percentile because the median is 1-2 votes on both and would calibrate on noise, a percentile rather than the max because the max is one outlier each. A single-provider artifact leaves the other scale at 0 and its term drops out. That was the state until MAL reached **29,174 pairs (21,575 of them AniList has no edge for)**; both scales are now live and measured stable, AniList p90 = 12 and MAL p90 = 4 on both the 4,879- and 29,174-pair artifacts.
- **`--top` is the honest way to run MAL.** Only 7,078 series carry a MAL id and no AniList one, so MAL is not mainly a coverage play - it is a second independent crowd voting on pairs the first already has. If the goal is reaching more titles, finishing the AniList run is far cheaper per title.
- **AniList's rate limit is per request, not per field, and the live ceiling is 30/min not the documented 90.** `X-RateLimit-Limit` reads 30; `Pacer.Observe` clamps to 0.8 of it and never revises up, so raising `--rpm` on an AniList fetcher is a no-op. Measured with a cleared window, a trivial one-field query got 429 after 20 requests while a 20-alias query ran 45 without one, so aliased batching is a free multiplier and is the only AniList lever there is. `fetch-coread-graph.cs` batches user lists this way (`--batch`, default 20, capped 25).
- **A batch containing one private AniList user 404s the whole request and nulls *every* alias.** Not just the offender: a user with 356 entries came back null purely for sharing a request with a private account. Believing those nulls files all twenty as "private", which `RecordUser` treats as settled and never retries, so the run silently keeps a fraction of what it fetched. `FetchUserLists` therefore never trusts a null above a batch of one. Recovery reads the offender's identity out of each error's `locations[].column`, matched against the alias columns recorded while the query was built - GraphQL requires the location, and AniList emits one `Private User` error per offending alias. Only `status: 404` errors are believed; anything else falls back to halving, because filing a transient fault as "private" dequeues somebody permanently. Halving alone was measured at twelve requests to resolve twenty users at a 3% private rate, barely better than not batching.
- **The co-read fetch is latency-bound, not budget-bound.** A 20-alias list query takes 5-13s, well over the pacer's 2.5s spacing, so a serial loop issues far fewer than the 24 req/min it is allowed. Batching alone moved measured throughput 24 to ~50 users/min; the remaining headroom is concurrent requests against the same shared `Pacer`, not a higher `--rpm`.
- **`fetch-coread-graph.cs build` accumulates co-occurrence in hash partitions, not one dictionary.** At 8,800 users the nested loop generates ~88M pair increments over ~39M distinct pairs, and 76% of those are seen exactly once and dropped by `minSupport` moments later. One dictionary holding all of them is several GB of random-access hash table that doubles and rehashes itself twenty-odd times on the way up; the measured symptom was a build that printed nothing for over half an hour. It now runs one pass per partition (`PairsPerPass = 12M`, count rounded to a power of two so the test is a mask), keeping only keys whose low bits match - the key is two dense indices, so its own low bits are already uniform and need no re-hash. **Memory is bounded by `PairsPerPass` however many users get fetched**; re-walking the cheap nested loop K times costs seconds. Two other fixes went with it: one `Dictionary<long, PairStat>` updated through `GetValueRefOrAddDefault` instead of two dictionaries and four lookups per pair, and each user's dense slots resolved once instead of twice per pair. 4m21s end to end, printing per pass.
- **A long silent loop in a distribution tool is itself the bug.** Nothing distinguished "thrashing" from "hung" from "nearly done" in that build, which is why it read as broken. Every phase that can run for minutes prints now, including the write.
- **Co-read coverage is what scale buys, measured.** At 108 users only 2 of a 14-series library had any co-read neighbour; at 8,828 users it is 12 of 14, over 31,570 series and 1.18M pairs; at 19,667 users it is 41,054 series and 1.58M pairs (52 MB, 16 MB compressed, far larger than the 3.5 MB recommendation graph because `topPerItem` keeps up to 60 neighbours per series). Catalogue coverage 24.4% to **31.2%** of the 125,983-row vector index. The export ships `pair` and `meta` only - **`user_entry` is personal data and must never leave the working database**.
- **`RecoGraphScorer` normalizes by the maximum, never min-max.** A min-max would floor the weakest real candidate at 0, and 0 is exactly what `SemanticRecommender` reads as "no co-recommendation evidence" - which is what sets the `CoRead` flag and what the injection gate is a threshold on. The two states must stay distinguishable.
- **`MaxInjected` was the vote graph's intensity dial and is now inert; `MinInjectedScore` replaced it.** On the 116k-pair artifact, dropping `Weight` 0.60 to 0.10 moved the channel's share of picks only 82% to 70% while the injection cap moved it 0% (off) to 28% (50) to 37% (100) to 48% (200) - so the cap was the dial and `Weight` was not. On the 134,818-pair artifact the cap does nothing at any value and the corroboration floor is what binds. The `Weight` half of that finding still holds; only which gate is the bottleneck changed. Nothing was retuned here, because a MAL pass was still running when this was measured and degree feeds the scoring denominator directly.
- **The graph channel does not collapse into a popularity chart, measured.** Every injection cap tested *improves* the over-fit metrics against baseline (more distinct genres and tags, lower mean pairwise cohesion). The cap ships at 100 for a different reason: at 300 barely a third of the pre-channel pool survives, and a feature on by default should refine an existing user's recommendations rather than replace them.
- **The corroboration gate costs measurable diversity and is kept anyway.** On the synthetic profiles, ungated injection scores strictly better on every over-fit metric (tags 689 against 620, cohesion 0.610 against 0.632). It is gated because `spread` measures how concentrated a pool is and cannot see a single under-evidenced title ranked first, which is the failure that actually reached a real user's recommendations. When the aggregate metric and reading the real output disagree here, the output wins - and no eval-level test would catch this regressing.
- **`DegreeSmoothing` exists because `degree^penalty` at degree 1 is exactly 1.0, i.e. no penalty.** Without it a series with a single edge outranked well-connected ones carrying an order of magnitude more votes. **Degree-1 nodes are ~31% of the graph and stay there as the fetch grows** (32% at 116k pairs, 30.7% at 134,818) - measured across the partial and complete artifacts - so this is structural, not a sampling artifact of an unfinished fetch. Read the constant as a prior that a title has more neighbours than anyone bothered to record, which is permanently true: a pair count reflects how many people submitted a recommendation, not how related two series are.
- **Injection requires corroboration (`MinInjectedScore`), and that gate is load-bearing.** Pool entry is a bigger privilege than it looks: `FuseByRank` pools on cosine alone while `HybridScore` ranks on genre, tag, author and quality too, so an injected row can top the final ranking without ever being near the cosine top-200. On the real library an obscure one-shot with a single 26-vote edge to one seed came back at **rank 1**, having been absent from the entire 200-item pool with the channel off. Requiring 0.60 of the best candidate's normalized score stops it (it scored 0.55) and lifts pool overlap from 0.43 to 0.57. There was previously a separate lower cosine floor for graph-backed rows; it was **measured byte-identical at 0.15, 0.25 and 0.30** across both the synthetic profiles and the real library, so it never admitted anything and was removed rather than kept as a knob whose documented purpose the data contradicted.
- **Graph injection reuses `Scan`'s negative-infinity sentinel rather than re-testing filters.** `Scan` writes `float.NegativeInfinity` into every channel for a row that failed the filter plan, the exclusion set or the required tags, so `InjectGraphCandidates` testing channel 0 for it is the same predicate `FuseByRank` uses. Duplicating `RecommendationFilters` logic there would be a third copy to keep in step, and a way to smuggle rows past a filter.
- **`recommendations.cograph` is a kill-switch with an endpoint and deliberately no UI**, same as `recommendations.tasteweighting`: it switches a derivation off at deployment level rather than expressing a taste. It is read per request *and* folded into `RecommendationService`'s pool cache key and `SimilarSeriesService`'s entry key - both halves are needed, since a channel that changes results without changing the key sits invisible behind a 12-hour hit, and a key that moves without the read being wired is the trap `recommendations.prebuiltenabled` already fell into (written by `SettingsController`, read by nothing).
- **The channel reaches the series-page "More like this" rail too**, because `SimilarSeriesService` shares `SemanticRecommender.GetSimilarAsync`. That is wanted - a single seed's graph neighbours *are* "readers also liked" - but it means the rail's cache key had to gain the flag as well.
- **`PairGraphIndex` (once `RecoGraphIndex`) cannot be called `RecoGraph`, because a type cannot share its namespace's name.** Anything inside `Maki.Metadata.*` resolves bare `RecoGraph` to the namespace, so the class compiled fine in `Maki.Metadata.Embedding` (which only names `RecoGraphCache`/`Scorer`/`Tuning`) and broke the moment a test referred to the type itself.
- **Seed weights are rating-first, behaviour-second** (`TasteWeights`/`TasteTuning` in `Maki.Core/Recommendations`, aggregated by `BehavioralTasteService`, killed by `recommendations.tasteweighting`). Ratings are sparse, so an unrated seed gets a weight derived from completed `ChapterProgress` + `ReadSeconds` + recency; `RatingBlendAlpha = 1` means a rated seed keeps `rating / 5.0` untouched. Three traps: **`Seconds == 0` means "unknown", not "no engagement"** — Kavita imports and OPDS never record time, so the engage channel is *dropped and renormalized* rather than scored zero, or an imported library sinks to `MinWeight` and the feature is worse than uniform; recency is computed against a **date**, not an instant, or the 12-hour pool cache dies on every chapter read (the cache key renders weights at one decimal, which is where that stability comes from); **`WeightQuantum` must stay well below that**, because `SemanticRecommender.PickRepresentativeSeeds` orders seeds by weight and breaks ties with `ThenBy(id)` — at 0.1 two series scoring 1.6533 and 1.7215 both became 1.7 and the more thoroughly read one lost the seed slot that starts the farthest-point walk to the lower catalogue id, which flipped 64% of the top 40 on a real 92-series library; and `RecencyFloor` sits *above* `NeutralSignal` on purpose, so an old favourite doesn't decay into "never opened". `IncognitoMode.Full` has to be excluded by hand here (its `ChapterProgress` rows exist, only the `StatsEvent`s are suppressed) — same gate as `UserMetricsService.FullyReadAsync`.
- **`RecommendationService` caches N pools, not one.** Behavioural weights make every user's cache key distinct, so the old single `_cacheKey`/`_cached` pair thrashed between users on a multi-user instance and recomputed a full index scan per request.
- **More crowd coverage improves a mainstream library and concentrates an obscure one; those are the same event.** Doubling the co-read matrix (8,828 to 19,667 readers) moved a real 14-series library's median popularity rank from 330 to 647 - straight improvement, every diversity column up too - while moving the 24 synthetic profiles from 7135 to 6026, i.e. worse. Not a contradiction: a popular library's seeds already had dense edges so extra data spreads the load, whereas the synthetic profiles are deliberately obscure and previously got **nothing** from the channels. Coverage growth is what makes a collaborative channel start firing on obscure seeds, and a famous title is simply reached from more of them. **Judge a fetch on both, and expect them to disagree in that direction.**
- **A channel measuring as inert on one library is not evidence it is inert.** On a 92-series install `CoReadTuning.Weight` at 0.15, 0.2 and 0.3 returns a byte-identical pool, and switching the channel off entirely leaves the picks unchanged (overlap 1.000) while still flagging 62% of them - the vote graph had already found everything it would have found, and the flag records agreement rather than influence. It does not reorder anything there until ~0.5. Tune this channel on `spread`, which models the libraries it exists for; use a real library to check it does no harm, not to size it.
- **`eval-reco.cs` runs against whatever `MAKI_CONFIG_DIR` points at, which is how it gets a realistic library without touching the live install.** `.simulated/` holds a copy of a production config dir (92 series, 489 `ChapterProgress` rows, 82 `ReadingState`s) against the 14-series dev one. **The graph artifacts have to be copied in by hand** - the eval reads `reco-edges.db`/`coread-edges.db` from that directory, and their absence is a silent no-op that reads as "the channel did nothing" rather than as a missing file.
- **`distribution/eval-reco-labels.cs` is the only tool here that can say recommendations got BETTER, and it works because the crowd artifacts were being spent as ranker input instead of held out.** `reco-edges.db` (134,818 human "if you liked X, try Y" pairs) and `coread-edges.db` (1.58M behavioural pairs) are relevance judgements; only **19.8%** of vote pairs also appear in the co-read graph, so grading against one with that channel switched off is genuinely held out. `.artifacts/coread-graph.db` additionally holds **19,935 real reading lists** (4.33M COMPLETED rows), 16,530 of them with >= 20 in-index titles - that is `library` mode, and it is the first time whole-library recommendations have been measured at n in the thousands rather than n=1. Reports R@10/20/40, nDCG@40, MRR, hit rate and `pop`, writes per-request reciprocal ranks for `eval-compare.py`, and `--strata` splits every metric by seed popularity.
- **The tool forces the graded channel off itself rather than trusting the variant**, and prints a note when it overrides one. `--labels reco` kills the vote channel, `--labels coread` kills co-read, and `library` mode kills co-read unconditionally because those lists ARE its training data. A graph reading its own answers looks like a spectacular result and is worth nothing.
- **Read its recall as a lower bound and never in isolation.** A missing edge is not evidence of irrelevance, and both label sets over-represent famous titles, so a variant that simply returns them scores better. `pop` and `--strata` are the counterweight, same rule as `eval-reco.cs spread`'s own `pop`.
- **The genre channel was the one un-normalized channel, and that was the single biggest ranking bug in the recommender.** `TagMath.Score` is a cosine; `genreSum` was a raw sum, so its scale tracked how CONCENTRATED the seed set was rather than how well a candidate matched. `BuildProfileAsync` gives each seed's genre `1/seedCount`, so a genre every seed carries scores 1.0 at two seeds and at four hundred alike, and a three-genre candidate collected ~3.0 - as much as the semantic term pays for a perfect cosine. Genre beat feel on exactly the requests where feel is all there is. `SemanticRecommender.GenreScore` is a cosine now, and at the **unchanged** `Genre = 1.0` it measures better everywhere: single-seed nDCG@40 0.115 to 0.124, three-seed 0.071 to 0.095 (paired MRR +0.097, bootstrap 95% [+0.067, +0.128], McNemar p=0.011), and whole-library 0.083 to 0.104 over 400 real reading lists (paired MRR +0.053, 95% [+0.028, +0.078], McNemar p=0.009) with `pop` rising 4425 to 6335, i.e. less popularity-concentrated as well. A sweep on the new scale is monotone downward above 1.0 (0.5 and 1.0 indistinguishable, 1.5/2.5/4.0 progressively worse), so the coefficient did not need retuning - only the shape did.
- **`SimilarSeriesService.SingleSeedWeights` is deleted, and the Author half of it was measured actively harmful.** The reduced vector was `(Genre: 0.15, Author: 0.25)`; splitting it shows Genre carried all of the win (single-seed nDCG 0.132 alone against 0.128 for the bundle and 0.115 for the default) while lowering **Author alone was worse than leaving it** (0.114 against 0.115 at one seed, 0.062 against 0.071 at three). The rail now asks for the same weights Discover does, which is also the end of the same seed returning different answers depending on which surface asked. `SimilarSeriesServiceTests.The_rail_asks_for_the_same_channel_weights_Discover_does` pins it.
- **The rail's `Diversity = 0.15` measures neutral on these labels and is kept anyway.** It is aimed at near-duplicate suppression (a seed pulls hardest on its own other volumes), which a graph of "readers paired these two" cannot see. Same class of judgement as the corroboration gate: when the aggregate metric and the actual output disagree here, the output wins.
- **Seed weights now reach the genre and tag profiles, not just the centroid.** They used to steer only which query vectors got built, leaving Genre + Tag (2.5 of the score's ~7 points) blind to the taste the rest of it was weighted by. `TagMath.BuildProfile` has a weighted overload and `BuildProfileAsync` takes the weights; both normalize, so only relative weights matter and no caller has to care what scale it hands in. **The measured effect is a wash** - seeding a real library by the reader's own AniList scores moved nDCG 0.105 to 0.103 and MRR 0.351 to 0.360 against holding out 20% of their list. Worth knowing before anyone credits `TasteTuning` with more than it has earned; the wiring is right either way, and it was measurably absent before.
- **`RecommenderTuning.CosineFloor` is measured inert across the band anyone would set it to.** 0.0, 0.30 (shipped) and 0.35 return a byte-identical pool over 500 single-seed requests, so `CrowdBypassesCosineFloor` is inert with it - the theory that the floor was quietly capping the crowd discovery channel is **wrong**. It is not unwired: 0.90 returns nothing at all, and 0.50/0.60 measurably degrade (nDCG 0.125 to 0.116/0.113), so the floor must not be raised either. Both knobs stay sweepable, in the same category as `SearchTuning.TagFloorAbsolute` - kept so the eval can reproduce a behaviour the data contradicts.
- **`RecommenderTuning.GenreChannelIsRawSum` exists only so the eval can reproduce the pre-normalization ranking**, and nothing in the app sets it. Every before/after number above came from it. It does not reproduce the unweighted tag profile, which is a no-op under uniform seed weights anyway.
- **`CoReadTuning.Weight` looks under-set on the pooled number and is not, and `--strata` is what shows it.** Sweeping 0.15 to 0.80 improves nDCG@40 monotonically (0.123 to 0.143) against held-out vote pairs, but `pop` falls 29,405 to 23,859 and the gain concentrates where the graph is already dense: top-1k seeds gain 30%, 1k-5k 16%, 5k-20k 17%, and past rank 20,000 **R@40 does not move at all** (0.087 to 0.087). Raising it buys agreement on famous titles and a more popular pool. It stays 0.15. Same failure `spread`'s `pop` column caught, and invisible in the pooled table.
- **`eval-search.cs` now writes per-query reciprocal ranks** to `.artifacts/eval/rr-<variant>-search[-<class>].csv`, keyed by the query's line number in the .tsv so two runs line up even when one scored a subset. The better/worse counts it prints are a summary, not a test: at n=90 on `premise` a three-query difference reads as a result and is inside the noise. `eval-compare.py <a> <b> search-premise` is the decision.
- **eval-queries.tsv has an optional fourth column of filters**, and 14 `filtered` rows use it. Filters are their own code path - a row mask on the `FilterPlan`, applied per row before the top-K, duplicated in C# from `RecommendationFilters.BuildClause` - and nothing measured it until that column existed, which is also the only thing that would catch the two copies drifting. Every filter was checked against the dump: at least one row carrying the label satisfies it, so a miss is a ranking failure and not an impossible query. Filtered MRR is 0.899 against 0.612 for the same queries unfiltered, because a filter narrows the field.
- **`eval-search.cs --engine title` scores the fallback, and the cost of an unbuilt index is total, not partial.** Over the same 190 queries the FTS5 path answers `premise` and `filtered` at **MRR 0.000** while matching or beating the fusion on `alias` (0.864 against 0.841) and `title` (0.981 against 0.979), for 0.370 overall against 0.749. The "Smart" toggle on a fresh install is not degraded for the query shape it exists for, it is absent - which is what the UI badge claims and is now a number.
- **`eval-search.cs` pins `CultureInfo.InvariantCulture`,** added after a run printed `0,841`. Every figure quoted in `SearchTuning`'s doc comments is a decimal point, and a comma-locale machine silently produced a table that could not be compared against any of them.
- **`RecommenderTuning.MaxSeedQueries` was the seed knob that mattered, and it was set too low.** Raised 8 to 16, and later to the 48 that ships; the reasoning for stopping at 16 is preserved below because it was right at the time and the price it weighed is still real. **Read this bullet as being about the TEXT space only.** The behavioural channel's own `MaxSeedQueries` is 0 and wants to be: the two spaces are monotone in opposite directions, for reasons written up further down. Over real reading lists with 20% held out, nDCG@40 is 0.096 / 0.104 / 0.112 / 0.116 / 0.117 / 0.121 at 4, 8, 16, 24, 32 and 48 queries, against per-request latency of 130 / 225 / 303 / 534 ms at 8 / 16 / 24 / 48. Paired against 8: **+0.0069 nDCG at 16, bootstrap 95% [+0.0035, +0.0104]**, +0.0095 at 24. Median pick popularity barely moves, so it is not winning by returning famous titles. Stopped at 16 because the gain is logarithmic and the price is linear, and the ~95 ms lands on a page load even though the pool is then cached twelve hours.
- **Which seeds get queried is measured not to matter; how many do.** `SeedSelection` has four strategies and they are all within noise of each other over 800 real libraries - medoid against the shipped farthest-point walk is **+0.005 MRR, bootstrap 95% [-0.007, +0.018]**, McNemar p=0.73. Farthest-point sampling really does return the seed set's *hull* rather than its centres of mass, which looks like a bug and `SeedSelectionTests.Farthest_SpendsBothQueriesOnTheOutliers_AndNoneOnWhatTheLibraryIsAbout` pins that it happens - it just does not cost anything, because the centroid query already covers the mass and the crowd channels cover what neither reaches. `Weight` selection is the one to avoid: same relevance, but it drove median pick popularity from 5812 to 3892 under real seed weights.
- **The alternative selection strategies are kept as dead-but-sweepable code on purpose.** "Surely we should pick better seeds" is the obvious hypothesis, it is wrong, and the answer is worth more with the code that produced it still present - same reasoning as `SearchTuning.TagFloorAbsolute`. `Medoid`'s k-means is seeded from the farthest-point walk rather than a random draw because `RecommendationService` caches a pool for twelve hours against a key that says nothing about which seeds were queried, so a strategy that answered differently on two identical requests would make that key a lie.
- **`eval-reco-labels.cs --csv ndcg|r40` picks which column gets the interval, and the default (rr) would have missed this finding.** `MaxSeedQueries` recovers *more* of a held-out list without changing the rank of the first hit, so on reciprocal ranks q16 against q8 reads as indistinguishable ([-0.003, +0.027]) while on nDCG it is unambiguous ([+0.0035, +0.0104]). `eval-compare.py` takes an optional fourth argument naming the metric, for the labels only - a table headed MRR while the file holds nDCG is how that gets misread.
- **The `ms` column exists because `MaxSeedQueries` is a pure CPU-cost knob** and a relevance table with no price on it makes "more is better" look free. Comparable within a run only.
- **Watch out for passing a bare variant name where an override was meant.** `-- library farthest medoid` runs the default twice: `medoid` is a *name*, and the strategy needs `medoid:seedselection=medoid`. It produced two byte-identical rows, which reads as "the knob is inert" rather than as "the knob was never set" - the same trap the `%TEMP%\dotnet\runfile` cache sets, arrived at from the other direction.
- **`distribution/eval-reco.cs` is the recommendation instrument, and its two modes claim different things.** `spread` builds synthetic narrow-and-deep profiles and reports pool concentration (distinct genres/authors/tags, mean pairwise cosine) against a `uniform` baseline — no labels, runs on any install, and it's what the over-fit risk is actually measured against. `loo` leave-one-outs the *installed* reading history: real behaviour, n = one library, a direction and a tripwire only — at the default `--limit` a 90-ish-series library returns all zeros, which the tool labels **NOT A RESULT** rather than letting a table of zeros read as a tie. Neither is `eval-search.cs`, which never touches seed weighting.

## v4 measurement (Phase 0)

- **Every label set before v4 came from AniList or MAL, and `distribution/build-mu-graph.cs` is the fix.** `reco-edges.db` is AniList plus MAL votes, `coread-edges.db` is AniList reading lists, and `library` mode reads those same lists, so a channel derived from AniList behaviour is partly reading its own answers however carefully the graded channel is switched off. MangaUpdates is a different site and population: the tool folds `source_manga_updates_response_category_recommendations` and `..._recommendations` out of the FULL dump into `.artifacts/mu-edges.db`, **361,007 pairs over 86,172 series, 96.5% of them in neither shipped artifact**. Eight seconds to build.
- **They are two label sets, not one, and the weights prove it.** `category_recommendations` is MangaUpdates' own derivation from category (tag) votes: 331,736 pairs, median weight 17,819. `recommendations` is human-submitted with a submitter count: 29,692 pairs over 7,036 series, median weight 4. Summing them would make the human half arithmetically invisible, the same failure `RecoGraphCache`'s per-provider rescaling exists to prevent, so they live in separate columns and are graded separately as `--labels mu` and `--labels mu-human`.
- **`--labels mu` is the wrong primary grader for a tag change and `--labels mu-human` is the right one.** The category list is derived from tags, so a tag-channel change will agree with it for reasons that have nothing to do with being better. The measured baseline shows the two behaving completely differently: switching the crowd channels on moves single-seed nDCG 0.040 to 0.047 on `mu` and **0.031 to 0.123 on `mu-human`**. Same picks, same seeds, different question.
- **The MangaUpdates columns exist only in the full dump.** In the standard dump every `source_*_response` column is present and 100% NULL, so reading it produces zero pairs and no error. `build-mu-graph.cs` checks for present-but-empty and refuses, rather than writing an empty artifact that reads as "MangaUpdates had nothing to say".
- **`eval-reco-labels.cs` wrote every run to `rr-<variant>-reco.csv` regardless of label set.** Grading the same variant against two label sets silently overwrote the first file, so `eval-compare.py` compared a run against itself. The suffix is the label set now (`library` in library mode), which is also why the old per-request CSVs cannot be compared against new ones by name.
- **`--fold-users k/n` is what makes a behaviourally-trained channel gradeable at all.** `library` mode holds out items within one reader, but every artifact saw that reader, which is why it force-disables co-read unconditionally. The fold splits the reader *population*: `build-taste-vectors.cs --fold-out k/n` trains without fold k and records the folds it did see in `meta.trainingFold`, and the eval refuses to grade an artifact whose training folds include the fold being evaluated. `UserFold.Of` is duplicated verbatim in both tools and **must stay byte-identical** - a builder that partitions readers differently from the grader produces an artifact that trained on part of the evaluation set while honestly reporting that it did not. It is FNV-1a and not `HashCode.Combine`, which .NET randomizes per process; AniList ids are dense and sequential, so a plain modulo would correlate a fold with signup date.
- **`--feel` measures the thing nDCG cannot see, and it is the acceptance criterion for v4.** Six columns from the dump: demographic agreement (`Audience Demographics` tag root), format agreement (`Work Info > Publication Medium` / `Page Layout`), original-language publisher agreement, era gap in decades, mean taxonomy distance through `name_path`, and the share of picks sitting in a seed's own `relationships_v2` component. The last is a DEFECT rate read downward, unlike every other column. English licensors are excluded from the publisher column deliberately: sharing Yen Press is a fact about a market, sharing Afternoon is a fact about the work.
- **The feel columns saturate in `library` mode and are only discriminative at one and three seeds.** Measured: a held-out reading list seeds from up to 300 titles, whose union covers nearly every demographic and format in the catalogue, so `default` scores demo 99%, format 93%, house 92%, era 0.04 and tree 0.13 there and no change will move them. Read `--feel` on `single` and `small`; in `library` the only column that still says anything is franchise.
- **One pick in five on a real library is in a seed's own franchise** (20% at `default`, 22% at `nocrowd`, `library` mode). Title-normalized dedup is the only franchise suppression v3 has, and `relationships_v2` is read by nothing. This is the number Phase 3's franchise collapse has to move.

## v4 Phase 1: hierarchical tags, measured and NOT shipped

- **`TagAncestorDecay` ships at 0, and the reason is the most useful thing this phase produced.** Crediting a tag's `name_path` ancestors was the plan's cheapest and highest-confidence idea, backed by a proxy measurement of Cohen's d 0.674 to 1.699 on 4,000 co-read pairs against 4,000 random ones. Done correctly it is **inert**: single-seed nDCG@40 on the independent grader is 0.127 both ways, and whole-library is 0.131 against 0.132. The mechanism, the schema column and the knob are all shipped and all default to off, in the same category as `SearchTuning.TagFloorAbsolute` and `SeedSelection`'s dead strategies. Kept so the finding stays reproducible.
- **The first version looked like a large win and was a pricing bug.** An ancestor was given the IDF of the tag that reached it, so `Themes` was priced at IDF 6.17 (the mean of its individually rare children) when its true IDF is 0.00, because it is on almost every series. Measured with that bug: single-seed nDCG 0.127 to 0.137 at decay 0.25, bootstrap 95% [+0.0069, +0.0140], gaining in **every** popularity stratum including past rank 20,000, which is where the co-read channel is known to do nothing. It looked like the cleanest result in the whole project.
- **What caught it was `pop`, then `library` mode.** Median pick popularity fell 26,938 to 19,878 to 14,236 as the decay rose, and whole-library nDCG went the other way: 0.131 to 0.116 with `pop` collapsing 1,233 to **311**, i.e. the median pick sitting inside the 311 most popular series in a 126k catalogue. The error compounds with seed count, because more seeds reach more of the tree, so a surface with 300 seeds degrades into a popularity chart while a surface with one looks better than ever. **A tag change measured only at one seed cannot be trusted.**
- **Re-running the original proxy with the ancestor priced by its own rarity closes the loop**: d 0.771 with expansion off, **1.800 with the child's IDF, 0.833 with its own**. The proxy was measuring the bug, not the mechanism. Both numbers were real; only one of them was about ancestors.
- **The document-frequency estimate is not what limits it.** A prefix that is itself a tag takes that tag's exact `series_count`; the rest take the sum of their descendants, which over-counts a series carrying two sibling tags. Checked against the true union over 162,237 series: median over-count ratio 1.23, and the estimated and true IDF distributions agree closely (78% against 82% of the 258 prefixes above IDF 3). The estimator is fine, so the mechanism genuinely does not help.
- **`TagAncestorIncludesSelf` is off and measured worse**, 0.132 against 0.137 for the same decay under the buggy pricing. It adds a meeting point (a series tagged `Themes > Romance` and one tagged `Themes > Romance > Harem` otherwise meet only at `Themes`) at the price of counting every exact match twice.
- **One thing did move in the right direction and is worth remembering**: demographic agreement rises with decay, 58% to 61% to 63% at decay 0.25/0.5/0.7 on single-seed, while nDCG falls. Ancestor expansion does make picks more demographically consistent. It is not free, and at whole-library scale it is expensive, but if Phase 3's provenance channel needs a demographic term this is evidence one exists to be had.
- **`tag_vocab.name_path` is populated by the ordinary index pass and needs no re-embed.** `SeriesEmbeddingIndexer` rebuilds the whole vocabulary before the unchanged-hash check, so the column fills in on the next pass without a single vector being recomputed; until then it reads empty and `TagTree.Build` returns `Empty`, which scores identically to before the column existed. `AddTagVocabColumn` is the generalized form of the old `AddTagCategoryColumn` and both migrations run from `EnsureSchema`, which `SemanticRecommender` already calls.
- **Ancestor nodes carry negative ids on purpose.** Most path prefixes are not tags (16 of the 17 roots have none), so they need ids of their own, and negative ones cannot collide. It also makes the UI correct for free: `SemanticRecommender` builds its matched-tag list by looking every contributing id up in the vocabulary and dropping what it cannot name, so an ancestor can never surface as a "matched tag" without anyone having to remember a rule.

## v4 Phase 2: the behavioural channel, measured and SHIPPED

- **`TasteVectorTuning.Weight` ships at 1.5, and it is the largest measured improvement the recommender has had.** Item vectors factorized out of the reading lists `coread-graph.db` already held, scored as a cosine beside the text one. Against the independent MangaUpdates grader, single-seed nDCG@40 goes **0.127 to 0.149** (paired +0.0228, bootstrap 95% [+0.0158, +0.0302], t=6.21 on 400 requests) and three-seed 0.129 to 0.156. On held-out READERS, whole-library nDCG goes **0.144 to 0.167** (+0.0231, 95% [+0.0170, +0.0295], t=7.30).
- **It is not the co-read graph with extra steps, and the coverage number is the argument.** That graph answers "did at least three of 19,667 readers finish both of these", which is a lookup and is empty for two thirds of the catalogue: 41,054 of 126,323 indexed rows. Factorizing the same interactions places every item with enough evidence in one space, so a similarity exists for pairs nobody was observed to share. The shipped artifact carries **60,053 vectors** against the graph's 41,054 series, and the difference in kind matters more than the count: a vector answers for any pair, an edge only for an observed one. `MangaBakaRecommendation.TasteMatch` is a third "why" for that reason and must not be folded into `CoRead`.
- **Six of the eleven million interactions were being thrown away.** The graph is built from the 4,326,424 `COMPLETED` rows. `build-taste-vectors.cs` also spends 3,275,937 `PLANNING`, 2,647,485 `CURRENT`, 579,171 `DROPPED`, 462,754 `PAUSED` and 10,279 `REPEATING`, plus 3,647,125 explicit scores. **1,166,330 cells end up negative**, which is a signal v3 could not express at all.
- **A dislike is carried by the confidence, not by a negative preference.** This is implicit ALS: every cell has p in {0,1} and c >= 1. An unobserved cell is p=0 at c=1 ("probably not, no idea"); a `DROPPED` row is p=0 at HIGH c ("we know they saw it and stopped"). Same for a title someone finished and scored well below their own average. So the solver needs no special case, and `Multiply` must use `|c|` rather than `c` in the normal equations or A can go indefinite and conjugate gradient stops being valid.
- **Scores are centred per reader and never used raw.** A 70 from someone averaging 85 is a complaint; the same 70 from someone averaging 60 is praise. The distribution is also spiky at multiples of ten (723,734 rows at exactly 70), so a raw threshold lands on a mode and moves a large block at once. Spread is a fixed 15 points rather than measured per reader: somebody who gives everything 80 has zero variance, and dividing by it turns one point into a certainty.
- **The apparent gain against co-read labels was 100% leakage, and this is the trap worth remembering.** `--labels coread` forces the co-read CHANNEL off, which used to be enough. It is not, once a second channel is trained on the same file: the first measurement read +0.102 nDCG (0.068 to 0.170) against those labels and **+0.022** against MangaUpdates ones. `forbidTaste` now covers it, and with the channel correctly off the two variants come back byte-identical. `--labels reco` is left on with a printed note instead: submitted "if you liked X, try Y" pairs are a curatorial act the trainer never sees, which is the same relationship the vote and co-read graphs already have, but the readers are shared and the inflated figure (0.119 to 0.221 single-seed) should not be quoted as if it were mu-human's.
- **`--fold-users` plus `--fold-out` is the only honest way to read `library` mode here, and no flag substitutes for it.** Holding a channel out is a switch; holding a MODEL out is a different artifact. `build-taste-vectors.cs --fold-out 0/4` trains on 14,878 of the 19,935 readers and records `trainingFold = 1,2,3`; the eval refuses the run outright if the installed artifact was trained on the fold being graded. Verified: asking for fold 1 against that artifact is an error, not a number.
- **Every feel column moves the right way, which is the opposite of what the tag phase did.** Single-seed against mu-human: demographic agreement 58% to **69%**, format 8% to 11%, original-language publisher 16% to **23%**, era gap **1.11 decades to 0.67**. On held-out libraries the same-franchise defect rate falls 20% to **17%**. This is the "feels like" the channel was built for, and it is measured rather than asserted.
- **`pop` halves at one seed and does not move at all on a library, and both are real.** Single-seed median pick popularity falls 26,938 to 12,934, which is the popularity bias implicit ALS is known for; on held-out libraries it is 948 against 955, i.e. flat. A single seed gives the centroid one well-listed neighbourhood to sit in, whereas 300 seeds already span the space. Read the one-seed number as the price of the "More like this" rail and the library number as the answer for Discover.
- **The gain is in every popularity stratum, including where the co-read channel does nothing.** Single-seed R@40 by seed rank: top 1k 0.181 to 0.273, 1k-5k 0.186 to 0.284, 5k-20k 0.114 to 0.137, and past rank 20,000 **0.041 to 0.057**. `CoReadTuning.Weight` is documented as moving R@40 not at all in that last bucket; this moves it 39%.
- **The vectors are loaded by `VectorIndexCache`, not by a cache of their own, and that is a deliberate trade.** The scan needs a vector per ROW, so a dictionary lookup per candidate per query would cost more than the dot product it feeds. The price is that installing the artifact has to invalidate the whole index, which is why `TasteVectorJob` is staggered at T+6 minutes behind every other artifact download: doing it while the index is still building the first time throws that work away.
- **`TasteVectorInstaller` refuses a fold-limited build, and that check has no runtime symptom.** An evaluation artifact is a valid file that is quietly missing a quarter of the readers; it installs, works, scores slightly worse, and gives nobody a reason to look. It is checked from the manifest (so it is not even downloaded) and again from the file (because a manifest can say anything). The per-user-table gate is the same one `CoReadInstaller` has and matters as much: these vectors are derived from `coread-graph.db`, which is the likeliest mispublish in the folder.
- **`scale IS NULL OR NOT (scale > 0)`, never `<= 0`,** for the reason already written down against `strength`: SQLite stores a NaN as NULL and a three-valued comparison lets exactly the rows it is meant to catch through. Zero has a second meaning here on top of that, since it is the layer's own "this row has no vector" marker, so a stored zero would make a row silently invisible rather than wrong.
- **Naming: `TasteVectorTuning`, not `TasteTuning`.** `Maki.Core.Recommendations.TasteTuning` already exists and is the seed-WEIGHTING feature. The two are unrelated and the collision is a compile error waiting in any file that uses both. For the same reason `RecommendationService`'s local is `tasteVectors`: its constructor parameter `taste` is `BehavioralTasteService`.
- **Training costs 91 seconds** for 128 dimensions and 15 iterations over 11.2M cells on 32 threads, so the sweepable knobs are genuinely sweepable. Conjugate gradient with three steps rather than an exact Cholesky is what makes that true; the Gramian of the fixed side is computed once per half-step, which is the identity that makes implicit ALS tractable at all.

## v4 Phase 3: franchise collapse, measured and NOT shipped

- **`MaxPerFranchise` and `ExcludeSeedFranchise` both ship at off, because the "defect" they fix is not one.** Phase 0 measured that one pick in five on a held-out reading list sits in a seed's own franchise, and that reads as a duplication failure: recommending volume two of what somebody is already reading, with title-normalized matching as the only defence and `relationships_v2`'s 149,319 typed edges having no readers at all. Capping a franchise to one pick measures **-0.0072 nDCG@40** over 300 held-out libraries (bootstrap 95% [-0.0100, -0.0046], t=-5.08); also excluding the seeds' franchises measures **-0.0442** (95% [-0.0532, -0.0357], t=-9.88). Both intervals exclude zero, so this is not noise.
- **Readers who finish something go on to read the rest of it, which is why those picks are in the held-out set.** The franchise share falls 18% to 14% under the cap and to 0% under the full collapse, exactly as designed, and relevance falls with it. The metric is not being fooled here; the hypothesis was wrong.
- **The app narrows it further than the eval can.** `RecommendationService` excludes every series the caller owns, so what actually survives into a real page is the franchise members they have not read. That is a recommendation, not a repeat. The eval's `library` mode cannot model this, because the held-out slice is by construction unowned and is also the answer key.
- **The two knobs are separate because they cost differently, and sweeping them together would have hidden that.** The cap is nearly free (-0.007) and removes 4 points of franchise share; the seed exclusion is six times more expensive and removes the remaining 14. One combined knob would have reported a single number for two effects with very different prices.
- **`FranchiseGraph` ships anyway and is not dead code.** `VectorIndex.FranchiseAt` is what the eval's `--feel` franchise column reads, so the definition the ranker would collapse on and the definition the metric measures are the same one. Two copies would let a future change move one and not the other, which is the failure mode that makes a metric quietly stop testing anything. `adaptation`, `source`, `parody` and `alternative` are excluded from "same work" on purpose: a manga adapted from the same novel is a different reading experience and suppressing it would make the recommender worse rather than tidier.
- **Unions run over every id the dump mentions, indexed or not.** A trilogy linked through a middle volume that is a novel, inactive, or never embedded still has to resolve to one component; unioning only over indexed rows splits it and leaks exactly the rows a collapse exists to catch. `FranchiseGraphTests.JoinsTransitively_ThroughASeriesTheIndexNeverCarries` pins it.
- **Component ids are assigned from the smaller id in each union**, so two builds over one dump agree. `RecommendationService` caches a pool for twelve hours against a key that says nothing about franchises, so a graph that answered differently on two builds would make that key a lie.
- **One thing worth looking at that this did not measure**: `SimilarSeriesService` passes an empty exclusion set, while `RecommendationService` adds `GetRelatedAsync`'s output to its own. The series page renders `RelatedSeriesSection` and `SimilarSeriesSection` together, so the rail can repeat, in the second, series already listed in the first. That is a duplication within one page rather than a ranking question, no label set can see it, and it was left alone rather than guessed at.

## v4 Phase 3: credits

- **Sentinel names are dropped from the credit channel at index build, unconditionally.** `"Anthology"` is the single most common value in the dump's `authors` column. Treated as a person it makes every anthology share a creator with every other anthology, which is worth the full `Weights.Author` for nothing. `CreditNames.IsPerson` is used by both the index build and the seed-profile query, because a name filtered on one side and kept on the other cannot match anything and would shrink the channel rather than clean it.
- **`CreditsIncludeArtists` ships off, and the reason is structural.** `artists` covers 98.3% of the recommendable catalogue and was read by nothing, which looks like an obvious gap: where the columns differ the artist decides what a series looks like, and no other channel carries that. They almost never differ. Union them and single-seed nDCG is 0.153 either way, three-seed 0.158 either way. On most rows the artist IS the author, so there is nothing to add.
- **The knob is applied at query time, not at index build, and that is a constraint worth knowing.** The eval builds ONE index and shares it across every variant in a run, on the grounds that tuning changes scoring and never the index. Anything baked into the index therefore cannot be swept without a rebuild per variant, which is why artists are their own column that the scorer unions, while sentinel filtering (which nothing needs to sweep) happens once at build.
- **The author channel itself may now be over-paying, and this is a lead rather than a finding.** Turning it off entirely (`wauthor=0`) measures **+0.0045 nDCG** at three seeds against the independent grader, 95% [+0.0008, +0.0081], t=2.39. That is the opposite of the pre-v4 measurement that lowering `Author` alone was worse than leaving it, and it is consistent with the behavioural channel already knowing who made what: it puts Fire Punch next to Chainsaw Man with no author signal at all. One weak result on one label set is not enough to retune a coefficient on. Sweep it across `reco`, `mu-human` and held-out `library` together, and expect the whole weight vector to want re-fitting once Phase 5 exists rather than one coefficient at a time.
- **Adding a column to the index scan is a compatibility surface.** `d.artists` broke three test fixtures that build their own minimal dump, two of them through positional `INSERT ... VALUES` with no column list. Real dumps always carry the column, but a fixture is not a dump.

## v4: publishing the behavioural artifact

- **`graph-artifact.cs` takes a third kind, `taste`, rather than there being a third tool.** It is not a graph, but everything except which tables it looks at is identical - integrity check, personal-data gate, zstd, manifest, checksum - and the half that would drift between copies is the half deciding what is safe to publish. `publish-graph.ps1 -Graph taste` (or `-Graph all`) drives it; the tag is `taste-vectors-latest`, matching `TasteVectorInstaller.ReleaseTag`, which is what clients poll.
- **The packer refuses a fold-limited build, and that is the check worth having twice.** `build-taste-vectors.cs --fold-out` writes a perfectly valid artifact that is missing a quarter of the readers on purpose so the eval can grade honestly. Published, it would install, work, score slightly worse and give nobody a reason to look. `TasteVectorInstaller` refuses it as well, but this is the gate that stops it being uploaded at all. Verified: packing `taste-fold0.db` exits with `meta.trainingFold is '1,2,3'`.
- **The existing personal-data gate already covers this artifact and needed no change.** It runs first, before `quick_check` and before any shape check, and refuses any file carrying `user_entry`/`user_state`/`pending_user`. The vectors are derived from `coread-graph.db`, which holds 11.3M per-user rows and sits in the same folder, so it is the same accident the gate was written for.
- **`trainedReaders` goes into the manifest as a NUMBER, not the string the meta table stores.** `TasteVectorManifest.TrainedReaders` is a `long` and System.Text.Json refuses a quoted number by default, so a manifest written the obvious way parses on the publisher's machine and fails on every client. The same applies to `dimensions`.
- **Vectors are validated on width and scale before publish**, not only at install: a vector narrower than the declared dimension is read past its own end into a row-aligned buffer, and `scale IS NULL OR NOT (scale > 0)` catches the NaN-stored-as-NULL case plus the one specific to this layer, where 0 is the "no vector here" marker and a stored 0 makes a row invisible rather than wrong.

## v4 Phase 5: fitting the blend, and why the fit is not what shipped

- **`distribution/fit-weights.cs` fits the nine coefficients jointly instead of sweeping them, and the honest result is that the naive fit chases fame.** Pairwise logistic regression over `--dump-features` output: for a candidate the labels call relevant and one they do not, both from the same request, the score difference should be positive. Pairs never cross requests, because two candidates from different requests never competed. AdaGrad rather than plain SGD, since a cosine, a boolean and a max-normalized graph score are on wildly different scales and one learning rate either crawls or diverges.
- **The fame diagnostic is the point of the tool, and it fired.** The fit runs twice: once without the popularity column and once with. Fitted on three-seed MangaUpdates pairs, giving it popularity directly moves `quality` from **8.84 to 3.68** while pairwise accuracy barely moves (95.39% to 95.56%) and `pop` lands at **-5.71**. The large quality coefficient was quality standing in for fame. `rating` has 55% of its mass in one decile, so it discriminates almost nothing except how famous a title is.
- **That prediction held end to end.** The fitted vector (`wquality=13.85`, `tasteweight=7.03`, …) wins on both pair label sets - mu-human +0.0149 (95% [+0.0102, +0.0197]), reco +0.0118 (95% [+0.0052, +0.0186]) - and **loses on held-out readers**, 0.166 to 0.161, with median pick popularity collapsing 955 to **405**. Both pair sets over-represent famous titles, which the harness has always said; this is the first time something optimized that bias directly and the `pop` column caught it before the run that proved it.
- **Fitting on held-out reading lists instead gives a different vector and a different trap.** `taste` rescales to 13.2, `graph` to 5.6, `coread` to **0.0** - and that last number is meaningless, because `library` mode force-disables the co-read channel, so the column is constant and unfittable. `single` mode has the same problem with `distinct`, which is always 0 there because one seed builds no seed query. **A constant column produces a coefficient of 0 that reads exactly like a finding**, so the tool now checks variance per column and warns by name.
- **What shipped is the one thing both fits agreed on, swept and interval-tested on its own.** Both wanted far more behavioural weight than 1.5. `TasteVectorTuning.Weight` is **2.5**: +0.0035 nDCG@40 on held-out readers (95% [+0.0005, +0.0065]) and indistinguishable on the independent pair grader (-0.0012, 95% [-0.0041, +0.0014]) with demographic agreement 69% to 71% and the era gap 0.67 to 0.61 decades. 4.0 has the larger point estimate (+0.0052) and an interval spanning zero, so it stays unshipped.
- **What makes 2.5 safe rather than merely better is that `pop` does not move with it** (955 against 955 on libraries, 12,871 to 12,374 on pairs), and franchise duplicates fall 18% to 17%. The channel buys agreement without buying fame, which is precisely what the fitted vectors could not claim.
- **The fitter is kept, and its output is a hypothesis rather than a patch.** It prints a ready-made eval variant string and tells the reader to test it against three label sets rather than ship it. Everything it found that survived that test was one coefficient; everything else it found was the label sets' popularity bias wearing a channel's name.
- **`percentile` is pinned to 0.5 whenever the obscurity dial is centred, which is right for scoring and useless for fitting.** The feature emission computes the live percentile regardless, or the fame diagnostic silently reports zero on a constant column - the same failure as `coread` above, arrived at from the other direction.

## v4: the pair label sets under-represent affinity, and that is now measured

- **The author-channel lead is dead, and killing it found a bias worth more than the lead was.** Switching the channel off measures **+0.0034** nDCG on three-seed MangaUpdates pairs (95% [+0.0004, +0.0064]) and halving it +0.0038 (95% [+0.0021, +0.0057]). On held-out READERS both reverse and hard: halving is **-0.0089** (95% [-0.0129, -0.0051]), removing it **-0.0255** (95% [-0.0321, -0.0192]), with median pick popularity collapsing 955 to 695 to 547. `Weights.Author` stays 0.75.
- **The explanation generalizes past this one channel.** A human submitting "if you liked X, try Y" reaches for a DIFFERENT creator, because the same-author case is too obvious to be worth submitting. So the pair graphs systematically under-count same-creator pairs, and a variant that stops rewarding them looks free there. A real reader who liked something goes and reads more by the same person, which is why held-out reading lists say the opposite.
- **Read this beside the franchise result, which is the same shape.** Collapsing franchises measured -0.0442 on held-out readers for the same underlying reason: readers act on affinity - same creator, same series, same world - far more than a curated recommendation list will ever admit to. **Any change that suppresses an affinity relationship will look free or positive on `reco`/`mu`/`mu-human` and cost real relevance on `library`.** Measure those changes on readers, and treat a pair-graph improvement on one as a warning rather than a result.
- **That is a second systematic bias on top of the popularity one, and they push the same way.** The fame bias makes an unconstrained fit prefer famous rows; the affinity gap makes it under-price the channels that find same-creator and same-franchise picks. Both are visible in the `pop` column, which is why every one of these reversals showed up there first: 955 to 405 for the fitted vector, 955 to 547 for the author channel.
- **Co-read is NOT redundant with the behavioural channel, measured.** The obvious worry, given both come from the same reading lists: switching co-read off costs **-0.0032** nDCG at three seeds (95% [-0.0047, -0.0018]). A sparse pair table and a factorization of the same data are still answering different questions, and the pair table is precise exactly where it has support.

## v4: the behavioural weight is a familiarity dial, and the two graders want opposite ends of it

- **`TasteVectorTuning.MaxSeedQueries` is 0, and the two vector spaces want OPPOSITE retrieval strategies.** In the text space the centroid dilutes, which is why `RecommenderTuning.MaxSeedQueries` is 48 and why raising it kept paying. Here it is monotone the other way: on held-out readers nDCG@40 is 0.182 / 0.179 / 0.175 / 0.170 / 0.172 at 0 / 2 / 4 / 8 / 16 behavioural seed queries. Centroid-only against the shipped 8 is **+0.0121** (95% [+0.0056, +0.0187]) with hit rate 91% to 95%, indistinguishable on the pair grader, and cheaper. These vectors were factorized out of whole reading lists, so a reader's centroid is already what the factorization was fitted to predict; querying individual seeds asks it to be a narrower reader than it is.
- **`TasteVectorTuning.MinInjectedScore` is inert across 0.50/0.70/0.85** on held-out readers (0.169 / 0.170 / 0.167, popularity unmoved), joining both crowd channels' injection gates in that category. Kept sweepable for the same reason theirs are.
- **`Weights.Author` is bracketed at 0.75 from both sides now.** Lowering it costs -0.0089 at 0.375 and -0.0255 at 0; raising it is indistinguishable at 1.5 (-0.0030, 95% [-0.0082, +0.0023]) and costs -0.0116 at 2.5, with the franchise-duplicate rate climbing 15% to 21% to 26%. The affinity finding says readers want same-creator picks, and this says the engine was already paying the right amount for them.
- **The Phase 5 fitter works. Fitting it on the pair graders was the mistake.** Refitted on held-out READERS it produces a vector worth **+0.0171 nDCG@40** there (95% [+0.0091, +0.0253]), and a conservative halfway blend between it and the shipped weights is +0.0162 (95% [+0.0093, +0.0232]). Median pick popularity RISES (943 to ~1600), so unlike the pair-fitted vector this one is not buying fame.
- **And it loses on the pair grader by about as much as it wins on readers**: -0.031 for the blend, -0.043 for the raw fit, at three seeds against MangaUpdates. Each fit overfits its own objective, in mirror image.
- **The disagreement is almost entirely ONE coefficient.** Isolated at three seeds against MangaUpdates: raising the behavioural weight alone from 2.5 to 10 costs **-0.033**, which is the whole of the blend's -0.031. Author 0.75 to 1.84 costs -0.012, and genre 1.0 to 0.16 costs nothing at all (0.154 against 0.153). Held-out readers want that weight near 10-17; curated pairs want it near 2.5.
- **Read that as a familiarity dial rather than a tuning failure.** The behavioural channel is trained on what readers actually read together, so weighting it heavily optimizes "more of what this person already likes" - affinity, and measurably so, with the franchise-duplicate rate rising 15% to 19% as it goes up. A human writing "if you liked X, try Y" is doing the opposite on purpose: reaching for a different creator and a different franchise, because the obvious neighbours are not worth submitting. **The two label sets are not disagreeing about quality. They are measuring two different products.**
- **Shipped at 2.5, which is the discovery end, and deliberately.** It is the value measured safe on both graders (+0.0035 on readers, indistinguishable on pairs). Nothing here says 2.5 is optimal for a reader who wants more of what they love; it says it is the value that does not sacrifice one objective for the other. A surface that knows which it wants - the whole-library Discover tab against the series-page rail - could reasonably ask for different numbers, and this is the coefficient to move.

## v4: what a hand-designed "feel" channel is worth, measured five times

- **`TagFormatCategoryBoost` ships at 1.0, inert.** `TagMath.StoryCategories` demotes `Work Info` and `Audience Demographics` deliberately - they are the least premise-bearing categories - and the feel columns say format agreement is by far the weakest thing the engine does (11-30% at one and three seeds against 69-90% for demographic). Boosting them exactly moves that column and costs relevance: at three seeds against MangaUpdates, nDCG@40 is 0.152 / 0.152 / 0.150 / 0.148 at boost 1.0 / 1.5 / 2.5 / 4.0 while format agreement climbs 25% to 27% and demographic 90% to 94%. On held-out readers it is inert because both columns are already saturated there (93%), which is also why the first sweep was run on the wrong mode.
- **`Weights.Distinct` stays 0, and now for a measured reason rather than an unexamined one.** Both fitted vectors wanted it positive (0.29 and 0.58). Isolated on held-out readers it is indistinguishable at 0.3 (-0.0009, 95% [-0.0079, +0.0062]) and costs **-0.0259** at 0.6 (95% [-0.0355, -0.0163]). The franchise-duplicate rate is what explains it: 15% to 27% to 35%. A candidate "distinctively closer to one seed than to the centroid" is very often another volume of that seed, so the term is a franchise amplifier wearing an attribution term's name.
- **Five hand-designed notions of "feel" have now been tested and none of them helped**: tag-taxonomy ancestors, franchise collapse, artists in the credit channel, a format/demographic boost, and per-seed distinctiveness. Three were inert, two were harmful, and every one of them moved the specific feel column it was aimed at. The column moved; the recommendations did not get better.
- **The one thing that did work was not hand-designed at all.** The behavioural channel does not encode any theory of what makes two series feel alike; it factorizes what readers actually read together and lets the answer fall out. It is worth +0.0266 nDCG@40 on held-out readers where the five designed channels are worth nothing, and it moves *every* feel column at once (demographic 58% to 71%, publisher 16% to 23%, era 1.11 to 0.61 decades) without being told any of those exist.
- **Take that as the direction for v5 rather than as five failures.** The catalogue metadata is already well mined by the tag, genre and credit channels; the marginal hand-built feature on top of them measures at zero. The behavioural artifact, by contrast, is built from 19,935 readers out of a `pending_user` queue holding 17,075 more, uses one of the two crowd sources available, and was trained with the first hyperparameters that ran. Every one of those is a lever that has never been pulled.

## v4: the behavioural trainer's central design claim was wrong, and fixing it doubled the gain

- **`build-taste-vectors.cs` trains on COMPLETED rows only, and that is a reversal.** It was built to spend the 6.9M rows the co-read graph discards - PLANNING, CURRENT, DROPPED, PAUSED, REPEATING - on the reasoning that intent and abandonment are signal being thrown away. Measured on held-out readers: **COMPLETED only 0.207, every status 0.182**, paired -0.0255 for the fuller data (95% [-0.0301, -0.0209]). The fuller data buys 1.6x the catalogue coverage (86,222 vectors against 53,652) and ranks worse anyway.
- **The likely reason is that the objective is COMPLETION.** A PLANNING row records what somebody added to a list; predicting that is a different and easier question than predicting what they will finish. Training on the first to answer the second imports a distribution that does not match the one being graded, and coverage cannot buy that back.
- **It goes the other way on curated pairs**, +0.0056 for the fuller data (95% [+0.0004, +0.0106]), which is the same discovery-against-familiarity split the behavioural weight shows. Readers win because the library gain is four and a half times the size and because "what will they actually read" is what a reading app is for.
- **With that fixed the channel is worth +0.0642 nDCG@40 on held-out readers** (0.143 to **0.207**, 95% [+0.0559, +0.0725]), MRR 0.363 to 0.467, hit rate 88% to 95%, the franchise-duplicate rate 21% to 16%, and median pick popularity *rising* 1043 to 1233. That is up from +0.0266 before the status fix, so more than half of the channel's final value came from taking data away.
- **Capacity is not the bottleneck: 256 dimensions measures indistinguishable from 128** (+0.0009, 95% [-0.0023, +0.0042]) for double the artifact and double the scan. Read that together with the status result: the model is not short of room, it was short of the right rows. `--all-statuses` restores the old behaviour so the finding stays reproducible.
- **`DROPPED` leaves with the rest, and the explicit negative survives anyway.** A reader who drops something completed nothing, so those rows go with the status filter. What remains is the score-derived dislike - a title somebody COMPLETED and rated well below their own average - which is 490,256 cells of the shipped artifact and is still something v3 could not express.

  | `nocrowd` | 29.17 | 61.67 | 631.17 | 0.6279 | - | 6815 |
  | `notaste` | 28.62 | 59.71 | 667.83 | 0.6211 | 0.700 | 4923 |
  | `default` | 24.54 | 57.17 | 623.67 | 0.6269 | 0.333 | 4066 |

  Adding it costs 14% of the distinct genres and pulls median pick popularity from 4,923 to 4,066, while replacing two thirds of the pool (overlap 0.333). Implicit ALS favouring well-listed items is exactly the known failure of the method.
- **On real held-out reading lists it goes the other way, and the two are not in conflict.** There `pop` moves 1,043 to 1,233, i.e. LESS fame-concentrated, alongside +0.0642 nDCG@40. A synthetic profile is 60 titles clustered on purpose; a real reading list spans hundreds and already covers most of the space, so there is no narrow neighbourhood for the channel to collapse into. Read the synthetic row as the price on a small, tight library and the held-out row as the answer for a real one - which is the same split the one-seed and whole-library `pop` numbers already showed for this channel.
- **Cohesion is the column that does not move**: 0.6269 against `nocrowd`'s 0.6279, so the picks are no more alike than with no crowd channel at all. What narrows is the genre spread, not the semantic spread, which is a different and milder failure than the one this tool was built to catch.

## v4 Phase 4: a recommendation-specific passage, measured and NOT shipped

- **`EmbeddingModelProfile.PassageFacets` ships off, because the passage is worth exactly zero and the feel columns say otherwise.** The plan's hypothesis was that the known text result - adding genres to the embedded passage cost MRR 0.493 to 0.393 - was a SEARCH result, and that recommendation, which matches a passage against a passage rather than a query against a passage, might pay differently. It does pay differently. It pays nothing.
- **The catastrophe did not reproduce, which is itself the finding.** `SeriesEmbeddingIndexer.BuildFacets` writes demographic, publication medium and page layout, the original-language house, and the six heaviest non-spoiler story tags, between the title and the description. Deliberately not genres, which are generic and already have a channel. Paired nDCG@40 against the plain index: **-0.0001, bootstrap 95% [-0.0022, +0.0022]** over 1,500 single-seed requests on the independent grader, and **-0.0022 [-0.0059, +0.0015]** over 500 held-out reading lists. Both span zero and both are tight. This is not the 0.152 collapse; it is nothing at all.
- **Every feel column moves, and more than any change except the behavioural one.** Single seed: demographic agreement 68% to **74%**, format 10% to 12%, original-language house 23% to **28%**, taxonomy distance 1.86 to 1.77. Three seeds: demographic 89% to **92%**, format 25% to **30%**, house 39% to **44%**. Recall and hit rate move too (R@40 0.145 to 0.154, hit 56% to 59% at one seed) while reciprocal rank goes the other way (0.255 to 0.251), which is the trade those columns buy: more of the right neighbourhood, not a better first pick.
- **So this is the sixth hand-designed change to move its own feel column, and the first to do it for free.** The other five cost relevance somewhere. This one costs nothing and gains nothing, which makes the case for shipping it entirely a case about a proxy metric this project wrote itself. That is not enough to make every install re-embed a 126,323-row catalogue.
- **Search prices it too, and the sign is the same direction the q4 note predicted, just far smaller.** Over the 190 hand-written queries: overall MRR 0.747 to 0.741, and `premise` - the largest class at n=90 and the one the semantic channel exists for - 0.607 to **0.577**. `creator` (0.564 to 0.612) and `filtered` (0.899 to 0.952) gain, but at n=14 each. Facets crowd the description out of a single pooled vector; that is the same mechanism, weaker because the clause is shorter and carries no genres.
- **The model half of the phase: no encoder swap is warranted, measured on the current catalogue rather than on August's.** The plan asked for the bake-off to be re-run "while the re-index is being paid for anyway", and although the facet re-index is not shipping, the question of whether `snowflake-arctic-embed-m` is still the right encoder is worth its own hour. On 2,000 held-out `clean` queries over all 126,323 rows, the shipped model scores MRR@10 **0.4205** against EmbeddingGemma-300m's **0.3886**: paired difference -0.0319, bootstrap 95% [-0.0474, -0.0165], McNemar p=8.19e-04 on the perfect scores (141 against 204). Gemma was the only candidate ever within reach - the August ordering over a 95,745-row pool was arctic-m 0.4561, gemma 0.4201, bge-base 0.3512, bge-large 0.3392, Qwen3-Embedding 0.2687 - and it loses clearly at full catalogue size.
- **Two gotchas cost an hour between them before that number existed.** A file-based app builds into a hashed folder under `%TEMP%\dotnet\runfile`, and a previous run still holding that folder makes the next build fail with `MSB3021` rather than anything about the tool; the eval then falls through to the paired-comparison step and happily reprints the PREVIOUS run's cached per-query files as if they were fresh. The tell is the elapsed time: five models in 2:14 means nothing was embedded. And `bge-large` at fp32 batch 128 fills 15.7 GB of a 16 GB card and drops from 236 passages/s to 23; batch 32 is what makes a large candidate finishable.
- **`run-eval.ps1 -Cuda` left `Maki.Metadata` restored against the GPU ONNX Runtime.** `-p:MakiOnnxGpu=true` is a global MSBuild property precisely so it invalidates the restore and flows to the ProjectReference, which also means its effect outlives the run. `publish-embeddings.ps1` has always undone it; this script never did, so a bake-off quietly changed which runtime every later build linked - fine here, an `EntryPointNotFoundException` on a machine with no CUDA, and in neither case anything that mentions the bake-off. `Restore-CpuOnnxRuntime` moved into `gpu-libraries.ps1`, which is the file that exists for exactly this ("Two copies would drift, and the failure mode of a drifted copy is a silent fall back to CPU").
- **`eval-embeddings.cs` was the one measurement tool not pinning `InvariantCulture`.** Its CSVs were always fine, since those pin the culture at the point of writing; its printed tables read `0,4205` on this machine, which is the number that gets quoted into a doc comment beside one written `0.4561`. The other three eval tools all pin it and all say why.

- **The mechanism, the build target and both eval flags are kept, in the same category as `TagAncestorDecay`.** `build-embeddings.cs base-facets` writes `embeddings-base-facets.db` under its own version string, and `eval-reco-labels.cs --facets` / `eval-search.cs --facets` grade it - without which every row is dropped at load as a model mismatch and the table reads as zeroes rather than as an error. Nothing publishes it: `publish-embeddings.ps1` asks for `base`.
- **`--keep-dump` exists because an A/B over two passages is only valid over one catalogue.** Step 1 of the build otherwise re-downloads several GB the moment upstream republishes, and the two indexes would then describe different series sets with the difference unattributable. Verified before grading: rebuilding the plain index against the same dump reported `embedded 0, unchanged 126323`, so the baseline and the faceted index differ in the embedded text and in nothing else.
- **`distribution/eval-embeddings.cs` had not compiled since `1924965 fix: retire large embedding model option`.** Its candidate table referenced `EmbeddingModelProfile.Large`, which that commit deleted. Nothing catches this: a file-based C# app is not part of `Maki.sln`, so `dotnet build` and `dotnet test` are both green while the tool is dead, and it only surfaces when somebody runs the bake-off. The profile is now defined inside the candidate table, which is where a retired product tier belongs anyway.

## v4 Phase 6: the inert knobs, re-measured with a third channel injecting

- **`CosineFloor` is still inert, and the behavioural channel was its best chance not to be.** The floor was measured inert at 0.30 before v4, and the open question was whether that survived a channel that can put a row in the pool on evidence the text index has none of. It does: over 400 single-seed requests on the independent grader, `cosinefloor` at 0, 0.15, 0.30 and 0.45 is **byte-identical on every column including all six feel columns**, and on 250 held-out reading lists 0 and 0.30 are byte-identical too. What readers finish together is semantically near enough to clear 0.30 anyway.
- **It does bind above 0.60, and the cost is the same shape on both graders.** Single-seed nDCG@40 0.140 at the shipped floor, 0.136 at 0.60, 0.128 at 0.75, with median pick popularity falling 13,093 to 10,687. Held-out readers: 0.208 to 0.202 at 0.60, and `pop` moves the wrong way there (1,428 to 1,675). So raising it does not buy obscurity, it buys a smaller pool.
- **`CrowdBypassesCosineFloor` remains a switch on a branch nothing takes.** Byte-identical to `default` at the shipped floor with three channels injecting rather than two. It is live only above 0.60, which is where the floor already costs relevance, so it stays on and stays undecidable.
- **The two crowd caps are still inert; the behavioural one is not, and 100 is its knee.** `coreadmaxinjected` at 10, 50 and 200 are indistinguishable, and `graphmaxinjected` at 10 costs 0.002 at one seed and nothing on readers. `tastemaxinjected` is the exception: 10 measures nDCG@40 **0.134 against 0.140** at one seed (MRR 0.134 against 0.148, demographic agreement 63% against 68%) and **0.198 against 0.208** on held-out readers. The artifact is dense enough that the cap binds before `MinInjectedScore` does, which is the reverse of both graphs.
- **Above 100 it saturates rather than improving.** 200, 300, 600 and 1200 return the same nDCG on 800 requests; the paired difference against 100 is -0.0033 (95% [-0.0072, +0.0007]) with R@40 up 0.148 to 0.152 and MRR down 0.256 to 0.253. Recall for precision at the top, not a gain. Left at 100.
- **`TasteTuning.TypeAffinityWeight` is deleted rather than wired.** It was inert twice over: zero by default, and multiplied by a `typeAffinity` no caller computed. Wiring it would have been a sixth hand-designed feel channel after five measured flat, and the behavioural vectors now subsume exactly this signal by learning it: manga against manhwa against manhua is one of the strongest patterns in reading co-occurrence, so it arrives in the cosine without being declared. One multiply line comes back if a future signal wants it.
- **`recommendations.prebuiltenabled` is now read.** The key, the admin endpoint and the frontend hook all existed; `PrebuiltIndexInstaller.IsEnabledAsync` returned `options.Enabled` and never consulted it, so the toggle stored a value nothing acted on. `RecommendationsCoGraph`'s own doc cited it as the trap to avoid. The switch is real (an air-gapped install otherwise retries the manifest daily forever, and a fork building its own vectors wants the local pass to win), so it is wired rather than removed, gated in `InstallAsync` as well as in the job because the settings page's "Download now" reaches `InstallAsync` directly.
- **`SeriesMetadata.AnimeName` was always empty, and the `?? string.Empty` was what made it harmful.** `anime` is NULL for all 558,743 rows of the published dump and all 558,421 of the full one, and `MangaBakaLocalStore` is the only code that fills the field. Mapping NULL to `""` defeats `SeriesMetadataRefreshService`'s `?? existing` preserve rule, so a refresh actively overwrote whatever was there. Nulls now stay null. `anime_start` and `anime_end` are real but thin: 3,126 and 2,514 rows.
- **`genres` splitting `Sci-Fi` from `Sci-fi` turns out to cost nothing, and that is worth recording so nobody "fixes" it.** Every consumer is already case-insensitive: `VectorIndexCache`'s genre vocabulary, `SemanticRecommender`'s seed profile, `LibraryCompositionService`'s tally and `ActivityStatsService`'s weights are all `StringComparer.OrdinalIgnoreCase` dictionaries, and browse matches with a case-insensitive `LIKE`. The two spellings collapse everywhere they are counted or matched. Only the displayed label is arbitrary between them.
- **An unknown `--flag` is now an error in `eval-reco-labels.cs` rather than a variant name.** Variant names are free-form because they become CSV filenames, so `--libraries 300` (the flag `run-reco-suite.ps1` takes, which the eval calls `--requests`) scored two variants named `--libraries` and `300`, each at the default request count, and printed a table that looked completely normal. It cost an hour of CPU before the variant column was read closely.

## v4: the familiarity dial, priced

- **`TasteVectorTuning.Weight` still ships at 2.5, and the better artifact moved the reader optimum well above it.** Re-swept on held-out readers against the COMPLETED-trained artifact: **+0.0114 at 4.0** (95% [+0.0080, +0.0149]) and **+0.0172 at 6.0** (95% [+0.0116, +0.0228]), with the franchise-duplicate rate FALLING 16% to 14% to 13% and median pick popularity rising 1233 to 1451. Neither of the usual warning signs fires.
- **The same raise costs the independent pair grader -0.0087 at 4.0** (95% [-0.0115, -0.0061]) **and -0.0205 at 6.0** (95% [-0.0251, -0.0159]). That is the exchange rate, and it is now measured at three points rather than argued about:

  | weight | held-out readers | curated pairs | ratio |
  |---|---|---|---|
  | 2.5 (ships) | +0.0035 | -0.0012 | ~3:1 for readers |
  | 4.0 | +0.0114 | -0.0087 | ~1.3:1 |
  | 6.0 | +0.0172 | -0.0205 | net negative |

- **No measurement picks a point on this dial; only the product does.** Held-out reading lists ask "what will this person finish next", which rewards familiarity. Curated pairs ask "what would a knowledgeable stranger suggest", which rewards discovery. 2.5 is the conservative choice with the best ratio and is safe on both. 4.0 is where the reader gain still exceeds the pair loss in absolute terms. 6.0 is past the crossover and should not ship without a deliberate decision that this is a familiarity product.
- **Whoever moves it should move it per surface rather than globally.** The series-page rail answers a single seed, where there is no seed-query dilution and the discovery framing fits; the whole-library Discover tab answers a reader, where the familiarity framing does. `SimilarSeriesService` and `RecommendationService` already resolve their own weights, so this costs a parameter, not an architecture - the only thing standing against it is the deliberate decision recorded in `SimilarSeriesServiceTests.The_rail_asks_for_the_same_channel_weights_Discover_does`, which was about channel weights drifting by accident rather than by measurement.
