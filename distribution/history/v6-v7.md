# Distribution history: v6 (256d embeddings) and v7 (EASE, rail votes, judged panel)

## v6: the embedding model, at 256 dimensions

The goal was a smaller resident footprint for the discovery artifacts. Two changes ship: every snapshot is memory-mapped instead of read onto the heap, and the text encoder moves from `snowflake-arctic-embed-m` (v1, 768 dims, int8) to `snowflake-arctic-embed-m-v1.5` truncated to 256 dims and packed at 4 bits. Three candidates were graded on the 128,403-row catalogue: v1 at lower widths, v1.5 with Matryoshka truncation, and `snowflake-arctic-embed-m-v2.0` (multilingual, XLM-R tokenizer) truncated the same way. Logs and per-request CSVs are in `.artifacts/v15/`.

- **v1 cannot be truncated.** It was not trained for it: held-out clean MRR@10 goes 0.4382 at 768 to **0.2679** at 256. Option 1 was dead after one run.
- **Dense channel on its own (`eval-embeddings.cs`, n=2000 held-out clean queries):** v1 0.4382, v1.5 0.4220, v1.5@384 0.3879, v1.5@256 0.3773, v2 0.3782, v2@256 0.3374. Paired against v1, v1.5@256 is -0.0608 and v2@256 -0.1008. The isolated model gets worse, and that is not the number that decides it, for the reason `eval-search.cs` exists: the dense channel is one of three fused ones.
- **On the hand-written queries the order flips.** Overall MRR v1 0.3574, v1.5 0.4143, v1.5@256 0.3973, v2@256 0.4199. v2 earns its overall figure on `title` and `typo`, which the lexical channel already answers; on `premise`, the class the dense channel is for, v1 0.3499, v1.5@256 **0.4035**, v2@256 0.2955. v1.5@256 against v2@256 on premise is +0.1079 [+0.0519, +0.1663], p=0.0018.
- **v2's multilingual support is real and weak.** `eval-queries-multilingual.tsv` (30 premises in en, de, es, fr, ja, ko, zh) scores v2 at de 0.23, es 0.17, fr 0.21, ja 0.08, ko 0.05, zh 0.06, where the English-only models score about 0 outside English. Its English premise score on the same set is 0.31 against v1.5's 0.45. It buys a little reach in European languages and pays for it in the language every passage is written in.
- **v2 also costs memory, which was the point of the exercise.** CPU int8 embedder: v1 and v1.5 are both a 105 MB file and +139 MB private bytes once loaded; v2 is 297 MB and **+390 MB**. That is +251 MB resident on every install that embeds a query, to save tens of MB of vectors.
- **Full search fusion (`eval-search.cs`, 190 queries), shipped build against v1:** ALL 0.784 against 0.748, paired **+0.0358 [+0.0085, +0.0646]**; premise 0.663 against 0.596, **+0.0670 [+0.0153, +0.1214]**. v2@256 scored 0.763 / 0.610 in the same harness.
- **Recommendations, shipped build against v1, nDCG@40 paired:** single-seed mu-human -0.0001 [-0.0037, +0.0036], nocrowd +0.0008 [-0.0043, +0.0060], three-seed mu-human -0.0013 [-0.0047, +0.0020], single-seed reco **+0.0108 [+0.0049, +0.0170]**, held-out libraries +0.0016 [-0.0036, +0.0067], libraries with no crowd channels -0.0053 [-0.0117, +0.0009]. Neutral everywhere it matters, ahead on curated pairs. The text-only library row is the one blemish (the int8 candidate read -0.0062 [-0.0121, -0.0003] there); with the crowd and behavioural channels on, which is what ships, it is gone. Library median pick popularity rises 1,413 to 1,982, i.e. less fame-concentrated, and the scan falls 280 to 142 ms per request.
- **4-bit packing is free at 256, so `PackMinimumDimensions` is 256 now, not 512.** Same index, q4 against int8: single-seed mu-human -0.0010 [-0.0028, +0.0007], held-out libraries +0.0010 [-0.0010, +0.0031]. The 512 floor was a guess about narrow vectors losing too much to 4 bits, and it was wrong at this width.
- **Decision: v1.5 at 256, packed.** v2 is rejected on the English premise loss, the -0.10 dense-channel gap, the +251 MB embedder and a 3x download, none of which its cross-lingual scores repay. `EmbeddingModelProfile.Candidates` keeps all five configurations so the bake-off reproduces; `ArcticV1` is the old profile.
- **Memory and size, v1 heap against v1.5-256 mapped, same catalogue:**

  | | before | after |
  |---|---|---|
  | vector index heap (with taste layer) | 76.9 MB | **3.5 MB** |
  | vector data inside it | 49.3 MB | 16.4 MB |
  | `embeddings.vecindex` on disk | 74.2 MB | 42.9 MB |
  | catalogue indexes heap | 16.9 MB | **0.5 MB** |
  | co-read graph heap | 16.8 MB | **0.1 MB** |
  | `embeddings.db` | 158 MB | 65 MB |
  | prebuilt download (zst) | 109 MB | 42 MB |
  | snapshot reload | 206 ms | 165 ms |
  | embedder, loaded | +139 MB | +139 MB |

  Mapped pages are file-backed, so the OS can drop them under pressure and re-read them rather than swap them. Measured on its own before the model change, mapping alone took the v1 vector index from 68.9 to 3.5 MB of heap.
- **v1.5's ONNX export is pooled in the graph.** It outputs `sentence_embedding`, not `last_hidden_state`, so the profile is `EmbeddingPooling.Pooled`; asking for CLS fails at session start with "last_hidden_state is not in the metadata". Truncation happens in `TextEmbedder` after pooling and before normalizing, so a profile's `Dimensions` below the graph's width is the whole of Matryoshka support.
- **v2 needed the fairseq id remap, and it is kept for the candidate.** XLM-R's SentencePiece ids are offset from the model's vocabulary (spm 0 to 3, 1 to 0, 2 to 2, n to n+1); `TextEmbedder.FairseqId` does it, verified against the Hugging Face tokenizer on 8 of 8 strings. Without it the model embeds every token one id off and scores look merely bad, not broken.
- **Switching the model re-embeds or downloads, and the old folder is deleted once.** The version string changes, so every existing vector is filtered as a model mismatch; the prebuilt tag is `embeddings-base-v15-256-latest`, which `publish-embeddings.ps1` reads from the `Base` profile. Publishing it before the release is a checklist step, or every install falls back to a local build. `EmbeddingModelStore.RemoveRetiredModels` deletes the listed retired folders, and only when the shipped profile is in use, because the models directory also holds the upscaler's.
- **`eval-reco-labels.cs --quant` had not compiled since `6b177cef`.** It read `TasteLayer.Data`, which the layer keeps private, and reached the text vectors by reflection on a field name. It now calls `VectorIndex.Requantized` and `VectorIndexCache.ReplaceLoadedForEval` through `InternalsVisibleTo`, so a rename is a compile error in the tool rather than a silent one.
- **Two eval gotchas from this run.** The single and small modes both wrote `rr-<variant>-mu-human.csv`, so running them back to back overwrote the first; the scripts move each step's CSVs into its own folder. And batch 128 on the GPU thrashes once the desktop holds a few GB of VRAM (15.8 of 16.3 GB, an order of magnitude slower); `MAKI_EMBED_BATCH=32` is what finishes.

## v7: grading what ships, and a judged panel

Background and the numbers behind each choice are in `research/recommender/2026-11-15-v7/` in the main checkout (git-ignored), mostly `evaluation/evaluation-audit.md` and `evaluation/evaluation-proposal.md`.

- **`rail` is the series-page rail as it ships, and it had never been graded.** `SimilarSeriesService` switches the vote graph, the co-read graph and the taste vectors off and asks for diversity 0.15. The `rail` shorthand still stood for the reduced weight vector that service deleted long ago, and `nocrowd` is not the rail either, because it leaves the taste channel on. Graded as shipped over the suite's 500 single-seed requests (the pre-v7 request set): nDCG@40 **0.032 against 0.138** for `default` on mu-human, paired -0.106 (95% [-0.120, -0.092]), hit rate 19% against 58%; on reco 0.087 against 0.201, paired -0.115 (95% [-0.132, -0.098]). One look at the confirm split agrees: mu-human 0.032 against 0.147, paired -0.115 (95% [-0.129, -0.101]). The diversity term costs nothing; the whole gap is the three crowd channels. Both graders are crowd pairs, so they favour crowd channels by construction, which is the reason the panel below exists. `rail` is a default variant in `run-reco-suite.ps1` now.
- **Requests are split into dev and confirm, and `dev` is the default.** `--split dev|confirm|all`: one bucket of five by `UserFold.Of(id, 5)`, on the seed id in the pair modes and the reader id in `library`. Roughly 630 result files had been scored on the same fixed request sets, with sweeps, fits and their confirmations all reading the same requests. Sweep and fit on `dev`. A default changes after one run on `confirm` agrees in sign with an interval that excludes zero, and not for a gain under 0.005 nDCG@40 unless the change is free. `all` reproduces the request sets every earlier row in this file was scored on, so **a `dev` number does not compare with any number above this section**. The confirm set draws from its own RNG stream.
- **`top1k` sits beside `pop`, and `--strata` also splits recall by how famous the LABEL is.** `top1k` is the share of picks inside the 1,000 most popular series. The label-popularity table reports recall over the labels in the top 1k, 1k to 20k and past 20k. On 60 mu-human requests the crowd channels' gain over `nocrowd` was 0.069 to 0.169 on top-1k labels and 0.169 to 0.176 past rank 20,000: that is the fame bias as a row instead of an inference from a median.
- **The judged panel is the only grader with a column for story and feel, and the only one where an unlabelled pick is not a miss.** 92% of `default`'s top-10 picks carry no mu-human label and count as wrong there; mu-human covers 4.1% of the index and 0.3% of its seeds are from the 2020s. `eval-reco-labels.cs single --panel distribution/eval-panel.tsv <variants>` runs fixed seeds, takes each variant's top `--depth` (10) and grades them against `.artifacts/judgements.db`. Picks with no stored judgement are reported as unjudged and written to `.artifacts/eval/judge-queue.tsv`; they are never scored as zero. A pair is judged once and reused by every later variant that returns it.
- **The panel is 300 dev seeds and 100 holdout seeds, checked in** (`distribution/eval-panel.tsv`, built by `build-eval-panel.py`). Four popularity bands with equal budgets, three types, three eras, a floor per populated cell and the rest by the square root of the cell size. A seed needs a 200-character synopsis and three non-spoiler tags and is never pornographic, so the judge has something to read. The holdout set is for one judging pass per release and is not in the suite. **Rebuilding the panel orphans every stored judgement**; the draw is stable for a given dump, not across dumps.
- **The first column of every `rr-*.csv` is the request's identity, not its row number**: the seed id for one seed, a hash of the seed list otherwise. `eval-compare.py` pairs on that column, so files from different splits or panel sets share no key and it refuses them. With a row index it paired request 7 of one seed set with request 7 of another and printed a normal-looking interval. `--fold-users k/5` with a split is refused for a related reason: both hash the same id, so fold 4 of 5 is exactly the confirm set.
- **In the judged table `good`, `poor` and nDCG are taken on `feel`**, the scale the judge is trusted on. The nDCG ideal is everything judged for the seed, so it moves as more pairs are judged and does not compare across dates.
- **Two scales, never merged: `enjoy` and `feel`.** `enjoy` ("a reader who liked the seed would enjoy this") was meant as the primary number for the rail; the known-pair check below shows the judge cannot tell it from `feel`. `feel` ("similar story, tone and feel") is the half no crowd label can see. The content channels and the crowd channels are expected to disagree on them, which is the measurement the "Reads alike" against "Readers also" question needs. Per-seed values go to `rr-<variant>-judged.csv` and `rr-<variant>-judged-feel.csv` for `eval-compare.py <a> <b> judged`.
- **The judge reads catalogue text only** (`judge-pairs.py show <seed> <candidate>` prints the exact prompt): title, format, creators, genres, non-spoiler tags, a cleaned synopsis. No popularity, rating, rank, variant or engine reason. It says separately whether it recognises each title, so scores can be split by that later; an LLM knows famous series far better than obscure ones and that is the bias to watch.
- **The judge is part of the key.** A row is (seed, candidate, judge, rubric) with judge = `<model>/<effort>`. The eval reads one judge at one rubric version and never averages two; with no `--judge` it takes the one with the most rows. Changing the rubric text means bumping `RUBRIC_VERSION`. No fallback model is configured, on purpose: a second model answering for the first would file two judges under one name. A refusal is stored with its own status and counts in the `thin` column.
- **The judge is checked without a human scorer, and what the checks found limits what it is for.** The owner has not read most of the catalogue, so scoring pairs from the same cards the judge reads would check nothing. `judge-pairs.py known` takes 160 pairs MangaUpdates readers recommended by hand (different creators) and gives each seed two controls of the real pick's type and popularity band: `near` shares two of the seed's genres, `far` is otherwise random, and neither is a pair any crowd links. `claude-opus-5-5/low` scored the human pick above `far` with probability 0.82 on `enjoy` and 0.83 on `feel`, above `near` with 0.79 and 0.77, and above `far` with 0.76 and 0.78 where it did not recognise the candidate. 1% of each control reached 2 on `enjoy`. A second pass over 150 pairs (`run --tag repeat`, then `agreement --against`) gave weighted kappa 0.94 on `enjoy` and 0.96 on `feel`. Medium effort scored the same pairs the same (0.82 and 0.83), so effort stays `low`. **The limit: only 41% of the human picks reached 2 on `enjoy`** (25% at two recommenders, 67% at ten or more), and `enjoy` equals `feel` on 80% of pairs and sits one above it on 19% (Pearson 0.87). The judge reads catalogue text, so it sees story similarity and little else. Its `enjoy` is `feel` with a small allowance, not evidence of what readers like, and it reads the same tags and synopsis the content channels rank on, so it leans toward them the way crowd labels lean toward the crowd channels. `calibrate`, `import-labels` and `agreement` still exist for a scorer who has read both series of each pair; nothing waits on them.
- **One primary metric per surface, except the rail, which needs two.** Series-page rail and the Discover modal: judged `feel@10` with the share of poor picks for the story half, and mu-human nDCG@40 for the readers half, side by side. Each grader is blind to the other half, so a change that wins one and loses the other is a trade to decide, not a win. Judged `enjoy@10` is reported and is not a primary number, for the reason in the bullet above. Recommended tab and Home: `library` nDCG@40 on a held-out reader fold. Recent-activity rail: `small` mode until the panel carries multi-seed requests. Reader-cohort rail: `eval-reader-cohorts.cs` recall@40. The reader-against-pairs disagreement on `TasteVectorTuning.Weight` stops being a dilemma once each surface names its own metric.
- **`MAKI_ARTIFACTS_DIR` names the artifacts folder**, the way `MAKI_CONFIG_DIR` names the config one. `.artifacts/` and `.simulated/` are git-ignored and sit in the main checkout, so the eval tools, `eval-compare.py`, `judge-pairs.py` and the suite could not run from a worktree at all before this.
- **First judged numbers: the shipped rail loses on story and feel too, and the taste channel is the whole of what it is missing against `nocrowd`.** 300 dev seeds, top 10, 6,143 pairs judged by `claude-opus-5-5/low` at rubric v1 (about $18 as a batch, $0.0033 a pair with the rubric cached). `feel@10` / `enjoy@10` / poor picks (scored 0 on `feel`): `default` 1.633 / 1.909 / 3%, `notaste` 1.639 / 1.862 / 5%, `nocrowd` 1.561 / 1.831 / 3%, `rail` 1.447 / 1.605 / 8%. Paired on `feel@10`: `rail` against `default` -0.185 (95% [-0.222, -0.149]), `rail` against `nocrowd` -0.114 (95% [-0.147, -0.082]), `nocrowd` against `default` -0.072 (95% [-0.087, -0.057]), `notaste` against `default` +0.006 (95% [-0.019, +0.031]). `rail:diversity=0` scores the same as `rail` and `nocrowd:diversity=0.15` the same as `nocrowd`, so the diversity term is free here as well and the gap between the two is the taste vectors alone. The judge leans toward the content channels and still prefers the lists the crowd channels helped build, in every seed-popularity band (rail against default on `feel@10`: 1.51 against 1.79 for top-1k seeds, 1.41 against 1.47 past rank 20,000). So the reason the rail runs content only, that a crowd-paired pick is off-topic under "More like this", is not what the judge sees: the content-only list is the less story-alike one, with more than twice the poor picks and a median pick at rank 24,000 against 10,000. In every bullet above this one, `rail` means that content-only list, which the eval now calls `railcontent`.
- **The rail got the taste vectors back, and `rail` now means that.** The owner's call on the numbers above: the row is for series alike in taste and story, so the behavioural vectors belong and the two pair graphs ("who else read this") stay off. `SimilarSeriesService` passes `taste` from the instance's `recommendations.tastevectors` switch, keys its cache on it, and clears `TasteMatch` on what it returns, because the card prints that as "Close to your taste" and this pool is about the seed and shared by every viewer. `rail` against `railcontent` on the dev panel: `feel@10` 1.569 against 1.447, paired +0.121 (95% [+0.088, +0.155]), poor picks 3% against 8%, median pick at rank 10,560 against 24,374 (98% of the new list's top 10 is judged). On mu-human, dev split: nDCG@40 0.094 against 0.036, paired +0.059 (95% [+0.048, +0.070]), hit rate 46% against 22%. One run on the confirm split agrees: 0.100 against 0.032, paired +0.068 (95% [+0.057, +0.080]). What is still left on the table against `default` is -0.064 on `feel@10` (95% [-0.079, -0.050]) and -0.049 on mu-human nDCG@40 (95% [-0.057, -0.041]): that is the price of keeping the pair graphs off this rail. In this bullet `rail` is the taste-only rail, which the eval now calls `railtaste`; see "v7: votes on the rail".
- **Not built yet:** a regression set of seeds with must-have and must-not neighbours; the order-swap check on the judge; a second judge from another model family; a harness entry that runs `RecommendationService` itself, so `Spread`, reason balancing and seed weighting are inside a measurement; a dated split, which needs the list fetch to store dates.

## v7 step 3: a cleaned plot text, measured and NOT shipped

- **The cleaned plot text was not shipped. The description junk is real and costs nothing measurable.** 17% of embedded description characters are links or markup, and `PassageText` removes them: markdown links and bare URLs, emphasis, "(Source: ...)" credits, and labelled sections such as "**Original Webtoon:** ... **Official Translations:** ..." whether they sit on their own lines, on the line below their label, or on the plot's own line. Where the MangaUpdates text is under 200 characters it takes the longest of the MangaUpdates, MangaBaka and Kitsu texts instead. That changes 61% of descriptions and takes the mean from 413 to 333 characters. Graded against the shipped index over the same dump (2026-11-03 full dump, 128,403 rows both, 41.5% of vectors identical at cosine 0.999 or more):

  | grader | variant | shipped | cleaned | paired, 95% |
  |---|---|---|---|---|
  | mu-human nDCG@40, 500 dev requests | `rail` | 0.0942 | 0.0934 | -0.0008 [-0.0042, +0.0024] |
  | | `default` | 0.1428 | 0.1418 | -0.0010 [-0.0039, +0.0015] |
  | judged feel@10, 300 dev seeds, 100% judged | `rail` | 1.567 | 1.561 | -0.006 [-0.022, +0.010] |
  | | `default` | 1.633 | 1.636 | +0.003, spans zero |
  | | `railcontent` | 1.447 | 1.432 | -0.016 [-0.050, +0.015] |
  | search MRR, 190 queries | all | 0.7835 | 0.7801 | -0.0034 [-0.0327, +0.0272] |
  | | premise, n=90 | 0.6636 | 0.6788 | +0.0152 [-0.0408, +0.0748] |
  | | filtered, n=14 | 0.8801 | 0.7726 | -0.1075 [-0.2607, +0.0009] |

  Every interval spans zero. The encoder reads past the junk: a link list after the plot barely moves a pooled vector, and the content-only variant, the one with nothing else to lean on, is the one that moved least in the right direction. This is the same shape as the faceted passage in "v4 Phase 4": a passage change that is plausible, cheap to state, and worth nothing once graded. It does not justify re-embedding every install.
- **Build the comparison index on the same runtime as the baseline, or the comparison is noise.** The first cleaned build ran on the CPU with the default quantized model; the published index is CUDA fp32. Rows whose text had not changed came out at cosine 0.985 against the shipped vectors, so every row carried that difference on top of the cleaning. The check is cheap: rows with unchanged text must reproduce the baseline vector. On CUDA the pass takes 2.5 minutes (900 rows a second) against 77 on a busy CPU.
- **Dropped, code not merged.** The mechanism (`PassageText`, `EmbeddingModelProfile.PassageClean`, `build-embeddings.cs base-clean`, `--clean --vectors` on `eval-reco-labels.cs` and `eval-search.cs`) lived on `feature/reco-text-channel` (tip 4fab515dd, based on 87f54a827) and was dropped on 2026-11-19 rather than kept sweepable: nothing graded it above zero. The three commits are saved as patches in `research/recommender/2026-11-15-v7/step3-clean-text/patches/` in the main checkout; `git am` them onto a branch to reproduce the table.
- **Not done from step 3, and the reason to be sceptical of each:** the hub correction (one float per row; +0.004 nDCG graded alone on a channel that scores 0.014 alone), the title-leak projection (the weakest of the three content experiments), and keeping art books, guides and doujinshi off the rail with spoiler tags unscored (hygiene, not relevance; no label set sees it). Three content-side changes have now been graded in the engine across v4 and v7 and all three were flat, while the two behaviour-side changes (taste vectors on the rail, the taste channel itself) were the large ones.

## v7: an EASE item-item channel, measured inside the blend and SHIPPED at weight 4 from two seeds up

Research round in `research/recommender/2026-11-15-v7/exp-behaviour/` (main checkout): EASE^R graded alone beat the taste vectors by +0.130 nDCG@40 on held-out readers. This section is the same model inside `HybridScore`. Scripts, logs and per-request CSVs are in `research/recommender/2026-11-15-v7/step4-ease/`.

- **What exists.** `distribution/build-ease-table.py` fits EASE^R (20,000 most-completed items, lambda 300, readers with at least 300 list entries) on the co-read working database's COMPLETED rows and keeps each seed's top 100 weights by absolute value, negatives included (2M rows, 38 MB, about 30 s). `--fold-out k/n` uses the same FNV-1a `UserFold` and records `meta.trainingFold`. `Maki.Metadata.Ease` (`EaseTable`, `EaseCache`, `EaseScorer`, `EaseTuning`) scores a seed set as the seed-weighted sum of table weights, divided by the best candidate's sum, floored at -1, with co-read-style pool injection. Eval keys: `easepath`, `easeweight`, `easenegative`, `easemaxinjected`, `easemininjected`.
- **`library` mode can grade co-read now.** `fetch-coread-graph.cs build --fold-out k/n` (run it against a copy of the working database, since build overwrites the stored matrix) and `export` writes `meta.trainingFold`. With such a graph installed, `library --fold-users` keeps co-read on instead of forcing it off. Before this, every `library` number in this file was measured without the co-read channel. Fold 0 graph: 39,285 readers, 1.79M pairs. It adds +0.0058 [+0.0041, +0.0076] on held-out readers.
- **The fold guard used to let a full taste artifact through.** `ReadTrainingFolds` reads `trainingFold = all` as "no claim", so `library --fold-users 0/4` against `.simulated/taste-vectors.db` (trained on every reader) graded it without complaint. Taste and EASE artifacts must now name their folds in fold mode. `--taste <path>` points the eval at a fold-limited taste build without copying it into the config dir. Note that a different taste file changes the vector snapshot key, so the eval rewrites `embeddings.vecindex` beside `embeddings.db`; use a private config dir to keep it out of `.simulated`.
- **The page-share table is a reader-derived input too, and the guard reads it** (v8). It is counted off reader pages, so a table holding a graded reader's page has seen that reader's shelf. In every `library` run (fold or not) each table a `commonweight` variant reads (`--common`, `commonpath`) must show it holds none of the graded readers, or the run is refused: a `.db` whose `meta.trainingFold` is `all` always is (the published table), a `.db` or text table with `<table>.provenance.json` is checked reader by reader against its `readerIds` (or by fold against its `foldUsers`), and a `.db` from one fold of readers (`trainingFold = readers k/n`) by fold. `eval-overlap.py table` and `build-page-share.py` (for evaluation builds) write the sidecar from the `readerIds` the pick dump's `.json` now records, so `table --skip 500` on a fold-0 dump passes when grading that fold's first 500. A table with no sidecar, which is every table built before this (`page-frequency-current-cap10.tsv`, lane B's `page-frequency-*.tsv`), is refused; `--common-unchecked` runs it anyway with a note, for reproducing those rows or deliberate research. Verified on fold 0, 20 readers: the published `page-share.db`, the cap-1.0 twin and a table over readers 1 to 60 are refused, a table over readers 21 to 60 is graded.
