# CLAUDE.md — Maki.Sources

Non-obvious per-source scraper facts (`ISource` implementations). Migrated out of the root CLAUDE.md so they only load when working here.

- **MangaDex delists English chapters of licensed titles.** For E2E tests use unlicensed titles (e.g. Hajime no Ippo) — licensed ones (Frieren) have 0 downloadable EN chapters.
- **Four sources are multi-language; the other nine publish English only.** `SourceCapabilities.SupportsLanguageFilter` means "`ListChaptersAsync` honours `languageFilter`" (a comma-separated list, parse it with `SourceLanguages.Parse`, where null means `en`, not "all"), and only **MangaDex** and **MangaFire** declare it. MangaDex repeats `translatedLanguage[]` per code, so several languages cost one paged walk, and tags each chapter with its own `attributes.translatedLanguage`. MangaFire has no subset view: one language drives the "Lang" dropdown to it, several drive it to `MangaFireBrowser.AllLanguages` (`"all"`, absent from `LanguageLabels` on purpose, the lookup missing is what routes it to the "All" item the fallback already clicks) and each item is kept or dropped on its own `language` field. **MANGA Plus is multi-language and declares the capability false**, correctly: a title id *is* a language (the Spanish One Piece is a different id with a different chapter list), so there is nothing to filter and a second language is a second mapping. Asura, Atsumaru, Flame Comics, MangaKakalot, MangaKatana, MangaPill, TCB Scans, TopManhua and WeebCentral are genuinely English-only catalogs. **Webtoons is multi-language and declares the capability false**, the same shape as MANGA Plus: each locale (`id`, `th`, `es`, `fr`, `zh-hant`, `de`, alongside `en`) runs its own service with its own `title_no`, so there is nothing to filter and a second language is a second mapping. The locale folds into `SourceSeriesId` with back-compat for stored ids: English keeps the bare 3-segment `{genre}/{slug}/{titleNo}` it always had, every other locale prefixes a fourth segment, `{locale}/{genre}/{slug}/{titleNo}`. `SearchAsync` fans out over all seven locales concurrently and drops any locale whose request fails rather than failing the whole search; English is always first in the result order so an auto-match scoring two locales identically still links the English edition.
- **MangaPlus language ids are read off `Title.language` (field 7), and English is `0` *or the field absent*.** `MangaPlusLanguages` maps them (`0 en, 1 es, 2 fr, 3 id, 4 pt-br, 5 ru, 6 th, 7 de, 9 vi` — note the gap at 8). The schema is unpublished, so that ordering comes from the app's own picker; `6 = th` is confirmed directly by the recorded `title_list/allV2` fixture, which carries a title under it named in Thai script. An id not in the map is **skipped**, never defaulted to English: filing a Vietnamese title under `en` puts its chapters in the wrong series folder and writes the wrong `LanguageISO` into the CBZ. The catalog is built English-first and `SourceCatalog`'s ranking sort is stable, so an auto-match scoring two editions identically still takes the English one, exactly as it did when the others were dropped outright.
- **MangaFire requires FlareSolverr**; FlareSolverr-fetched JSON comes back `<pre>`-wrapped (unwrapped in `MangaFireSource`).
- **MangaPlus is protobuf now — never send `format=json`.** That parameter used to hand back JSON; the edge 403s any request carrying it (nginx, not the API), which is why every call failed. Responses are decoded by `PbMessage`, a wire-format reader written to avoid a Google.Protobuf dependency plus generated code for an unpublished schema; the field numbers are named constants at the top of `MangaPlusSource`. Test fixtures are recorded binary bodies, so `FakeHttpClientFactory` takes a second, binary map.
- **MangaPlus needs a residential IP** (datacenter IPs get banned) and a `SESSION-TOKEN` header. Any value works (the site generates a UUID client-side and keeps it in localStorage), so one random per-process value is enough; without it the API answers **200** with an "Account Banned" error popup rather than a 4xx. Only first-few/latest-few chapters per title are free. Pages are XOR-encrypted with a per-page key on `PageRequest.XorKeyHex`.
- **TCB Scans / MangaPlus / Flame Comics have no search endpoint** — all three match against a cached full catalog (`SourceCatalog`), filtered by normalized title. Empty catalog is treated as stale so a failed fetch doesn't pin "no results" for the whole TTL. TCB's domain rotates on DMCA takedowns.
- **Flame Comics is read through its Next.js `__NEXT_DATA__` blob**, not markup. Missing blob **throws** rather than returning empty (a Cloudflare interstitial shouldn't read as "no chapters" and silently stall a monitored series). `/browse` also lists prose novels (`novel_id` not `series_id`) — filter on `series_id`. A chapter's `images` object is keyed by page index **as a string** — sort numerically or page 10 lands between 1 and 2.
- **Webtoons chapter numbers are `episode_no`**, not the "Ep. N" in the title (restarts every season, collides on identity). CANVAS titles print no episode number at all. `ListChaptersAsync` reads the undocumented mobile API (`GET m.webtoons.com/api/v1/{webtoon|canvas}/{titleNo}/episodes?pageSize=99999`, one request, whole list) with one retry on `HttpRequestException` (the host throws intermittent SSL errors) before falling back to the old HTML walk, `li._episodeItem`, 10 entries per `&page=N`, no bulk endpoint (653-episode series = 73 requests), on any non-2xx, `success:false`, or null `result`. Some Originals cap the public list to ~9 episodes without the app; that also routes through the same fallback. `webtoon-phinf.pstatic.net` hotlink-blocks every Referer but its own, only proxy through `SearchController`'s `/search/cover`.
- **Asura is manhwa/manhua**, JSON API, no descrambling needed (site's tile-scramble isn't applied to the API's `page.url`). Premium chapters with 0 pages are skipped.
- **ImageSharp pinned to 3.1.12** (Split License) — 4.x needs a paid build-time license key. Don't upgrade it.
- **Page fetching**: `GetPagesAsync` returns `PageRequest`s carrying their own `Headers` end-to-end; resolve pages at **download** time, not enqueue time (MangaDex at-home URLs are short-lived).
- **Four sources publish cross-site tracker ids** (`ISource.GetExternalIdsAsync`, consumed by `SourceMatchService`): **MangaDex** in `attributes.links` on the search response itself, so it fills `SourceSeriesResult.ExternalIds` instead and costs nothing; **Atsumaru** on `manga/page` (`mangaBakaId`/`malId`/`anilistId`/`kitsuId`/`mangaUpdatesId` — MangaBaka's own id among them, the key our metadata is stored under, and some arrive as bare numbers rather than strings); **WeebCentral** as anchors on the series page (AniList + MangaUpdates, no MAL); **MangaFire** as `a.tracker-link` in `.title-detail__trackers` (MAL + AniList + MangaUpdates + MangaDex, the widest set) — those links are rendered into the DOM and are **not** in the detail JSON, so `MangaFireBrowser.ExternalLinksAsync` reads the page rather than capturing an API response. Atsumaru's search index carries `weebCentralId` and none of the tracker ids, while its series page carries the trackers and not that — both halves are kept (`SourceExternalIds.Merge`), since `weebCentralId` is a **WeebCentral mapping**, not evidence about identity, and it rides the existing search request via `include_fields`. MangaPill publishes none. Everything else is unchecked and inherits the default (no ids, no code).
- **MangaKakalot (`mangakakalot.gg`) is entirely behind Cloudflare** — every HTML page 403s a plain client — so it takes `IHtmlFetcher` (the seam on `ChallengeAwareFetcher`: direct with cached clearance first, FlareSolverr on a miss; `FetchAsync` also carries extra cookies and a form-urlencoded POST body through both paths, since FlareSolverr accepts `cookies` and `postData` but not custom headers) rather than an `IHttpClientFactory`. That interface exists so the parser can be tested against recorded fixtures; the concrete fetcher drags in FlareSolverr and app settings. **The chapter list is not in the series HTML at all** — the page ships an empty `#chapter-list-container` and fills it from JS — so it comes from `/api/manga/{slug}/chapters`, which pages **50 at a time** unless asked for more and must be walked by `offset` until `has_more` is false (Tower of God is 658). `/home/search/json?searchword=` looks like a better search than scraping `/search/story/{keyword}`, and is deliberately **not** used: it only answers JSON to a request carrying `X-Requested-With: XMLHttpRequest` **and** a form-urlencoded `Content-Type`, Cloudflare lets it through only sometimes, and neither condition survives the FlareSolverr fallback — which would hand back HTML where JSON was parsed. Covers and page images share TopManhua's `2xstorage.com` CDN, which **403s a request with no `Referer`** (hence the `CoverHosts` entry, so the cover proxy supplies one, and the `Referer` on every `PageRequest`). Search-result thumbnails carry an unterminated `alt` attribute that swallows the attributes after it; `src` comes first and survives.
- **MangaKatana 404s a search that matches nothing** instead of serving an empty result page, so `SearchAsync` checks the status itself rather than using `GetStringAsync` — otherwise every unmatched title threw out of auto-match and 500'd `/api/v1/search/source`. The search parameter is `search_by=book_name` (`m_name` is not a value the site accepts), and a search matching exactly **one** title redirects to that series page, where there is no `div#book_list` to read — the single hit is built from the detail markup at `response.RequestMessage.RequestUri` instead.
- **Toonily's search (both the admin-ajax POST and the GET fallback) hides mature titles unless a `toonily-mature=1` cookie is sent.** Both go through `IHtmlFetcher.FetchAsync`, which now carries cookies and a form body on the direct request and into FlareSolverr's `request.post` alike, so no separate named `HttpClient` is needed for the POST. The GET search is kept only as a fallback for when the POST throws, including when the direct POST hits the fetcher client's 30s timeout (`ChallengeAwareFetcher` lets that `TaskCanceledException` escape without trying FlareSolverr, so `SearchAsync` catches it itself when the caller's token is not cancelled). Series and chapter pages serve mature content without the cookie, so it isn't sent there. The chapter list needs no extra request: it is server-rendered into the same series-page document Madara sites already ship. `MadaraParser` in the Toonily folder is written Toonily-constant-free so a future Madara-themed site can reuse it.
- **MangaLib is behind DDoS-Guard, not Cloudflare**, so a plain client works, but only with a `Referer: https://mangalib.me/` on every request (403 without it); that's why it takes `IHttpClientFactory` rather than `IHtmlFetcher` despite the anti-bot proxy. Its own `main`/`secondary` image server (`img2.imglib.info`) serves AVIF bytes under a `.jpg` name regardless of `Accept`; only `download`/`compress` (`img3.cdnlibs.org` for `site_id: 1`) return real JPEGs, so `GetPagesAsync` must read the server list off `/api/constants?fields[]=imageServers` and use `download`, never `main`. A chapter can have several `branches` (competing scanlation groups, not languages); `ListChaptersAsync` takes the first one whose `restricted_view` isn't closed and skips the chapter entirely if every branch is.
- **Dynasty Scans has a JSON twin at every permalink page's own path plus `.json`** (series, chapters), except search, which has no JSON endpoint (`/search.json` 500s) and is scraped from `/search?q=...&classes[]=Series`. A series' `taggings` array mixes `{"header": "Volume N"}` markers with chapter objects in listing order; the running volume applies to every chapter until the next header, and any header that isn't a whole "Volume N" (`"Extra"`, `"Volume 10.5"`) resets it to null, since `Volume` is an int and reading 10.5 as 10 files its intermissions under volume 10. Several specials in one volume (`Vol. 5 Special`, `Special 2`, `Extra`) all parse to `(Number: null, Volume: 5)` and are told apart by title.
- **Olympus Scanlation's API never surfaces a real HTTP status to the source.** `ChallengeAwareFetcher.TryDirectAsync` swallows `EnsureSuccessStatusCode()`'s exception for *any* non-2xx (not just 403/503) and falls through to FlareSolverr, which hands back whatever body the origin served regardless of status. A 400 (numeric id where a slug is expected) and a 404 (rotated slug) both arrive as an ordinary-looking `{"error": true, ...}` JSON body, so `OlympusSource` detects failure by that `error` field, not by catching an exception. Its `SourceSeriesId` is the numeric id because slugs rotate (grow a date-suffix, old one 404s); the id-to-slug map is rebuilt on every catalog fetch and a failed series/chapter lookup forces exactly one refresh-and-retry before giving up. An `error` body on any chapter-list page, the pages endpoint or the catalog throws rather than parsing as empty (pages errors as a 404 `HttpRequestException` so the download fallback runs; only an empty `pages` array is `ChapterLockedException`), and a failed catalog fetch leaves the id-to-slug map alone. Because the URL carries only the slug, Olympus overrides `ISource.ResolveSeriesIdFromUrlAsync` (what `SearchController.ResolveSource` calls): it loads the catalog, and on a miss forces a refetch at most once a minute. The sync `ResolveSeriesIdFromUrl` only reads the in-memory map. Nothing fetches at construction time, since every registered source is instantiated at startup whether enabled or not.
- **Shinigami's website is Cloudflare-challenged but its JSON API (`api.shngm.io`) is not**, even with no User-Agent, so the source never requests the website at all, only the API host. The two are separate env overrides (`MAKI_SOURCE_SHINIGAMI_BASEURL` for the numbered, rotating subdomain used only for links/URL resolution; `MAKI_SOURCE_SHINIGAMI_APIURL` for the client's `BaseAddress`) because they rotate independently. Every API response is wrapped in `{ retcode, message, meta, data }`; the search parameter is `q`, not `search` (which is silently ignored and returns the whole catalogue).
- **Manhwa18.net is a Laravel + Inertia.js app**: every page's full server props ship as an HTML-entity-encoded JSON blob on `div#app[data-page]`, which AngleSharp decodes when the attribute is read — no separate unescape step. Cloudflare is passive today (a plain client gets 200), but `NeedsFlareSolverr` is still declared so a future challenge degrades gracefully instead of 403ing. Raws are **separate series**, not per-chapter variants: a raw's `genres` carry `Raw` instead of `Adult`/`Manhwa`/`Mature`, and its slug/name end in `-raw` — `SearchAsync` drops them by slug or a whole-word `raw` at the end of the name, so "Quick Draw" survives (search hits carry no genres), `ListChaptersAsync` tags every chapter of a raw series `ko` by reading `genres` when one is linked directly by URL. `Chap 01` falls outside `ChapterNumberParser`'s `ch`/`chapter` word-boundary pattern (it only matches "ch" or "chapter"), so the number is pre-extracted with a local regex before handing off to the parser. Duplicate numbers happen (`Chapter 316` / `Chapter 316 Uncensored`); `Normalize`'s `preferred` picks the Uncensored copy.
- **Manhuagui's chapter page has no page markup at all** — the image list is a Dean Edwards "packer" call (`window["\x65\x76\x61\x6c"](function(p,a,c,k,e,d){...}(...))`) whose word list is itself lz-string-compressed, so `ManhuaguiSource` ships hand-written `LzString` (decompressFromBase64 port) and `PackedScript` (packer unpack, base-`a` token decode, not a fixed base 62) helpers instead of a JS engine. The CDN (`i.hamreus.com`) 403s any page fetch without `Referer: https://www.manhuagui.com/`, verified live even from the downloader's own `Maki/1.0` UA. The site bans IPs on bulk reads, so its named client carries its own strict limiter (1 req/2s) instead of sharing the standard batch's rate — a library-wide sync is exactly the bulk-read pattern that gets banned. Its chapter list mixes numbered chapters ("单话") with numbered volumes ("单行本") covering the same run from a different angle (both kept, by design, since dropping either loses chapters); the "番外篇" extras section is skipped outright because its entries are bare numbers that would collide with main-chapter numbering. Sections are paired to their heading by DOM sibling order, never by `id` — One Piece renders `id="chapter-list-2"` on two different sections' lists.
- **MangaDenizi's `ResolveSeriesIdFromUrl` cannot use plain `SourceUrl.PathTail` with marker `/manga/`**: the API path `/api/v1/web/manga/<slug>` contains that same marker, so `PathTail` alone would resolve it as a series id. It checks `url.AbsolutePath.StartsWith("/manga/")` first. Every reader page is tile-scrambled (`scramble.method: "tiled-v1"`), so `GetPagesAsync` fetches and descrambles each page itself through the `Data` hatch (`MangaDeniziDescrambler`, ported from Keiyoushi's `UnscramblerInterceptor.kt`, uint-arithmetic xorshift32) rather than returning bare URLs.
- **Taiyo's Meilisearch key is a public build-time constant, not a secret**, baked into the Next.js bundle at `NEXT_PUBLIC_MEILISEARCH_PUBLIC_KEY` in `app/layout-*.js` (or, if a rebuild moves it, any other `/_next/static/chunks/*.js` the home page references). `TaiyoSource` fetches the home page once, greps the referenced scripts for it, and caches the result behind a `SemaphoreSlim` so concurrent searches don't stampede; a 401/403 from Meilisearch clears the cache and retries discovery once. tRPC calls (`chapters.getByMediaId`, `chapters.getById`, `medias.getById`) are unrelated and need no key, only the `?batch=1&input=` GET envelope.
- **Rawkuma's chapter-list ajax response is a bare fragment, not a subtree of `#chapter-list`.** `GET /wp-admin/admin-ajax.php?manga_id={id}&page=99&action=chapter_list` returns the `div[data-chapter-number]` rows directly, with no wrapping id, confirmed against a live 195-chapter response. That id only exists on the series page whose innerHTML this fragment replaces. Select `div[data-chapter-number]` on its own, not `#chapter-list > div[data-chapter-number]`. `ListChaptersAsync` also has to fetch the series' WP REST detail first (slug carries no numeric post id), so listing a series' chapters costs two requests, not one. Series id is the slug, not that numeric id, since search and URL-resolution never see it.
- **Adding a source**: one `ISource` impl in `Maki.Sources` + one `AddSingleton<ISource, ...>()` registration. Return chapters via `SourceChapterList.Normalize` (dedupes by `(Number, Volume, Language)`). Tag each chapter with the language **the site says it is**, never a hardcoded `"en"` — the tag reaches `Chapter.Language`, which is half of chapter identity, the CBZ's `LanguageISO`, and the ` [es]` suffix that stops two languages of one chapter overwriting each other on disk. Also set `Kind`/`Content`/`Rating` when they differ from `ISource`'s defaults (`Aggregator`/`Manga`/`General`). Those three drive the tags `/search/sources` reports to the UI, and an aggregator left at the default when it's actually a scanlator or publishes manhwa/manhua/webtoon/doujinshi mislabels it there.
- **Anime-Sama's chapter list lives in a hand-written inline script per scan page** (`resetListe()`/`creerListe(a,b)`/`newSP(x)`/`newSPF("x")`/`finirListe(n)`), not in markup, and every scan panel (colour vs black-and-white, side stories) is a separate "oeuvre" with its own script and its own page-count endpoint — `AnimeSamaSource.BuildLabels` walks it after stripping `/* ... */`/`//` comments, because the page always ships a commented-out usage template right next to the real calls and the template's own literal text (`resetListe();`) would otherwise look like an active call. The built label list is checked against the page-count JSON's key count and throws on a mismatch, since a future call this parser doesn't know about would silently skew every position after it. Series-page cover art (`img#imgOeuvre`) is never a real DOM node — it only exists inside `panneauScan`/`panneauAnime`'s own `document.write` template string, so it has to be read with a regex over the raw HTML rather than AngleSharp's selector API, which parses `<script>` contents as inert text.
- **Naver Webtoon's `dailyPass` (기다리면무료) titles can stay mostly `charge: true` on the web API forever, even long-completed ones.** 열렙전사 (titleId 670152, completed 2016) answers only 15 of 319 episodes as `charge: false` today. The rest wait-unlock inside the app, one per day, and the web API never reflects that state. `ListChaptersAsync` keeps only `charge == false` (and drops `thumbnailLock == true`) at list time, so a `dailyPass` title's chapter count reflects whatever the web currently opens, not the series' real length; there is no way to read the app's per-user wait-unlock state from this API.
- **The two headless browsers close themselves when idle** (`IIdleBrowser`, `BrowserIdleShutdownJob`, `MAKI_BROWSER_IDLE_MINUTES`, default 10, 0 disables). `MangaFireBrowser` and `TopManhuaImageBrowser` both launch lazily and used to hold Chromium for the life of the process, which measured on a NAS as 96 MB of anonymous memory for the Playwright Node driver plus 65 MB across the headless shell's four processes. None of it is on the managed heap, so none of it shows up in any heap measurement, and one MangaFire chapter downloaded once paid for it until the next restart. `ReleaseIfIdleAsync` takes the same `_gate` every scrape holds, with a **zero timeout**: failing to take it means a scrape is running and the browser is not idle after all, and the job runs again in five minutes. **Disposing `IPlaywright` is the part that matters** - closing the browser leaves the Node driver up, and the driver is the larger half. Relaunching costs a couple of seconds plus a fresh FlareSolverr clearance, which is why the window is minutes.
- **ManhwaWeb series carry two ids, `_id` and `real_id`, that diverge after a rename.** Chapter links in `/manhwa/see/<real_id>` are built on `_id`, but the page endpoint (`/chapters/see/<slug>`) only accepts a slug built on `real_id`: a slug still carrying the old `_id` answers the plain-text body `errorrgaarotosi` instead of JSON. `ManhwaWebSource.ListChaptersAsync` rewrites every chapter's id/URL from `_id` to `real_id` before returning it, so `GetPagesAsync` never has to know the two ids exist. `GetPagesAsync` also throws `ChapterLockedException` rather than returning an empty page list, since the site has no paid chapters and an empty `img[]` (or a `roto` flag other than `"no"`) means something is actually broken, not a chapter still to unlock. Search and series JSON also list prose novels (`_tipo == "novela"`), dropped rather than surfaced.
- **CuuTruyen's page CDN hosts in its own JSON don't answer** (`storage-ct.lrclib.net`, `storage-ct-riften.site` both refuse a connection). The site's frontend JS silently swaps them for `storage-bravo.cuutruyen.net`/`storage-charlie.cuutruyen.net` before fetching, so `CuuTruyenSource` rewrites every `cover_url`/`image_url` the same way. A host that starts failing needs a new map entry, not a retry. Pages carry a base64+XOR `drm_data` blob (fixed key, ASCII digits of pi) that decodes to a `#v4|dy-h|...` row-shuffle map; a version other than `v4` must throw rather than write a scrambled page. FlareSolverr JSON comes back `<pre>`-wrapped (`CuuTruyenPreUnwrap`, since `MangaFireSource`, 00-GENERAL's pointer for this, is Playwright-only now and has no such helper left to copy).
- **MangaWorld is passive Cloudflare today** (plain client gets 200, no `cf-mitigated`) but still takes `IHtmlFetcher` since the plan calls it Cloudflare-fronted. It declares `SourceCapabilities.None`, not `NeedsFlareSolverr`: that flag only drives the settings badge and makes `HealthMonitor` warn when no FlareSolverr URL is set, and `ChallengeAwareFetcher` reads that URL only after a direct request is challenged. Chapter numbers are Italian (`Capitolo 1194`), pre-extracted with a local regex before `ChapterNumberParser.Parse` (which only knows `ch`/`chapter`); the volume text (`p.volume-name`, e.g. `Volume 116`) is passed straight through as `volumeRaw` since the shared parser's own `vol(?:ume)?` pattern already reads it. Dates are Italian long-form (`25 Settembre 2026`, `CultureInfo("it-IT")`, `dd MMMM yyyy`); unparseable returns null rather than throwing. Series pages are huge (1.7 MB for One Piece) and carry both the detail block and the full chapter list, so `GetSeriesAsync`/`ListChaptersAsync` each fetch it once and parse only what they need. Keiyoushi's `MWCookie` interstitial (a JS shell that sets a cookie and reloads) isn't served today and isn't recognised by `ChallengeAwareFetcher`'s challenge detection, so every fetch checks the raw HTML for the `MWCookie` marker itself and throws rather than silently reading back "no chapters".
- **Manga-Tube (`manga-tube.me`) gates every request, API included, behind a home-grown arithmetic challenge**, not Cloudflare, not FlareSolverr-shaped. A request without a valid `__mtbpass` cookie gets 200 `text/html` carrying `window.__challange = {arg1,arg2,arg3,tk}` (hex operands, an op letter, a token); solving means hex-decoding both operands, applying the op, formatting the result exactly like JavaScript's `Number.prototype.toString()` (`double.ToString("R", CultureInfo.InvariantCulture)` matches), and POSTing it back as `x-challange-arg4` alongside the other three args and the token. `MangaTubeSession` holds the resulting cookie behind a `SemaphoreSlim` and re-solves once on a second challenge rather than trusting the DI-owned `HttpClient`'s own cookie jar: `IHttpClientFactory` rotates primary handlers every couple of minutes, which would silently drop a `CookieContainer`-held pass. A challenge on a request that already carried a pass means the server rejected it, so the session re-solves regardless of the pass's stated expiry; it skips the solve only when another caller has already swapped in a different cookie. The named client registers `UseCookies = false` so the manually-attached `Cookie` header is the only one sent. Licensed titles either shorten their chapter list (`limitChapters`) or 401 the chapters call outright (`{"error":["licence-check"]}`); the 401 is a stable site state and reads as zero chapters, not a sync failure. Any other non-success status throws `HttpRequestException` with the status (so `RateLimitDetector` sees 429/503), and a 2xx chapters response without a `data.chapters` array throws rather than reading as an empty list.
- **Comic Walker search only matches Japanese text** (romaji hits zero), so auto-match works only for a series whose stored title is Japanese. Most episodes are inactive at any moment (paid until a later free campaign), so the chapter list legitimately shows only the first couple plus the newest few. Episode titles carry the chapter number as `第N話`, with an optional part suffix (`前編`/`中編`/`後編`) and an optional circled digit (`①`-`⑨`, or the dingbat `➀`-`➈` the site also uses) for a sub-part; `ComicWalkerChapterNumber` never reads `internal.episodeNo`, which is sequential over parts and announcements and disagrees with every tracker's count. Pages are XOR-encrypted per page like MANGA Plus, riding `PageRequest.XorKeyHex`.
