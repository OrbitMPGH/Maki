# Headless browsers (MangaFire & TopManhua)

- **The two headless browsers close themselves when idle** (`IIdleBrowser`, `BrowserIdleShutdownJob`, `MAKI_BROWSER_IDLE_MINUTES`, default 1, 0 disables; the job checks every minute, so a browser goes one to two minutes after its last call). `MangaFireBrowser` and `TopManhuaImageBrowser` both launch lazily and used to hold Chromium for the life of the process, which measured on a NAS as 65 MB across the headless shell's four processes (plus 96 MB for the Playwright Node driver of the time). None of it is on the managed heap, so none of it shows up in any heap measurement. `ReleaseIfIdleAsync` takes the same `_gate` every scrape holds, with a **zero timeout**: failing to take it means a scrape is running and the browser is not idle after all, and the job runs again in a minute. **There is no Playwright and no Node process**: Maki drives Chrome Headless Shell over the DevTools protocol from its own process with PuppeteerSharp (`HeadlessBrowserLauncher`; each source launches its own browser, and the shell's files leave the page cache when the last one closes). **It talks over a pipe (`LaunchOptions.Pipe`), never a debugging port**: over a port Chromium outlived a hard kill of Maki and any local process could drive it. **Launch flags are Playwright 1.61's own Chromium switches, never Puppeteer's defaults** (`BrowserSupport.ChromiumArgs`, `IgnoreDefaultArgs`): Puppeteer's would add `--enable-automation`, and `--no-startup-window` needs `WaitForInitialPage = false` or the launch times out waiting for a page. **What a Playwright context did for every page, `BrowserSupport.PreparePageAsync` does per page before its first navigation** (`BrowserProfile`): `Emulation.setUserAgentOverride` with Playwright's `userAgentMetadata`, device metrics with the screen equal to the viewport, `Browser.setWindowBounds` so `outerWidth` matches too, the client-hint headers, init scripts, the cache off (Playwright's routing did that, which is why every request carries `pragma: no-cache`), and request interception for the abort filter. Cookies go on the browser context once. A fingerprint probe of both engines on 2026-11-19 (`research/resource-usage/2026-11-19-cdp-browser`) matched on every field and header; anything that changes this setup should be checked against it. Puppeteer's selector waits are not Playwright locators: the MangaFire pager, Lang dropdown and tracker row are small DOM scripts that keep the old matching rules (accessible name as a case-insensitive substring, `text-is` as the exact trimmed text, CSS candidates give up on a hidden first match, the role candidate skips buttons hidden from the accessibility tree); `MangaFireDomScriptTests` runs them in the real shell when one is installed and does nothing otherwise, which is the case in CI. **PuppeteerSharp joins launch arguments into one command line** (through `sh -c` on Linux and macOS), so every extra argument goes through `BrowserSupport.QuoteArgument`: unquoted, the spaces in a `--host-resolver-rules` value split it and Chromium exited at launch. **A response body read has no timeout of its own** and waits on a DevTools event a dead Chromium never sends, so read bodies with `BrowserSupport.ReadTextAsync`/`ReadBytesAsync` (30 s), never `TextAsync`/`BufferAsync` directly. **Both shells launch with `BrowserSupport.LaunchArgs`** (`--disable-gpu --disable-software-rasterizer`, which stop the SwiftShader GPU process, about 55 MB per tree). That removes WebGL, which Cloudflare's bot script can read; it was kept after five flagged and five unflagged rounds per site on 2026-11-15 (search, chapter list, page list with TopManhua's in-browser image capture, through FlareSolverr) showed no challenge or block on either side. If either site starts challenging the browser, try without these two flags first. Relaunching costs well under a second and **does not** re-solve Cloudflare: `ChallengeAwareFetcher` caches clearance per host with no expiry and drops it only on a challenge, 403 or 503, so a relaunch reuses it. **A source proxy is set per browser context, never as a launch flag** (`BrowserSupport.ContextOptions`, `BrowserContextOptions.ProxyServer`): each browser resolves its source's route once per context, asks `ChallengeAwareFetcher.GetBrowserSessionAsync` for clearance through that same route, and starts a new context when the route changes, so the launch flags above stay untouched and no relaunch is needed. Behind an HTTP proxy Chromium lets the proxy resolve hosts, so `mangafire.browserhostresolverrules` no longer applies to the site. A proxied context sets `ProxyBypassList = "<-loopback>"`, which drops Chromium's implicit bypass, so loopback and link-local destinations go to the proxy too instead of straight from Maki's network. Navigation errors `ERR_PROXY_CONNECTION_FAILED` and `ERR_TUNNEL_CONNECTION_FAILED` become `SourceProxyException` (`BrowserSupport.ProxyFailure`). The fingerprint probe has not been re-run with a proxy set. **`TopManhuaImageBrowser` activates lazy `img[data-src]` nodes in small batches (`ImageBatchSize = 4`), removes completed `<img>` elements from the DOM between batches so Blink drops decoded bitmaps, and stages captured bytes to temp files (`StagedImages`)** instead of keeping every page's `byte[]` in RAM; `TopManhuaSource` wraps staged paths in `PageRequest.Fetch` (ref-counted for duplicate URLs) and disposes the staging directory through `ChapterPages.Dispose()`.
